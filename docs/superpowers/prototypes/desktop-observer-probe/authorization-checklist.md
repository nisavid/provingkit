# Authorize one disposable observer probe

Use this checklist in the authorization ticket after independent review of the
candidate. Record accepted or amended terms in the user's own decision. A
source review or completed preparation ticket supplies no live grant.

| Scope | Proposed terms to confirm |
| --- | --- |
| Source and application bytes | Published procedure/source revision and the exact archive, manager, and sidecar digests in its build receipt |
| App changes | Temporary replacement of the inspected installed archive, preserving executable/native assets/sandbox layout; close before staging, close before restoration, and launch after each |
| Existing work | One scheduled quiescent window using the current signed-in profile, with two shutdown/launch cycles and explicit restoration expectations; stop if unrelated work cannot be preserved |
| Fixture | One disposable local Code task named `Desktop observer probe 278` in an empty disposable worktree; approve creation and selected identity acquisition, then bind its actual profile/account route, metadata path, and task/Code IDs before staging |
| Setup | Two submissions of the exact `PROBE_READY` prompt in the procedure, one before staging and one afterward, on that fixture only |
| Local configuration | One selected private configuration outside a new private run directory; exact fixture and artifact binding, 60-second setup deadline, 100-millisecond setup polling |
| Arm and getters | One fresh exact arm, accepted within 60 seconds of bootstrap; three samples over at most 30 seconds, at least five seconds apart; the three named getters sequentially with two seconds each; no retry after terminal failure |
| Receiver data | The procedure's named provider/model, rules/directory grants, account IDs, host settings/grants, cwd, and Code process/version report; no prompt/transcript, credential, environment, or raw-error export |
| Linux process observation | One separately invoked observation sourced from a freshly validated sample with matching before/after reports: selected process directory metadata, three bounded `stat` reads, two opens of `exe`, and at most 256 MiB hashed; require the calling user's UID before process-file reads, with no enumeration or alternate PID |
| State changes | No deliberate account/model/permission/grant/cwd transitions; stop for a separately reviewed proposal if one becomes necessary |
| Retention | Keep raw fixture outputs in the manifest-listed private directory through the return decision, accessible only to the user and authorized execution/decision workflow; then delete after that decision approves the redacted summary and evidence to keep |
| Cleanup | Approved removal of the experimental configuration and output, disposable task, and empty worktree; restore verified pristine package bytes and check application/work expectations |

Bind the concrete paths, package metadata, launch arguments, staging, and
restoration steps from [application staging and restoration](application-operation.md)
in the private approval packet. The future fixture's allocated identifiers are
recorded after its approved creation; they must never be guessed in advance.

The executor must first verify the actual positive grant against this source
revision. Resolve missing fields before the corresponding action. Any changed
fixture, artifact, access scope, or package identity returns for a decision.

The source experiment excludes malicious code running as the same user. Hashes
and nonces identify bytes and freshness; they do not authenticate the producer.
Uncancellable or synchronously blocking getters, package changes during the
probe, and restoration of task state remain concrete operating risks. The
no-send probe cannot qualify notification delivery or acknowledgment.
