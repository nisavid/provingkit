# Codex desktop packaging and reversible routing changes

**Start with the exact desktop package and an offline test of its submission coordinator.** The retained build contains a desktop-side failure path that can stop a send before it reaches App Server. Replacing the CLI alone cannot repair that path. A process-local CLI override remains a candidate if the defect is shown to occur after dispatch and the target build actually selects that executable. Current package bytes are the missing discriminator. [Packaging research](https://github.com/nisavid/provingkit/issues/932) · [Missing-turn-ID report](https://github.com/openai/codex/issues/56503)

## Package and source identity

- **Retained Linux archive, verified by static inspection.** `resources/app.asar` contains `package.json` naming `openai-codex-electron`, product `Codex`, launcher identity `chatgpt.desktop`, version `26.1023.51421`, build `22530`, flavor `prod`. The entry point is `.vite/build/early-bootstrap.js`. The archive index distinguishes `.vite/build/main-UOTY8NmV.js`, its imported `.vite/build/src-tOjGKoT3.js`, `.vite/build/preload.js`, and the renderer asset `webview/assets/app-initial-e8b2527a6d62.js`. The renderer asset and preload are indexed, while the manifest and both main-side chunks were available as bytes and matched their indexed SHA-256 values. The index also flags native modules such as `@parcel/watcher-linux-x64-glibc/watcher.node` as unpacked. Electron uses the ASAR and its unpacked companion together. [Electron ASAR packaging](https://www.electronjs.org/docs/latest/tutorial/asar-archives) · [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model)
- **Desktop routing, verified in the retained main bundle.** `Lke` at byte `1301120` waits on an in-progress conversation whose `turnId` is null and raises a generic timeout if the ID never arrives. The steering caller awaits it before `Ike` can emit `turn/steer` or the tool-output form of `turn/start`. `Ake` and `jke` recognize the distinct inactive-turn condition, and `fAe` also recognizes some backend errors under host conditions. The generic timeout does not match those conditions. This is a pre-dispatch failure path in build `22530`, based on source inspection. The separately reported macOS renderer reproduction names build `26.1016.61520`, asset `app-initial-c95ddb62696e.js`, and functions `kfn` and `gfn`. The similar failure shape gives a useful search signature across builds. It does not identify the transition that caused the stale state. These are build dependency names. They do not establish the version or transport selected by the GUI owner. At public `openai/codex` revision `b9099a145b305a470e9a2f7d6d35b6a4b0f58d57`, `turn_start_inner` calls `start_or_steer_turn`. Core `start_or_steer` attempts a steer, starts on `NoActiveTurn`, and preserves other refusals. A prior source assessment on Desktop `26.1027.51404` also found a conditional shared-daemon route. The actual backend for the selected GUI chat, its association with any public binary, and server-side behavior behind remote routes remain unknown. ## Override surfaces

| Surface | Applicability and reversibility |
| --- | --- |
| **Documented Follow-up behavior** | The app offers steer or queue for messages sent while it works. The retained main bundle reads `followUpQueueMode` through `readFollowUpQueueMode` at byte `1733769`. Whether the affected peer-send path consults that preference is open. Trace it first because it is a supported control. If it applies, assess the scope of the preference and any change to normal composer behavior before proposing it. Rollback is restoring the recorded preference. [Desktop settings](https://learn.chatgpt.com/docs/reference/settings#general) |
| **Process-local executable selection** | `Ga` in build `22530` reads `CODEX_CLI_PATH` before its bundled-path fallback, but the retained call site explicitly labels the resolver consumer `browser-use`. This proves a selection surface for that consumer. Windows user reports describe an App Server use of the same variable, with mixed outcomes. Publisher support for the target Linux GUI path and actual selection for the affected chat are unestablished. `CODEX_APP_SERVER_FORCE_CLI=1` suppresses WebSocket routing in historical `mwt` and `J7`, with possible SSH and other host effects. `CODEX_APP_SERVER_MANAGER_IN_MAIN` is gated to unpackaged execution in those bytes. Neither is a narrow supported routing fix. Standalone CLI `--config` and private App Server startup are documented for the process launched by that client. A separate server supplies no owner association for an existing desktop chat. | **Disposable extraction or package copy** | Extracting a trusted package for static analysis, or extracting a small coordinator fixture for an offline test, is feasible without using the installed launcher. A runnable copy is conditional. Electron checks `app.asar` before the unpacked `app` directory, and `OnlyLoadAppFromAsar` can require the archive. Embedded ASAR integrity is documented for macOS and Windows, independently of platform signing and package integrity. The retained index’s per-entry hashes establish file identity. They supply no fuse or signature observation. A runnable copy would also need compatible Electron and native modules, separate App Server and user-data roots, and isolation from single-instance handoff and the production updater. Any enforced integrity refusal ends that route. ## Smallest discriminating prototype

1. **Bind an inert package artifact to `26.1103.32239` build `25471`.** Prefer retained bytes or a separately authorized publisher/package-manager artifact. Record its package identity and provenance, archive hash, manifest, Electron identity and fuse metadata, `app.asar.unpacked` inventory, relevant bootstrap/main/preload/renderer hashes, and any CLI/App Server resource identity. Trace the affected entry point through the effective follow-up preference, owner checks, and first App Server request. Stop when that path is located or name the exact missing chunk or binding. No existing-chat connection is required for this step.
2. **Replay that one coordinator boundary with invented events and a fake request sink.** Distinguish a send that never crosses the request boundary from one that reaches the server and receives a refusal or loses its acknowledgement. Cover idle, busy with a valid ID, missing ID followed by completion, turn rollover, and uncertain submission. Require the expected method and exact turn ID where applicable, a stable logical message ID, at most one admitted submission, and zero automatic resends after uncertain delivery. Include a composer case if the traced function is shared. This is a proposed test. The current package was not executed.
3. **Choose the patch layer from that result.** A pre-dispatch reproduction warrants testing the smallest coordinator change. A server-side reproduction warrants a standalone App Server fixture before any executable override. A documented preference is viable if it covers the peer path and the resulting composer behavior is acceptable. Current-build evidence that contradicts the historical routing signature sends the proposal back to diagnosis.

**Rollback and verification.** For the offline test, keep the pristine artifact and its hashes and discard the derivative fixture after retaining the test evidence. A separately approved executable-override trial should use a disposable launcher and owned scratch roots, with a readback of the selected executable and protocol version. Exit the owned instance, remove the launch-only override, and verify that a new disposable baseline selects the original executable and matches the pristine manifests. A full copy would additionally need proof that it owns its process tree and does not reuse the installed app’s lock, data, socket, or updater. Package-managed updates can replace installed resources, and any changed version or hash invalidates the applicability check. [Electron user-data paths](https://www.electronjs.org/docs/latest/api/app#appgetpathname) · [Electron platform update behavior](https://www.electronjs.org/docs/latest/api/auto-updater#platform-notices)

The remaining blockers are current package bytes, the initiating transition, and, for any future test using an existing chat, legitimate binding to its actual owner. A patch needs independent review before any running-app proposal. Native attachment remains open under #868. Message accountability remains a separate acceptance requirement, and the mailbox comparison stays held.
