# Choosing receiver-observation components

The parallel investigation gives us a credible combination to investigate:
native MCP submission, bounded stored-session evidence, and a small receiver
hook. App-side observation remains a possible supplement for specific missing
fields. **No current combination establishes the full preservation contract,
and the research has not established that patching Desktop is necessary.**

I recommend choosing components for the next bounded source increment before
resuming probe preparation. Keep the native sender, separate exact-file
acquisition from record interpretation, and develop the minimal hook projection
if its configuration cost is accepted. Investigate the remaining runtime
producers in parallel. Keep app instrumentation as a conditional alternative
until those producers and the required sampling lifecycle are settled.

This comparison resolves [the comparison join](https://github.com/nisavid/provingkit/issues/387)
and supplies [the component decision](https://github.com/nisavid/provingkit/issues/388).
It adopts nothing and authorizes no live access or operation.

## Coverage and the next discriminating checks

The [accepted notification contract](https://github.com/nisavid/provingkit/issues/192#issuecomment-5845461915)
remains the requirement. The following entries describe candidates and gaps,
not demonstrated receiver behavior.

| Required evidence | Candidate components and current evidence | Missing fact or next check |
| --- | --- | --- |
| Exact consented existing peer | Selected Desktop metadata and lineage; hook Code ID/socket projection; fresh native discovery. Source and documented interfaces support these separate pieces. | Establish their join to the exact native send target. Recheck identity and scoped purpose consent for every send. A socket, title, or newest file is insufficient. |
| Informational notification and payload | Native sender candidate; short text, reviewable context link, and correlation ID remain the accepted payload. | Set the interface and ACK grammar. An action request remains a different operation, and ACK means receipt. |
| Receiver-origin delivery | An authorized selected transcript, with source-backed SDK origin interpretation where useful. | Observe the actual external native ingress row and its attribution. Assess exact acquisition before reading. |
| Explicit correlated ACK | Optional `Stop.last_assistant_message`, or a qualified assistant transcript record. | Verify selected-engine emission, attribution, correlation, and quote/echo rejection. Stop can be skipped on interruption; it does not prove incoming delivery. |
| Bounded wait/inspect and unknown reconciliation | Positive bound records, acquisition times, and optional hook evidence. | Define time bounds, freshness, and lookup behavior. Missing, delayed, or incomplete evidence stays unknown. Reconciliation uses observation only and never automatically resends. |
| Held and refused | Explicit selected-route admission/outcome evidence. | Establish the actual producer and retain synthetic failure coverage. Held may later release; silence identifies neither state. Neither outcome counts as acknowledgment or triggers an automatic resend. |
| Actual account before/after | Spawn identity, account cache, and refresh paths are known partial sources. | No fresh authenticated executor-route producer is established. A saved or cached identity cannot fill this gap. |
| Actual model before/after | Existing-query response plus startup/model-switch events as candidates. | Establish endpoint freshness and the meaning of the reported model, including pending changes or fallback. Events need a baseline and qualified coverage. |
| Applied permissions before/after | Code mode/rules, manager-recorded completed pushes, host grants, and pending-change sources. | Complete the combined producer inventory and its applied/pending semantics. Completed host pushes cover only particular categories. |
| Worktree and current cwd before/after | Selected path/association metadata, manager worktree reports, and hook event-time cwd. | Obtain sufficiently fresh bound endpoint observations. `harnessCwd` resolves a registered worktree; it is not an arbitrary current-cwd getter. |
| Idle/busy proof and continuity | The accepted disposable-fixture qualification and harmless continuity canaries. | Real idle/busy delivery and ACK remain required. Original-task resumption and canaries remain diagnostic, without a new pass threshold. |
| Compatibility | Dependency-specific checks over readers, events, bindings, getters, and exports. | Carry justified evidence forward; assess relevant changes from cheap checks through targeted source/live checks. A new build starts unassessed, not incompatible. |

These gaps prevent qualification under the full accepted claim. Source work
can identify producers and design access; an experiment can establish actual
behavior. Neither may silently replace an uncovered field with a weaker one.

## Costs and credible combinations

| Combination | What it contributes | Access and operating cost | What it cannot currently claim |
| --- | --- | --- | --- |
| Existing readers, with possible UI corroboration | Stored identity/lineage and positive receiver records | Private acquisition scope, polling/lag handling, format compatibility. No app-file or hook change. UI exposure, focus effects, and a usable identity surface still need assessment. | Complete applied state or fresh query access |
| Readers plus minimal receiver hook | Adds final ACK text, event-time fields, and a Code-ID/socket binding lead | Project settings change, command execution, approved event-input exposure, private log lifecycle, callback latency, and cleanup. Documentation supports reload; the selected engine still needs verification. No archive exchange is proposed for this combination. | Complete endpoint state, incoming delivery solely from ACK text, or coverage before the hook emits |
| Those components plus temporary app observation | Adds selected existing-query access and host-state projections for a bounded experiment | The retained procedure exchanges the archive while Desktop is stopped, then restores it: two restarts, possible task interruption, package/restore checks, and an unmeasured total window | Automatic transfer of instrumented observations to ordinary Desktop, or complete state from the current partial producers |
| Those components plus a maintained app observer | Could make selected residual observations repeatedly available if required | Integration/update ownership, repeated collection protocol, output retention, recovery, and relevant compatibility checks | An existing recurring service: the current prototype is one shot per manager |

The alternatives combine components; no lane wins by vote. A diagnostic app
observer may be useful without becoming an operating dependency. A successful
instrumented sample establishes facts about that candidate. Transferring a
claim to restored Desktop needs an observer-effects argument and relevant
unmodified-runtime evidence; restored bytes alone do not prove restored behavior.

## Keep acquisition and sampling decisions separate

Fixture acquisition needs an independently bound Desktop task, its Code identity
and lineage, and the native peer mapping. The internal creation result does
not establish external access. A bounded directory listing exposes identifiers;
opening candidate JSON acquires its full serialized contents even if output is
filtered. The SDK's explicit-directory helper can inspect additional candidates.
The grant must cover the chosen acquisition footprint.

The proposed app receipt supplies stronger registration, persistence, transition,
and same-query handoff witnesses. Those are useful to that design, rather than
universal requirements imposed on every identity method. Bounded discovery
cannot be called equivalent to the receipt. Selection must state the claim each
method supports. The accepted 15-minute admission ceiling applies only if the
receipt procedure is retained; it does not bound restoration or the full window.

Initial qualification requires full actual before/after state. Fresh peer and
consent checks are required for every send. The accepted decisions have not
settled whether ordinary sends also repeat all full-state samples. Settle that
operating policy before choosing a recurring observer dependency.

The current prototype takes three automatic samples within 30 seconds. That
does not establish that samples bracket idle or busy notification and ACK.
Explicit before/after phase requests are a concrete alternative to design and
test if app-side collection is selected. No interval-wide invariant is added.

## Next decision and work

The component decision should settle these points in dependency order:

1. Define the observations required during ordinary sends, separately from the
   accepted initial qualification measurements.
2. Choose components for the next source increment and the proposed acquisition
   scope. My recommendation is bounded acquisition/interpretation plus a minimal
   hook projection, with residual-producer source investigation in parallel.
   Keep the app bridge available for concrete gaps; defer archive integration
   until its value and sampling contract are established.
3. Select useful prototype seams and agree their tests: hook partial-evidence
   projection, acquisition separated from interpretation, or the app's
   completed-push projection and finite endpoint collection. These test source
   behavior, not the truth of unknown runtime producers.
4. Map precise source gaps and the smallest separately authorized experiments.
   A no-send hook experiment could use one disposable dedicated-project Code
   task, independently bind its identity, install a Stop-only logger, submit an
   agreed harmless setup prompt, compare approved event and stored evidence,
   and restore the settings. It tests activation, binding leads, payloads, and
   latency. It does not prove native delivery or complete preservation. It
   cannot proceed before identity, acquisition, procedure review, and live
   authority are settled.

Source investigation should first seek a matched selected-engine artifact for
hook emission and native target resolution, plus concrete producers for fresh
account and complete applied state. The named offline inputs did not establish
that engine artifact. If a producer cannot be found, bring back the specific
gap and alternatives rather than adding instrumentation without a source.

After selection, revise probe preparation and its authorization, execution,
restoration, and evidence-decision tickets to the chosen components. Retire
obsolete patch or receipt requirements and renew affected reviews. Native-send
qualification remains behind its own consent and complete observation plan.

The comparison method remains proposed for the
[agent-panel workflow catalog](https://github.com/nisavid/provingkit/issues/306).
Its useful lessons here are to inspect acquisition as well as returned fields,
allow source findings to correct a shared seed, defer a prototype only with a
concrete contract rationale, and place input-isolation limits in the initial
dispatch request before automatic context gathering. Broader codification does
not block the component decision.
