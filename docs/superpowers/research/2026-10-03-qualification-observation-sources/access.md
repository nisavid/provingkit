# Access mechanisms for qualification endpoint observations

**DONE_WITH_CONCERNS.** The retained sources establish renderer IPC and Desktop-owned MCP routes to selected manager observations, plus control getters on a query already owned by the app. They establish no standalone passive attachment to that existing query. A finite diagnostic adapter at the manager boundary could expose that query and otherwise inaccessible app state without starting or reinitializing a query. Its result would still be incomplete where the owning producers lack the accepted endpoint semantics.

This first report was completed independently: I read no parallel endpoint-state report, newer draft, or private conversation and sent no substantive preliminary findings. I performed source reads and hashing only.

## Existing routes and their actual costs

### Renderer IPC

The main process registers `Ob.for(webContents).setImplementation(aB(r))`. Its lazy factory loads `createLocalSessionsApi` and obtains the manager through `gC()`; `gC()` loads the manager singleton if necessary. `Oo` registers methods on that particular `webContents.ipc`, validates the sender through `Ab`, and validates declared arguments/results. This is an app renderer route; the channel's name does not provide an external connection. [Common `[650150,651320)`, `[2192968,2193868)`, `[2350715,2351000)`, `[3571224,3571620)`, `[5913130,5913620)`.]

The API takes an explicit Desktop session ID. `getContextUsage` and `getContextUsageSummary` forward to the manager; `getPermissionMode` returns the manager's stored mode. The manager captures `sessions.get(id)` and its query, rejects a missing/stopping process, and calls the captured query's context getter. Its summary route also has an eligibility check and an existing wait bound. No inspected handler returns account route, complete permissions, or raw engine cwd. [Renderer API `[47500,50600)`; Common method declarations `[2169030,2171200)`, `[2177300,2178200)`; Manager `[1439250,1441750)`, `[1477500,1479150)`.]

A usable existing-interface experiment would require an authorized existing renderer caller and an independently selected task ID. The allowed members do not establish a specific frontend control or an external automation route that invokes these methods for this task. An ordinary UI label or a fabricated IPC call cannot fill that fact. When the manager is already active, this route needs no new manager creation; a cold call can load app modules. It adds IPC, control-request scheduling, context analysis, validation, and existing logging. It preserves the ordinary application bytes, but covers only its declared fields.

The manager's request-accounting helper increments host-request counters only while the captured query matches, then returns the original promise. It does not reject an old query's response after replacement. Any collector layered over this route must recheck binding itself. [Manager `[531000,531700)`.]

### Desktop-owned MCP tool

`Gd` enables the session-management server for `sessionType === "ccd"`. `createProxyServers` constructs SDK MCP server objects and handler closures carrying the owning Desktop session context; there is no demonstrated standalone listening endpoint in this chain. `get_session` resolves `self` or the supplied selector against that context, then calls manager `getSession`. It reports formatted task fields, including recorded model, cwd/worktree paths, and conditionally permission mode. [Host `[209773,210250)`, `[210900,213500)`, `[397700,400550)`.]

Manager lookup can load session storage and check folder existence before formatting. The host proxy adds tool-call telemetry, timers, and cancellation handling; its stall timer is deferred while its pending-permission predicate is true. This is not a cost-free memory projection or a universal total deadline. [Manager `[1265319,1266439)`; Host `[397700,400550)`.]

This route is useful if the already selected ordinary task can make the existing tool call under later authority. Arranging a new prompt or tool use to obtain it is an intervention with conversation/usage effects. It still returns host records rather than the applied engine fields. A host tool name exposed inside Desktop is not evidence that this coordinator can call it externally.

### SDK query transport

On a query already owned by the caller, SDK `getSettings`, `listPermissionRules`, `getStatus`, and `getContextUsage({detail:"summary"})` issue correlated control requests on that query's transport. `request` registers a request-ID handler and writes the request; `readMessages` dispatches the matching response. That correlation supplies transport provenance, not independent task selection. [SDK `[1099837,1100260)`, `[1103100,1105600)`, `[1107265,1107940)`, `[1084530,1085250)`.]

This is the strongest existing acquisition primitive for app-owned engine results. Getting its object is the unresolved external-access problem. Calling the public SDK `query` creates a query/subprocess transport; resume/session-store paths continue or reconstruct sessions. Direct-connect initialization POSTs to `/sessions` and opens the returned WebSocket; `cc+unix://` is explicitly unsupported. None establishes unchanged attachment to the ordinary Desktop query. [SDK `[1139202,1140500)`, `[678135,684591)`; the retained runtime-access report traces subprocess construction.]

Reinitialization also has observable effects. It resends initialization configuration; the engine can retire/replace host hook callbacks and redeliver pending permission/dialog requests. `initializationResult()` and `accountInfo()` retain the original initialization promise. Reinitialization is not selected as a fresh mode/account getter. [SDK `[1105369,1106869)`, `[1109600,1110000)`; Engine `[221253742,221258750)`.]

The getters' effects differ. Settings reads merged settings/sources and errors; rules load their builder and read current permission context/settings; summary analyzes engine context; status reads credential/store state and formats display sections. Some connection types reject settings/rules/status, and status may be unavailable in a build. No supported result may be assumed before a bound check. [Engine `[221193550,221194700)`, `[221225050,221226960)`, `[220676180,220677150)`, `[211588683,211589600)`, `[232758900,232759650)`, `[222912573,222912950)`, `[200778533,200779100)`.]

### Event hooks, files, and the native inbox

The [fixture collector](https://github.com/nisavid/provingkit/blob/e971ae6fde6f4f4fa0b603e3a08bd0369b9481c6/docs/superpowers/prototypes/receiver-evidence/collector-contract.md) acquires one bounded Stop event through inherited stdin and an explicitly selected socket environment value. The [fixture procedure](https://github.com/nisavid/provingkit/blob/e971ae6fde6f4f4fa0b603e3a08bd0369b9481c6/docs/superpowers/prototypes/receiver-evidence/fixture-check-procedure.md) proposes normal UI selection, one setup response, and bounded selected metadata acquisition. These can establish event/file associations and useful event-time cwd/mode; they cannot access the manager's existing query or Desktop grant evaluators.

Hook installation changes configuration and executes a command, acquiring the whole permitted event before projection. Exact metadata reads acquire whole serialized records. Their acquisition, retention, and restoration costs remain those of the reviewed procedure. A later read does not freshen an earlier event. These are useful adjuncts to either access choice, with their own authority and intervals.

The native inbox queues peer-origin input; it is not an established control-getter transport. Sending a getter-shaped message would still be receiver input. SDK filesystem helpers also do not expose app-held state and have broader lookup behavior than an exact-file reader. The retained reader-hook and runtime-access reports establish these distinctions. Neither route solves the selected-query access gap.

## Finite temporary adapter proposal

The named gap is access to the selected app-held query and selected-record permission/lifecycle/worktree state. The proposed adapter adds a finite main-process diagnostic entry beside the existing manager singleton, with a separate module and a disabled-by-default load guard. It must receive that existing singleton; it must not construct another manager, start/warm/resume a task, replace its query, or call reinitialization.

The concrete source hook is adjacent to singleton construction/export at Manager `[1595508,1596495)`. A candidate module would expose an attachment operation with these injected dependencies: existing manager, selected pure browser/computer-use evaluators, clock, phase-request reader, and bounded result writer. This source shape makes all added access and scheduling reviewable. Its exact source bytes, build mechanism, dependency identities, load guard, and installation route remain the next candidate's deliverables.

Observed fallback diagnostics need an explicit access path too. The proposed additional hook is a bounded diagnostic callback in the existing manager-owned query receive loop, immediately after its normalized frame is produced. The loop already holds the record and exact query; pass both to the adapter and require its selected binding before copying only represented fallback type, original/fallback model, direction/trigger, and event identity. Do not create a second query iterator or intercept its transport. The allowed source shows the single owned loop and its refusal-fallback branch, but does not prove every normalizer/output path; schema/support remain a compatibility check. The callback starts with binding admission, records its finite coverage interval and overflow, and stops after the two phases. It supplies observed diagnostics only. [Manager `[1566350,1574700)`; Engine fallback schema `[199722179,199723000)` and branch `[213024300,213027950)`.]

The finite request contract is two explicit phase slots, `before` and `after`, plus a task-owned configuration. Configuration binds a run ID, source candidate, independently selected Desktop ID, expected current Code ID, allowed backend, exact request/result paths, expiry, query-operation deadlines, collection/serialization caps, and retention. A request carries that run ID and one phase. The adapter consumes each admitted slot once and writes a new result without replacing one. It never schedules periodic sampling, retries a timed-out request, or waits for pending permissions to settle.

The startup guard binds only the module and fixed run/config locations. Task-specific configuration is admitted after the candidate fixture has been independently selected and its current Code ID joined; before that, the adapter collects no task state. This avoids treating a pre-launch identity as the identity of a newly created query. Missing configuration or an expired slot leaves the adapter inactive.

Named regular request files and result files would be a new external interface. The adapter can poll only those fixed slots until its finite expiry; no new socket, native inbox, receiver prompt, or general command evaluator is needed by this shape. Polling interval and expiry are explicit proposed parameters to bind before implementation. They add timers and filesystem I/O. This proposal does not certify those files as an authenticated or private channel.

### Binding and collection sequence

1. Load the reviewed candidate and verify its actual manager/executor separately from its source target. The fixture-identity procedure supplies an independent UI/project/setup witness and unique current-Code join. Pass the resulting explicit task ID to the adapter; do not discover tasks through a title search or bulk manager enumeration.
2. At phase admission, use `manager.sessions.get(taskId)` directly. Require the expected record/current Code ID, supported local backend, existing query/input stream, and non-stopping/non-starting state. Capture references to the record, query, and stream plus current Code ID, `promptEpoch`, lifecycle fields, and query-associated pending state. Assign opaque run-local reference labels for output; never serialize the objects.
3. Copy a bounded host projection synchronously. Its distinct interval records selected/confirmed/pending model state; spawn-bound account/org; permission selections and pending markers; represented grants; completed host-rule push caches; desired/applied MCP distinctions; registered-worktree resolution fields; and pending cwd move state. Missing fields remain missing. Do not call synchronization, flush, permission-handler, refresh-token, worktree-move, or task-loading methods to make it complete.
4. On the captured query, issue only the separately approved existing getters. `getSettings` supplies applied model configuration; `listPermissionRules` supplies represented effective Code rules/directories. Include summary only where its resolved-model diagnostic is needed, and status only where its route/cwd/display diagnostic justifies its additional acquisition. Record operation start, response end, operation label, errors/support outcome, and binding checks. A source-level method check is not a supported-response result.
5. Recheck record/query/stream/current-Code/`promptEpoch` and lifecycle before and after every asynchronous operation and host projection. Teardown closes and clears query/stream, increments `promptEpoch`, and clears many caches. If identity/lifecycle changed, retain independent observations but mark the combined phase incomplete; never accept the old query's reply as the replacement's. [Manager `[1037450,1043550)`.]
6. Publish each field's source meaning, interval, binding, coverage, failure/overflow, and pending state. Group them by phase without inventing a single instant. Compare only like meanings across the two admitted phases.
7. At expiry or completion, stop accepting requests, release only adapter timers/listeners, and settle its own writer. Preserve uncertain/partial output for the reviewed cleanup procedure. Disposing observation must not call `query.close()`, stop the fixture, or clear receiver queues.

The existing `promptEpoch` and reference checks are a smaller binding candidate than adding the old adapter's full lifecycle-hook set. I have not proved that they cover every supported query installation/Code-ID reuse path. Trace those paths before implementation; add a diagnostic generation only if a specific uncovered transition needs it. Endpoint identity checks do not establish absence of transient changes between checks.

Getter methods do not expose a timeout argument in the inspected signatures. A deadline implemented by racing their promises bounds result admission, not engine execution, transport bytes, or pending SDK handlers. Late replies can still arrive. The internal `request` accepts an AbortSignal and can send a control-cancel request, but using that internal API is an additional integration/compatibility choice with cancellation effects. Do not silently close the owned query or claim cancellation from a local timeout. [SDK `[1103100,1105600)`.]

### Exact host acquisition boundaries

Browser effective mode requires the selected record plus surface, sandbox/launcher status, and applicable gate inputs. Computer-use helpers evaluate expiry using time and grant policy; pass one recorded evaluator time to both helpers where their API permits it. Raw stored grants remain separate from effective results. Calling the broker's real permission handler would evaluate a proposed tool/input and can mutate state or prompt, so it is excluded. [Manager `[938350,942800)`, `[202245,205250)`; Host `[522350,523850)`; Common `[3692300,3693500)`.]

The selected-record projection can report `permissionModeRequestsInFlight`, `permissionModeUserSet`, chip/bypass markers, `flagScopeSyncPending`, the completed deny/ask/laptop-allow arrays, and MCP dirty/held/unanswered/adoption/applied-key facets. Desired directories and grants are distinct from completed pushes. Setters and pushes are excluded. [Manager `[1290598,1292000)`, `[1333100,1336850)`, `[1409543,1413400)`, `[1429203,1430700)`, `[944500,945900)`, `[1478900,1480600)`.]

`hasPendingFor` omits out-of-turn permission entries. A complete selected-session pending projection cannot be manufactured from that boolean. Filtering the broker's global pending map reads other entries' session IDs even if it retains only the selected entries. A later candidate must either enumerate and authorize that broader bounded in-memory inspection or provide a separately reviewed selected-session index. The minimal adapter leaves those categories explicitly incomplete until one choice is made. [Manager `[136100,136950)`.]

Projection caps do not bound full control replies already acquired by the SDK. Settings/source values, rules, paths, context metadata, and display/error details may be acquired before filtering. A proposal must enumerate that whole acquisition and distinguish response-size limits enforced at the producer/transport from output-only limits. Exceeding an output cap yields incomplete evidence, not assurance that only capped bytes were read.

A startup-loaded adapter can observe the query that exists in the candidate after it is loaded and independently bound. It cannot claim to have preserved or passively attached to a pre-restart query. If the objective is the currently running ordinary query without interruption, a verified authorized in-process load/control surface is a missing prerequisite. Resuming the same Code ID after launch does not establish the same query object or endpoint interval.

The candidate plan must specify application artifact location, launch identity, profile/state access, shared-desktop effects, fixture disposition, environment, output location, finite shutdown, and exact restoration conditions. It must measure interruption, residual requests, and the added receive-loop callback's scheduling/serialization effects in the eventual experiment. The former archive replacement, two restarts, fixed sample cadence, and receipt deadline are not inherited.

Transfer to ordinary Desktop needs a source comparison at the changed loader/manager boundary, the same selected producers and contextual inputs, measured added scheduling/I/O/query/evaluator effects, and an ordinary-build check of the material behavior claim. Candidate observations establish candidate behavior. Restored hashes establish content; they do not establish restored runtime behavior or substitute for an unavailable ordinary endpoint measurement.

Later private-data/security review needs concrete acquisition and retention scopes, the file/interface owner and access controls, source/loader identity, concurrent-update handling, credential exclusion, cancellation behavior, and the authority for each app intervention. This report identifies those control questions and certifies none.
