The frozen results fit as separate evidence facets. The optional executable prototype can observe an ancestor image near one admitted Stop invocation. Neither result supplies the other's missing binding, and their combination does not establish the running manager's current account/organization pair without independent U/A/O provenance or a separately selected app projection. ## Join findings

1. **The image observation can precede task binding, but cannot replace it.** In the new `collector.mjs`, optional acquisition starts only after complete Stop input, matching whole setup text, a valid receipt window, ordinary session kind, equality of hook `CLAUDE_CODE_SESSION_ID` and event `session_id`, and a decimal claimed `CLAUDE_PID` distinct from the collector. Initial `expectedCodeId: null` remains usable. `executor.mjs` follows at most six parent records from the collector to that claimed PID and hashes the opened `exe`; `matches_configured_identity` compares only with a configuration digest. The same record remains `unqualified` and carries `independent_task_binding_required`. The asserted hook values and ancestry do not authenticate Code as the producer, prove that the image is the assessed native Code build, or identify the Desktop task. The later packet must bind the digest to an independently assessed native artifact and join the UI-selected project/whole response, event Code ID E, and exactly one current metadata candidate S. Sources: `docs/superpowers/prototypes/receiver-evidence/collector.mjs`, `executor.mjs`, `executor-contract.md`, and `fixture-check-procedure.md` in the frozen executable snapshot; [directory comparison, “What must be bound”](2026-10-07-selected-directory-binding-comparison.md#what-must-be-bound).

2. **Finding S's file does not establish the active manager directory.** The new fixture procedure retains one supplied account/organization directory D, one nonrecursive 128-entry listing plus overflow detection, at most three selected metadata files, and 1 MiB plus overflow per file. A unique current `cliSessionId = E`, matching serialized/filename S, and project relation support an association only within those authorized candidates. The executable extension reads no Desktop profile or metadata and has no manager query. The directory report found no externally callable source-backed active U/A/O getter; a historical configuration or parent listing nominates paths but does not show which pair the running manager selected. Keep the result as “fixture found in declared D” unless current U/A/O/D comes from an independent selected-profile binding or a separately chosen finite manager projection. Source: `docs/superpowers/prototypes/receiver-evidence/fixture-check-procedure.md` in the snapshot; [directory comparison, “Route 1”](2026-10-07-selected-directory-binding-comparison.md#route-1-existing-surfaces-independently-supplied-tuple-bounded-discovery).

3. **The native role remains conditional even when the image observation says `observed`.** `executor.mjs` checks the ELF header and image identity around a bounded whole-file hash. ELF alone cannot distinguish Code from another native image or an interpreter. The configurable `expectedSha256` does not carry its source identity in the result; a match is to supplied bytes, not automatic build qualification. The frozen tests exercise invented ELF bytes and one test-owned Linux Node image, not the selected Desktop Code process. A different digest is `unassessed`; interpreter input is an explicit gap. The persistent top-level `selected_executor_unobserved` gap in `collector.mjs` should be read as unresolved selected-role/build evidence even when the lower-level facet is `observed`; the label can otherwise be mistaken for a contradictory claim. Record image observation, assessed-artifact compatibility, native Code role, and selected-task association separately. Sources: `docs/superpowers/prototypes/receiver-evidence/executor.mjs`, `executor-command.test.mjs`, `collector.mjs`, and `executor-contract.md` in the snapshot.

4. **Acquisition and timing limits remain separate.** The new worker acquires up to six before and six after process `stat` records of 8 KiB plus overflow each, an opened image up to 256 MiB plus overflow, file/process identity metadata, and at most 16 KiB of worker output. It reads no `environ`, `cmdline`, symlink text, registry, metadata, or transcript. The previously researched link-text proposal was not implemented; the prototype's chosen observation has a narrower pathname acquisition and still needs an explicit live process-root/PID-namespace and path grant. The collector already acquires up to `maxInputBytes + 1` of the whole Stop event, regardless of retained fields. The worker's separate 30-second maximum wait begins after Stop acquisition and includes startup, followed by at most 100 ms of cleanup waiting. It does not bound the full command, result publication, Desktop turn, or the age between UI response, event, executable sample, and later metadata read. The later packet must state maximum join age and selection/lifecycle recheck; a later file read cannot freshen the event. Sources: `docs/superpowers/prototypes/receiver-evidence/collector-contract.md`, `executor-contract.md`, `executor.mjs`, and `fixture-check-procedure.md` in the snapshot; [directory comparison, “Freshness, build scope, and choice”](2026-10-07-selected-directory-binding-comparison.md#freshness-build-scope-and-choice).

5. **Reader cleanup adds a distinct obligation.** The collector starts an owned Node helper without a shell and asks only that helper to stop on timeout or output overflow. If `close` is not observed within the cleanup grace, it records `exit_unconfirmed` and stops waiting. That preserves the Stop evidence but does not prove the helper exited. The one-shot claim, partial/result files, hook setting, and helper quiescence require separate closeout. Preserve the claim after uncertainty, inspect only authorized run artifacts, do not retry the setup turn, and do not signal a reused PID. Remove the introduced hook entry while preserving concurrent settings changes; remove task-owned files only after the chosen lifecycle check and evidence retention. Sources: `docs/superpowers/prototypes/receiver-evidence/executor.mjs`, `executor-contract.md`, `collector-contract.md`, and `fixture-check-procedure.md` in the snapshot.

## Method and decision boundary

The executable snapshot adds a synthetic command prototype and updates its proposed procedure. It does not install a hook, create a task, acquire private metadata, choose a directory, run an app adapter, or depend on Task Witness. Its `processRoot` can be synthetic for tests; `/proc` and a real Code image are later live scope, not observations from this result. The directory report's manager projection remains a conditional design alternative, with unimplemented loader, access, installation, interruption, and restoration costs. The older app receipt's two restarts and deadline do not transfer. The current next choice remains whether current U/A/O/D can be independently supplied for the new active fixture or whether that precise gap warrants a separately reviewed app projection. Either choice still needs the independent UI/Code/file join, native-role/build evidence, full acquisition/effects review, and an explicit live grant. This peer comparison is not a Tricritical review, private-data safety finding, authentication claim, or qualification result.
