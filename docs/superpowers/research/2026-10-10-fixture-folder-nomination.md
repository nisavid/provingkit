**Result: two bounded parent listings can nominate a declared metadata folder, but cannot identify the running Desktop manager's active folder.** A separately admitted host ID can nominate one filename inside that folder. Neither method replaces the independent UI, Stop, and whole-file association. This is source and operating-cost research for [folder nomination #522](https://github.com/nisavid/provingkit/issues/522), not a grant for private reads or an adopted live method.

## The two parent listings

The first proposed read is exactly one nonrecursive names/types listing of `P = join(U, "claude-code-sessions")`. An independently established absolute U for the selected Desktop profile is required before this path exists as a defensible input. A profile title, inferred default path, hook socket, or Code configuration home does not supply U. Retain at most 128 names/types and one overflow observation; traversal may inspect a 129th entry to detect overflow. Missing P, error, or overflow gives `unknown`, without trying another root.

Select exactly one account directory child A from that first output before the second read. The listing provides names and types, not an account-to-ID mapping or active-selection proof. When IDs are opaque or several directory children exist, a supplied exact A with independent provenance is needed. A sole directory child is a structural candidate only. If no defensible A is selected, stop with `account_child_unresolved`; do not list every account's organizations.

The second proposed read is exactly one nonrecursive names/types listing of `Q = join(P, A)`, under the same 128-entry plus one-overflow bound. Select one listed organization directory child O explicitly, then nominate `D = join(Q, O)`. Several opaque O entries need independent mapping. A sole O is again a structural candidate, not proof of the held pair. Missing Q, error, overflow, or unresolved O remains `unknown`. Neither parent listing reads settings, cookies, transcripts, metadata files, or other account children.

The [existing metadata helper](https://github.com/nisavid/provingkit/blob/b63b4a6f45fb9294e9c39122df56279906ddd4cd/docs/superpowers/prototypes/receiver-evidence/fixture-metadata.mjs) accepts one caller-declared absolute directory per `list` invocation. Two invocations would acquire two complete request files, each capped at 128 KiB plus one overflow byte, and produce two records with names/types, times, counts, and overflow state. It neither chooses A/O nor observes Desktop selection. Across the two parent traversals, up to 129 entries per directory may be observed, with at most 256 names/types retained and two overflow observations. The elapsed filesystem cost is unmeasured. Record exact P and Q, the supplied U/A/O and their independent sources, profile/window, listing intervals, all returned names/types, overflow and errors, selection rules, and a later lifecycle recheck. A later file match cannot freshen an earlier selection sample.

## Host-ID hint and conditional file check

The frozen initial [host-ID nomination design for #521](https://github.com/nisavid/provingkit/issues/521), received with SHA-256 `9ab9f0469af4d2155365449b6032ede368571930c31e050ef99f4b336d811a05`, proposes a separate unqualified collector facet. It admits a selected hook `CLAUDE_CODE_HOST_SESSION_ID` only with complete matching Stop evidence, an ordinary non-served Code ID, a valid receipt window, and agreement between selected hook `CLAUDE_CODE_SESSION_ID` and the Stop ID. A filename-compatible ASCII host ID of at most 250 characters can nominate `S + ".json"`; invalid, missing, oversized, or unadmitted values yield an explicit gap. The newly inspected Manager source supports the host-ID environment assignment, but does not establish live hook inheritance. This hint supplies no U, A, O, D, independent UI identity, or active-selection proof.

A parent listing alone does not identify the task file. If the host hint is admitted, its basename must still be checked against a separately nominated D listing and receive an exact whole-file grant; no automatic open follows from the hint. The [fixture procedure](https://github.com/nisavid/provingkit/blob/b63b4a6f45fb9294e9c39122df56279906ddd4cd/docs/superpowers/prototypes/receiver-evidence/fixture-check-procedure.md#proposed-ordered-live-steps) requires an independently selected disposable UI task and project, its whole displayed setup response, and a complete unbound Stop record with ordinary Code ID E. The existing single-D listing remains capped at 128 names/types plus one overflow observation, followed by at most three explicitly selected regular JSON files, each whole file capped at 1 MiB plus one overflow byte. The complete serialized files may contain settings, grants, titles, summaries, errors, and remote/MCP details; retaining only IDs does not narrow acquisition.

The [metadata helper contract](https://github.com/nisavid/provingkit/blob/b63b4a6f45fb9294e9c39122df56279906ddd4cd/docs/superpowers/prototypes/receiver-evidence/metadata-contract.md#acquisition-and-association) requires exactly one acquired candidate with basename `S + ".json"`, serialized `sessionId = S`, current `cliSessionId = E`, and the selected saved project relation matching the UI project. It checks supplied UI/Stop windows and a later selection recheck, but reports uniqueness only among acquired candidates and `activeDirectory: "unproved"`. Zero, multiple, stale, changed, incomplete, or overflowing results stay unknown. The host hint narrows candidate selection; it does not upgrade this conditional association.

## Decision and consumer invocation

If U cannot be independently established, the first listing has no defensible root. If opaque A or O entries cannot be mapped, two listings may still fail to nominate a defensible D. Even a unique structural path plus a matching file supports association in a declared D, not the running manager's active pair. The later choice is whether the two additional parent-name acquisitions and their operating cost are useful for that limited claim, or whether [probe preparation #278](https://github.com/nisavid/provingkit/issues/278) should obtain a current independent U/A/O tuple or separately review a projection of the already loaded manager. The host-ID facet can be considered independently as a file-selection hint. Task Witness remains deferred.

For downstream use under `capturing-agent-procedures`, #278 should load the reviewed revisions of this report, the fixture procedure, metadata helper/contract, collector contract, and any accepted host-ID extension; bind the actual static source identity and independently selected U/A/O or report their absence; record separate parent-listing, UI, Stop, D-file, and lifecycle intervals; obtain exact later grants for every added read and live effect; and preserve unknown results without expanding the scan. Corrections from actual observation belong in the maintained source. This is a procedure proposal pending review, publication, and consumer invocation, not installed operating guidance. I performed no private read, fixture, hook, installation, or live receiver action.
