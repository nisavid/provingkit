# Directory binding for the selected Desktop fixture

**Result: the current source supports a conditional file association, but no externally callable, source-backed observation of the running manager's current account/organization directory.** A supplied active-profile tuple plus independent UI, Code, and task evidence is the least app-changing route. If that tuple cannot be established, a finite projection from the already loaded manager is the precise app-side alternative. Neither route is adopted or authorized by this research.

## What must be bound

The assessed Manager stores Electron app.getPath("userData") as U and uses base B = "claude-code-sessions". Its current account and organization IDs are A and O. Its active metadata directory is D = join(U, B, A, O), and the selected task S has file join(D, S + ".json"). The superclass can change the held A/O pair after resolving an account transition and reload sessions. The account resolver can draw on provider overrides, current account details, IPC waiting, or bootstrap fallback; the organization resolver can use cached or overridden state or a last-active-org cookie. A profile title or historical path does not establish U or the current A/O. Primary-source anchors and exact member identities are in [fixture-binding source report, “Bind one Desktop account/organization directory”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#bind-one-desktop-accountorganization-directory), notably Manager [870200,870700), [919200,919920), Serializer [451900,454050), and Desktop core [3010750,3022900).

A successful fixture association needs the independently selected normal-UI task and dedicated project, the whole approved setup response, complete unbound Stop capture with ordinary Code identity E, and exactly one current authorized metadata candidate whose filename and serialized Desktop sessionId are S and whose current cliSessionId is E. The project relation must agree. The [fixture procedure, steps 3–7](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/prototypes/receiver-evidence/fixture-check-procedure.md#proposed-ordered-live-steps) supplies this proposed join. Newest filename, title, timestamp, prior Code lineage, or a historical directory nomination is insufficient. A match proves association within the acquired candidate set; it cannot prove global uniqueness or the active manager pair if D was merely guessed.

The current [collector source](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/prototypes/receiver-evidence/collector.mjs) reads one bounded inherited Stop event and selects only CLAUDE_CODE_MESSAGING_SOCKET from its application environment. It emits an unbound Code ID and matching response only under its checks. Its own PID identifies the Node collector, not Code; it does not read manager state, discover D, or implement the proposed process witness. The hook socket and Code configuration home are separate from U/A/O. Desktop's internal cliPid is a Code-reported value tied to the held local query, but the inspected external surfaces provide no passive callable reader for it. [Fixture-binding source report, “Concrete execution chain”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#concrete-execution-chain), Manager [1565500,1566750), Code RC [203572506,203572856).

## Route 1: existing surfaces, independently supplied tuple, bounded discovery

The preparation packet would receive the exact selected Desktop profile/window, independently established current absolute U, current manager A and O directory tokens, and exact D, with provenance and an observation interval for each. It would check D against the source formula before any candidate read. The evidence must refer to the newly selected active manager, not a parked task's stored pair or a prior configuration. No source-backed public interface in the inspected set currently supplies that tuple; operator knowledge would have to be specific, current, and independently supported. Without it, the route supports only “fixture found in declared D,” not “D is the running manager's selected account/organization directory.” [Fixture-binding source report, “Smallest route: explicit operator binding”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#smallest-route-explicit-operator-binding).

The route then uses the separately authorized normal-UI observation of the dedicated project and whole setup response, the collector's unbound E, and the metadata join above. Preserve the accepted discovery bounds inside **one** independently bound D: one nonrecursive listing of at most 128 entries plus one overflow entry; at most three explicitly selected regular JSON files; at most 1 MiB plus one overflow byte acquired per file, with complete JSON and opened-file identity checks. The three whole serialized files may contain titles, settings, reminders, grants, summaries, errors, and remote/MCP details, even if retained output contains only IDs. The listing reveals sibling names/types. Overflow, ambiguity, mismatch, or an absent match is unknown, not permission to scan another directory. [Fixture-binding source report, “Preserve the accepted metadata bounds”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#preserve-the-accepted-metadata-bounds), Serializer [503942,509796).

A bounded parent listing could nominate A or O, but it cannot establish current selection. A distinct proposal would have to enumerate one listing of join(U,B) and one operator-selected account child, each at most 128 plus one overflow entry, acquiring names/types outside D. A private config.json read would add the whole settings object under an exact separately approved file and size cap; cached keys still would not establish both current manager fields. Neither acquisition belongs to the accepted one-directory limit, and neither is recommended as a substitute for active-selection evidence. [Fixture-binding source report, “Scope that parent discovery or settings would add”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#scope-that-parent-discovery-or-settings-would-add).

Existing renderer IPC can reach some manager methods only through a validated app webContents sender; the Desktop-owned MCP tool formats selected task records but requires a tool call and may load storage/check folders; SDK getters require the exact already owned query. The inspected surfaces expose no external passive U/A/O getter or independently demonstrated UI task-ID control. A fabricated IPC call, fresh SDK query, resume, direct connection, or reinitialize would not observe the unchanged selected query. [Existing-access report, “Existing routes and their actual costs”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-qualification-observation-sources/access.md#existing-routes-and-their-actual-costs). Normal-UI selection is a proposed independent witness whose actual controls and readable task identity remain a live feasibility check.

This route changes no Desktop bundle. Its later live effects would still include the disposable task/model turn, a project Stop-hook settings change and command execution, whole event acquisition, selected metadata reads, run files, and exact-entry restoration. The [collector contract](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/prototypes/receiver-evidence/collector-contract.md#files-and-termination) describes one-shot claim/partial/result files and interrupted states. Remove only the introduced hook entry while preserving concurrent changes; verify quiescence and task/run-file disposition. No restart is selected in the current fixture procedure. Hook loading, whole response representation, UI association, join age, and lifecycle recheck are unobserved. [Fixture procedure, “Configuration proposal” and “Interpretation and recovery”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/prototypes/receiver-evidence/fixture-check-procedure.md#configuration-proposal).

## Route 2: smallest selected-manager projection

If current U/A/O cannot be supplied independently, a disabled, finite app-side adapter could read the **already loaded** Code manager and output only the selected task S and active/parked classification; manager userDataPath and baseDir; direct getAccountIds() result; the selected task's storageDirFor(S) and getSessionFilePath(S); current cliSessionId and initialized cliPid; and run-local opaque manager/record/query/stream identities, generation or transition epoch, and before/after selection/lifecycle checks. The new active fixture must use the current manager A/O branch; a parked task's stored pair is a distinct result. These are in-memory projection fields, not a metadata-file or credential read. The inspected superclass has a direct getAccountIds getter, while Desktop core's manager peek does not itself load a manager. The adapter must not call account resolvers, load sessions for discovery, enumerate records, start/resume/reinitialize a query, or follow paths found in a record. [Fixture-binding source report, “App observation for the missing binding”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#app-observation-for-the-missing-binding), Serializer [450000,451000), Desktop core [2350500,2351100).

The adapter would admit S only after independent selected-UI/project/response evidence and the bounded E-to-S metadata join or an independently reviewed acquisition witness. It would compare manager object, selected record, current A/O, Code ID, held query, and lifecycle around each asynchronous boundary. A pair sampled once proves only its sample interval; an account change away and back can escape two simple equal-value reads. A transition epoch/hook is a proposed stronger interval claim and would add instrumentation and review. The [earlier fixture-receipt design](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-09-30-fixture-identity-acquisition-design.md#acquisition-lifecycle-and-selection) traces such writer and transition hooks, but it remains an unadopted design and its admission claim, deadline, and restart plan do not transfer to this smaller projection.

This projection would directly attest that the selected manager reported U/A/O/D at its observation interval and could cross-check the hook's claimed Code PID. It would not by itself prove that the selected metadata file was written, that the actual Code executable matches assessed bytes, the query's effective authentication route, or continuous selection after the observation. Exact-file evidence remains separately scoped if that claim is needed. An adapter needs exact loader/module/output protocol and byte caps, source/build compatibility checks, selection admission, installation and access controls, cleanup, and restored-runtime evidence. The [qualification access design](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-qualification-observation-design.md#access-alternatives-and-actual-effects) locates an attachment seam beside the existing manager singleton but identifies no current external passive interface or hot-load method. Candidate installation may require stopping Desktop and launching changed app bytes; any candidate/restored launches, task interruption, file outputs or polling, package replacement, and restoration must be priced and authorized separately. The older observer's two-restart procedure and 15-minute receipt window are historical candidate-specific costs, not current allowances. [Earlier packaging evidence](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/prototypes/desktop-observer-probe/packaging-evidence.md), [earlier receipt design](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-09-30-fixture-identity-acquisition-design.md#complete-two-launch-procedure).

## Freshness, build scope, and choice

Record separate intervals for profile/manager selection, UI response, Stop receipt, each metadata listing/read, app projection if selected, and lifecycle recheck. A later file read does not freshen the Stop event; equal endpoint samples do not prove uninterrupted state. Set a maximum join age and exact selection/query recheck in the later packet. The reviewed source report is tied to Desktop 2.9939.4-1 with Manager SHA-256 bd2144a3653bb843f4b75fe652124a4e478f273b5f6c2e10a2139fa3a9a3152f and Serializer SHA-256 dad88ac66fe13f72d0225c49d48e124d238ff643ff96426c4a2020482621e62d. Desktop declares Code 2.1.284 RC; the stable SDK 0.3.284 is comparative, not proof of its RC wrapper or selected executor. A changed build needs graduated source and behavior comparison; a hash difference alone proves neither compatibility nor incompatibility. [Fixture-binding source report, “Controlling inputs and source identity”](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-fixture-binding-sources/research.md#controlling-inputs-and-source-identity).

The narrow next decision is whether a current independently supported U/A/O/D tuple can be supplied for the selected profile and new active fixture. If yes, select the bounded route and define its precise UI, file, timing, effects, and restoration grant. If no, choose whether the selected-manager projection's additional app mutation and restart/transfer cost is warranted; otherwise retain the active-directory gap and the narrower declared-directory association. Neither parent discovery nor the older receipt is an adopted default. The coordinator can use this provisional acquisition procedure by loading this reviewed revision with the collector/procedure, binding the selected source identity and entry tuple, recording interval-specific outputs and partial claims, then returning source corrections. This report alone establishes source/interface feasibility, not authentication, access protection, private-data safety, full-state qualification, or permission for live acquisitions.
