# Access design for receiver runtime observations

**DONE_WITH_CONCERNS.** The retained sources support a concrete collection design for the selected Desktop query, applicable Code rules and directories, several Desktop permission facets, registered worktree association, and event-time Stop fields. They do not establish an ordinary external attachment to that query, fresh authenticated running-account evidence, a bound observation of a particular executing model attempt, or complete applied permissions. Those gaps continue to block full qualification. They do not, by themselves, block preparation of the accepted fixture-identity and Stop check.

## Claim, authority, and frozen inputs

This design preserves the [accepted experiment decision](https://github.com/nisavid/provingkit/issues/397#issuecomment-5972295427): full account, model, applied-permissions, worktree, and current-cwd observations belong to initial qualification and affected requalification. Ordinary sends retain fresh peer and purpose-consent checks, receiver-origin delivery, and a distinct correlated acknowledgment. The design adds no interval-wide invariant. The smaller proposed fixture check can establish selected-executor/task binding, hook activation, final-response representation, and collection behavior; it cannot qualify notification delivery, acknowledgment, or full preservation.

## Which access an external process actually has

An internal method name is not an external endpoint. Renderer `LocalSessions.getContextUsage`, `getContextUsageSummary`, and `getPermissionMode` forward to the app-held manager. Manager `liveQueryOf(sessionId)` returns its existing query; `readContextUsage` captures that session record and query, rejects missing/stopping processes, and distinguishes unsupported requests from failures. No standalone attachment to that selected local query is established by these paths. `getPermissionMode` returns the manager field. [Renderer API `[47600,50400)`; Manager `[1440000,1441700)`, `[1477500,1479000)`.]

On an already owned SDK query, `getStatus()`, `getSettings()`, `listPermissionRules()`, and `getContextUsage({detail:"summary"})` issue `get_status`, `get_settings`, `list_permission_rules`, and `get_context_usage` respectively. `request` allocates a request ID, associates its handler with that query, and writes a control request on its transport. The response handler correlates that request ID. This establishes query-transport correlation, not independent selection of the intended Desktop task. Status, settings, and rules handlers can reject connection types through `$g`; their availability must be checked on the selected query. [SDK `[1099400,1100400)`, `[1103100,1105600)`, `[1107200,1108805)`; RC `[204546800,204547800)`, `[221193550,221194550)`, `[221225050,221226950)`.]

The public SDK `query` path constructs a query and subprocess transport. Its `resume` options describe process/session continuation; they do not demonstrate read-only attachment to the ordinary Desktop query. Exported `DirectConnectTransport` is also insufficient: initialization calls `FOe`, which POSTs to `/sessions`, then opens the returned WebSocket; it accepts optional session-key and permission-mode inputs. The retained client does not establish that this operation selects the intended existing Desktop task or leaves it unchanged. Its URL parser rejects `cc+unix://`. No direct-connect service was contacted. [SDK `bA` `[1131549,1138578)`, `Kze` `[1139202,1140500)`, subprocess construction `[1069942,1071321)`, `H$`/`FOe`/`UOe` `[678135,684591)`, exports `[1158984,1159746)`.]

The native messaging UDS has a different purpose. Its receive path turns a user message into a peer-origin command and queues it with `isMeta:true`. The connected native sender accepts an encoded `uds:` destination. Neither path establishes a control-request attachment for these getters. Sending a getter-shaped message would be a receiver input, not a demonstrated status operation. The retained [identity engine report](https://github.com/nisavid/provingkit/blob/88d1962aefdf40676148462fc495089fb18d1026/docs/superpowers/research/2026-10-02-reader-hook-sources/identity-engine.md) supplies the sender/encoder chain; the queue producer is RC `[221431000,221432900)`.

Under a later reviewed grant, an external hook command could acquire its serialized Stop stdin and explicitly allowed environment fields, and an exact-file reader could acquire selected metadata files. Those paths expose event/file evidence rather than the app's query object or grant evaluators. Host `get_session` is an app-served projection of manager fields, including selected model, cwd, worktree path, and conditionally permission mode; it is not a fresh engine snapshot. Its manager lookup can load sessions and check folder existence, so using its name does not establish a narrow acquisition footprint. [Host `[211050,213500)`; Manager `[1265319,1266439)`; RC Stop `[207307500,207308900)`, `Tc` `[207318493,207319450)`.]

## Requirement-to-access design

The following results are proposed data records. None was collected live. Query requests require later authority to use the bound app query; app-only projections require a separately selected access mechanism. Every response or projection carries its own collection interval, source/meaning, binding, errors, and unresolved gaps. A later query observer needs explicit timeout, response-size, rule-count, and retention bounds; a projection cap cannot undo full replies already acquired by the transport. Overflow or incomplete coverage must remain an incomplete field, with no automatic retry.

## Applied permissions require completed, effective, and pending observations

The candidate permission result needs three separate parts: currently applicable Code state; effective Desktop evaluator results; and changes or decisions still pending. Equal saved configurations or equal manager modes cannot substitute for these parts.

For Code state, retain `notInEffect` rules distinctly. The builder includes represented `mcpServerPolicy` and `hostCredential` rule sources and current additional working directories. Its allow helper filters by mode and other conditions. This is useful applied-rule evidence, but neither the builder nor `getSettings.applied` reports every bypass-availability, sandbox/filesystem, or host permission input. `getSettings.applied` explicitly names model, effort, advisor, and ultracode values. [RC `[201860380,201862030)`, `[231927050,231928958)`, `[221225050,221226950)`.]

For Desktop state, the broker consults session permission updates and cached reasons with tool, input, mode, origin, and policy conditions. Reading those stores does not reproduce every decision for all contexts. Browser mode passes through `BE` using surface, sandbox, mode, and gates. Computer-use `Kqn`/`Jqn` evaluate grant expiry at their invocation time for dispatched sessions; raw stored grants can differ from effective values with no intervening event. The proposed record therefore retains evaluator result, time, applicable expiry policy, and context rather than reporting stored grants as current. [Manager `[202245,205250)`, `[938500,942700)`; Host `[522450,523650)`; Common `[3692300,3693500)`.]

For pending state, the following inspected distinctions must survive collection:

| State | Required interpretation |
| --- | --- |
| `permissionModeRequestsInFlight`, `permissionModeUserSet`, chip-level requests, bypass restore/defer state | Changes can continue after an agent setter reports `pending`; a rejection can cause query replacement. Capture the pending markers and query association without invoking a setter or waiting for settlement. |
| `flagScopeSyncPending`, completed deny/ask/laptop-allow caches, query-scoped spawn push | Completed caches cover named arrays. They do not retain the full allow array or applied directories. Directory addition saves a session update and starts a push before returning. |
| `mcpServersDirty`, `hostMcpHeldForRules`, `hostMcpSpawnPushOwed`, `hostMcpSetUnanswered`, adoption state, applied server keys | A desired server set, written request, held operation, accepted answer, and pending idle application are different facts. Some inspected branches concern SSH/adoption; record applicability rather than assuming every local receiver has those paths. |
| Broker pending entries and side-person waits | `hasPendingFor(sessionId)` excludes out-of-turn entries. Use a bounded selected-session projection with categories and unknown coverage; its boolean alone cannot certify complete absence. |

These distinctions are directly supported by Manager `[1290598,1292000)`, `[1409543,1413400)`, `[1274000,1281600)`, `[1333100,1336850)`, `[1429203,1430700)`, `[944500,945900)`, `[1478900,1480450)`, and broker `[136100,136950)`. No read-only complete aggregate producer is established. Calling synchronization, evaluator-associated mutation, flush, warm, reinitialize, or permission methods to make a sample complete would change this observation design.

## Binding and sampling procedure for a later collector

1. **Admit the source and actual executor separately.** Record this report's revision and retained identities. Require later authorized evidence that the fixture's actual launcher/executor uses the assessed target. Manager spawn-version metadata can contribute; a packaged target digest alone cannot settle the running process. New builds remain unassessed until relevant compatibility evidence is refreshed.
2. **Select the fixture independently.** Bind the operator/UI-selected disposable Desktop task to a unique setup response. Join its Stop `session_id` and allowed socket environment field to exactly one selected metadata record's current Code ID. Keep an optional host-session label as corroboration. Reject ambiguous joins as unresolved.
3. **Capture a query only through the chosen access mechanism.** If app observation is selected later, take the exact selected session record, its query, input stream, current Code ID, and lifecycle baseline synchronously. Prefer a selected-record projection over manager lookup that loads or scans other sessions. Retain record/query/stream reference identity within the app; emit bounded opaque identities, never the objects themselves.
4. **Observe fields independently.** Record request start and reply/end times for each control request; record capture intervals for host projections and event receipt. Retain unsupported/failed/missing results separately. Use a common sample label to group results while preserving their individual intervals. The SDK request ID binds a reply to its captured transport.
5. **Recheck selection and lifecycle around replies.** Verify the same selected record, query, input stream, and current Code ID before and after each request or grouped collection; retain boot/start/stop and turn-state changes. Manager `$` counts host requests while the query matches but returns the original promise; it does not reject an old query's reply after replacement. Teardown clears query/stream, increments prompt epoch, and removes many caches. A replaced or stopping query makes the group incomplete rather than a valid combined endpoint sample. [Manager `[531000,531700)`, `[1038000,1043500)`.]
6. **Distinguish task from turn.** Code session ID identifies a Code conversation; selected Desktop ID identifies the app task. Main Stop, SubagentStop, and `served:` identities must remain distinct. Optional Stop `prompt_id` comes from the engine request journal; this trace does not establish equality with Desktop `pendingCycle.userMessageUuid`. Do not manufacture that join. [RC `[197619983,197621503)`, `[207307500,207308900)`, `[207318493,207319450)`.]
7. **Compare qualification endpoints only within their evidence.** Preserve pending state and uncovered fields in both samples. Separate replies are not an atomic snapshot, and equal endpoint values do not prove an interval-wide invariant. Stop receipt time dates collection, not production of its selected assistant text.

The eventual result should contain a selected receiver binding, source and actual-executor evidence, field observations with meaning and intervals, pending-state observations, per-field completeness, and an overall qualification gap list. A field can be useful while the full sample remains incomplete. No observation absence becomes proof of nondelivery or triggers an automatic resend.

## The named app-adapter gap and its alternatives

The named unavailable access is the existing app-held selected query and selected-session Desktop grant evaluators. A temporary diagnostic adapter could project those exact objects' existing producer results, correlate requests, and record lifecycle checks. This does not supply the missing authenticated-account producer, bound execution-model semantics, fresh raw endpoint mode/cwd provenance, or a complete permission model.

| Access choice for that gap | Installation, interruption, restoration, maintenance, and observation cost |
| --- | --- |
| Temporary diagnostic app adapter | Requires a concrete separately authorized change/load method, selected-record/query binding, bounded output sink, and restoration plan. The old archive exchange/two-restart procedure is not inherited. Restart necessity and interruption duration remain unmeasured. Restoration must preserve concurrent changes and verify restored bytes; that proves restored content, not ordinary-runtime behavior. Maintenance is limited to the pinned diagnostic candidate, with reassessment for later builds. Observation adds query requests, host request accounting, serialization/I/O, and evaluator execution. |
| Ongoing app observer dependency | Requires an adopted supported endpoint, persistent installation/update/removal lifecycle, compatibility ownership, failure handling, retention policy, and continued evidence after app upgrades. It offers reusable access but retains ongoing observation, privacy, and maintenance costs. No recurring qualification cadence or ordinary-send need establishes its necessity in these inputs. |

Transfer to ordinary Desktop requires evidence that the same producer, source, contextual inputs, query selection, and meaning apply without the adapter; a source comparison of the changed boundary; an account of scheduling, logging, I/O, and lifecycle effects; and an ordinary-build observation or comparison that tests the material transfer claim. A synthetic callback proves mechanics. Restored hashes prove bytes. Neither establishes transferred runtime qualification. The pinned [experiment comparison](https://github.com/nisavid/provingkit/blob/88d1962aefdf40676148462fc495089fb18d1026/docs/superpowers/research/2026-10-02-receiver-experiment-options.md), “Resolve specific qualification gaps”, governs this comparison. Neither choice is adopted here.

## Unresolved decisions and experiment gates

The next access decision is whether a later non-prompting selected-query request can be reached through an existing authorized app surface, or whether the temporary diagnostic adapter is warranted for that named gap. Prepare its exact footprint and lifecycle before requesting a grant. An ongoing dependency remains an alternative requiring separate justification.

The authenticated-account requirement needs an authoritative producer tied to actual execution. The actual-model requirement needs a declared distinction between session selection, resolved next/current model, and the models reported for specific attempts, plus an honest coverage result. Complete permissions need the uncovered runtime consumers and pending stores traced to a meaningful aggregate. Raw cwd fallback provenance and fresh endpoint mode remain distinct producer questions. Investigate these paths or return concrete alternatives for the operator; do not replace the accepted obligations with cached or partial values.

Fixture preparation can proceed with the accepted command test boundary and acquisition limits: one account/organization metadata directory, at most 128 nonrecursive entries plus overflow detection, and at most three explicitly selected files of up to 1 MiB plus overflow detection. Reading a file acquires all serialized fields before projection. The actual paths, environment allowlist, executor evidence, hook configuration/loading, sink, cleanup, and independent selection witness belong in the reviewed live proposal.

A missing actual-executor/task witness, unavailable hook loading, missing Code/socket field, or ambiguous current-Code join blocks that fixture's identity/Stop claim. A missing authenticated-account getter, full permission aggregate, arbitrary endpoint cwd provenance, or bound execution-model evidence blocks later qualification; it does not automatically block the smaller fixture proposal. The fixture can test final-text normalization, event-time optional fields, collection limits, and binding. It cannot resolve selected-query transport access or host-evaluator completeness through Stop output alone.
