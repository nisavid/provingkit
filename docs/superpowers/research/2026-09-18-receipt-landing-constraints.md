# Receipt constraints across source landing

A replacement must qualify the actual landed Candidate while preserving the original comparison, complete input closure, original observations, and the processor that interpreted them. The current checker requires both unchanged inputs and source ancestry. The writing squash demonstrates that unchanged bytes alone cannot satisfy that contract: all 25 bound inputs survived, but the evaluated source commit did not become an ancestor of the landed commit. The existing procedure repairs this through a second PR; the new destination requires a supported landing process that avoids a corrective Receipt PR solely for rewritten history.

## Contract and distinct identities

The [accepted Receipt decision](https://github.com/nisavid/provingkit/issues/29#issuecomment-5524457529) requires acceptable coverage and results for readiness and merge. CI checks committed evidence and never runs evaluations. Ordinary policy requires three application repetitions, every safety expectation passing 3/3, every quality expectation passing at least 2/3, and every required trigger correct. An operator-only waiver remains a separate recorded decision; changing the landing strategy cannot supply one. The [implemented policy](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/release/behavior-eval-policy.json#L1-L10) retains those thresholds.

| Identity | Current meaning and required distinction |
| --- | --- |
| B | Original comparison base selecting affected consumers. It is not automatically the current merge target or a receipt-only PR's base. |
| S | Committed source evaluated after preparation, or matched to retained observations during reconciliation. The Receipt calls this `candidate_revision`. |
| C | Commit containing the public Receipt and checked source. The check also calls this `candidate_revision`; that field has a different role from S. Current checking requires S to be an ancestor of C and the complete bound source closure to match. It does not claim execution of C. |
| P | Committed processing implementation used for reconciliation, separate from S and original execution revisions. Its tool, corpus adapter, inventory adapter, policy, and schema must match the running processing files. |
| Procedure revision | Published instructions loaded by a consumer. A documentation change can leave P unchanged. A separately consumed publication/relation tool closure can also use this revision without becoming the Receipt processor. |
| M, H, Q, T, W | Respectively: actual target immediately before source landing; reviewed source-and-Receipt PR head; first actual squash result; receipt-only successor candidate; actual final main revision after that successor. |

These meanings come from the published [input contract](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L19-L28) and [landing sequence](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L202-L229). The original observations retain their own revisions and execution identities; reconciliation does not replace those with S or manufacture execution at C.

## What the published checker establishes

### Inputs, applicability, and freshness

The core reads committed bytes with `git show` and modes with `git ls-tree`. Its snapshot binds regular files, including executable mode, from the complete skill subtree, content lock, required corpora and fixtures, shared references, declared behavioral inputs, dependencies, selected source documents, and expectation map. Preparation additionally binds processing files at S; reconciliation binds them separately at P. [Source reads and closure construction](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_receipts.py#L128-L203).

The inventory discovers the Slate and Rosters from the Kit definition and plugin topologies. It derives B-to-C applicability from both old and new consumers, including skill files, shared inputs, operative ownership and expectation mappings, matrix consumption, projections, and topology consumption. Removed skills, changed unsupported ordinary corpora, and unresolved affected owners remain explicit coverage failures. Proposal or rationale changes do not independently select every consumer. The separate production-routing tier does not automatically enter ordinary coverage. [Inventory contract](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L41-L62); [comparison implementation](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_inventory.py#L696-L791).

Applicability and freshness are different tests. A whole map, content lock, or processing change can stale an already required Receipt without independently selecting untouched skills. Per-consumer matrix selection does not narrow the full freshness closure. Once selected, the current descriptor must match the Receipt, the Receipt and snapshot must name the same S, S must be an ancestor of C, the reconstructed S snapshot must match the recorded snapshot, and S-to-C inputs must match in bytes and modes. [Freshness contract](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L178-L188); [core checks](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_receipts.py#L1452-L1480).

### Committed Receipt, provenance, and thresholds

The inventory reads actual regular Receipt blobs at `C:release/eval-receipts/<plugin>/<skill>.json` and records their path, mode, blob identity, and byte digest. It passes C as both core comparison revisions with each inventory-selected skill explicit; this preserves the inventory's per-consumer selection while retaining S-to-C freshness. Missing or unresolved selected evidence fails. An empty complete selection returns `not-required` without checking every stored Receipt. [Committed reads](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_inventory.py#L49-L76); [inventory checking](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_inventory.py#L794-L831).

The direct core CLI instead consumes mutable local Receipt files and caller-declared complete coverage. That route is useful before committing, but does not establish the committed-C claim or independent inventory selection. [Direct-caller boundary](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L231-L239).

Reconciliation requires distinct retained executions, complete per-case delivered inputs, matching prompts and responses, original source references, executor and grader identities with their evidence bases, actual grades, and explicit adjudication lineage when the rubric changes. Original failures remain in that lineage. Sentinel body-load discovery remains a bounded surrogate; recorded ordered routing has its own complete-catalog and sequence requirements. Public checking compares those retained public correspondences without reopening private originals. [Reconciliation and delivery contract](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L90-L126); [routing limits](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/docs/behavior-eval-receipts.md#L128-L164).

The checker recomputes complete case/repetition and trigger coordinates, expectation IDs and severities, Boolean grades, thresholds, and trigger correctness rather than trusting a stored overall verdict. Reconciled Receipts also require the recorded processing snapshot to equal the committed and running P implementation. A newer processor is not interchangeable merely because it accepts the same schema version. [Processor binding](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_receipts.py#L381-L396); [coverage and results](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_receipts.py#L1324-L1375).

A waiver still undergoes descriptor and freshness checks. The local core returns `waiver-pending` with authority and expiry verification false, making the overall outcome fail until its separate owner resolves those requirements. [Waiver outcome](https://github.com/nisavid/provingkit/blob/0797623a3d8dfafb600f0cb1009e4f6d4538bb30/scripts/behavior_eval_receipts.py#L1482-L1506).
