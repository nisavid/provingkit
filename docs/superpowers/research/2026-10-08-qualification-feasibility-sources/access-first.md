**DONE_WITH_CONCERNS.** The exact assessed Desktop archive is publicly recoverable, so the declared SDK RC wrapper and authoritative worktree owner can be inspected for this build. ## The actual bundled SDK wrapper

Desktop Common declares SDK wrapper `0.3.284-rc.20260927.t043816.sha16cbb4d` and Code target 2.1.284 at Common `[1736100,1739150)`; its lazy SDK load references `index.chunk-vRLpacfH.js` at `[3127500,3127800)`. The bundled module exports `query` and `startup` near its end, and its query implementation contains `getSettings()`, `listPermissionRules()`, `getStatus()`, and `getContextUsage()` at SDK `[1066200,1066800)` and `[1073700,1074500)`. These methods issue `get_settings`, `list_permission_rules`, `get_status`, and `get_context_usage` through the same `request` method. `getSandboxDialog()` is also present at `[1074650,1074900)`; the controlling design already identifies its cache/dependency effects and partial semantics, so its mere presence does not fill applied permissions.

`request` assigns a request ID, registers a pending handler, and writes a `control_request`; `readMessages` dispatches matching `control_response` frames (SDK `[1069950,1071850)`, `[1051300,1052050)`). The public getter signatures above take no timeout or AbortSignal argument. The internal request accepts a signal and may write `control_cancel_request` on abort, but calling that internal route would be a separate compatibility and effects choice. An adapter-side deadline would only stop waiting while the underlying request could remain pending. `accountInfo()` returns the original initialization account at `[1076200,1076400)`; it is not a fresh route getter. `reinitialize()` runs initialization again at `[1072100,1072350)` and is not a passive refresh.

`query()` constructs a query instance through `L9` (SDK `[1105000,1105500)`, `[1097400,1098100)`). A direct-connect path POSTs `/sessions` and opens its returned connection; the `cc+unix://` form is rejected (SDK `[658000,659200)`). These paths initiate or resume a session; they do not demonstrate an external attachment to Desktop's already owned query. The [current official TypeScript SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript), fetched via Context7 on 2026-10-08, documents `query()` session options and its configuration controls. It does not supply a source-backed passive attachment route. The actual compiled wrapper, rather than stable SDK 0.3.284, now establishes these method and transport facts for the assessed Desktop archive. I queried the official npm registry for the declared RC version; its version endpoint returned HTTP 404 and the registry version list did not contain that exact RC string at the time checked. That is an availability observation, not proof that no other private distribution exists.

The recovered Code RC binary confirms the producer side only for its assessed source target: `get_settings` reads current configured model and returns `applied` fields; `list_permission_rules` builds a represented rule/directory view (Code `[221225050,221226960)`, `[231927050,231928958)`). Environment updates can return a correlated success/error when supplied a nonempty request ID (Code `[220379600,220381850)`), while the retained Manager's token push omits that ID. The raw cwd helper uses an async scope or current process cwd, but its presentation helper catches an exception and substitutes original cwd (Code `[198480300,198481850)`). The retained design traces the conditional auth route and main-task context layers. Nothing in the confirmed SDK methods turns these partial projections into a complete selected-task account, permission, or cwd descriptor. Response support on an actual selected query remains untested.

## Registered worktree: existing owner read and lifecycle limit

The exact owner is `gitWorktreeManager` in `index.chunk-D6vCltAs.js`, not the Manager's cached `harnessCwd`. It stores `worktrees` in a `git-worktrees` store with a structured-cloned in-memory cache; if initialization cannot use the store, it substitutes an in-memory pool (owner `[109000,111100)`). `getWorktreeForSession(sessionId)` directly calls `findByLeasedBy`, which scans that registry and returns the first entry leased by the selected session whose status is not `creating` (owner `[112300,112950)`, `[153750,154150)`). In an already loaded owner, this getter has no Git resolution or registry write in its body. It is a concrete existing producer for the registered association and record fields, including path/status, when it returns a matching entry. A null result does **not** distinguish absent registration from an in-progress `creating` entry, corrupt-store fallback, or a registration transition, and it does not verify the path on disk. Reading its full returned record would acquire record metadata beyond a path; a later projection must enumerate and minimize it.

Registry mutation is real elsewhere: `registerWorktree` writes an adopted lease; `setWorktreeLeasedBy`, pooling, failure, and other setters write updated registry snapshots; creation first writes a `creating` entry and can remove it on failure (owner `[133300,134100)`, `[153750,156300)`). `forgetRecoveredWorktreeEntries` deletes other leases for the selected session (owner `[112200,112800)`). `resolveRegisteredWorktree` performs Git commands and filesystem checks (owner `[151100,152500)`). The Manager's `applyHarnessWorktreeMove` increments `harnessCwdGen`, clears its cached cwd, invokes that resolver, and later may update/save the Desktop record and emit change events (Manager `[508250,511700)`). Therefore the direct owner getter can replace a speculative new owner status record for a settled registered association, but it does not certify a pending transition or current Engine cwd. A complete endpoint sample needs task/owner binding checks and an explicit incomplete result when creation or movement is in flight. Invoking resolution to make a status look current would add effects and is outside this read-only research.

## Code source, extension, and load feasibility

The recovered Code target is an ELF x86-64 executable whose embedded Bun modules expose inspectable compiled JavaScript/bytecode. The [Anthropic Code release tag `v2.1.284`](https://github.com/anthropics/claude-code/releases/tag/v2.1.284) points to public repository commit `8364969e9f5234ef3d9743cf7c790e9aab0ac3b1`; the [tag's complete public Git tree](https://api.github.com/repos/anthropics/claude-code/git/trees/v2.1.284?recursive=1) had 1,980 entries and no `src/` entries when checked. The embedded Code RC commit `16cbb4ddeeb473f57fd8d5b713764903d7928e66` did not resolve as a public repository commit through the GitHub API. These checks do not establish a canonical editable source checkout, reproducible build procedure, or supported way to load a new control producer into the exact ordinary Code executable. Source and build availability outside these public routes remains unknown.

The [official SDK features documentation](https://code.claude.com/docs/en/agent-sdk/claude-code-features), fetched through Context7, describes settings and event hooks supplied at query creation; the [official user-input documentation](https://code.claude.com/docs/en/agent-sdk/user-input) describes a tool-permission callback. Their documented inputs are event/tool specific. The inspected Desktop owning-task MCP route and renderer IPC can expose selected host records only through an admitted app caller; the MCP route adds a prompt/tool action, and neither supplies the missing Engine-local semantics ([retained access report](https://github.com/nisavid/provingkit/blob/21dbe9a0b30c972e12662cb06f7929c20d137694/docs/superpowers/research/2026-10-03-qualification-observation-sources/access.md)). I found no documented passive SDK, plugin, or hook API that returns the effective auth route, all applicable permission inputs/pending changes, and raw cwd/fallback state for the existing Desktop query. This is a bounded public-source finding, not a claim that such a private API cannot exist.

The specific missing Engine producer would have to describe already selected state without refreshing credentials or making an inference request: relevant main-task model context, effective credential/account/org route and provenance, raw permission context plus applicable layers and pending applications, and raw current cwd with scope and failure provenance. The direct worktree owner getter should be used for settled registration before adding a worktree producer. Any proposal must trace the selected ordinary-task consumers, narrow each field to applicable state, avoid acquiring unrelated broker entries, and preserve missing versus authoritative empty results. A speculative edit to compiled Bun/ELF bytes would not provide a canonical rebuild, maintained compatibility surface, or supported load route; I do not propose one.
