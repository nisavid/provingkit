## What the coverage report gets right

- **Applied model meaning remains conditional on the selected main context.** Code `get_settings` reads current `st()` into `applied.model` and related values (Code `[221225050,221226960)`). The query path can incorporate a tool's `newContext` into the main next-turn context (Code `[213041300,213043800)`), while context composition can change model and permissions (Code `[201213000,201218850)`). That proves a possible relevant main-task layer, not that every endpoint has one or that an idle context remains available. The coverage report's proposed selected-context lifetime check is necessary before a new model producer is justified. A universal context registry and per-inference backend proof would expand the accepted claim.
- **Account route is not initialization account.** The exact bundled `accountInfo()` returns the initialization account from the original promise (SDK bundle `[1076200,1076400)`), while provider/client/header selection can vary by chosen route and request (Code `[198737300,198740000)`, `[203886700,203896950)`, `[200140524,200142150)`). Code can acknowledge `update_environment_variables` with a supplied nonempty request ID (Code `[220379600,220381850)`), but the retained Manager token push omits it; even acknowledged environment handling would not prove the later effective route. A source producer should describe already established selected-query binding and explicitly distinguish a route not yet established at an idle endpoint. It must not construct a client or refresh credentials to manufacture evidence.
- **Permissions need applicable consumers and pending decisions.** The Engine rule getter builds a represented view from current context and settings (Code `[221225050,221226960)`, `[231927050,231928958)`); it is not the entire mode/layer/runtime decision. Manager `hasPendingFor` explicitly ignores out-of-turn entries (Manager `[136100,136390)`), so that boolean cannot establish no relevant pending permission change. Browser, computer-use, broker, trust, connector, scheduled, and special-consent paths in the coverage report are *candidate* categories. Each requires a selected ordinary-task consumer and enabled-surface check before inclusion; unrelated tasks, isolated forks, generic dialogs, and unavailable tool families do not become mandatory merely because a store exists. An enabled standing grant can remain applicable without a fixture tool call.
- **Current cwd still needs provenance.** The Code cwd helper reads its async scope or process cwd and the presentation helper catches a failure and returns original cwd (Code `[198480300,198481850)`). A raw read from an observer control handler may itself run in a different scope. A proposed producer must bind the selected main task's cwd owner/scope and report success versus fallback/failure, rather than simply call the raw helper in an arbitrary handler.
- **Partial getter acquisition has costs.** The exact wrapper registers request IDs and pending callbacks, writes control requests, and dispatches matching responses (SDK bundle `[1051300,1052050)`, `[1069950,1071850)`). Whole settings/rules/status replies can be acquired before output filtering. `getSandboxDialog()` exists (SDK bundle `[1074650,1074900)`), but the Code path described by the design can invalidate settings/check dependencies. The coverage report correctly treats this as a separate effectful diagnostic, not a complete passive permission snapshot. All of these are static producer findings, not supported response on an actual selected query.

## Corrections and narrowed conclusions from recovered Desktop source

1. **The actual wrapper gap is closed for method *presence*, not task access or runtime support.** Common declares RC wrapper `0.3.284-rc.20260927.t043816.sha16cbb4d` and lazily loads `.vite/build/index.chunk-vRLpacfH.js` (Common `[1736100,1739150)`, `[3127500,3127800)`). That exact bundle implements `getSettings`, `listPermissionRules`, `getStatus`, and `getContextUsage` as control requests (SDK bundle `[1066200,1066800)`, `[1073700,1074500)`). It also confirms `accountInfo` is initialization data. The coverage report correctly withheld RC equivalence in its frozen first pass because it had only stable SDK bytes then. The original gap now becomes: admitted Desktop caller, actual owned-query support/reply shape, and selected record/query/executor binding. Public `query()` constructs a new query instance (SDK bundle `[1105000,1105500)`); direct connect creates a server session, and `cc+unix://` is rejected (`[658000,659200)`). These are not passive external attachment to Desktop's existing query. Reinitialization is not a fresh getter. The public getters have no timeout/signal parameter; an internal cancellation frame is a separate choice, and a local wait deadline does not stop the underlying request.
2. **A worktree association getter exists, with a wider read than either first report allowed for.** The Manager eagerly imports the owner chunk at startup (Manager `[700,1850)`), whose exported singleton is constructed as `new Qs` (owner `[298800,299000)`). Its constructor initializes the `git-worktrees` store and caches `worktrees`; a cold load may read the store or handle a corrupt/unavailable store, including fallback to an in-memory pool (owner `[109000,111100)`). Once that Manager and owner are loaded, `getWorktreeForSession(id)` itself performs no Git command, path resolution, or write: it calls `findByLeasedBy` (owner `[112300,112950)`, `[153750,154150)`). This resolves the coverage report's direct owner-source gap and supports a *registered association* read without invoking Manager resolution.
3. **The owner getter is not a narrow selected-only acquisition.** The owner store's `get("worktrees")` returns `structuredClone(i)` for the entire registry; `findByLeasedBy` then iterates `Object.values` and returns the first non-`creating` entry leased by the ID (owner `[109000,111100)`, `[112300,112950)`). Even if output serializes only one path, this method acquires all registry entries and inspects their lease/status fields. My access first report identified broader returned-record bytes but omitted this full-registry clone/scan. It also implicitly treated the first match as the authoritative singular association: the method does not prove uniqueness. A later acquisition contract must authorize and account for the whole clone/scan or establish a source-owned selected index/projection, and must report duplicate selected leases as ambiguous rather than silently accept an iteration winner. No new owner change is selected by this finding.
4. **Null and stale meanings are limited.** The owner getter filters `creating`; creation writes that status before work and removes an entry on failure (owner `[133300,134100)`). Null can mean no matching settled entry, a creating entry, or store unavailability/in-memory fallback, and it does not settle an in-flight Manager movement. Manager `applyHarnessWorktreeMove` increments `harnessCwdGen`, clears cached cwd, invokes `resolveRegisteredWorktree`, then may save the record, update lazy path, and emit events (Manager `[508250,511700)`). The resolver executes Git and filesystem checks (owner `[151100,152500)`). The direct getter reports registry association, not filesystem operability or Engine cwd. If the accepted field remains "registered worktree," no disk validation should be added merely for this observation; task/owner binding and a pending/ambiguous status are needed at transitions.
5. **Fallback access is narrower than a generic stream promise.** The exact Manager receive loop normalizes each owned-query message through `j.S`, then explicitly handles `model_refusal_fallback` for the selected query (Manager `[1566300,1567100)`, `[1572450,1573600)`). The normalizer's exported function removes specific synthetic bookkeeping fields from message objects (ASAR `.vite/build/index.chunk-D8aWeSvo.js`, 9,047 bytes/SHA-256 `cee58d55b7fd748b938fe966af4a9af5e10d6252ec7f64dc9fb224feaed83e3d`, `[600,850)`). Code separately defines/emits `model_fallback` for primary-model failure (Code `[199722000,199722850)`, `[213024300,213027950)`). I found no literal `model_fallback` handling in the assessed Manager or bundled wrapper. That absence does not prove the generic transport drops it; it does mean neither frozen report proves complete normal/decline/refusal fallback capture through the proposed tap. Trace the exact Code serialization, SDK transport pass-through, and Manager callback placement/schema for each selected event type before claiming interval coverage. An absence of recorded events cannot become a no-fallback result without that coverage and overflow check.

## Build/load and full-claim consequence

The access first report's public recovery is useful but only for compiled Desktop bytes. The [versioned public packager asset](https://github.com/patrickjaja/claude-desktop-extra/releases/download/v2.9939.4/claude-desktop-extra-2.9939.4-1-x86_64.pkg.tar.zst) matched its release digest and the retained ASAR/member hashes. The separate [official apt package](https://downloads.claude.ai/claude-desktop/apt/stable/pool/main/c/claude-desktop/claude-desktop_2.9939.4_amd64.deb) has the same displayed version and commit but different Manager/Host/Common bytes. Version strings alone do not transfer source anchors or wrapper behavior between them. The Code RC artifact is an inspectable compiled ELF/Bun executable; the public `v2.1.284` repository tree checked in the access first report did not establish canonical Code implementation source or a build/load procedure for adding a producer. This is an evidence gap, not proof that Anthropic lacks private source or cannot offer a supported API. Hooks and SDK callbacks have event/tool inputs; the existing app MCP route needs task activity. No inspected extension replaces the missing passive selected-query descriptors.

Thus the full selected-task before/after claim still requires: a proven applicable main-task model layer disposition with fallbacks separate; effective selected-query account/organization/auth route provenance, including a not-yet-established state if relevant; complete *applicable* Engine/Desktop permission inputs, evaluated grants and task-bound pending changes; an unambiguous registered-worktree association through transition; and raw selected-main-task cwd/failure provenance. It also requires an admitted access path to the existing selected query, actual wrapper/Code support on the bound executor, per-acquisition intervals, and distinct source/actual-executor/task/query identities. Equal endpoint values do not prove continuous preservation; partial results do not qualify the full claim. No broader all-context inventory, server-attributed identity, every inference attempt, or universal grant registry is implied.

The smallest source continuation is to close the selected ordinary-task consumer/applicability map and search for existing nonmutating route/permission/cwd producers before designing any new one; verify exact fallback pass-through and the owner getter's full scan/duplicate behavior; and ask the relevant Code/SDK owner for a supported diagnostic API or canonical source/build/load path only for still-missing facets. A separately authorized disposable-task check could test one getter's actual support, reply shape, selection, timing, and effects, but not create the absent producers. A candidate Desktop adapter would need a reviewed startup/load route, exact read footprint, query lifecycle checks, interruption/restoration and ordinary-build transfer argument. No alternative or implementation is adopted here.
