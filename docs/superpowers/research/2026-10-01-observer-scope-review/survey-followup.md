# Cross-informed survey delta

**The direct native MCP sender is the smallest supported send path found so far.** The frozen native report observed `ListAgents` and `SendMessage` exposed by a separate `claude mcp serve` process and successfully made a read-only `ListAgents({})` call. That process does not need the extra model-driven `claude -p` session I recommended in round one. No message was sent, and its formatted peer listing has not yet been bound to one consented Desktop task. More importantly, no retained observation connects an external `SendMessage` to a receiver record and an explicit acknowledgment carrying the application’s correlation ID. [Frozen native report](native-first.md); [Anthropic’s messaging contract](https://code.claude.com/docs/en/cross-session-messaging).

The conceptual report correctly separates transport, receiver evidence, and effective-state preservation. Its preferred native route now has concrete sender evidence, so the next comparison should concern **observation**, rather than another transport. Two proposed tests in that report exceed the accepted contract: requiring the receiver to open the context link, and requiring evidence unforgeable against a malicious same-user sender. The link must be reviewable and present in the notification; making dereferencing part of receipt needs a separate decision. Receiver-origin evidence still must be distinguished from a sender’s submission result, without silently adding a hostile-sender threat model. [Frozen conceptual report](conceptual-first.md); [contract history](history-trace.md).

I also correct my own round-one classification of held messages. **Held is an observed undelivered state that may later become delivered** after approval or a mode or settings change. Refused is dropped. Neither a held result nor an immediate successful send proves receipt, and an uncertain send needs reconciliation before any resend. Anthropic documents delivery between tool calls for an active receiver and a new turn for an idle receiver; that is the route-specific behavior a later disposable-peer proof should observe. [Inbound and delivery documentation](https://code.claude.com/docs/en/cross-session-messaging).

## What the independent projects contribute

I selected projects for distinct mechanisms, then read their source at pinned revisions. These are implementation examples, not evidence that their behavior applies to the existing Desktop task.

- **Remote Control bridge:** [cc-tap at `b18e9a2`](https://github.com/es617/cc-tap/tree/b18e9a2f448bc83b338f444262e4f19d96f6c0c8) is an MIT-licensed experimental MCP server. Its [client](https://github.com/es617/cc-tap/blob/b18e9a2f448bc83b338f444262e4f19d96f6c0c8/cc_tap/client.py) lists and reads Remote Control sessions and posts user messages; its [server](https://github.com/es617/cc-tap/blob/b18e9a2f448bc83b338f444262e4f19d96f6c0c8/cc_tap/server.py) offers `send_and_wait` by polling events until a result. The project explicitly uses undocumented Anthropic endpoints and local Claude Code OAuth credentials. Its [protocol notes](https://github.com/es617/cc-tap/blob/b18e9a2f448bc83b338f444262e4f19d96f6c0c8/PROTOCOL.md) report incomplete session-ID mapping and event pagination. A returned result is not the requested correlated receiver acknowledgment, and messages appear as user-typed rather than attributed peer messages. Anthropic now documents enabling Remote Control from an **existing Desktop Code task**, which keeps this a genuine research lead if that exact task has opted in. It does not qualify cc-tap’s private API or establish the task’s effective state. [Official Remote Control documentation](https://code.claude.com/docs/en/remote-control).

- **Terminal session manager:** [tmux-ccm at `32799c9`](https://github.com/yohasebe/tmux-ccm/tree/32799c9d1ec9362101417c5beceaeb81aff88994) is MIT-licensed. Its [send implementation](https://github.com/yohasebe/tmux-ccm/blob/32799c9d1ec9362101417c5beceaeb81aff88994/lib/ccm_send.py) resolves a Claude-bearing tmux pane, rechecks state, and types into that pane; it refuses permission dialogs and normally refuses busy delivery. Its [hooks](https://github.com/yohasebe/tmux-ccm/blob/32799c9d1ec9362101417c5beceaeb81aff88994/hooks/on-notification.sh) and [JSONL reader](https://github.com/yohasebe/tmux-ccm/blob/32799c9d1ec9362101417c5beceaeb81aff88994/lib/ccm_jsonl.py) combine event signals with transcript activity. This is useful evidence that UI/pane senders need identity and modal checks and that transcript freshness is only a **positive** activity signal. It controls tmux CLI panes, not an existing Desktop Code task.

- **Transcript observer:** [Recensa at `aee7df8`](https://github.com/S40911120/recensa/tree/aee7df884284b0f3656385a9c3bb6525fd9f5519) is MIT-licensed. It indexes Claude JSONL into SQLite and serves a reader. Its [watcher](https://github.com/S40911120/recensa/blob/aee7df884284b0f3656385a9c3bb6525fd9f5519/backend/src/ingestion/watcher.js) uses file events or bounded hot/discovery/full-scan ticks; its [message reader](https://github.com/S40911120/recensa/blob/aee7df884284b0f3656385a9c3bb6525fd9f5519/backend/src/services/messageService.js) uses byte checkpoints and ignores incomplete trailing records. The transferable approach is incremental, uncertainty-aware transcript acquisition. A positive, uniquely bound record might help establish receipt after fixture qualification. Silence cannot establish refusal or nondelivery, and transcripts do not expose every applied account, rule, grant, pending change, or current directory.

- **Channel bus:** [cc-dm at `5012841`](https://github.com/gitrishiom/claude-code-dm/tree/5012841e0af8fb6a56bd19373dbc4bb93a0e5640) is MIT-licensed. Its [server](https://github.com/gitrishiom/claude-code-dm/blob/5012841e0af8fb6a56bd19373dbc4bb93a0e5640/src/server.ts) declares Claude’s experimental channel capability and polls a [SQLite bus](https://github.com/gitrishiom/claude-code-dm/blob/5012841e0af8fb6a56bd19373dbc4bb93a0e5640/src/bus.ts) for messages. It deletes a bus row after a channel notification call succeeds. That establishes a channel push attempt, not a model acknowledgment. Its README starts specially configured CLI sessions with a plugin; I found no source-backed attachment to an already running Desktop task.

- **Custom relay and hooks:** [Claude Relay at `573d196`](https://github.com/gvorwaller/claude-relay/tree/573d1963e719cc317ade100d573394ba00a77839) runs an MCP/WebSocket relay with a separate session registry. Its [receipts hook](https://github.com/gvorwaller/claude-relay/blob/573d1963e719cc317ade100d573394ba00a77839/scripts/relay-receipts-hook.js) deliberately distinguishes injecting a delegate receipt into context from verifying that a later assistant response reported it. That distinction is valuable for acknowledgment design, but those receipts concern its own delegates; they do not witness native delivery into this Desktop task. I found no top-level `LICENSE` file at the pinned revision and make no licensing conclusion.

The surveyed wrappers either control sessions they launch, attach through optional Remote Control using a private API, or observe files and hooks. None supplies, from its pinned source, a supported complete route for the exact existing Desktop task plus correlated receipt and full before/after applied-state evidence. This is a bounded finding about the representatives inspected, not a claim that another integration cannot exist.

## Observation should be tested independently

**UI and accessibility reads** could corroborate the selected Desktop task, a visible inbound preview or acknowledgment, and displayed model or permission controls. They should be assessed as evidence collection, separately from typing into the composer. A visible control is not by itself the applied account route, complete rules and grants, pending changes, or current worktree/cwd. UI selection and refresh also need explicit binding to the consented task. This remains a hypothesis; I did not inspect a live UI.

**Hooks** offer different partial evidence. Anthropic’s documented hook input includes session identity, cwd, and permission mode at particular events; `SessionStart` may include model. `UserPromptSubmit` concerns a submitted user prompt, while `Notification` concerns notification events. The public hooks material retrieved through Context7 did not establish a cross-session-message-received callback or a complete effective-state snapshot. That is an evidence gap, not proof such observation is impossible. A receiver-installed hook would also be a receiver change requiring its own later scope decision. [Hooks reference](https://code.claude.com/docs/en/hooks).

**Session readers** have similarly bounded semantics. Context7’s current official Agent SDK TypeScript material describes `listSessions` as discovery of past sessions with lightweight metadata and `getSessionMessages` as reading past transcript messages. It does not document attachment to a running Desktop task or fresh applied account and permission state. The [official SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript) was retrieved through Context7 because the web reader returned an internal error for that page; I make no claim beyond the retrieved entries.

## Changed recommendation and unresolved findings

Retain **direct MCP `ListAgents`/`SendMessage`** as the proposed sender. Compare a selected-file reader, evidence-only Desktop observation, and the prepared app-side observer against each separate obligation: positive receiver record, explicit correlated acknowledgment, and before/after applied account, model, permission mode/rules/grants/pending changes, worktree, and cwd. Preserve the accepted full claim and graduated evidence reuse. The observer probe’s offline package checks did not execute a modified app; its proposed stopped-app archive exchange and restoration require two restarts and have unmeasured total duration. The exact fixture-identity receipt direction and 15-minute acquisition-admission ceiling were accepted in [Decide whether to incorporate the fixture-identity receipt](https://github.com/nisavid/provingkit/issues/353#issuecomment-5925012453), but implementation remains held for this scope review. [Coordinator history trace](history-trace.md).

Material unknowns remain: whether an external native send produces a uniquely attributable receiver record; where an explicit ACK can be observed; whether the selected-file reader covers that record after compaction and persistence delays; which receiver-owned surface can report each **applied** state field freshly; and whether optional Desktop Remote Control can expose useful read-only evidence through a supported interface. No third-party project resolves those unknowns by adoption alone. The next authorized proof, if selected, belongs on purpose-created disposable idle and busy peers with fresh exact-peer consent, while historical tasks remain outside experimentation.
