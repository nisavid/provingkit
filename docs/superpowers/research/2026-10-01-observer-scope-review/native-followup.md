## Cross-examination of the first reports

The conceptual report usefully separated transport, receiver evidence, applied state, and fixture identity. Its proposed *unforgeable* receiver receipt, receiver dereferencing of the context link, and per-build live smoke test are stronger than the supplied qualification contract. They are hypotheses or optional tests, not new acceptance gates. The accepted claim asks for receiver-origin delivery evidence, an explicit correlated acknowledgment, a reviewable link, before/after applied-state evidence, and graduated compatibility assessment. It does not ask for a hostile same-user threat proof or an interval-wide proof that no transient state change occurred. The [observer design](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/specs/2026-09-29-desktop-runtime-observer-design.md#field-producers-and-remaining-gaps) likewise distinguishes bounded before/after samples from a stronger continuous-change claim.

The external survey found useful current public surfaces, especially hooks, but its recommended `claude -p` sender adds a model turn and a second Code session that the retained native MCP discovery already avoids. The observed `claude mcp serve` tools remain the smaller sender candidate; neither sender has a qualified receiver record. The survey also called held and refused “terminal observations.” **Refused** drops a message; **held** is undelivered and can later be released by approval or a settings change. Neither state authorizes automatic resend. Anthropic documents those distinct transitions in its [cross-session messaging reference](https://code.claude.com/docs/en/cross-session-messaging#message-delivery). The survey correctly treated direct socket writes, Channels, and CLI resume as unproven for the exact Desktop task. [Pinned sender report](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md).

My first report accurately separated the built offline candidate from live proof, but it treated the chosen source path as closer to architectural necessity than the evidence supports. The ten unique patch anchors prove where the proposed hooks can be placed in the pinned manager bytes. They do not prove those hooks are the least costly way to satisfy each obligation. Conversely, the presence of an SDK reader or hook does not prove it can replace an app hook. The meaningful comparison is by **field and producer**, not by whether an alternative sounds more “native.”

Installing or enabling a hook is also a receiver configuration change whose scope and effects require their own decision; this research does not authorize it. The check is whether current Desktop-hosted Code actually runs that documented hook for the selected fixture and whether a read-only source trace can bind its `session_id` to the chosen Desktop task. “Could” is the supported conclusion today. ## Fixture identity: policy-driven scope versus technical gap

The current procedure requires reading **only** a constructed, selected metadata file. Its path includes the effective user-data root, account ID, organization ID, and Desktop task ID. Before normal creation and the first Code init, that full tuple is not established. The difficulty is partly a selected-fixture-only **read-scope rule**: broader metadata-directory enumeration or “newest file” selection could discover candidates, but would inspect unrelated tasks and would not by itself prove which record came from normal UI creation. That is a possible scope change for an operator, not evidence that the filesystem is technically unreadable. The difficulty is also technical: a native `ListAgents` reference, Code session UUID from an SDK or hook, and Desktop task ID are different identifiers; their exact live relationship is not exposed by the public SDK contract. [Fixture path and scope](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/probe-procedure.md#disposable-fixture), [sender listing limits](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md), [SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript).

The accepted receipt design addresses both concerns without a scan: it observes one qualifying new-local-task registration and the actual writer fulfillment, then reads only the derived file and admits the same live query. Its `initiator: "user"` discriminator is explicitly **not** authentication of a click or proof that all other callers were excluded. The current candidate does not implement that design. A scoped alternative would need to state exactly which extra path, UI field, or event can yield the tuple and why that observation binds normal creation. Relaxing the selected-file rule merely to simplify acquisition is an operator scope choice, not an automatic optimization. [Receipt design](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-30-fixture-identity-acquisition-design.md#claim-and-boundary), [current candidate limit](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/README.md#start-here).

## What the candidate still cannot establish

The built probe intentionally names seven unknown claims: current account route, model freshness, permission mode, complete applied permissions, current cwd, native address binding, and external delivery plus ACK. Its fixed getters are `accountInfo()` (initialization cache), `getContextUsage(summary)` (model freshness unproven), and `listPermissionRules()` (partial permission coverage). The host projection supplies a spawn route, manager mode and event, selected grants and pending markers, and last manager-observed cwd. The process helper can add separate PID/executable evidence but leaves query-to-OS association unresolved. Offline packaging and a syntactically valid sidecar do not reduce any of those live unknowns. [Unknown claims](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/observer-contract.mjs), [getter provenance](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/observer-probe.mjs), [process limit](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/process-binding-evidence.md).

An app change becomes justified as the **smallest credible automated option** only after bounded source checks fail to establish an external selected-manager read or a sufficient hook/SDK combination, and after the patch can name a producer for each remaining applied-state field it claims. The present patch is justified as a partial **no-send experiment** in the accepted preparation direction; its existence does not establish the full notification architecture. No immediate redesign or contract reduction follows from that finding.

The smallest offline checks left are: trace whether the pinned host `get_session` and `LocalSessions` bridges expose any already existing external read-only invocation, including their exact field projections; compare current documented hook events with the selected Desktop executor’s source registration and event routing, particularly incoming native peer text, `MessageDisplay`, mode/model/cwd, and startup; trace whether SDK session readers resolve the exact Desktop Code ID without scanning unrelated tasks; and enumerate what fixture identity can be obtained from a normal new-local-task UI event or selected record **before** invoking the accepted receipt hooks. Stop each check at “not established” if the source lacks the link; do not turn a bounded search into an impossibility claim. Compatibility of a later build remains graduated and behavior-specific. [Observation-path survey](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md), [observer design](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/specs/2026-09-29-desktop-runtime-observer-design.md), [history trace](history-trace.md).
