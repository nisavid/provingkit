# First-round external survey: notifying an existing Claude Desktop Code session

**Finding, as of 2026-10-01:** Anthropic now documents Claude Desktop Code on Linux and a same-machine, per-session messaging transport. The strongest route to investigate is a narrowly restricted Claude Code CLI sender using Claude Code’s own `ListAgents` and `SendMessage` tools to reach the existing Desktop session. A direct connection to the receiver’s Unix socket could be simpler, but the public documentation I found describes scripts posting to their *own* session and does not specify a complete external-peer protocol. Neither route is qualified for this task. A successful send or socket write does not establish receiver delivery or the required correlated acknowledgment. [Desktop on Linux](https://code.claude.com/docs/en/desktop-linux), [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging).

This is public-source research only. I did not inspect the machine’s Claude installation, accounts, sessions, settings, transcripts, sockets, or app UI; run either app; create a task; send a message; or test a route. The proposed proof must use the purpose-created disposable peers in the supplied charter. Historical tasks supply no test target.

## What the current product contracts establish

The current English Desktop reference lists a Linux beta and describes Code-tab conversations as independent sessions with their own context and project folder. The Code tab supports local sessions, model and permission selectors, and worktree isolation. The model and permission mode can change during a session. This matters because a saved session title or launch configuration cannot by itself certify the current execution state. A stale, four-month-old localized search result still says Desktop is unavailable on Linux; I used the current English page and its dedicated Linux page for the platform finding. [Desktop reference](https://code.claude.com/docs/en/desktop), [Linux beta](https://code.claude.com/docs/en/desktop-linux).

Desktop can itself list, read, and message other Code-tab sessions when Claude is operating *inside* a Desktop session. That discovery surface sees Desktop-run local, SSH, and WSL sessions, with its own recency and archive filtering; separate cross-session messaging can also reach terminal sessions. This is a native Claude-to-Claude facility, not a documented API that ChatGPT can call. Desktop says a message to a receiver mid-task is held until its current work finishes. The broader cross-session reference says an active receiver reads messages between tool calls and an idle receiver starts a new turn. Those may describe different sending surfaces; busy delivery and context continuity need a route-specific test. [Desktop cross-session behavior](https://code.claude.com/docs/en/desktop), [cross-session delivery](https://code.claude.com/docs/en/cross-session-messaging).

Cross-session messaging requires Claude Code **v2.1.224+ on Linux**; same-machine support on some providers or with feature-flag fetching disabled requires **v2.1.248+**. Live sessions normally expose an inbox over a Unix domain socket on Linux. `/list-agents` lists reachable peers, and `/status` shows the current session’s peer address or why its inbox is unavailable. A local recipient can be addressed by a unique name, or by a listing-specific short identifier when names collide. A peer appears only while it binds an inbox. A bare session ID is not presented as the documented `SendMessage` address. [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging).

The documented receiver outcomes are **delivered**, **held**, and **refused**. A hold does not place the message in Claude’s context; later approval or a settings change may release it. A refusal drops it. The receiving session’s `crossSessionInbound` setting and permission-mode relationship affect that decision. The sender can receive later failure information, but an immediate send result should not be treated as an acknowledgment from the receiver. A 2026 issue reports `success: true` preceding a hold and expiry; that is a user report, useful as an adverse test case, not proof of the behavior of any build here. [Inbound controls](https://code.claude.com/docs/en/cross-session-messaging), [reported delayed hold](https://github.com/anthropics/claude-code/issues/85503).

Anthropic documents that peer text is attributed to its sender and cannot approve a permission prompt, execute slash commands, or change the receiver’s configuration merely by saying so. The receiver still applies its own permission rules to subsequent work. This supports an *informational* notification, provided the payload makes no claim of user authority. It does not prove that the effective account route, model, grants, or cwd stayed fixed; those require observation of the actual receiver. [Incoming-message treatment](https://code.claude.com/docs/en/cross-session-messaging).

## Candidate routes

### 1. A restricted Claude Code CLI sender using native peer messaging

A short-lived `claude -p` session can, in principle, find a live peer through `ListAgents` and send plain text through `SendMessage`. Anthropic documents `claude -p`, the `--tools` restriction, JSON output, and inbox participation for noninteractive `-p` sessions. A sender with only the minimum relevant tools could deliver the brief text, reviewable link, and correlation ID to an already running Desktop Code session. This uses Claude Code’s supported peer routing and inbound controls; it does **not** resume or replace the target. [CLI reference](https://code.claude.com/docs/en/cli-reference), [noninteractive peer behavior](https://code.claude.com/docs/en/cross-session-messaging).

Its costs are a second Claude session, model usage, and an additional model-mediated target-selection step. It must not infer identity from a matching title alone. A safe qualification would bind the operator’s purpose consent to a specific disposable receiver, freshly list reachable peers, resolve any duplicate names from that live listing, check the destination again immediately before sending, and refuse to send if identity or purpose is ambiguous. The supplied charter calls for a receiver acknowledgment; the CLI sender’s exit and `SendMessage` return cannot replace it. Whether a short-lived `-p` sender can remain reachable long enough for the receiver’s reply, or whether a separate receiver-origin receipt channel is needed, remains untested.

This route also has an **account-route gap**. A new CLI sender may authenticate or route differently from Desktop. The local transport may still work across providers, but that is distinct from proving the existing Desktop task’s account route stayed intact. The Desktop reference says the CLI and Desktop have separate session lists while sharing certain configuration files; Desktop’s live model and permission selectors can override defaults. The receiver’s own state must be checked, without changing it. [Desktop CLI comparison](https://code.claude.com/docs/en/desktop), [cross-session provider availability](https://code.claude.com/docs/en/cross-session-messaging).

### 2. A direct, receiver-bound Unix socket adapter

Claude Code publicly documents a per-session socket, its `/status` “Peer address,” and `CLAUDE_CODE_MESSAGING_SOCKET` for hooks and child commands. It explicitly discusses a script posting to **its own** session socket, an optional auth line on Linux, socket ownership checks, a 30-second incomplete-line timeout, and inbound controls. This makes a local transport plausible without creating a model-driven sender. It is the smallest *potential* implementation if the protocol and external-peer behavior are demonstrated on disposable sessions. [Socket contract](https://code.claude.com/docs/en/cross-session-messaging).

The cited page does not give a complete message-frame example for an independent process targeting another session, nor a receipt/acknowledgment contract. The documented “own-child” exception depends on receiver-verifiable process ancestry or its exported token; a ChatGPT-side process would not qualify as that child. Treating its socket path as sufficient authority would also miss purpose consent, freshness, held/refused outcomes, and correlation. The full Claude Code engine is not licensed as open source in the public repository; its repository license reserves rights and subjects use to Anthropic’s Commercial Terms. Public documentation can define this route’s starting hypothesis, but source inspection of third-party copies or reverse-engineered bundles would not substitute for supported contract evidence. [Socket and own-child rules](https://code.claude.com/docs/en/cross-session-messaging), [Claude Code license](https://github.com/anthropics/claude-code/blob/main/LICENSE.md).

### 3. Exact-session UI entry, including a Remote Control view

The Desktop prompt box sends text into the selected session; the reference says a correction sent while Claude is working is read after the current action. Entering the informational payload in an explicitly selected existing session could preserve its live Desktop host, account route, model, permissions, and worktree. The UI also exposes the current model and permission mode to the operator. Remote Control can expose a connected local Desktop session through claude.ai/code while the computation remains on the local machine. [Desktop prompt and selectors](https://code.claude.com/docs/en/desktop), [Remote Control](https://code.claude.com/docs/en/remote-control).

I found no public programmatic Desktop-session message API in these references. The documented Remote Control client is a browser or mobile UI, not an external send endpoint. An authenticated, interactive UI route would need exact-session selection, a pre-send freshness check, and receiver-origin verification. It could be operationally simpler than building a transport where a permitted UI control surface exists, but this round did not exercise one. Anthropic’s statement that *Claude Desktop’s own* computer-use feature is unavailable on Linux does not establish whether an independent automation harness can control its UI. [Desktop feature comparison](https://code.claude.com/docs/en/desktop), [Remote Control platform comparison](https://code.claude.com/docs/en/remote-control).

### 4. A purpose-scoped channel or external broker

Anthropic’s Channels research preview permits an MCP server to push events into a **running CLI session**. The published reference specifies `claude/channel`, `notifications/claude/channel`, metadata attributes, and a reply tool. Its own warning is decisive for acknowledgment design: `mcp.notification()` resolving means a transport write, **not** Claude’s receipt; events can be silently dropped if the server is not loaded as a channel or policy blocks it. A receiver-origin reply tool is needed for delivery confirmation. Busy events queue and may be handled together on the next turn. [Channels reference](https://code.claude.com/docs/en/channels-reference).

This family could use a local HTTP listener, a file reader, or an external service such as Telegram or Discord as the incoming transport. The official fakechat source implements a localhost UI, channel notification, and reply tool; its README says it has no history or search and is a development example. It is evidence that the channel contract can be implemented, not proof it works in a Desktop-hosted Code task. Channel activation is documented through CLI flags and a plugin allowlist or development override; the platform comparison labels Channels as CLI. Establishing Desktop-hosted support would require a separate current contract or live proof. [Channel setup and limits](https://code.claude.com/docs/en/channels), [fakechat source](https://github.com/anthropics/claude-plugins-official/blob/main/external_plugins/fakechat/server.ts), [fakechat README](https://github.com/anthropics/claude-plugins-official/blob/main/external_plugins/fakechat/README.md), [platform comparison](https://code.claude.com/docs/en/remote-control).

A normal MCP server is a **reader on demand**, not a push channel. A GitHub issue, Slack message, repository file, or standalone notification can hold a reviewable link and correlation ID, but it does not itself enter the exact existing Code session. A polling or event receiver has to be attached to that session, and receipt must still be evidenced there. The `FileChanged` hook observes external file edits and runs a hook; its `systemMessage` is described as a terminal notification rather than SDK message-stream content. `UserPromptSubmit` can add context when a user sends a prompt, but cannot wake an idle session from a broker event. A hook or ordinary MCP reader alone therefore does not meet this notification contract. [MCP/channel comparison](https://code.claude.com/docs/en/channels), [FileChanged hook](https://code.claude.com/docs/en/hooks), [UserPromptSubmit hook](https://code.claude.com/docs/en/hooks).

### 5. SDK or CLI resume of the receiver

The Agent SDK documents `resume` for a saved Claude Code session ID and full conversation context. That is attractive for automation but changes the execution surface to an SDK-managed invocation. The Desktop reference says its interactive Code tab lacks `--print`/Agent SDK scripting equivalents and that the CLI and Desktop keep separate session lists. On Linux, the documented `claude --desktop --resume` bridge is unavailable; it is limited to macOS and x64 Windows. Resuming or duplicating the receiver this way risks a different account route, active model, permission interpretation, worktree, or cwd, and conflicts with the requirement to notify the **existing Desktop-hosted task**. I would exclude it from the first live proof unless the operator changes that requirement. [SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions), [Desktop and CLI boundary](https://code.claude.com/docs/en/desktop).

## Receipt and state evidence needed for qualification

For any route, the minimal payload is a short informational statement, a reviewable context link, and a unique correlation ID. The requested receiver response should say only that the same ID was **received**. It must not imply agreement, work acceptance, permission, or a change of priority. A sender-side “sent,” HTTP 200, CLI exit code, socket write, or channel transport resolution stays in a **submitted** state until receiver-origin evidence names the ID. Held and refused are separate terminal observations, with no automatic resend. If submission has an ambiguous outcome, reconcile it against receiver evidence before deciding whether a fresh submission is justified. These are proposed application rules from the supplied charter, not features proved to be enforced by Claude Code.

The public hooks expose useful partial observations: common hook input includes session ID, cwd, and permission mode; `SessionStart` can include the active model but may omit it; model-switch hooks can observe a change. `/status` identifies settings sources loaded, while Anthropic explicitly says that view does **not** identify which file supplied each key. Settings may reload during a running session. None of these alone proves the effective account route, all applied rules and grants, pending changes, or current worktree/cwd at the moment of receipt. The first proof needs a receiver-origin observation of those facts or must leave each missing item as a qualification gap. Do not replace live observation with persisted session metadata. [Hook schemas](https://code.claude.com/docs/en/hooks), [settings loading and status limits](https://code.claude.com/docs/en/settings), [Desktop mode and model controls](https://code.claude.com/docs/en/desktop).

The first live matrix should use an **idle disposable peer** and a **busy disposable peer** created for this purpose. For each, check target binding immediately before send; submit one correlated payload; distinguish delivered, held, refused, and unknown; obtain receiver-origin receipt; and compare receiver state before and after. Add synthetic duplicate names, a stale socket or exited peer, a send failure after an ambiguous client result, a receiver hold/refusal, and a busy receiver that preserves or loses task context. The Desktop and general messaging references disagree enough about busy timing that continuity is diagnostic, not an assumed guarantee. A new app or engine build starts **unassessed**, so the same checks should graduate from read-only discovery to disposable proof rather than being called incompatible from its version string alone.

## Ranked next checks

1. **Confirm native peer availability on a disposable Desktop Code session.** Record Desktop and embedded Claude Code versions, the session’s own peer address/status, actual account route, model, permission state, and cwd/worktree through receiver-controlled observation. If there is no inbox, record the reported reason rather than trying another target.
2. **Test a constrained CLI-to-Desktop peer send.** Use a purpose-created sender and receiver, live `ListAgents` resolution, a single informational payload, and a correlated receiver reply or equivalent receiver-origin evidence. Test idle, then busy. Do not count `SendMessage` success as receipt.
3. **If a direct local adapter is still attractive, obtain its supported message-frame and response contract or test it solely on disposable peers.** Specifically determine whether an independent same-user process can address the intended Desktop socket, how inbound controls classify it, how held/refused outcomes appear, and whether a receiver acknowledgment can return without touching the target’s runtime settings.
4. **Assess an exact-session UI route** if the harness has an authorized interactive control surface. Verify that it selects the intended task and observes the message and acknowledgment without altering the target’s model, permissions, cwd, or worktree.
5. **Reconsider a channel only with evidence of Desktop-hosted activation.** Otherwise it is a CLI-session solution and brings a plugin, runtime dependency, listener, and sender gate beyond the simplest increment.

Any decision to install a plugin, accept an experimental channel, change inbound permission policy, expose a listener, inspect private transcripts, or alter receiver hooks is a separate operator choice. This survey proposes no security acceptance or permission/containment redesign.
