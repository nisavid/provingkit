# Native and offline route audit: first-round finding

**The native sender is the simplest credible actuation path, but no retained evidence qualifies an end-to-end notification route.** A separate `claude mcp serve` process exposed `ListAgents` and `SendMessage`, and a read-only discovery call succeeded. The remaining gap is receiver-side proof: the listing is not a typed binding to the consented Desktop task, the selected external send has no demonstrated receiver record, and no automated read-only path supplies all effective account, model, permission, and cwd observations. The offline reader and observer work makes those gaps more precise. It does not close them. [Pinned sender report](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md), [receiver-evidence report](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-28-claude-desktop-receiver-evidence.md), [observation-path report](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md).

I would retain native discovery and `SendMessage` as the proposed sender, then make the next comparison narrowly about observation. A selected-file reader is substantially smaller than a modified Desktop build and might establish a positive receiver record and explicit correlated ACK after fixture qualification. It cannot, on the present evidence, establish all required effective state. The app-side observer is a concrete way to reach more state, but even its current built candidate reports several fields as cached, last observed, or incomplete. Treating that candidate as the architecture already chosen would outrun the evidence. A change to the preservation claim, operator-assisted evidence, or receiver surface requires an explicit operator choice. [Observation-path assessment](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md#requirement-to-observation-assessment), [observer design](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/specs/2026-09-29-desktop-runtime-observer-design.md#field-producers-and-remaining-gaps).

## How the route reached the present candidate

The first retained investigation established the sender without sending a notification. Anthropic documents `claude mcp serve` as an external MCP entry point. Local probes of Code binaries 2.1.280 and 2.1.283 found callable `ListAgents` and `SendMessage` schemas; only `ListAgents({})` was invoked. It returned a formatted listing with short references, states, and local/Desktop labels, rather than a typed task identity. `SendMessage` accepts `to` and plain-text `message`, with optional `summary` and `notify_when_idle`; it has no correlation-ID field. Putting the ID in the text is therefore an application convention to qualify, not native acknowledgment support. No sender success, recipient read, or receiver ACK was observed. [Sender report](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md). Anthropic’s [cross-session messaging documentation](https://code.claude.com/docs/en/cross-session-messaging) distinguishes delivered, held, and refused admission, and says a busy Code receiver reads between tool calls while an idle one begins a turn.

The receiver investigation then inspected Desktop source rather than using a historical task. At Desktop 2.7032.0, the session serializer and manager showed a Desktop task ID, Code session ID, transcript lineage, stored model and permission inputs, and worktree fields. Its host-side `sendPeerMessage` path stored sender receipts and receiver inbound state, but the investigation could not connect an **external native** `SendMessage` to that host producer. Nor could pair-level `repliedAt` prove an explicit ACK with the application correlation ID. A synthetic HTML reader tested candidate parsing, identity changes, partial JSONL rows, echoes, quotes, and absence; every result remained `unqualified`. [Receiver findings](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-28-claude-desktop-receiver-evidence.md#installed-source-findings), [reader prototype](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/claude-receiver-reader.md).

The refreshed 2.9939.4 source survey made file acquisition concrete. The manager writes selected metadata beneath its user-data root and maps the Desktop task to `cliSessionId`; the Code transcript resolver finds JSONL candidates for that ID. A standalone process could read an explicitly selected metadata file and uniquely bound transcript file without importing Desktop modules. That process would miss Desktop’s in-memory message buffer and cannot turn file silence into negative delivery evidence. Writes are debounced; transcript selection can be ambiguous; reads, compaction, retention, and truncation affect coverage. The refreshed survey also traced separate runtime state: spawn account identity, confirmed or queried model, permission rules and host grants, and `harnessCwd`. Stored metadata alone is insufficient for the accepted before/after claim. [Acquisition paths](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md#acquisition-paths), [effective-state analysis](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md#effective-receiver-state).

That gap drove the runtime-observer design. The manager owns the existing Code `query`; proposed app-side code would select one task, call bounded read controls on that exact query, project a small envelope, and export it for a standalone reader. A fake-query prototype demonstrated binding checks, getter deadlines, partial fields, and file reading. Its integration plan identified source insertion sites but expressly did **not** patch or load Desktop at that stage. [Observer design](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/specs/2026-09-29-desktop-runtime-observer-design.md), [synthetic prototype](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-runtime-observer/README.md), [initial integration plan](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-runtime-observer/integration-plan.md).

The later `desktop-observer-probe` is more than that initial plan: it contains an exact manager replacement set, adapter, observer, strict reader, Linux process helper, offline ASAR builder, verifier, retained build receipt, and a proposed installation and restoration procedure. The retained packaging report says an offline candidate passed complete comparison of 365 members: one changed manager, one added sidecar, and 363 unchanged originals. Both generated JavaScript members passed syntax checks. The receipt names candidate SHA-256 `08035aee33b3fe1a8eacee63c6fd9b527f79b3ca9c65a96a23057a41fd0a2a07` and explicitly sets `runtimeExecuted: false`. I verified in this round that all eight current build-input file digests match the retained receipt and that the permitted offline manager extract matches the patch’s expected manager SHA-256. I did **not** inspect the staged candidate archive or reproduce its build or tests. [Probe README](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/README.md), [packaging record](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/packaging-evidence.md), [build receipt](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/candidate-build.json).

A practical circularity appeared in the proposed live procedure: its observer configuration requires the task and Code IDs before candidate launch, while normal creation and a Code query may establish those IDs only through Desktop. The current procedure proposes creating the disposable task before staging, then two setup prompts across candidate and restored cycles. The later fixture-identity design instead proposes a disabled-by-default acquisition mode in the candidate launch: observe one normal new-local-task registration, witness the qualifying metadata writer, validate the exact selected file, and admit one frozen existing query for observer continuation. That design would reduce the proposed operation to a candidate launch and a restored launch with one setup prompt. It is **source design awaiting adoption and implementation**. The current candidate has no `fixture-acquisition.mjs`, and its README says the acquisition route is not implemented. [Current fixture procedure](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/probe-procedure.md#disposable-fixture), [acquisition proposal](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-30-fixture-identity-acquisition-design.md), [current-candidate limit](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/README.md#start-here).

## Simpler read-only paths worth separating

The public Desktop surface is useful for a human or a Desktop-hosted Code task: it can list, read, and message **other Desktop-run** Code sessions, and it holds a busy session’s message until that work finishes. The documentation describes this as Claude working inside Desktop, not an externally callable read-only endpoint for ChatGPT. Its host messaging receipts must not be reused as proof of the distinct external native `SendMessage` route. [Desktop session documentation](https://code.claude.com/docs/en/desktop#work-across-sessions), [producer distinction](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-29-desktop-observation-paths.md#delivery-and-acknowledgment).

The documented SDK `listSessions`, `getSessionInfo`, and `getSessionMessages` deserve a narrow check against a **purpose-created disposable** Desktop task before assuming an app patch is necessary for positive transcript inspection. The retained report says the published metadata fields omit effective account, model, and permission mode; it found no documented live freshness guarantee or exact Desktop-task binding. The documented `/export` and `transcript_path` hook inputs offer narrower transcript access, but `/export` is an interactive rendered export, and a hook would need to be in the receiver’s lifecycle. Neither presently proves an external, fresh, complete, selected-task observation of the required effective state. [SDK assessment](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-28-claude-desktop-receiver-evidence.md#documented-surfaces), [Anthropic session interfaces](https://code.claude.com/docs/en/sessions#access-conversations-from-scripts).

The native inbox socket is another sender candidate, but the initial investigation found the public description insufficient for a complete frame and response implementation; the observed MCP tool is the smaller supported sender route. `notify_when_idle` reports an idle transition and can omit status under inbound controls; it is not a correlation ACK. `/proc` can add process evidence once a selected PID is bound, but cannot reveal active model or complete applied permission rules. Thus these are useful substitutes for **individual observations**, not demonstrated substitutes for the whole accepted claim. [Sender comparison](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md), [idle notices](https://code.claude.com/docs/en/cross-session-messaging#get-a-notice-when-another-session-goes-idle), [process-binding limit](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/process-binding-evidence.md#required-probe-disposition).

The meaningful missed opportunity is a **separate, explicit comparison of the narrowest receiver read** against the full preservation requirement before allowing packaging work to imply a settled architecture. The retained reports did name operator-assisted observation, holding for a documented endpoint, and changing the receiver; the later source survey also compared selected files, host `get_session`, renderer `LocalSessions`, and existing query controls. Those alternatives were not ignored. They were not shown to satisfy the unchanged contract either. A smaller reader might resolve positive delivery and ACK evidence while leaving effective-state gaps; a complete app observer could still require new producers. That is an inference from the observed field limits, not a claim that the reader works live. [Earlier alternatives](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/research/2026-09-28-claude-desktop-receiver-evidence.md#decision-and-maintenance-tradeoffs), [surveyed paths](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/specs/2026-09-29-desktop-runtime-observer-design.md#existing-access-paths).

## Live status and next decision

The retained preparation expressly reports **no candidate installation or launch, private receiver read, task creation, setup prompt, cleanup, or notification**. Its offline archive comparison and synthetic tests support review of a candidate, not application loading. The receipt design has not been adopted or built. No first idle or busy disposable peer has supplied receiver-origin delivery, correlated ACK, held/refused evidence, current effective-state preservation, or busy continuity diagnostics. [Preparation status](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/README.md#review-boundary), [packaging status](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/packaging-evidence.md#builder-and-current-candidate), [acquisition adoption status](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/README.md#start-here).

The restoration proposal is concrete but unexecuted: protect the pristine archive, stage the reviewed candidate, exchange only after identity checks, verify the candidate launch and selected process, stop and establish quiescence, exchange back only if package and archive identities still match, launch the original without the observer binding, then assess application and disposable-task behavior separately. Package cleanup is conditional on verified restoration. A restored hash alone is not evidence that session context survived. [Operation plan](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/application-operation.md#atomic-candidate-exchange), [restoration procedure](https://github.com/nisavid/provingkit/blob/c1d77f8dd6a5dab58f6dfd96275dff0ea6015ae0/docs/superpowers/prototypes/desktop-observer-probe/probe-procedure.md#restoration-retention-and-return).

My first-round recommendation is to preserve the current qualification contract and ask one operator-level architecture question before making the fixture-receipt design the default: **must the first automated route prove the full effective-state preservation claim, or may selected observations become explicitly operator-assisted or narrower?** If the full automated claim stays fixed, the present sidecar is a partial experiment and needs identified producers for fresh account route, model, mode, complete rules/grants/pending changes, and current cwd. If the claim changes, specify exactly which observations change and retain receiver-origin delivery, a separate correlated ACK, exact-peer consent, unknown-send reconciliation, and held/refused distinctions as independent requirements. Neither choice authorizes a live probe or send.
