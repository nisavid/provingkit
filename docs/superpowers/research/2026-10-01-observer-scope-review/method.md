# Comparing observation routes before implementation

Use this packet when choosing the first Desktop notification route and before
revising the observer preparation. It records the comparison method and the
facts its consumer must preserve. The next decision loads this method, the
synthesis, and the relevant lane follow-ups, records their published revision,
and carries unresolved facts into native prerequisites before releasing work.

## Question and fixed requirements

Find the smallest credible route for ChatGPT in Codex mode to notify an exact,
existing, purpose-consented Claude Desktop Code task on the same Linux machine.
Keep receiver-origin delivery evidence, explicit correlated acknowledgment,
unknown-send reconciliation, distinct held/refused states, and before/after
actual account/model/applied-permissions/worktree observations. Applied
permissions include mode, rules, grants, and pending changes. Busy continuity
is diagnostic. Initial qualification uses disposable idle/busy receivers and
synthetic failures. New builds receive graduated compatibility assessment.

A changed receiver, operator-assisted evidence, a reduced observation claim,
or a different operation is a contract-changing option. No research result
silently adopts one. Research permits public documentation and named offline
source reads; no live app action, private receiver read, installation, fixture,
prompt, send, or debugger attachment is part of this comparison.

## Independent first rounds

Three fresh native child contexts received the same neutral contract and their
lane-specific assignment. None inherited the coordinator conversation. Each had
a separate input and artifact directory. They returned Markdown; the coordinator
captured it before exchanging any peer findings. The work used `research`,
`choosing-agent-models`, and `delegating-cross-agent-work`.

## Cross-examination and follow-up

Each lane received the frozen reports, their input inventories, and the history
trace. It independently criticized the others, corrected its own assumptions,
and produced a cross-informed follow-up:

- [Conceptual follow-up](conceptual-followup.md) separates five obligations,
  evaluates competing preservation hypotheses, and raises qualification of
  modified versus restored Desktop.
- [Survey follow-up](survey-followup.md) expands the initial vendor-focused
  search into five pinned third-party mechanisms and corrects the extra
  model-driven sender recommendation.
- [Native follow-up](native-followup.md) compares hook and session-reader
  candidates by field, corrects stale receipt-adoption status, and separates
  read-scope choices from technical capability.

A [targeted native source delta](native-source-delta.md) then checked four named
extracted members for actual caller, field, and bridge behavior. Its coordinator
correction distinguishes the Desktop metadata filename from Code transcript
binding. This additional pass addressed a concrete remaining source question;
round count was not the completion criterion.

The first survey follow-up failed at the native worker boundary without a
research result. That failure was retained as unusable, and the same bounded
request was frozen again for recovery. It is not counted as an evidence round.
The successful follow-ups correct held-state semantics, remove extra proposed
acceptance obligations, and preserve graduated compatibility rather than
requiring a live test for every build.

First-round independence is limited to the enforced workflow and recorded
worker exposure; the native tool supplies no portable model-execution or
per-spawn authority attestation. All requested workers used GPT-6 Sol xhigh for
ordinary comparative research. The coordinator reviewed their outputs. None
performed security acceptance, and this packet does not replace that review
for any later selected integration.

## Verification and limits

The coordinator rechecked all eight candidate build-input digests and ten unique
manager patch anchors; they match the retained source identity. Eleven pinned
third-party source files were fetched independently to corroborate the survey's
key mechanisms. Source checks establish source facts, not successful adoption
or live compatibility. Current public documentation is date-bound where it
provides no immutable revision.

The search covers native messaging, selected files and SDK readers, host/renderer
interfaces, hooks, UI/accessibility, Remote Control bridges, terminal managers,
channel buses, and custom relays. It is not exhaustive. The first external round
was vendor-heavy; the follow-up explicitly addressed that coverage defect.
Complete live receiver-state observations and the selected external sender's
actual receiver records remain unqualified.

Use `capturing-agent-procedures` when the route decision revises its downstream
procedure. This packet captures the research method for that consumer. It does
not add a new installed skill or change shared equipment; broader promotion of
the method would need its own source-ownership and usefulness decision.
