# Conceptual cross-examination: keep the native sender, split the evidence problem

## Revised finding

The frozen reports narrow the transport choice substantially. The native audit reports an observed `claude mcp serve` surface with `ListAgents` and `SendMessage`, plus a successful read-only `ListAgents` call. That direct MCP sender avoids the second model invocation and target-selection step proposed in the external survey’s `claude -p` route. It remains a **candidate sender**, not a qualified notification path: no external send, receiver delivery, or correlated acknowledgment was observed. The current design decision is therefore which evidence sources can qualify that sender with the least additional machinery.

The accepted requirements should be decomposed into five dependencies: fresh exact-peer binding and consent; native submission and admission state; receiver-origin delivery and correlated acknowledgment; before/after observation of the named effective-state fields; and disposable-fixture acquisition for whatever observer is selected. A single modified Desktop build need not own all five. Conversely, a source-built observer is not justified merely because it can expose some of them.

## Corrections to the first round

My first report treated native task messaging as an unverified possibility. The native lane found a concrete direct MCP surface and read-only discovery, so that uncertainty is now narrower. I also proposed an unforgeable receipt against a malicious same-user sender, receiver-side link dereferencing, and a live smoke test for each new build. Those are possible design or assurance choices, **not accepted qualification obligations**. The accepted link must be reviewable; whether the receiver must open it is a separate decision. A new build is unassessed, with graduated source and behavioral checks according to what changed.

The survey’s CLI sender is useful evidence that Anthropic’s peer tools can be invoked from a Code session, but it adds another session and model-mediated selection when direct MCP is already available. Its direct-socket alternative might eventually reduce a dependency, yet the surveyed public contract lacks a complete independent-peer frame and response protocol. Replacing the observed MCP route with a socket adapter now would trade a known control surface for protocol research without reducing the receiver-evidence burden. The survey also calls held and refused “terminal observations.” Refused is a drop; held may later be released. Both require distinct records and no automatic resend, but a hold is not necessarily terminal.

The native report correctly separates host-side Desktop peer-message receipts from the external native `SendMessage` path. The source producer must not be credited to the latter without a traced connection or disposable proof. Its selected-file reader may be the smallest way to establish a **positive** receiver event, but the external send’s persisted row shape and timing remain unknown. File silence cannot prove non-delivery. A reply row is not an explicit acknowledgment unless it identifies the correlation ID and is bound to the same receiver. The native report’s question about relaxing the preservation claim is premature as a next step: first compare a composite of existing observations against every accepted field, then identify the exact residual gap. Any reduction still needs operator choice.

The coordinator’s history trace corrects one adoption point: the fixture receipt direction and 15-minute acquisition-admission ceiling were accepted in [Decide whether to incorporate the fixture-identity receipt](https://github.com/nisavid/provingkit/issues/353#issuecomment-5925012453), while implementation is held for this scope review. The receipt is still design, not code in the current candidate. The proposed installed-archive exchange occurs while Desktop is stopped and requires candidate and restored launches. It is not a hot patch of a running process. The 15 minutes limits acquisition admission, not total interruption or restoration time.

## Three preservation hypotheses

**Before/after observations can satisfy the accepted claim** if each observation is freshly tied to the same running receiver task and reports the *applied* account route, active model, permission mode, rules, grants, pending changes, worktree, and cwd at its respective observation point. This is an endpoint claim. It does not require proving that no field changed and changed back between observations. Its weak point is provenance: a stored launch choice, cached `accountInfo()`, last observed model, manager mode, or metadata cwd may not describe the effective state when sampled. The current observer candidate expressly has several such partial fields. A composite of first-party controls, selected live process evidence, and a narrow receiver read may be enough, but no report establishes complete coverage.

**Structural noninterference can reduce observation machinery** if supported source shows that native `SendMessage` admits text through the receiver’s existing inbox without resuming, replacing, or reconfiguring its query, model, permissions, account route, or directory. That would explain why the transport should preserve them. It cannot alone establish the accepted before/after actual-state claim: the task may change through another cause, and source describing a send path does not reveal the live values. Paired with credible endpoint observations, structural evidence may avoid a comprehensive continuous observer. The next source audit should trace the precise external MCP send path, not infer it from Desktop’s separate host-side peer-message path.

**A complete app-side observer could satisfy the field claim** if it binds to the exact existing query and produces fresh, applied values for every field before and after the send, while its reads do not change that query. The built sidecar is not yet that observer: the native report identifies cached or historical route information, uncertain active-model meaning, incomplete permission stores and pending changes, and no fresh mode or cwd getter. The offline package comparison proves what bytes were staged, not that the observer loaded or that its values describe effective state.

These hypotheses are alternatives for *how to prove the same claim*, not permission to drop fields. A field-by-field matrix should name the producer, freshness, exact-task binding, applied-versus-saved semantics, and what remains unknown. This can show whether only one or two fields require an app adapter.

## Instrumented proof and production validity

The proposed probe changes one manager archive member and adds a sidecar, then restarts Desktop with the user’s existing profile. Even if a disposable task under that candidate yields all desired observations, the observed runtime is **instrumented Desktop**. A later unmodified production run would lack those observations, and the inserted hooks could affect ordering, task registration, or query lifecycle. The offline check that 363 other ASAR members are unchanged constrains the package delta; it does not establish equivalent behavior.

A qualification plan must state which implementation it qualifies. If the instrumented build is itself the intended operating route, its package and update lifecycle become part of that route. If it is only a measuring device for the original build, the case for transfer needs source-level noninterference, matched task behavior under candidate and restored launches, and whatever independent endpoint evidence the original can expose. A restored archive hash proves restoration of bytes, not task-context survival or effective-state equivalence. This transfer question should be answered before fixture-receipt implementation is treated as the shortest route.

## Smallest next facts and decision order

1. **Trace external MCP `SendMessage` to receiver evidence.** Determine whether the exact external path writes a task-bound transcript or host event, how delivered, held, and refused are represented, and where a correlated reply can be read. This distinguishes a selected-file or documented session reader from a mandatory app adapter. Use source and public contracts now; reserve actual row confirmation for disposable peers.
2. **Map unmodified-state observations per field.** Recheck the documented SDK session reads, receiver lifecycle hooks, Desktop host `get_session`, renderer views, query controls, and process evidence against the accepted before/after fields. The survey should look especially for an existing task-bound way to obtain current account route, active model, complete applied permissions, and cwd. “Not found in the first survey” is not “absent.”
3. **Resolve exact-peer binding from live discovery to Desktop identity.** `ListAgents` returns short references and labels, not a typed Desktop task ID. Identify a supported mapping and freshness check before designing a receipt around a particular internal ID. Purpose-scoped consent remains independent of discoverability.
4. **Build only the residual observer, if one is needed.** If a bound receiver transcript supplies delivery and ACK while existing controls supply most state, add the smallest producer for the missing fields. If those producers are unavailable, the current sidecar still needs completeness work before an instrumented launch can qualify the full claim.
5. **Then plan the disposable idle and busy proof.** Exercise positive receipt, explicit correlated ACK, held and refused outcomes, ambiguous submission reconciliation, before/after state, and busy continuity as a diagnostic. No historical task or sender success result substitutes for that proof.

The survey should keep an exact-session UI route and a documented receiver-side session read in view as narrow alternatives. It should check whether either can expose the missing observation without a package exchange, while preserving the distinction between Desktop-hosted tasks and CLI or SDK-managed sessions. Channels and a new broker remain lower-ranked: current survey evidence describes CLI activation, and they add a receiver dependency without solving applied-state observation.

## Unresolved findings and exposure

No reviewed source yet connects the selected external send to a receiver-origin record and explicit correlated acknowledgment. No reviewed combination supplies all required effective-state fields. The exact task-binding method and the current candidate’s effect on unmodified production validity remain open. These are qualification gaps, not findings that native messaging or an unmodified reader is incompatible.

The likely least-invasive route would still expose a selected task identifier, peer reference, short text, context link, correlation ID, consent record, and receiver event. Selected transcript or SDK reads would expose private task content unless narrowed to the disposable fixture and relevant rows. The sidecar proposal additionally projects account identifiers, rule and directory values, grants, pending markers, and process information, and its archive exchange interrupts Desktop across two launches. This inventory informs later route and security review; it is not security acceptance.
