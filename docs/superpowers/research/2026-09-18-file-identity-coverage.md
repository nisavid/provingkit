# File-identity coverage and the next design increment

The existing file-identity contract is broader than URL normalization. A useful next increment must preserve the production composition of path-specific exemptions, original file bytes, format extraction, normalization, identity detection, and repository checks before moving any tests to a smaller interface.

This note inventories the authored tests and production source at `ad31344cdcb9891438cf1e92c27c776945bee6ab` for [Map file identity cases to production acceptance coverage](https://github.com/nisavid/provingkit/issues/125). It establishes coverage obligations and a bounded next design step. It does not establish runtime success, behavior equivalence, adversarial qualification, allowlist parity, or a final interface.

## Scope and evidence

The research increment owns this note and [the machine-readable case inventory](2026-09-18-file-identity-cases.json). The inventory includes all 94 `test_` methods in `tests/test_validate_provingkit.py`, with every assertion's source lines and every parameterized method's labels. It marks 41 methods as the file-identity surface: the allowlist-entry assertion at [lines 1467–1489](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/tests/test_validate_provingkit.py#L1467-L1489) and every identity test from [lines 1711–2681](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/tests/test_validate_provingkit.py#L1711-L2681). Other methods remain visible as composition context or other repository contracts; they are not silently counted as file-identity fixtures. In particular, Git history identity and plugin content identity are distinct contracts.

All links into the inspected source use the pinned commit. Source code, tests, workflow configuration, the root glossary, and both existing ADRs were read. The ADRs concern response outcome storage and Git operation profiles; neither settles this file-identity seam. No test module was imported, validator was invoked, fixture was executed, suite was run, or dependency was installed for this inventory. AST parsing and source reads establish what is written, not what passes.

## Production composition observed in source

1. **CLI and accepted candidate.** `main` checks argument count and repository existence, then validates definition, excluded source, marketplace, cutover provenance, historical qualification discovery, historical identities, release prohibition/schema, and Git history, in that order. A `ValidationError` prints its message to stderr and returns 1; success prints the one success line and returns 0. Earlier errors prevent later checks from running. The source-stage claim covers the whole sequence; file-identity acceptance alone cannot establish it. [CLI composition](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L2405-L2430)
2. **Repository discovery and symlinks.** Historical-identity validation loads and checks the allowlist first, materializes a sorted `repository.rglob("*")`, skips paths with `.git` or `__pycache__` components, rejects a symlink before testing regular-file status, skips non-files and the allowlist file, and reads original bytes. Discovery/read `OSError` becomes `repository identity scan failed`. This is filesystem discovery, not Git's tracked-file list. The source does not require a matching suffix before reading a file. [allowlist, traversal, and reads](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L1609-L1674)
3. **Path context before format.** `_identity_scan_content` recognizes exact repository-relative paths. `CONTEXT.md` must contain one exact Base Loadout guidance block; only the legacy slug within that block is removed for scanning. Two disposition documents have strict JSON/field/reference rules; only the designated tracker references are removed. Other paths keep their bytes. This transformation does not replace the original bytes retained for hashing. [path-scoped exemptions](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L335-L446)
4. **Format selection.** `_normalize_identity_scan_file` always keeps its input bytes as a scan source. A case-insensitive `.yaml` or `.yml` suffix adds YAML scalar sources for the whole file. Otherwise, an initial frontmatter block adds its YAML scalar sources, allowing an initial UTF-8 BOM and LF or CRLF delimiters. Only the metadata block is parsed as YAML in the frontmatter branch; the body remains in the raw source. [frontmatter pattern](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L68-L72), [file composition](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L824-L832)
5. **YAML source extraction.** `yaml.compose_all(..., Loader=yaml.SafeLoader)` supplies nodes, not constructed application objects. The walk tracks visited node identities, visits mapping keys and values and sequence children, includes each scalar's UTF-8 bytes, and additionally decodes binary-tag bytes. This retains overwritten mapping nodes. Missing PyYAML and caught Unicode/YAML/recursion/value failures produce path-bearing `ValidationError`s. [YAML extraction](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L735-L767)
6. **JSON and byte decoding.** JSON string extraction is attempted while collecting canonical URL paths for each content source, irrespective of filename suffix. It ignores numeric construction, visits dictionary keys/values and list members, splits strings at lone surrogate code points, and returns no extracted strings for the listed parse/Unicode/recursion/value failures. Raw bytes still remain available to the surrounding scan. General normalization applies repeated percent decoding, ASCII JSON escapes, escaped solidus replacement, and HTML unescaping, with the eight-pass limit and a further-change check, then lowercases combined content and canonical paths. [JSON extraction](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L704-L732), [decoding operations](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L449-L473), [source expansion and normalization](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L770-L821)
7. **URL interpretation.** Candidate scanning, hard-delimiter handling, literal syntax/control processing, userinfo/port handling, UTS 46 host encoding, and path decoding/dot-segment processing are separate functions on the production call path. Host parsing precedes repeated path percent decoding. The inventory records the tests' accepted and rejected examples without treating them as independent proof of URL-standard or adversarial equivalence. [URL implementation](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L476-L701)
8. **Detection, allowlist membership, and original-byte hashes.** Any of four literal identity tokens in the normalized result records the original file bytes. Unexpected paths produce a sorted, path-bearing error. The observed path set must then equal the allowed path set, and each recorded SHA-256 must match the original bytes. The allowlist is itself a strict, ordered, 31-entry exact-path/whole-file-digest contract with validated entry shape, path form, and digest syntax. Parsing or canonicalizing file contents before hashing would change this contract. [identity tokens](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L57-L65), [allowlist shape](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L1610-L1653), [detection and exact-byte checks](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L1675-L1692)

The test helper launches the validator script from the test checkout while passing a separate fixture repository. Its clone helper uses a shared local clone, explicitly restores three retained remote refs, and overlays current contract files and selected plugin content. This is a deliberate composed fixture, not an untouched historical checkout. Accepted fixtures traverse all CLI checks; many copied-repository rejection tests omit `.git` and establish only that the expected earlier diagnostic is reached. [validator and clone helpers](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/tests/test_validate_provingkit.py#L25-L75), [overlay](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/tests/test_validate_provingkit.py#L113-L165), [fixture execution and assertions](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/tests/test_validate_provingkit.py#L167-L192)

The checked-in workflow specifies Python 3.13 and pins idna, jsonschema, and PyYAML, then runs the repository contract unittest module and the actual source-stage CLI. Those are configured production-path checks, not checks executed for this research. [workflow route](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/.github/workflows/provingkit-source.yml#L19-L49)

## Coverage obligations and unresolved questions

The source observations above establish obligations for any proposed change. They do not establish that every obligation currently has a dedicated test. The existing suite gives concrete coverage for content variants, BOM/hash composition, exact guidance/tracker exemptions, a regular-file symlink, and full accepted candidates. I did not find dedicated tests in this file for the following production branches: discovery/read `OSError`; missing idna or PyYAML at the identity call site; the allowlist validator's full shape/path/sort/duplicate matrix; a directory or dangling symlink; direct discovery inclusion/exclusion controls; and each CLI usage/non-directory/error-precedence case. Their branches are visible in [idna loading](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L651-L660), [YAML failures](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L735-L767), [repository scanning](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L1609-L1692), and [CLI handling](https://github.com/nisavid/provingkit/blob/ad31344cdcb9891438cf1e92c27c776945bee6ab/scripts/validate_provingkit.py#L2405-L2426). This is an in-file coverage observation, not a repository-wide absence claim or a request to add all those cases now.

Production-path obligations that still need CLI or repository integration include:

- Discovery, relative-path calculation, excluded directory components, symlink handling, original-byte reads, and scan-read failures.
- Allowlist shape, exact membership, original-byte digest comparison, and interaction with path-scoped exemptions.
- Diagnostic placement and formatting, subprocess exit behavior, dependency availability, and validation ordering.
- An accepted real candidate composed with definition, provenance, release checks, and attested history.

Cases that might later cross a production-used file-identity seam directly are the 117 helper fixtures, including their accepted counterexamples and format/path context. The four guidance/tracker methods and the excessive-encoding negative probe also contain file-local behavior, but their repository placement and pristine acceptance remain separate obligations. The BOM/hash method and symlink method are repository integration cases. The existing JSON and timeout probes already target private helpers; their present behavior does not demonstrate a deep public test surface.

The design questions remain open:

1. Does the intended seam own the complete path-specific transformation plus format extraction, normalization, and token decision? Stopping at a URL parser omits the observed production behavior. Adding a pass-through only for tests may move complexity instead of concentrating it.
2. Which outputs must callers rely on: the identity decision, diagnostic context, and/or another minimal result? Whether original bytes remain solely with the repository caller must be explicit before moving digest-related evidence. No return type or final interface is selected here.
3. Which error text and ordering are part of the supported contract? Current assertions range from exact stripped stderr to substrings and acceptance-only return codes. A rewrite cannot infer that all diagnostics are interchangeable.
4. Which representative cases must remain through the CLI after a future test move? Selection must cover accepted composition and every retained repository obligation, not merely one reject/one accept example.
5. What evidence will demonstrate that the production caller actually crosses the proposed seam, and that the supported cases retain their results? A test-only parser or a mock of the production composition is insufficient. Full parity, especially for URL counterexamples and allowlist behavior, needs a separately routed qualification decision.

No adversarial or allowlist-parity claim is made in this research. Security qualification is outside this inventory's scope. Preserve those unresolved questions for the appropriate route; neither this inventory nor passing future ordinary examples would settle them.

## Smallest useful next increment

Prepare one bounded design/prototype increment for the **per-file identity decision actually used by `_validate_historical_identities`**, while keeping repository discovery, allowlist validation, exact-byte hashing, and CLI sequencing at their observed call sites. Use this inventory as its acceptance map. First decide whether concentrating the existing per-file composition would add depth and locality; do not introduce a wrapper solely to obtain an attractive test entrypoint.

The prototype should establish production caller reachability and exercise a small set of existing ordinary examples through the proposed seam: plain content, YAML metadata, frontmatter with original bytes retained, one exact path-context case, a reported parse error, and an accepted counterexample. Retain all existing tests during that experiment. Measure the cost of those repeated file fixtures separately from complete CLI/repository work. Any later test migration requires an explicit, reviewed mapping of every moved case and every retained integration obligation. The prototype's claim must remain narrower than complete equivalence until the required qualification route exists.

This is the next design and measurement decision, not authorization to ship a refactor or remove coverage. The current research stops with the static inventory and the supported next increment; implementation, runtime validation, qualified equivalence, and test migration remain future work.
