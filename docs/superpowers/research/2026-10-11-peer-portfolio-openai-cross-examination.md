# OpenAI control surfaces: cross-examination addendum

The OpenAI inventory remains a set of unqualified candidates. I confirmed its distinction between stored continuation and active-owner attachment, and found three details that must accompany it: queue changes can be discovered through a shared database watcher; the Codex plugin resumes selected associated tasks rather than an arbitrary supplied ID; and AI Functions accepts an explicit stored ID but sends notifications as user input through its own server.

I verified and read the frozen OpenAI, Claude, and shared-fabric FIRST reports against the supplied manifest. I compared their claims without changing those reports. Primary sources below were read on 2026-10-11. I verified that Codex `rust-v0.162.1` resolves to `092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`, and the Claude Code plugin `v1.0.6` resolves to `db52e28f4d9ded852ab3942cea316258ae4ef346`. AI Functions was examined at the shared report's commit `145efc8398dc1a0d91fface870a240e6d813a0b2`; I did not assign that commit's behavior to its earlier release. These are public source identities, not installed executor identities. [Codex tag](https://api.github.com/repos/openai/codex/git/tags/7a078f6bb4ce0dc2a81408b334ce52979d92c603), [plugin tag](https://api.github.com/repos/openai/codex-plugin-cc/git/ref/tags/v1.0.6).

## Ownership and continuation

**An existing native ID does not identify a callable active owner.** Codex's `resume_running_thread` looks for the thread in the addressed server's thread manager. Separately, the local store's resume path acquires a writer lock; the lock implementation refuses a competing writer within the same Codex-home namespace. This supplies a concrete source reason that a second server can fail to resume an already held thread. It does not identify the actual GUI or CLI owner, its store, or a callable transport. The shared report's stored-session adapters and the Claude report's distinction between a held query and a new SDK query are consistent with this finding. [Resume implementation](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/request_processors/thread_processor.rs#L4281), [store resume](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/thread-store/src/local/live_writer.rs#L40), [writer lock](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/rollout/src/writer_lock.rs#L20).

**Refine FIRST's configuration-override warning.** The schema permits overrides, but the loaded-thread path preserves rejoin behavior and ignores mismatches when another client can still observe that thread or shutdown does not complete. An eligible idle cache entry with no subscribers can instead be shut down and resumed cold with the requested configuration. Thus neither automatic override application nor complete preservation follows from a successful resume. This distinction affects inspection, continuation, and busy-input probes for independent tasks. [Loaded-thread handling](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/request_processors/thread_processor.rs#L4348).

**The SDK mappings stand.** TypeScript launches `codex exec --experimental-json`, adding `resume` and the ID when supplied. Python's default client launches a stdio app-server subprocess. Both support controlled work and stored continuation; neither launch path establishes connection to an independently running GUI owner. Wrapper support for resume therefore cannot fill the active-owner attachment gap by itself. [TypeScript launcher](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/sdk/typescript/src/exec.ts#L94), [Python launcher](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/sdk/python/src/openai_codex/client.py#L242).

## Admission, wakeup, and external content

**Queue admission remains distinct from consumption, with a shared-store nuance.** The processor accepts eligible stored threads without loading them; explicit queue start requires a loaded thread and can reject active or pending work. The queue service also polls SQLite changes on a configured ten-second interval, considers threads loaded in its own manager, and can wake eligible idle threads after an external queue write. Consequently, direct attachment to the owner is not the only source-declared way for a queue write to reach it: shared queue storage and an operating watcher are another conditional path. Neither store sharing nor watcher activity was observed here. The interval is source configuration, not a measured delivery latency. [Queue processor](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/request_processors/thread_queue_processor.rs#L190), [external-change watcher](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/ext/queue/src/service.rs#L89).

Automatic dispatch removes the queue entry after `StartIfIdleSubmission::Started`; this is not an assistant acknowledgment or completed assignment. The direct wake path requires a loaded, non-interrupted thread. This agrees with both other reports' separation of transport submission, worker progress, and semantic result. It also means queue disappearance alone is insufficient evidence for notification, reply, or work completion. [Dispatch and wake](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/ext/queue/src/service.rs#L405).

**ExternalMessage is external tool content, not a verified peer principal.** The pinned Python contract describes untrusted content below user/developer instructions, saved as `functionCallOutput`; it starts an idle turn or joins an active regular turn without a preceding call ID. Source names and namespaces do not prove identity or permission. A joining handle can collect the turn result, but that does not establish that the receiver acted on this notification or can later reply through an independent reverse route. FIRST's representation claim stands; any reading of it as peer authentication or authorization is incorrect. The Claude report's peer-origin discussion therefore does not make ordinary queue input or SDK steering equivalent to this representation. [ExternalMessage contract](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/sdk/python/docs/api-reference.md#externalmessage).

## Plugin and shared-wrapper corrections

**Replace the plugin's loose “latest rescue thread” description with its actual selector.** At `v1.0.6`, `--resume` and `--resume-last` are booleans. The selector scopes job records to the Claude session when available, rejects visible queued/running task jobs, and selects a task with a thread ID that is neither queued nor running. The shared FIRST report's “completed task” wording is too narrow: this predicate does not require successful completion. When no Claude session ID and no eligible tracked task are available, it falls back to a cwd-filtered search for app-server threads with the plugin's task-name prefix. The public command still does not accept an arbitrary resume ID. These rules affect which associated task gets continued; terminal/plugin support does not establish Desktop-hosted or cloud Claude compatibility. [Selector and command](https://github.com/openai/codex-plugin-cc/blob/db52e28f4d9ded852ab3942cea316258ae4ef346/plugins/codex/scripts/codex-companion.mjs#L298), [fallback search](https://github.com/openai/codex-plugin-cc/blob/db52e28f4d9ded852ab3942cea316258ae4ef346/plugins/codex/scripts/lib/codex.mjs#L1162).

**Promote AI Functions from FIRST's historical lead to a narrowly source-examined candidate.** `resume_thread_id` reaches `AsyncCodex.thread_resume`; `fork_of_thread_id` takes precedence, and a failed connection is cleaned up and re-raised in this path rather than silently replaced by a new thread. The wrapper creates its own SDK/server connection and runtime tool server. It is therefore an explicit stored-ID continuation candidate, with active-writer compatibility still requiring a fixture. Its declared dependency is `openai-codex>=0.147.0`, so the actual SDK and CLI must be pinned independently; the source does not bind execution to Codex 0.162.1. [Connection path](https://github.com/strands-labs/ai-functions/blob/145efc8398dc1a0d91fface870a240e6d813a0b2/src/ai_functions/codex/codex.py#L673), [dependency](https://github.com/strands-labs/ai-functions/blob/145efc8398dc1a0d91fface870a240e6d813a0b2/pyproject.toml#L67).

I also narrowed its notification claim: an active notification calls `handle.steer(text)` as additional user input; an idle notification or failed steer is buffered for the next execution. `notify()` starts no new cycle, and teardown can precede buffered delivery. This is not the ExternalMessage path and does not establish idle wakeup. The distinction changes both notification-origin and continuation checks for registered peers. [Notification implementation](https://github.com/strands-labs/ai-functions/blob/145efc8398dc1a0d91fface870a240e6d813a0b2/src/ai_functions/codex/codex.py#L492).

## Hosted identities and caller access

**The cloud identity gap remains.** Current documentation distinguishes Codex Cloud's published environments from Codex Cloud (Legacy), which supports Code Review, Linear, and GitHub workflows. The Projects page separately describes Work Cloud with local computer access and separate Work/Codex histories. The pinned CLI's cloud enum contains only `exec`, `status`, `list`, `apply`, and `diff`. These sources do not establish equivalence among a CLI cloud task ID, current Cloud task, legacy task, and ChatGPT Work conversation, nor a general existing-task follow-up endpoint. Desktop tool declarations remain caller-specific schema evidence; neither shared MCP/ACP support nor the Claude report's cloud follow-up route resolves OpenAI's identity or external-caller gap. [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments), [Projects and chats](https://learn.chatgpt.com/docs/projects#use-local-projects-for-folders-and-codebases), [cloud CLI enum](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/cloud-tasks/src/cli.rs#L16).

## Smallest proposed checks

These are proposals requiring separate concrete authorization, not executed probes. No runtime, provider, setup, latency, reliability, or cleanup cost was measured.

| Candidate and operation | Smallest check and necessary evidence | Unmeasured cost drivers |
| --- | --- | --- |
| Independent GUI/CLI inspection and continuation | Bind one disposable native ID to its actual server, store, and current client. Establish whether the operation rejoins that server or cold-resumes storage. Inspect before sending; record refusal without replacing the owner. | Fixture binding, client setup, permitted state observations, and any receiver turn. |
| Queue notification and bounded request | Use one loaded idle fixture, then a bounded busy case; separately check an unloaded stored case. Correlate admission ID, owner-side start, receiver acknowledgment, and requested result. Test direct-owner and shared-store watcher paths only when each is explicitly bound. | Queue inspection, watcher observation, model turns, waiting, and cleanup. |
| ExternalMessage notification | On one owned fixture, compare idle and active delivery. Inspect the saved item type and a response naming the correlation token; keep an independent reverse reply as a separate operation. | SDK/runtime preparation, two receiver turns or overlapping handles, and history acquisition. |
| Plugin continuation | With synthetic job records, check session scoping, queued/running refusal, unsuccessful terminal jobs, and missing-session fallback. Later continue one authorized associated job and compare its returned native ID. | Selector fixture work, plugin/host compatibility, and a provider turn. |
| AI Functions continuation and notification | First use a fake SDK to check explicit resume, fork precedence, failed resume, idle buffering, failed-steer fallback, and teardown. Later resume one permitted stored ID; an active-owner collision needs a separate disposable fixture. | Coordinator/tool-server setup, exact SDK/CLI pinning, native-store access, and model usage. |
| Cloud identity and follow-up | First obtain a supported caller interface and one permitted task reference with its backend identity. Compare only that task's UI/API references and one authorized continuation; absence of an interface remains an unresolved result. | Account/environment setup, cloud startup, reader access, and provider/service use. |

Unresolved concerns for separately classified security review are peer names being mistaken for authenticated senders, user-input steering being mistaken for peer-origin content, configuration effects during cold resume, and authority exposed through any remote adapter. I established no security property. Actual deployed owners, sender reachability, receiver behavior, settings preservation, reverse replies, and recovery remain unobserved; no candidate is selected.

For procedure capture, I propose adding owner/store binding, warm-versus-cold resume, user-versus-tool input, and admission/start/acknowledgment/result distinctions to the portfolio's pending probe procedure. The downstream probe should consume the reviewed FIRST-plus-addendum revision and record its runtime dependencies. Placement, independent review, publication, and consumer invocation remain with the coordinator; this addendum does not install a procedure.
