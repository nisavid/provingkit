# Repository-configuration packaging feasibility

Both source shapes are feasible without making the new procedure a seventh Kit member. The standalone Skill requires less new packaging machinery. The independently installable Plugin supplies its own installation identity, but current Provingkit source validation, artifact projection, and dotfiles reconciliation do not support an additional independent plugin unchanged. Choosing between them remains a human packaging decision.

This is a source assessment, not design acceptance or installed-client qualification. It compares one focused Skill with maintained decision guides and private helpers where earned. Client targets, qualification contexts, the final name, and promotion policy remain open.

## What current source establishes

**Provingkit separates a Plugin's identity from the Kit's identity.** A Plugin is a self-contained root with a canonical manifest; its Skill resources stay inside that root. The Kit is the named six-member set, and a Release is a whole-Kit compatibility claim over independently releasable identities. Individual equipping already exists as a concept. Thus neither option inherently requires a whole-Kit release. [Provingkit glossary](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/CONTEXT.md#L9-L25), [Kit and Release](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/CONTEXT.md#L65-L80), [individual equipping](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/README.md#L31-L35).

**The present repository source root is stricter than that conceptual separation.** `_validate_excluded_source` requires the directories under `plugins/` to equal exactly `EXPECTED_MEMBERS`; adding a seventh directory there would take its rejection branch. The Kit definition separately fixes exact membership and declares that a partial selection is not Provingkit. An outside-Slate Plugin therefore needs an explicit source-organization/validation amendment, not an unnoticed directory addition or an automatic membership expansion. [Source-root check](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/validate_provingkit.py#L1589-L1606), [definition](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/release/provingkit/definition-v1.json#L18-L114).

**The current projector supports subsets of known members, not arbitrary plugins.** Its policy names the six members; that list also supplies the default build selection. `--slate` can select one known member but rejects unknown names. The generated catalog identity is hardcoded to `provingkit`. Adding the new plugin to this policy merely to get a build would also enlarge the default artifact selection. [Projection policy](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/release/artifact-projection-policy-v1.json#L1-L24), [selection](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/build_release_artifacts.py#L146-L158), [catalog identity](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/build_release_artifacts.py#L184-L213).

**Dotfiles' maintained Provingkit installer is also specialized.** It only accepts the six member names and the prescribed marketplace identities. It consumes pinned clean artifacts and does not build from a checkout. Its own contract explicitly separates materialization/native configuration from interactive discovery and Skill behavior. The generic protected `agent-equipment apply` route is documented as unavailable. [Installer checks](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/home/private_dot_local/bin/executable_provingkit-installations#L19-L33), [selection checks](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/home/private_dot_local/bin/executable_provingkit-installations#L99-L127), [maintained installation contract](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/docs/agent-equipment/provingkit-installations.md#L3-L11), [pinned-input contract](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/docs/agent-equipment/provingkit-installations.md#L66-L84).

## A: Repo-carried standalone Skill, provisionally deployed globally

The concrete source shape is one canonical `.agents/skills/<chosen-name>/SKILL.md` with its guides and any earned helpers inside the Skill. Provingkit already carries this form: its Sys1 instructions name `.agents/skills/handling-sys1-incidents/` as canonical and require regeneration and byte equality for its repo-local Claude projection. This is evidence for source shape, not an existing global installer for the new Skill. [Repository instructions](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/AGENTS.md#L21-L27).

Dotfiles owns existing user-global projection conventions. Its maintained capture procedure requires one source and standard harness projections, permits provisional repo scope, and keeps broader promotion a proposal. Its Claude synchronizer derives missing links from the shared `.agents/skills` root; it preserves existing destinations and does not acquire a Skill from Provingkit. Its deployment tests demonstrate the source-owned `home/dot_agents/skills` plus Claude-link pattern. These are reusable pieces, not proof that arbitrary Provingkit source is already managed end to end. [Capture ownership](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/home/dot_agents/skills/capturing-agent-procedures/SKILL.md#L12-L23), [Claude projection](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/home/run_after_sync-global-agent-skills-to-claude.zsh#L8-L48), [deployment test shape](https://github.com/nisavid/dotfiles/blob/9e8000a7542203defcc58c5f23e883764f8fa405/tests/public-agent-skills.zsh#L594-L637).

The smallest honest local-alpha path is to review and pin that one Skill, then use the selected client's existing installation owner to place a derived copy or projection and verify it against the pinned source. The deployment record must identify the source revision, selected runtime files, destination owner, and update/removal route. If dotfiles is selected to own placement, its binding must point to or reproducibly derive from Provingkit's source; a second independently edited Skill under `home/dot_agents/skills` would create two semantic owners. I found no maintained arbitrary-Provingkit-Skill acquisition/reconciliation contract in the inspected dotfiles sources, so that small binding/procedure remains work to define.

This option needs no Plugin manifest, Kit content lock, marketplace entry, or Kit membership change. A separate alpha identity can be a named candidate bound to the source commit and content digest; it should not be represented as a Provingkit Release. Existing projection machinery does not establish whether a fresh client invokes that candidate.

## B: Independently installable Plugin outside the current Slate

The concrete source shape is one Plugin root with canonical `plugin.json` and `skills/<chosen-name>/`, plus only the adapter material required by the selected clients. This keeps one semantic owner and packages its runtime resources together. Proseweaving is an existing one-public-Skill example, including an adapter projection and package-owned validation; its README explicitly leaves release-Slate inclusion outside the plugin. It is a useful pattern, not a requirement to copy all its supporting machinery. [Proseweaving source shape and checks](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/plugins/proseweaving/README.md#L30-L58).

The smallest honest local-alpha path needs three deliberate additions:

1. **Represent independent source separately from Kit membership.** Admit the new maintained Plugin through an explicit source-organization rule and focused validation while retaining the six-member definition. The current `plugins/` equality check needs a narrow amendment if that root is used. Moving the source to an ungoverned directory merely to evade the check would not establish the intended contract.
2. **Produce a separately identified clean runtime artifact.** Use a focused independent projection contract or a small explicit independent-plugin mode with its own selection and catalog identity. Reuse the existing file-selection, containment, canonical digest, and target-adapter primitives where applicable; preserve the Kit builder's default selection and published identities. Do not install the development source tree or simply append the plugin to the Kit policy. The present projector CLI cannot do this unchanged.
3. **Use the selected client's supported native route and verify adoption.** The maintained install guide supplies precedents for native local-marketplace registration and installed-payload checks, but the specialized dotfiles reconciler cannot accept this new identity unchanged. A focused local installation procedure can reuse those operations without extending the whole host reconciler for the first alpha. The chosen route still needs its own update/removal ownership and fresh invocation evidence.

Reusable source-level checks already exist for canonical manifest shape, direct-child Skill discovery, and resource containment in `scripts/agent_plugins_standard.py`. They are independent of the six member names. The projector's `selected_files`, `tree_digest`, and Cursor-manifest transformation are also useful implementation pieces; the public build operation remains Kit-specific. [Manifest and discovery primitives](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/agent_plugins_standard.py#L87-L187), [resource containment](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/agent_plugins_standard.py#L203-L246), [projection primitives](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/scripts/build_release_artifacts.py#L45-L96).

An independent Plugin must retain its own identity, candidate digest, and evidence. Reusing the existing `provingkit` or `provingkit-local` catalog as though the new Plugin were already a member would blur the distinction and could affect existing registrations. The current installation guide specifically records marketplace-name collision risk; a new version string alone does not solve it. [Local identity contract](https://github.com/nisavid/provingkit/blob/70879ae2ea94fac8708ab77051d08ded9429fce4/docs/preview/install-and-update.md#L401-L411).

## Decision implications

| Question | A: standalone Skill | B: independent Plugin |
| --- | --- | --- |
| Canonical procedure owner | One repo-carried Skill. | One Skill inside one Plugin. |
| Additional source integration | Repo discovery pointer and projection contract. | Explicit independent-plugin source allowance, validator, and distribution contract. |
| Existing machinery reusable unchanged | Source/projection conventions; selected existing installation operations where their contracts fit. | Manifest/discovery/containment primitives and ordinary native-client operations. |
| Existing end-to-end deployment already established | No arbitrary-Provingkit-Skill reconciliation found. | No: current projector and dotfiles reconciler restrict identities. |
| Principal ownership risk | A second authored global copy or competing installer owners. | Treating independent distribution as Kit membership or exporting the same Skill simultaneously through standalone and Plugin routes. |

Both options can reach a separately identified local alpha before whole-Kit release work. Neither changes the procedure's authorized GitHub actions or contextual judgment. Package selection changes source organization, distribution identity, and installation ownership. The selected client targets and qualification contexts determine the necessary adapters and installed-invocation evidence; this report does not select them.
