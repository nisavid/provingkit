# End-to-end repository work with selective automation

I recommend agent-led end-to-end workflows through existing native tools and owners, supported by concise decision guidance and focused executable checks where they prevent demonstrated errors. The caller's task is the interface. An editable proposal is useful when choices remain; it must not become a compulsory stop before an already authorized action.

This revises my initial proposal in two material ways: application is part of the selected alpha, and the absence of a catalog entry or bespoke actuator does not bar an otherwise supported, authorized change. The first three reports are one convergent architecture with presentation variants, not three independent demonstrations of superiority. The structured-knowledge and operation-automation variants supply real alternatives; none has been behaviorally compared here.

## What changes after comparison

Ivan selected creation, assessment, defaults adoption, focused changes, and project-specific CI hardening through authorized application. Advice-only or single-effect alpha proposals therefore no longer satisfy the chosen capability scope. He also selected contextual judgment: preserve informed choices, cite applicable policy, and intervene for concrete active harm. Intentional freezes remain valid. These choices authorize design, not live changes during this panel.

| Architecture | Where maintained complexity lives | Advantage and cost |
| --- | --- | --- |
| Agent-led workflow | Source-linked guidance, task reasoning, native-tool use, and focused helpers | Adapts to unfamiliar settings with a small caller interface; correctness depends on retrieval, judgment, and reliable execution of the procedure. |
| Structured decision knowledge | Applicability predicates, relation records, evaluator bindings, prose, and their consumer | Makes recurring interactions inspectable and repeatable; incomplete relations can conceal missing reasoning, and corrections span several representations. |
| Operation automation | Each operation's observation, preparation, allowed progression, write/readback, and fixtures | Concentrates preservation and recovery in testable modules; new operations and provider changes cost implementation and qualification while policy judgment still sits outside code. |

The initial reports' document names and number of entry points do not distinguish these architectures. Their substantive difference is what maintainers must change when a producer changes, documentation conflicts, or an unfamiliar setting arrives.

I would not start with a relationship language: the record structure is plausible but no comparison yet shows that authored predicates outperform a short decision guide. I would also reject automation as the only allowed application route. Its explicit unsupported-effect response is an honest product-support claim, but becomes an unnecessary restriction when generalized to what an authorized agent may do through existing tools. Automation is strongest inside difficult operations, not as a universal admission system for repository work.

My initial claim that unowned setting operations need a selected narrow actuator was too easy to read as “build a new helper first.” The corrected requirement is an understood, available operation route. A native tool may already provide it. An existing maintained owner remains authoritative where one exists; native-tool flexibility must not become a bypass around that owner's failed checks.

## Concrete trace: CI security

This is a constructed trace, not a new observation of Provingkit. Suppose inspection finds Python tests, a plugin-contract job that can skip changed plugin content, no configured CodeQL default setup, pinned checked-in actions, permissive repository Actions admission, and a known sole-maintainer contribution model. A check named `tests` has also changed producer. The request initially authorizes a recommendation.

The caller receives a concrete proposed outcome:

> I recommend making the plugin-contract result reliable for plugin changes, retaining Python tests as a merge requirement with their current producer, and adding supported Python and workflow analysis. Keep the current review arrangement and action-admission choice unless you want to change them. The workflow pins already protect those references; they do not require future changes to use pins.
>
> I would first repair the skipped validation path and establish the new analysis results. Then update required results to the intended producers. Choose an alert threshold after we know what the analysis covers; adding the scanner alone would not establish that coverage.

The implementation must supply named jobs and producer identities, actual source diffs, observed event paths, scanner suitability, and concrete proposed settings. “Map your checks” is preparation, not the final answer. It must also identify whether skipping is legitimate for irrelevant paths; an always-required aggregate is warranted only if it reliably checks the selected coverage contract. Plugin content validators retain their role because code analysis does not establish those contracts.

If Copilot approval documentation conflicts, the module keeps both claims and does not use an unqualified preview to promise the sole maintainer an independent approval path. If inherited restrictions cannot be read, it states which effective-configuration claims remain unresolved while continuing independent source work.

Once the concrete choices are accepted and application is authorized, the agent edits and verifies source through existing development/review owners, publishes through Versionkeeping and Mergecraft where applicable, observes the selected producers, and applies the authorized setting delta through its actual configuration owner. It preserves producer identity when a label is reused. Scanner execution, selected coverage, and alert-gate behavior are verified separately when claimed. Hosted enforcement claims require their own discriminating evidence; enabling a setting does not supply it.

A focused checker earns its keep here by comparing check identities and identifying missing or mismatched event/result observations. It cannot infer source coverage merely from passing labels. The knowledge variant makes those dependencies explicit; the automation variant can protect a required-check update that sends a larger enclosing object. Both contribute useful internal modules without requiring a universal graph or automatic policy engine.

## Concrete trace: uncertain application

Continue the hypothetical accepted change. Source publication succeeds. The required-check write times out. Its first readback fails. Scanner gate activation depends on the preceding result.

The caller should see:

> The workflow change is published. I could not confirm whether the required-check change took effect. I am checking the current rules before continuing; scanner gate activation remains pending.

The maintained procedure must preserve target identity, intended delta, relevant before-state, the attempted effect, and the uncertainty. It attempts reasonable reconciliation during the active work rather than declaring the entire task finished at the first failed read. It neither repeats the write blindly nor restores a guessed preimage. Independent work can continue.

Suppose later readback shows the intended required checks plus an unrelated rule added by the configuration owner. The agent preserves that rule and verifies the selected delta. It can then continue independently authorized dependent work if the effective conditions still fit. If readback instead shows a changed producer or incompatible managed state, it revisits only the affected plan. If readback remains unavailable, the handback identifies the exact unresolved effect and the observation needed to resume.

A helper is particularly valuable when repeated operations must preserve enclosing objects, detect changed preconditions, or reconcile uncertain effects. Code can enforce those mechanics consistently. It still cannot promise atomicity where the provider supplies no usable concurrency guarantee, authenticate human authority from an “authorized” Boolean, or restore coupled source and documentation by changing settings alone. Those limits survive the user-facing simplification.

## Uncataloged settings and authority already present

Suppose the user says, “Enable Discussions on this repository,” with sufficient authority, an available native tool, and no competing manager or applicable restriction. The agent checks the target, current value, relevant ownership, and current operation semantics; uses the existing tool; and reads back the selected result. It reports enabled or already enabled. It does not create a catalog record, implement a bespoke actuator, or require the user to say “apply” again.

This route still needs semantic understanding and evidence. If the setting or available control cannot support the requested effect, say exactly what is unavailable. If another tool owns the field, use its maintained source. A documented command discovered at runtime is not automatically a qualified reusable integration; the completed action can have concrete readback evidence without claiming exhaustive regression coverage. The alpha should evaluate this adaptive route with held-out routine settings, including native-tool errors, rather than promising every future GitHub field.

Likewise, “Change this repository's merge setting to X” can proceed from a sufficiently specified, authorized request. Preparation and verification remain internal duties. Confirmation is needed for newly proposed defaults or a consequential changed meaning, not as a universal three-step ceremony. Guidance must distinguish a documented restriction, an informed unconventional choice, an intended freeze, and active harm. The selected policy supports stopping a concrete privileged-CI credential exposure and explaining its evidence; it does not support treating every failed recommendation check as harm.

## The smallest maintained representation

Start with a discoverable procedure for the five workflows; short decision guides for demonstrated interactions; primary-source and procedure references; and evaluation cases. Retain consequential evidence dependencies in the task result. Ordinary unrelated settings need no normalized record. Source corrections identify dependent conclusions; an unrelated documentation revision does not invalidate everything.

Add structure when repeated interpretation demonstrably fails or becomes expensive. A check-identity comparison benefits from structured facts and a deterministic evaluator. A complex settings update benefits from an operation-owned plan and reconciliation record. These have narrower claims than a global decision graph. Add a relation vocabulary only if comparison shows that retrieval consistently misses the same consequential links and explicit relations correct that failure at an acceptable maintenance cost.

Local files and processes stay local-substitutable through temporary repositories and real readers. GitHub remains true external. Where a helper owns provider interaction, live CLI/API and replay adapters justify an internal seam. Agent-native operations can instead use a harness tool replay during evaluations; they do not all need to be wrapped in a second provider client. This keeps tests at the actual caller interface while preserving a way to induce inaccessible reads, timeouts, and drift.

## Qualification and the remaining human choices

The strongest objection to this recommendation is variability: flexible native-tool use can regress into inconsistent reasoning or ad hoc recovery, and selective helpers can become an incoherent collection. The implementation needs one visible procedure and explicit helper ownership. “Use judgment” alone is insufficient equipment.

A discriminating evaluation should run all three architectures on the same complete requests and provider responses, then introduce a changed check producer, procedure correction, contradictory source, uncertain write, and uncataloged setting. Compare useful completed outcomes, consequential omissions, unauthorized or duplicate effects, preserved choices, needless questions, recovery quality, and maintainer changes required. Hold out some combinations and relationship hints. A second evaluator should examine the completed trace, not just polished final prose. If structured knowledge materially reduces omissions or operation automation prevents recovery errors the recommended design repeatedly makes, adopt that machinery for the demonstrated scope.

The selected alpha needs end-to-end evidence for all five workflows, including success, unchanged, and partial/unknown cases appropriate to their effects. Application support must include the adaptive native-tool route. Separately verify published artifact identity, installed payload, fresh discovery, and useful invocation in the chosen harness; local invocation cannot establish hosted enforcement.

I recommend proposing one Provingkit-owned, repo-carried Skill as the initial maintained procedure, with references and earned helpers, independently scoped from the current Slate. A distinct Plugin is an alternative if independent distribution warrants its manifest and release work; a maintained document invoked by existing equipment is lighter but must demonstrate equivalent discovery. No reviewed existing Plugin owns this whole concern. Keep Git, forge, review, security, model, and release ownership unchanged.

The operator still needs to choose source home/packaging, initial qualification contexts, and local deployment target. A public personally owned GitHub Python/plugin repository and the current Codex desktop/Linux surface are concrete candidates to propose, not settled choices. Organization inheritance and an existing manager should at least receive replay-based handling tests; declaring their live support requires additional selected evidence. Scope across contexts can be bounded while retaining all five chosen workflows. Capture, publication, deployment, correction, and downstream invocation belong in the implementation map.
