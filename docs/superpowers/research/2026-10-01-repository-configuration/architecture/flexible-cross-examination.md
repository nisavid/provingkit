# Flexible execution with maintained decision guidance

I recommend agent-led configuration equipment with one ordinary-language interface, maintained decision guidance, and focused checks where repeatability matters. It should execute authorized work through existing tools, including researched settings outside its maintained knowledge. Start with neither a general predicate language nor coded operations for every setting. Add structured relationships and operation helpers only where a concrete case demonstrates their value.

This recommendation combines a small part of the knowledge variant with the convergent proposal design. It rejects operation-specific automation as the mandatory path for every effect. These remain architecture judgments, not measured superiority or qualified runtime behavior.

## Critique dispositions

The three original proposals converge materially. A decision document, editable proposal, and owner-directed brief differ in presentation and continuity, but place most reasoning and execution judgment in agent-consumed prose. Their agreement is not three independent demonstrations that prose suffices.

I withdraw the implication in my original report that a setting without a qualified operation-specific actuator must remain preparation-only. My knowledge variant's “qualified owner route” wording has the same problem. Tested reusable coverage is an evidence claim; it is not the user's authority or the complete capability of an agent with available native tools. A novel setting can be understood, changed, and read back without first adding a library entry or bespoke helper. Actual policy, missing authority, unresolved consequential semantics, unavailable controls, and concrete harm still matter.

I also narrow the automation variant's rule against using raw commands after a failed helper check. A failure that establishes a real unmet invariant must survive every route. A parser limitation or unsupported field does not automatically prohibit an independently researched native route. The agent must preserve the underlying invariant and reconcile any uncertain prior effect; switching tools cannot become a way to evade a valid finding.

The minimal design's mandatory-looking **advise/carry out** split should be internal sequencing, not a compulsory ceremony. The caller-focused design already preserves existing execution authority more clearly. A fully specified “Enable this feature here” request can proceed through preparation and verification in one task. Unselected defaults still need concrete confirmation where the user has not delegated that choice.

Ivan's later decisions settle end-to-end alpha capability and contextual judgment. Advice-only scope is no longer an option. Creation, assessment, defaults adoption, focused changes, and project-specific CI hardening must work through authorized application in the selected qualification contexts. Honor informed choices, identify actual policy constraints, distinguish intentional freezes from accidental deadlocks, and intervene for concrete active harm.

## What differs between the architectures

| Architecture | Where it provides depth and locality | Principal cost or failure |
| --- | --- | --- |
| Prose/proposal | Agent absorbs discovery, interpretation, explanation, and native-owner coordination; mechanism corrections concentrate in maintained guidance. | Retrieval and interpretation can omit an interaction; a persuasive proposal can conceal weak execution. |
| Structured knowledge | Explicit relations reliably bring known adjacent decisions into consideration; focused evaluators repeat computations and expose premises. | Missing relations create false confidence; predicates and explanations can drift; adding unfamiliar settings can become schema work. |
| Operation automation | Code preserves supported preimages, identities, transitions, and partial-result handling for repeated effects. | Each operation carries implementation and qualification cost; rigid coverage can turn an available native tool into an artificial dead end. |

All three still need judgment for intent, policy interpretation, contradictory documentation, and unfamiliar circumstances. None eliminates that work by shortening its public interface. The automation variant is strongest for repeatedly executed, consequential migrations; the structured variant is strongest where the same relationships are repeatedly missed. Neither advantage has yet been measured here.

## The smallest maintained structure I recommend

Expose one request: target, intended outcome or exact change, and whatever constraints the caller knows. Recover the rest from discoverable context. The result is either completed work with scoped evidence, useful advice, or the specific unresolved decision. Keep an editable proposal when there are choices or continuity needs; do not require one as a separate deliverable for a routine toggle.

Maintain focused decision guides with a tiny index:

```yaml
id: required-ci-results
concerns: [ci-security, contribution-acceptance]
guide: required-ci-results.md
related: [security-analysis, merge-availability]
checks: [compare-check-contracts]
```

The links ensure known related questions are considered; the guide explains when they matter. They are not blanket requirements. Source references and consumed revisions accompany the claims that use them, without forcing every guide into one comprehensive fact schema. Do not initially adopt my variant's condition language: equality predicates alone do not buy enough over clear applicability prose to justify another semantic owner.

A focused check earns code when it can compare concrete facts repeatedly: selected acceptance claim, check producer, source revision, event, and observed result are a credible candidate. It can identify mismatches and unknowns; it cannot infer that a validator proves a claim merely because their names resemble each other. A source correction invalidates the affected consumer assumption, with semantic review determining relevance.

An operation helper earns code when preservation or uncertain-outcome handling is repeated and error-prone. Keep those helpers private to the module and colocate their explanation and fixtures. Local files/processes remain local-substitutable dependencies. GitHub observation and selected operation helpers use a real CLI/API adapter and replay adapter at internal seams; replay validates handling of supplied behavior, not hosted enforcement.

## Trace 1: project-specific CI hardening

Use these constructed facts: a selected contribution policy requires invalid plugin content to be rejected; ordinary PR unit tests run, but the dedicated plugin validator is path-filtered away for some plugin changes. A lock-reproduction job overlaps partially. The required list names a familiar result whose producer changed. Source actions are pinned while admission permits unpinned actions, deliberately. CodeQL default setup is absent; analysis coverage is unknown. The operator has one eligible human maintainer and has retained zero mandatory approvals.

For the recommendation-only request in the common brief, the caller should see:

> I recommend making plugin validation run on the intended plugin-change PRs, then requiring its verified result for the selected content policy. The lock check has not been shown to cover the same failures. The familiar check name now has a different producer, so its previous binding needs review.
>
> I would add suitable analysis for the Python content after checking the current setup requirements, then decide whether alerts should block merging once coverage and your threshold are known. Keep the deliberate admission and approval choices. Pinned source and permissive admission describe different controls.

The maintained guide supplies event/result distinctions and the overlap warning. A focused comparator can expose the changed producer and missing observations. Agent source inspection establishes what the validator actually checks and whether its trigger covers the selected paths. Current source research establishes scanning fit; no Rust baseline is copied.

If later authority covers the selected changes, the agent prepares source changes, uses existing review/Git/forge owners, obtains the relevant producer observations, and updates the authorized gate through its owner. It does not require a fresh approval for already specified effects. A new scanner threshold remains a real decision unless existing policy supplies it. If the selected claim includes actual refusal of invalid plugin content, a separately authorized hosted fixture isolates that failure from other gates; configuration readback alone cannot support the claim.

This trace is achievable by prose alone in principle. The comparator earns its place only if it reliably catches omissions across repeated cases. The structured library does not make the scanner or gate choice inevitable merely because `ci-security` selected the guide.

## Trace 2: unknown application outcome

Construct an authorized request containing two effects: change a repository feature toggle, then change a related policy setting whose meaning depends on that toggle. The first write returns a verified result. The second times out, and readback is unavailable.

The caller should receive a concrete result such as:

> The feature toggle is enabled and read back successfully. The policy update timed out; I cannot yet tell whether it took effect. I have not repeated that write. I need a usable read of the policy state to verify completion.

The retained task evidence names the target, intended effects, relevant before-state, successful observation, timeout, and unsuccessful readback. It does not need a general transaction service. On continuation, read the unknown target first. If it matches, report observed desired state without claiming the earlier request caused it. If it differs, inspect current ownership and relevant changes before continuing under the surviving authority. A new conflicting writer requires reconciliation; guessed rollback or blind replay is unacceptable. Independent work can continue.

A helper for this operation family may make the bookkeeping more reliable. It cannot manufacture readback, atomicity, or authorization. An unavailable observation is a genuine limitation regardless of architecture.

## Trace 3: an authorized uncataloged setting

The user names a low-impact repository feature toggle, target, and desired value. The setting is supported by an available native tool but absent from this equipment's index.

The agent consults current official documentation or installed help, establishes target applicability and the tool's field semantics, reads the current value, checks relevant policy and existing ownership, and prepares the smallest supported native update. If there is no consequential ambiguity or real conflict, it executes under the existing instruction and reads back the selected field, checking affected neighboring state where the tool's update semantics require it. An existing infrastructure owner redirects execution into that owner's maintained source; it does not force a second hosted writer.

The final answer names the verified change and any actual limit. There is no “install a new actuator first” requirement, mandatory catalog entry, or extra accept/apply question. Report that this was a researched native-tool route if that distinction matters to the reusable coverage claim. A useful recurring method can later be captured and evaluated; capture is not a prerequisite invented for every routine field.

## Remaining choices and qualification

I recommend canonical repo-carried source in Provingkit, a focused discoverable Skill with internal references/helpers, and no new Plugin identity or Slate membership until packaging benefits are established. Extending an existing Plugin would need a real ownership fit; none of the inspected declarations assigns it the whole repository-configuration concern. A separate Plugin remains a reasonable alternative if independent distribution is desired. Broader Agentworks promotion is a later decision.

The invocation trigger is repository creation, configuration, defaults, configuration review, or a concern that requires changing repository controls. Ordinary code changes and generic code review should not invoke a whole configuration assessment. Git publication, forge publication, model selection, security work, review, and release retain their existing owners.

The operator still needs to select supported owner/product/actor contexts, target harnesses, source/packaging, and deployment destination. A practical qualification choice is one primary local harness plus disposable public GitHub repositories, including an existing-writer case; organization inheritance can be either included with its required observations or explicitly outside the initial claim. These are recommendations, not selections. Local alpha deployment is not a whole-Kit Release.

The strongest objection to my recommendation is that “add code when earned” could become permanent underinvestment while agents repeatedly make the same mistakes. The implementation contract should include a discriminating comparison: identical facts, held-out interaction combinations, a procedure correction, an uncataloged authorized toggle, and uncertain application. Measure missed consequences, false prohibitions, needless questions, correct recovery, and maintainer effort. Require complete useful examples of all five selected workflows, including application and no-op behavior. A pattern of misses must change the implementation before qualification, not become a caveat beneath polished prose.
