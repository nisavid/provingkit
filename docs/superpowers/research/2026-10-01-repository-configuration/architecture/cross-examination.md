# Architecture cross-examination questions

The first three designs materially overlap around an agent-written proposal and maintained prose. Treat them as a convergent candidate with interface variants, not three empirically independent architecture wins. The additional isolated variants make two alternatives concrete: structured decision knowledge with focused evaluators, and operation-specific automation. No preferred shape is selected.

1. Where do these designs actually differ in maintained complexity, public interface, change locality, ownership, and failure behavior? Which differences are only presentation?
2. Each initial report seems to require a qualified owner/actuator route for application. Does that confuse the boundary of tested reusable support with the user's authority to request a supported but uncataloged setting through an available native tool? Work the uncataloged-setting case. Explain an adaptive, researched tool route or justify a narrower claim. Do not require a new bespoke component for every routine field by assumption.
3. A fully specified initial request already authorizes an effect. Can the design complete it without forcing a propose/accept/apply ceremony? Concrete defaults still need confirmation when the user has not chosen them; inherited authority must stay usable.
4. Ivan selected useful end-to-end alpha workflows and contextual judgment. Update any advice-only alpha preference and fixed prohibition assumption. Make arbitrary deliberate choices, real policy constraints, intentional freeze, and active harm distinguishable in execution as well as prose.
5. Work at least two difficult shared cases concretely, including CI hardening and partial/unknown application. Show what the caller actually sees and what maintained machinery must supply; a table of desired outcomes alone is insufficient.
6. What smallest knowledge representation earns its upkeep? Separate useful evidence references from mandatory schemas. State when prose ceases to be enough, when focused checks help, and when an operation-specific helper is earned.
7. Recommend an architecture or justified combination under the accepted scope, with its strongest remaining objection and a discriminating evaluation. Compare complete caller and maintainer costs, not file length or an unsupported efficiency claim.
8. Propose source ownership, packaging, invocation trigger, and qualification/deployment context options for the human decision. Keep existing Git/forge/security/release owners; local deployed equipment is not a whole-Kit Release by implication.

Use the frozen common research and actual choices. Do not revise preserved first reports. Return critique dispositions, changed conclusions, concrete traces, remaining decisions, and actual additional exposures. These are design reasoning and proposed tests, not observed runtime outcomes. No implementation, provider experiment, installed/configuration edit, Git/forge write, or delegation.
