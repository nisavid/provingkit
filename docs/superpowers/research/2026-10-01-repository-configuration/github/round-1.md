# GitHub repository configuration: mechanisms, relationships, and qualification

We can build brief repository guidance around an evidence-backed settings catalog, provided the catalog distinguishes the operator's intent, GitHub's effective rules, the actor performing the operation, and the evidence that a gate actually evaluated the intended change. A list of enabled protections cannot establish those things by itself.

## Research boundary and evidence

This first survey covers GitHub.com repository governance, merge gates, Actions trust, code and dependency scanning, secret protection, and four existing configuration or assessment approaches. It does not select the operator's final policy, test hosted enforcement, inspect any repository's effective settings, or certify security. Arbitrary deliberate configurations remain possible within applicable policy; an unavailable reviewer or unsupported scanner is a configuration constraint, not a reason to impose a nonfunctional gate.

I retrieved these sources on **2026-10-01**, approximately 09:15–09:30 UTC. GitHub documentation pages identify their product variant as `free-pro-team@latest` unless otherwise stated. They are mutable documentation, not a fixed platform release. Some Firecrawl responses were cached earlier that day or on the previous day; each retained source records the cache timestamp when supplied. Context7 used `/github/docs` and `/integrations/terraform-provider-github`; it returned some Enterprise Server snippets, which I did not generalize to GitHub.com without checking the public GitHub.com documentation. REST documentation requested with an older `apiVersion` query still displayed `2026-03-10` examples: the query string alone does not establish the effective API contract. A future adapter should bind its API version explicitly and qualify it.

**Observed** below means I retrieved or read the named source. **Source-backed** means the source documents behavior; it does not mean I exercised that behavior. **Inference** means a conclusion drawn from those facts. **Proposal** is an option for the later design. All platform behavior in this report is source-backed, and all qualification cases are unrun.

I used the `research`, `context7-mcp`, and Firecrawl skills. I consulted Codex Security's `define-security-policy`, `threat-model`, and `propose-security-hardening` guidance for evidence boundaries and tradeoffs. This is source review using those principles, not a security scan, generated repository threat model, or hardening implementation. The single-report destination and no-mutation research charter govern the output.

Signed commits are another interaction, not a free-standing checkbox. It also distinguishes branch creation under rulesets from classic protection, and permits partially verified commits in the documented vigilant-mode case. A catalog should preserve these conditions and qualify the intended human and bot paths before proposing required signatures. ### Reviews, freshness, and one-person operation

A pull request requirement can have **zero required approvals**. Requiring a PR supplies a change record without itself requiring another reviewer. Authors cannot approve their own PRs, and the current approval documentation also excludes the person who assigned Copilot to the linked issue from approving that Copilot PR. **Inference:** a sole eligible account cannot satisfy a positive independent-approval requirement through self-review. Do not create another account merely to manufacture nominal independence. A deliberate zero-approval PR process, a real additional reviewer, a documented bypass, or a separately evaluated agent-review arrangement are materially different choices. [Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging), [review eligibility](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews).

Dismissal of stale approvals tracks changes to the reviewed diff, including relevant merge-base changes. Requiring approval of the latest reviewable push instead requires an eligible approver other than its pusher; earlier reviews may remain. These serve different collaboration patterns. CODEOWNERS approval is also not “every listed owner”: one eligible owner can suffice for a matched ownership rule. Rulesets now document required teams for selected paths, unavailable to user-owned repositories. Record reviewer availability and actual GitHub identity separately from the human or agent that prepared the change. [Review settings](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging).

**Time-sensitive correction:** current GitHub documentation offers Copilot approving reviews and a separate toggle permitting them to count toward merge requirements, with optional path globs; this is **public preview**. It is no longer safe to state categorically that Copilot approvals never count. Rulesets also document an extra approval, enabled by default, for unattributed Copilot PRs when the configured approval count is positive. These are product-specific conditions, not a general guarantee that an arbitrary agent's review counts or is independent. [Copilot review settings](https://docs.github.com/en/copilot/how-tos/copilot-on-github/set-up-copilot/configure-code-review#customizing-copilot-code-review), [additional approval rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#additional-approval-for-unattributed-copilot-pull-requests).

### Checks: identity, revision, event, and completeness

Required checks must satisfy the latest relevant SHA. If the test merge commit has a status, that commit's result is used; otherwise the head commit is used. Earlier-commit success is insufficient. Current troubleshooting docs also distinguish eligible workflow events: a passing `workflow_dispatch` job does not satisfy the PR requirement, while merge queues require their separate `merge_group` event. [Required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

Required-check acceptance includes `success`, `skipped`, and `neutral`. A whole workflow excluded by path/branch filters can leave a required check pending; a conditional job skip can count as success. A skipped dependent job after an upstream failure can fail to block. **Proposal:** model the check's semantic promise and every route that produces its conclusion, including a total-result job where suitable. Merely requiring its name cannot establish full execution. Job names should be unique across workflows. [Troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

Pinning a required check to an expected GitHub App excludes other producers of the same named status. The rules API represents this through `integration_id`. **Inference:** this identifies the producer, not the correctness of the workflow, its path coverage, or isolation from PR-controlled code. A GitHub Actions check still needs workflow-trust analysis. Strict checks test against current base code and cost additional builds; loose checks reduce churn but permit integration incompatibility. A merge queue checks the combined prospective change with the current base and earlier queued PRs, requires suitable CI triggers, and has timeout, concurrency, grouping, and batching choices. [Required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging), [rules API](https://docs.github.com/en/rest/repos/rules), [queue behavior](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

## Security configuration and its dependencies

### CodeQL and code-scanning gates

The current CodeQL language list includes C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript, Python, Ruby, Rust, Swift, and GitHub Actions workflows. Unsupported languages and unmodeled frameworks remain coverage gaps. Availability differs between public repositories and private organization repositories with GitHub Code Security. [CodeQL coverage and availability](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning).

Default setup can be enabled without running any scans when no supported language exists. It can also remain enabled after every attempted language analysis fails. If a new language's configuration fails, GitHub can resume the previous working configuration. **Inference:** enabled is not an acceptable coverage witness. Record selected languages, actual successful analyses, excluded paths, query packs, model packs, revision, and build mode. [Setup types](https://docs.github.com/en/code-security/concepts/code-scanning/setup-types), [default setup](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/configure-code-scanning/configure-code-scanning).

Default setup is now customizable through selected languages, suites, models, and a configuration-file repository property; “any customization needs advanced setup” is stale advice. Advanced setup remains useful for custom builds, matrices, scheduling, and external CI. No-build analysis does not analyze generated code; Java `none` mode does not analyze Kotlin. Matrix entries and build commands therefore matter in mixed-language and multi-project repositories. Analysis-path configuration and event path filters are distinct: the latter decides whether the workflow runs at all. [Setup choices](https://docs.github.com/en/code-security/concepts/code-scanning/setup-types), [compiled-language modes](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/manage-your-configuration/codeql-for-compiled-languages), [workflow configuration](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options).

The code-scanning ruleset gate can require specified tools and separate ordinary-alert and security-alert thresholds. It can block while required analysis is in progress or when the required tool is not configured. **Proposal:** choose thresholds only after coverage and triage expectations are known; test the gate with the actual scanner configuration before requiring it. A successful scanner execution and absence of reportable findings are separate claims. [Merge protection](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/manage-your-configuration/set-merge-protection), [available scanning rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-code-scanning-results).

### Actions trust and token authority

For ordinary fork PR workflows, tokens are restricted and secrets are withheld under the documented fork model; private-fork settings can explicitly send write tokens and secrets. `pull_request_target` uses the trusted repository context, and `workflow_run` can gain secrets/write authority even after an unprivileged predecessor. Untrusted checkout, build hooks, artifacts, and shared caches can cross that boundary. Approval to run a workflow is not evidence that every file it executes is safe. **Proposal:** present a data-flow explanation when a privileged workflow consumes PR material, with separate choices for unprivileged execution and authorized follow-up actions. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use), [fork settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).

New personal repositories default to `GITHUB_TOKEN` read access for contents and packages, and disallow workflow-created/approved PRs; organization repositories inherit relevant settings. Workflow/job permissions still need inspection. These defaults are not evidence for an existing repository. Least-required job permissions are a reasonable suggestion, but write jobs remain legitimate when they perform an authorized publication or maintenance operation. The approval toggle affects `GITHUB_TOKEN`; do not infer that all Apps or personal tokens are constrained by it. [Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [permissions REST API](https://docs.github.com/en/rest/actions/permissions).

Full-commit pinning stabilizes an action reference; it does not audit its code or everything it downloads. GitHub can require action SHA pins, including GitHub-authored actions, but reusable workflows can still use tags under that policy. Allowlisting and Marketplace identity badges are separate signals. Proactive pinning suggestions should include an update route and attention to reusable workflows, container images, and runtime downloads. Self-hosted runner exposure and cloud OIDC trust conditions require separate analysis. [Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).

### Dependencies and secrets

Dependabot alerts, security-update PRs, scheduled version-update PRs, and dependency-review merge checks are separate controls. Security updates depend on the dependency graph and alerts; automatic remediation is constrained by manifest/lockfile support and ecosystem behavior. Dependency review can report introduced vulnerable dependencies, but blocks only when its check is required. Directory coverage, supported ecosystems, grouping, private registry access, and notification ownership matter before a “turn on Dependabot” recommendation. [Security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates), [dependency review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review).

A concrete counterexample to blanket advice: current Dependabot alerts documentation says GitHub Actions alerts are generated for semantic-version references, not SHA references. Pinning remains useful, but does not justify assuming the same vulnerability-alert coverage. Version-update configuration and an alternative vulnerability-monitoring route need evaluation. [Dependabot limitations](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts#limitations).

Secret scanning detects committed secrets; push protection prevents supported patterns from reaching the repository; bypass and post-bypass handling are separate policies. Public repositories receive free automatic secret scanning. User-level push protection is enabled by default for public pushes, but a bypass does not generate repository alerts unless repository-level protection is also enabled. Repository push-protection bypass normally permits writers to state a reason; delegated bypass and exemption change that authority. Avoid treating an alert or a user's default protection as proof that all credentials or all contributors are covered. [Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning), [push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection).

The current rules catalog also includes a **public-preview** secret-scanning merge gate that waits for the PR head scan and selected open secret alerts; AI-detected secrets are excluded. A separate **public-preview** coverage rule evaluates uploaded data without waiting for uploads, so required uploader checks are needed to ensure all expected results arrive. These are useful examples of a setting that depends on an evidence-producing process. They need refreshed availability checks before implementation. [Secret gate and coverage rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

## Proposed shape for brief guidance and its catalog

The compact core can ask for the repository's purpose, ownership/visibility/plan, change actors and identities, code/layout/build shape, and the outcome the operator wants. It can then read effective settings, show only relevant relationships, recommend a coherent option, ask for decisions that change that option, and qualify the selected setup. This is a hypothesis for later design, not a chosen workflow or authorization to apply it.

A setting record should identify: stable semantic name; provider/UI/API field and API version; owner/visibility/plan/preview predicates; source and retrieval identity; native and tool-specific defaults; observed value versus unknown/unavailable; scope and inheritance; actor/permission/bypass authority; prerequisites and conflicts; evidence producer, revision, event, and coverage; recovery/rollback effect; goals served; tradeoffs; and unrun qualification cases. Relationship types should include `requires`, `conflicts`, `narrows`, `inherits`, `overrides-in-tool`, `aggregates-in-provider`, `produces-evidence-for`, and `invalidates-evidence`. A plain Boolean “secure” would erase the distinctions this survey found.

| Goal stated by operator | Candidate recommendation | Confirmation needed |
| --- | --- | --- |
| Keep a usable change record for a sole maintainer | PR required; approval count chosen independently; appropriate reliable CI. | Does the operator want human approval, agent analysis, an audit record, or a combination? Which identities are actually eligible? |
| Prevent unreviewed changes after approval | Stale-review dismissal or latest-push approval, matched to review topology. | Who can reapprove, and how should base-branch churn affect review? |
| Avoid races between independently passing PRs | Strict integration checks or a qualified merge queue. | Owner/plan eligibility, concurrency, CI cost, queue event support, and desired merge method. |
| Catch vulnerabilities in a mixed-language repository | Map supported language/build/path coverage before selecting CodeQL setup and thresholds; add other tools for gaps. | Generated code, Kotlin/no-build limitations, custom frameworks, alert triage, and required result completeness. |
| Permit agent maintenance without broad token access | Grant only required job/App authority; review config and workflow changes through an eligible route. | Which operations must the agent perform, and which identity, credentials, and bypass route do they use? |
| Stabilize third-party workflow inputs | Qualified SHA pinning and a maintained update path. | Reusable-workflow references, runtime downloads, update ownership, and Actions vulnerability-monitoring gaps. |
| Reduce leaked secrets and vulnerable dependencies | Distinct scanning, prevention, remediation, and review controls with assigned response ownership. | Entitlements, supported patterns/ecosystems, exception handling, and expected noise. |

Proactive suggestions should be triggered by observed contradictions or uncovered goals: incompatible merge methods, a positive approval count with no eligible reviewer, a required job that cannot run for some PRs, a scanner enabled without a successful supported analysis, or a pinned action with no update route. They should explain a repair and its consequence. The catalog should also support “deliberately unchanged” with the operator's reason; it should not convert every suggested improvement into a mandatory hardening gate.

## Falsifiable qualification cases

These are proposed future tests on separately authorized disposable repositories or approved fixtures. None was run in this research.

1. Add overlapping rules with different review counts; verify the effective requirement and its reported source, including a classic protection rule. Then disable one ruleset and confirm the authored inventory remains distinct from active rules.
2. Exercise PR-only, always, and exempt bypass through the intended account/App; compare direct push, PR merge, and audit records. Confirm whether the actor can change the rules themselves.
3. Open a PR as the sole maintainer; try the selected review path. Repeat with the actual agent identity and any enabled Copilot approval preview, including changed-file globs and unattributed PRs.
4. Approve, push a diff-changing commit, and change the merge base; observe invalidation. Distinguish latest-push approval from dismissal of all stale approvals.
5. Produce a same-named check from the wrong App, an earlier SHA, an ineligible workflow event, and a skipped conditional job. Confirm the intended gate's acceptance behavior.
6. Submit a path-only change that excludes CI, a failed prerequisite job, and a queued PR lacking `merge_group`; verify that qualification detects pending or misleadingly successful routes before enforcement.
7. For each stack/layout, inspect successful CodeQL analysis coverage. Include unsupported-only input, Java plus Kotlin under `none`, generated code, nested projects, and failed language initialization. An “enabled” setting must not pass this case by itself.
8. Verify scanner tool/threshold gating for pending, missing, and completed analyses, and any coverage-upload ordering. Use harmless fixtures with no production secrets.
9. Trace an untrusted fork payload, artifact, and cache into any privileged follow-up job without executing attacker code. Qualify fork, Dependabot, same-repository, and self-hosted-runner paths separately.
10. Compare public/organization/private eligibility and inherited policy behavior; exercise unavailable-field and permission-denied reads without converting either into a false “disabled” result.

## Coverage gaps, long tail, and map questions

The first survey substantively covers protection/ruleset composition, review freshness, bypass, merge/check interactions, Actions authority, code-scanning coverage/gates, dependencies, and secrets. It samples general repository features and permissions through existing configuration tools. It does **not** fully catalog organization/enterprise custom roles, identity/SSO, all required-workflow rules, environment/deployment policy, Pages/domains, package/release provenance, immutable releases, webhooks, deploy keys, repository visibility transitions/transfers, Codespaces, storage/retention/billing, every preview, or every API mutation. Those belong in a versioned long-tail inventory with explicit “not yet qualified” entries; they should not be implied by a claim of complete GitHub coverage.

Questions for the map:

- What first capability is being qualified: read-only explanation, recommendations plus a proposed diff, controlled application, or ongoing reconciliation? Each needs different authority and recovery evidence.
- Which owner types and product surfaces are in the first supported slice, and how is unknown entitlement handled?
- Is a policy exception a recorded operator choice, an organization constraint, or a temporary bypass? Those need different records and reminders.
- What evidence establishes “reviewed” for agent-operated work: an eligible GitHub approval, a trusted review check, a human decision, or an explicitly chosen combination?
- Who owns settings currently managed by another App or infrastructure tool, and how can a new mechanism avoid competing writers?
- How will documentation drift, preview changes, and tool-schema lag invalidate catalog claims and qualification evidence?
