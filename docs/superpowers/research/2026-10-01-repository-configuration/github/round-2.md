## Copilot approval confidence and security limits

The feature-specific [configuration source](https://github.com/github/docs/blob/10844e10c034b5e5d9b62793c3af9feb4b91de07/content/copilot/how-tos/copilot-on-github/set-up-copilot/configure-code-review.md) describes separate controls for submitting approving reviews and counting them toward merge requirements, with optional changed-file globs. The [usage source](https://github.com/github/docs/blob/10844e10c034b5e5d9b62793c3af9feb4b91de07/content/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review.md) says approvals are off by default and distinguishes a review's approval assessment from an approving review. The linked [notice](https://github.com/github/docs/blob/10844e10c034b5e5d9b62793c3af9feb4b91de07/data/reusables/copilot/automatic-approvals-public-preview.md) marks approvals as public preview.

The same revision's [generic review tips](https://github.com/github/docs/blob/10844e10c034b5e5d9b62793c3af9feb4b91de07/data/reusables/repositories/request-changes-tips.md), included by the required-review article, say that Copilot reviews do not count toward those requirements. The retrieved [Copilot usage page](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review#pull-request-approvals-from-copilot) and [required-review page](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews) reproduce the discrepancy. Calling the generic passage stale is a plausible explanation, but I have no authoritative resolution and do not adopt it as fact.

Confidence is high that GitHub publishes conflicting claims and documents a preview path. There is no observed evidence here that Provingkit has that path enabled or eligible, that the intended actor can satisfy it, or that GitHub counts the resulting review on the intended change. A design may preserve the option for later qualification; it must not use it to promise a working sole-maintainer approval gate. Feature-document visibility and template version conditions do not establish an account's entitlement or rollout state.

The unattributed-Copilot extra-approval option is a separate preview rule. The [rules source](https://github.com/github/docs/blob/10844e10c034b5e5d9b62793c3af9feb4b91de07/content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets.md#L133) says it has no effect when zero approvals are required. Thus O1's observed enabled option does not, under that documented condition, establish an additional approval requirement. Nor does the Actions-token approval toggle answer whether a different App's review counts. Keep the controls and actor identities distinct.

Approval counting is also separate from review independence and quality. The Copilot usage source says review instructions and skills come from the PR's head branch. **Inference:** an agent-review policy must consider contributor-controlled review inputs before treating a counted review as independent scrutiny. This is a trust-boundary question, not a demonstrated exploit or evidence that Copilot ignores other safeguards. No arbitrary agent's review inherits Copilot's product-specific approval semantics.

A later authorized qualification would bind the owner/product/entitlement, controlling settings, author and reviewer identities, changed-file scope, and reviewed revision; observe the actual required-approval count with other gates satisfied; then check a new push. No such experiment is authorized or completed in this report.

## Questions to carry into the maps

The coordinator should retain the documented conflict and check-coverage question as unresolved findings, not turn them into selected settings. The following questions are precise enough to distinguish designs without prescribing one:

1. **First useful capability:** must the local alpha explain existing state, recommend a concrete change, apply an authorized change, or reconcile continuing drift? Which repository owner/product/actor contexts must it support? Select those claims before choosing implementation or qualification costs.
2. **Conflicting evidence:** what must an answer do when first-party sources disagree? Use the Copilot case to compare whether designs retain both claims, their product/source identities, target uncertainty, and the smallest useful next observation without pretending the conflict is resolved.
3. **Coverage:** how will the design connect a selected behavior requirement to its check, producer, workflow path, revision, event, and actual acceptance decision? Use the source-boundary/Proseweaving/projection case to test whether a broad title or structural assertion creates false confidence.
4. **Choice and authority:** which accepted policy can restrict an arbitrary user configuration, and who decides what active harm means? Test a legitimate freeze, a deliberately unconventional choice, and an accidental unavailable-reviewer gate under separately supplied purposes.
5. **Reuse and ownership:** can the equipment consume an existing reviewed procedure, such as the DCO runbook identified by H1, while preserving the consumer's local policy and avoiding a second writer? Compare interfaces before relocating ownership or imposing one general configuration manager.
6. **Freshness:** which recommendation must be reconsidered when a platform preview changes, an upstream procedure is corrected, or target settings drift? These are different dependency changes; a universal refresh interval or blanket invalidation is not selected.
7. **Completion:** what evidence will show the selected equipment's maintained source, current review, supported behavior, publication, local alpha deployment, and actual harness invocation? Keep local invocation separate from any hosted enforcement claim; each needs its own evidence when included in the alpha's scope.
