# Repository configuration history: independent first round

The retained evidence contradicts a simple “Sacrysty and Codiquary were configured, Provingkit was not” account. All three received deliberate repository controls. Sacrysty and Codiquary share a scaffold and a subsequent security-controls rollout; Provingkit was provisioned during a source-and-history extraction, with controls tailored to preserving evidence and blocking premature releases. The useful research question is which differences remain intentional, which have lost their rationale, and which need reconsideration for each repository.

This is historical research and a bounded present-state comparison, not a selected repository policy, security qualification, or authorization to change settings. I used `research` and the read-only baseline branch of `checkpointing-and-publishing-git-work`.

## Creation and configuration sequence

### Codiquary: a governed release-operations scaffold

The repository was created on September 3, 2026, at 22:43:58 UTC, under the earlier `release-ops` identity. The controlling provisioning issue expressly required Apache-2.0 licensing, governance, DCO/contribution policy, security reporting, CI, release metadata, source layout, a provenance handoff, and a native implementation map. It explicitly excluded production keys, credentials, providers, host bindings, and releases. Its closeout identifies scaffold commit `ab85201b936c43363b1cd13f35e6ce77403d74d8`, a no-bypass all-tag freeze, and a no-bypass main rule requiring PRs, resolved conversations, strict base freshness, and four policy checks. [Provisioning issue and closeout](https://github.com/nisavid/dotfiles/issues/261#issuecomment-5533265783), [immutable scaffold](https://github.com/nisavid/codiquary/tree/ab85201b936c43363b1cd13f35e6ce77403d74d8).

That first commit contains `CONTRIBUTING.md`, `GOVERNANCE.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CODEOWNERS`, a PR template, Dependabot, Conventional Commit, DCO, dependency-review, and repository-policy workflows, local hooks, and `scripts/check-repository.sh`. It is affirmative evidence of a methodical scaffold, not proof that every GitHub setting was audited. Its provenance document assigns reusable public source and releases to the product repository and private bindings, protected state, production ceremonies, and acceptance evidence to the system user. [Initial tree](https://github.com/nisavid/codiquary/tree/ab85201b936c43363b1cd13f35e6ce77403d74d8), [ownership handoff](https://github.com/nisavid/codiquary/blob/ab85201b936c43363b1cd13f35e6ce77403d74d8/docs/provenance/reusable-release-trust-handoff.md).

The root source later adopted the Codiquary identity. The historical `release-ops` URLs and initial names remain provenance; they are not separate current owners. [Naming commit](https://github.com/nisavid/codiquary/commit/0646eaf7612a3225c171c5fadb836b35f714389e).

### Both products: a separate, tested hardening increment

Sacrysty #8 and Codiquary #12 then owned a distinct security-and-quality rollout. Their accepted scope selected CodeQL for Rust and Actions, weekly analysis, formatting/Clippy/build/test/rustdoc checks on Linux x86_64 GNU and macOS Apple Silicon, Cargo and Actions Dependabot updates, restricted Actions sources, full-SHA enforcement, read-only workflow tokens, approval for external contributor workflows, linear history, and required observed checks. [Sacrysty contract](https://github.com/nisavid/sacrysty/issues/8), [Codiquary contract](https://github.com/nisavid/codiquary/issues/12), [Sacrysty source commit](https://github.com/nisavid/sacrysty/commit/a96c715ebc593999fe9f0f5a0b0a94e453826178), [Codiquary source commit](https://github.com/nisavid/codiquary/commit/8320be34bff8269e66566e6083f5ce1030a3908f).

The rationale for an important permissive choice is explicit: avoid an impossible solo-maintainer approval gate; do not require human approval while `nisavid` is the sole collaborator; do not turn a quota-dependent review service into a merge gate. Paid products and new third-party services were outside that increment. The contracts preserve CodeRabbit, Greptile, and advisory Copilot review without selecting those services as required approvals. These are recorded historical choices, not a fresh recommendation that every repository should copy them. [Sacrysty acceptance contract](https://github.com/nisavid/sacrysty/issues/8), [Codiquary acceptance contract](https://github.com/nisavid/codiquary/issues/12).

The closeouts retain useful practical evidence: the CodeQL action allowlist initially failed because a parent action pattern did not match sub-actions; the correction named `init` and `analyze`. Required CodeQL enforcement waited for same-repository, Dependabot, and approved external-fork observations. A harmless note-level alert then produced a reported merge blocker, although an unresolved conversation was also a blocker, so the experiment did not establish CodeQL as the sole cause. The closeouts explicitly leave additional broader audit proposals undecided. [Sacrysty completion](https://github.com/nisavid/sacrysty/issues/8#issuecomment-5574014764), [Codiquary progress and completion](https://github.com/nisavid/codiquary/issues/12#issuecomment-5572331432), [Codiquary final enforcement receipt](https://github.com/nisavid/codiquary/issues/12#issuecomment-5574016358).

## Retained procedure and the DCO correction

The clearest maintained repository-configuration procedure found is Sacrysty's `docs/agents/dco-provisioning.md`. It covers provision, verification, migration, recovery, and rollback for the DCO GitHub App. It names itself as Sacrysty-owned and adaptable by other repositories, explicitly declining to create a global convention. The final merged procedure's SHA-256 is `2dbcb4b4d3c8ee545dcff4e22c87ada051ff923df462aec6f8c7fab5b5a9c1b6`. Its bytes match the file observed at the live Sacrysty default-branch revision during this research. [Reviewed merged procedure](https://github.com/nisavid/sacrysty/blob/3dd23c4f53da47f83bdf7a82cc98094a4f574501/docs/agents/dco-provisioning.md).

The decision record explains the correction: the copied custom checker required exact, case-sensitive author signoff and mishandled Bot-associated contributions. The maintained app preserves the human certification goal while accepting ordinary bot updates. It documents bot/merge exemptions, case-insensitive independent author-or-committer field matching, default remediation restrictions, and the explicit manual-approval exception. DCO certifies contribution rights; it does not cryptographically authenticate a release or pusher. The app-bound check changes from `DCO compliance`/GitHub Actions `15368` to `DCO`/app `1861`. [Sacrysty ADR](https://github.com/nisavid/sacrysty/blob/3dd23c4f53da47f83bdf7a82cc98094a4f574501/docs/adr/0003-maintained-dco-github-app.md), [Codiquary control contract](https://github.com/nisavid/codiquary/blob/3720499e03334352560071e0c1ea60d3c3e5c4db/docs/repository-controls/dco.md).

This is also an existing owner/consumer seam worth preserving. Sacrysty maintained and reviewed the procedure; Codiquary required an immutable revision and review receipt, recorded its invocation, and later renewed that binding for the corrected merged procedure. Codiquary's control page owns its local policy and allowed delta rather than duplicating the shared runbook. The migration retained the original bot PR, qualified signed/unsigned human and Bot behavior at stated layers, compared full before/after rules, and changed only the check identity. [Initial consumer invocation](https://github.com/nisavid/codiquary/issues/40#issuecomment-5694925951), [applied-rules receipt](https://github.com/nisavid/codiquary/issues/40#issuecomment-5707523713), [completed recovery](https://github.com/nisavid/codiquary/issues/40#issuecomment-5708013257).

Codiquary also consumed Provingkit Versionkeeping's destination commit-policy procedure during the migration. Generic Git publication equipment already owns discovery of destination DCO requirements; a future repository-configuration component should integrate with that responsibility instead of silently creating a second commit-policy authority. [Consumption receipt](https://github.com/nisavid/codiquary/issues/40#issuecomment-5707523713), [immutable Versionkeeping procedure](https://github.com/nisavid/provingkit/blob/af38d9d27ce6416a9ba5be13d4e638fdcc919ecd/plugins/versionkeeping/skills/checkpointing-and-publishing-git-work/references/commit-policy.md).

## What is retained, what is missing, and useful next questions

Retained evidence includes scaffold contracts and receipts, explicit scaffold lineage, immutable workflow changes, a tested security-controls rollout, a detailed DCO ADR and runbook, consumer invocation receipts, and a substantial Provingkit cutover evidence record. I did not find a single maintained, general repository-configuration procedure covering all three, a complete settings-to-rationale catalog, or a decision receipt for every present Provingkit difference within the scoped sources. That is a bounded search result, not proof that no older artifact exists.

The following questions are candidates for a future Wayfinder map, not decisions made here:

1. Which settings are repository-specific preferences, which protect a documented invariant, and which can become impossible or harmful under a particular collaborator/automation model? Preserve the historical solo-maintainer rationale as an example to investigate, not a universal default.
2. Should the reusable equipment own discovery, recommendations, actuation, and verification as separate operations, while repository-owned policy remains authoritative? The existing DCO runbook/consumer binding and Versionkeeping destination-policy discovery provide concrete seams.
3. What must a catalog entry bind: purpose, supported values, prerequisites, effects on contribution paths and release paths, owner, inherited policy sources, verified API/UI observation, qualification evidence, and rationale? The DCO migration shows why a check's display name alone is insufficient.
4. Which Provingkit differences are intentional today: conversation resolution, DCO, Actions allowlisting/SHA enforcement, code scanning, dependency updates, and merge-history shape? Assess each against its actual Python/plugin workflow and users rather than copying Rust-specific checks.
5. What qualifies a settings change without over-testing? The hardening rollout and DCO migration supply positive/negative, source/hosted, same-repository/fork, inherited-config, rollback, and before/after comparison examples, each with deliberately limited claims.
6. Where should brief discovery guidance and the detailed evidence/rationale catalog live, and who maintains downstream invocation? Do not duplicate Sacrysty's current DCO procedure before deciding whether it remains the owner or should transfer ownership.

No repository, tracker, settings, installed equipment, or Git refs were changed. The report and value-free evidence files are the only outputs of this lane.
