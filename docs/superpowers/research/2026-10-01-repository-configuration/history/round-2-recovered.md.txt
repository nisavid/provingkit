# Repository configuration history: cross-examination

The shared evidence supports adaptable configuration equipment, but it does not establish a universal Sacrysty/Codiquary baseline or select a catalog architecture. All three repositories were deliberately configured. Their settings reflect different work, and some present differences still lack a recovered rationale. The design panel should preserve those distinctions while choosing how to reach a locally deployed alpha.

That is an authorized reuse decision for Sacrysty, not an organization-wide template or permission for later agents to reproduce every setting elsewhere. ## Corrections and stronger evidence

**DCO terminology.** My first report used the historical shorthand “signed/unsigned human” in discussing DCO fixtures. Read that strictly as commits **with or without the required `Signed-off-by` trailer**. I did not verify cryptographic commit signatures. Versionkeeping's maintained policy expressly separates DCO attestation, cryptographic signing, license compliance, review, and release authority. Future equipment should keep those names distinct at the point of use. [Destination commit policy](https://github.com/nisavid/provingkit/blob/02812cdee184023ecc06214e263c308d9131a1b0/plugins/versionkeeping/skills/checkpointing-and-publishing-git-work/references/commit-policy.md).

**Actions admission versus source practice.** Provingkit's repository setting permits all actions and does not mandate SHA pins, but its observed source workflow pins all three action repositories it invokes, requests `contents: read`, and disables checkout credential persistence. The comparison supports asking whether future changes should be constrained by repository policy. It does not support saying the present workflow is unpinned or broadly write-enabled. Full action pins also leave separately downloaded Python packages and their dependency resolution as distinct inputs. [Workflow at the observed revision](https://github.com/nisavid/provingkit/blob/02812cdee184023ecc06214e263c308d9131a1b0/.github/workflows/provingkit-source.yml).

## Historical cases that should challenge the design proposals

The DCO procedure is stronger evidence for selective qualification than for any particular catalog architecture. It explicitly avoids reproducing every upstream parser and membership fixture as a hosted PR. It retains a bounded hosted missing-signoff failure, real positive cases, effective-configuration reads, installation permissions, and full rules comparisons. It distinguishes a fresh conclusive absence read from a semantic configuration change when deciding what must be repeated. The platform lane's ten proposed qualification cases are therefore a menu to scope against a claim, not an automatic acceptance checklist for each repository or alpha release. [Reviewed DCO procedure](https://github.com/nisavid/sacrysty/blob/3dd23c4f53da47f83bdf7a82cc98094a4f574501/docs/agents/dco-provisioning.md).

That procedure also supplies two concrete counterexamples for all three conceptual representations:

- A successful check from the expected App can represent manual approval rather than ordinary evaluation. Its output distinguishes those cases. A recommendation that consumes only `success` loses the intended evidence claim.
- Restoring old settings is insufficient rollback when source and contributor guidance describe the new behavior. The prescribed rollback restores the checker, workflow, executable-file policy, and affected current documentation before switching the gate; it preserves historical receipts and other repositories' App selection.

These are documented operation contracts, not a claim that the rollback was executed in this research. The generic lesson is to represent enough context to explain the promised behavior; it is not to impose DCO's exact output strings or rollback sequence on unrelated integrations. [Ordinary result and rollback contract](https://github.com/nisavid/sacrysty/blob/3dd23c4f53da47f83bdf7a82cc98094a4f574501/docs/agents/dco-provisioning.md).

Likewise, the CodeQL rollout's negative fixture had both an alert blocker and an unresolved-conversation blocker. Its receipt explicitly declines to attribute rejection solely to CodeQL. A behavior-first proposal must preserve that causal limit; a relationship model must not turn the observation into proof that either independent path is sufficient; a casebook must not compress away the caveat. [Qualified enforcement receipt](https://github.com/nisavid/codiquary/issues/12#issuecomment-5574016358).

Finally, historical completion does not authorize continuing configuration reconciliation. The DCO source owner, shared App-installation owner, and Codiquary settings owner coordinated one bounded migration. The consumer bound an immutable procedure and renewed its binding after correction. This supports testing explicit ownership and revision consumption. It does not establish that future equipment must be one Skill, one Plugin, a continuously running reconciler, or a separate actuator. [Consumer invocation](https://github.com/nisavid/codiquary/issues/40#issuecomment-5694925951), [local rules ownership and applied delta](https://github.com/nisavid/codiquary/issues/40#issuecomment-5707523713).

## Remaining disagreement and exact map questions

No unresolved factual contradiction remains among the historical claims examined here. The genuine open methodological difference is priority: the conceptual lane tentatively expects a casebook to suffice and proposes comparing it with sparse relations; the platform lane's field and relation list points toward more explicit structure. I withhold either preference. Successful use of one detailed prose procedure establishes neither broad retrieval reliability nor an advantage for structured relationships. Compare the alternatives on the same relevant cases and count unnecessary work as well as missed dependencies. This does not select the architecture or require a solver.

The history leaves the reason for several Provingkit settings unrecovered. “Unrecovered” is neither accidental nor approved-by-default. It calls for a current scoped decision, informed by the present source and users. These questions can enter the design and implementation maps without predetermining their answers:

1. **What first alpha behavior will be demonstrated locally?** Select supported creation/advice/assessment/application behavior and its repository, platform, actor, and policy inputs; keep unrelated capabilities outside its completion claim.
2. **What counts as binding policy for each recommendation?** Require an identified applicable source, and distinguish a repository precedent, an adopted local rule, a user preference, and an unresolved potential harm. Which choices need stakeholder adjudication rather than an invented prohibition?
3. **How will competing representations preserve the historical counterexamples?** Compare manual versus evaluated DCO success, overlapping CI coverage, incomplete causal attribution, effective-configuration changes, and source-plus-settings rollback without favoring one storage shape in the scoring.
4. **What owns each managed surface and existing procedure?** Decide whether the current Sacrysty DCO owner and Versionkeeping destination-policy owner remain consumers/producers or transfer responsibility. Who can change desired state when another App or infrastructure tool already owns it?
5. **What is the smallest sufficient qualification for the selected claim?** Name which evidence is documentary, constructed, source-executed, hosted, and locally deployed; what invalidates it; and which cases justify an actual external fixture. Do not inherit every old canary as a universal gate.
6. **Which Provingkit omissions need a current decision?** Investigate the two absent required job names and the differing contribution/Actions/review controls against current behavior and policy. Preserve optional recommendations unless a binding requirement or evidenced harm changes their status.
7. **Before design closes, what exact implementation route reaches local alpha?** Populate source ownership, chosen interfaces and supported contexts, review/evaluation, publication, local deployment, verified invocation, recovery, and downstream consumption in the implementation map. The map plans those actions; this research increment does not execute them.

No new live-platform behavior was exercised. I did not repeat the full historical scan, inspect audit logs, or infer the unidentified reason for a setting from its present value. Only this follow-up and value-free evidence files were written; the independent first report remains frozen.
