# Simpler messaging routes for existing Codex and Claude chats

**Keep the current Intercom qualification moving. For Claude → Codex, `codex queue` is a promising candidate for messages that can wait for a turn boundary, subject to owner binding and preserving the authority of peer content. The existing owner-admission experiment remains a prepared candidate for active-turn delivery.** The public Codex `ExternalMessage` interface is a credible alternative where the actual owner’s App Server is reachable. For Codex → Claude, the documented Claude Code inbox socket could remove the per-send MCP child, but the target Desktop session and the receipt contract still need to be established.

## Existing catalog coverage

These are already recorded candidates. The [published coordination catalog](https://github.com/nisavid/provingkit/blob/caf455bcbc23a34f20c558d74135f38c3915f224/docs/coordination/catalog.json) contains `codex-queue`, `codex-shared-queue-backend`, `codex-external-message`, `claude-message-entrances`, and the separate `claude-message-entrances-claude-inbox-socket` entry and profiles. It already distinguishes queue admission from consumption, shared storage from an actual owner binding, and the inbox socket from the MCP entrance. The socket’s external contract and receiver readback remain gaps.

This investigation refreshes source pins and compares these existing candidates against the current Intercom work. The Intercom owner should reconcile its evidence with the maintained source register, research pointers, and catalog entries, preserving their unqualified status until the actual receiver association and outcome evidence exist. No duplicate fabric or new live-qualification claim follows from this refresh.

## Codex → existing Claude Desktop chat

**Keep native `SendMessage` through the current Intercom sender as the reference path.** At the baseline, the sender launches a nominated MCP child, negotiates the `SendMessage` tool, writes at most one call, and retains submission and child closure separately. There is affirmative same-chat receipt and handling for one message. The MCP shutdown timeout remains part of that result. [Pinned Claude sender contract](https://github.com/nisavid/provingkit/blob/a4f2976e2dafc816d79219a04efb19eb80dfca1e/plugins/surreal-intercom/skills/communicating-with-agents/references/claude-mcp-sender.md#closure-and-reconciliation) · [Claude receiver evidence](https://github.com/nisavid/provingkit/issues/851)

**Shortlist Claude Code’s documented inbox socket as a possible replacement for the MCP child.** Anthropic documents posting from scripts or hooks to a per-session socket. Generic cross-session messages arrive between tool calls or start an idle turn; inbound policy may deliver, hold, or refuse them. Desktop’s separate **Work across sessions** interface waits for the current task. Those contracts do not establish direct external-write behavior for the nominated Desktop chat. Same-OS-user access identifies neither the sender nor its authority. The receiving session’s version, exact endpoint, posting shape, and receipt meaning still need binding. [Inbox socket and delivery](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket) · [Desktop interface](https://code.claude.com/docs/en/desktop#work-across-sessions)

Removing the child could avoid startup, negotiation, and shutdown costs. A successful socket write would still leave receipt and handling to establish. Claude Code Channels need a channel-enabled session and a channel process; the first-party terminal setup does not establish a smaller route to this existing Desktop peer. ## Observation and new sessions

- **Observe completion separately from delivery.** For an accessible Codex App Server, a correlated input item and the terminal `turn/completed` status can narrow the result. A turn may have other inputs, and terminal status alone leaves the peer obligation open. Claude Code’s `notify_when_idle` is a one-shot Claude-session notice of idle or exit, subject to inbound policy on both sides. A Claude `Stop` hook can report normal completion, with separate behavior for API errors and user interruption. Desktop OS notifications are useful for a human check. None of these supplies a durable cross-harness reply by itself. A receiver-authored acknowledgment or result tied to the original correlation remains the lowest-assumption observation. [Codex App Server events](https://learn.chatgpt.com/docs/app-server#events) · [Claude idle notice](https://code.claude.com/docs/en/cross-session-messaging#get-a-notice-when-another-session-goes-idle) · [Claude Stop hook](https://code.claude.com/docs/en/hooks#stop) · [Claude Desktop notifications](https://code.claude.com/docs/en/desktop#get-notified-when-a-session-finishes)
- **Keep new CLI and SDK sessions in their own profile.** Codex App Server/SDK and Claude Agent SDK provide structured I/O for sessions the application owns. Claude streaming input explicitly queues multiple messages for sequential processing. Resuming saved history through a new process does not prove attachment to the running Desktop owner, preservation of its pending work, or normal GUI composer behavior. Codex’s documented composer Queue and Steer controls and the first-party remote UIs are useful assisted controls. They require a user/client action and do not supply the cross-harness sender contract.
