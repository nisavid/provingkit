### Desktop and native peer routes

Desktop's documented tab surface lists and reads app-run local, SSH, and WSL Code sessions. It excludes cloud, terminal, and VS Code sessions; defaults to 20 recent nonarchived sessions; attributes messages to the sender; allows replies; and waits for current work to finish before a busy recipient reads a message. Archived or unattended scheduled sessions are ineligible. Creation is separately available through the UI and suggested task chips. No externally callable Desktop tab-tool endpoint was established. This is a **partial existing-Desktop candidate**, not proof that another harness can invoke those tools. [Desktop session documentation](https://code.claude.com/docs/en/desktop#work-across-sessions)

Native peer messaging is a different **partial existing-task candidate**. The current reference documents local socket/named-pipe transport, idle wake, busy delivery between tool calls, and accept/hold/refuse admission. Held means undelivered; refusal drops the message. Messages retain peer attribution and cannot supply operator consent. Cloud and other-machine discovery requires a Remote Control connection with eligible claude.ai authentication; a cross-machine send without a return connection can be one-way. An idle subscription is a state notice, not acknowledgment of content. Bare sessions have no inbox. These conditions require actual route proof after any quota reset. [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)

The external MCP route remains attractive because its caller can invoke tools without first asking a new model turn to compose the send. The current MCP reference documents `claude mcp serve` as a stdio tool server and assigns confirmation to its client. The **historical schema** observation at Code 2.1.280 and 2.1.283 exposed `ListAgents` and `SendMessage`, including `to`, `message`, optional `summary`, and `notify_when_idle`; it also warned that sender success is not receiver reading. Current 2.1.296 peer-tool exposure was not exercised because server activation is excluded here. [MCP server contract](https://code.claude.com/docs/en/mcp#use-claude-code-as-an-mcp-server), [dated sender findings](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md)

The socket documentation supplies address/token and admission guidance but did not establish a complete externally supported message/response contract in this pass. A raw socket adapter therefore remains **partial and less supported than the native MCP candidate**. The retained September notification and acknowledgment establish one historical Codex-to-Desktop outcome only. Neither that task nor its address is a current fixture. [Dated research](https://github.com/nisavid/provingkit/blob/c7f12ec05c1af911d186ac0854e522a78667d380/docs/superpowers/research/2026-09-25-directed-inter-harness-coordination.md)

### Cloud callers and user-role input

The documented external command `claude -p MESSAGE --cloud SESSION_ID --output-format json` queues a follow-up and exits without waiting for a reply. It accepts a session ID or URL, requires appropriate Anthropic account authentication and organization policy, and returns `{ok, session_id, url}` on success. Some configuration failures go to stderr without JSON. This supports a **partial exact-reference continuation candidate** for either task population, with ownership consent handled separately. The task-description form creates a cloud session. The web UI supplies progress, conversation, and diff views, but automated receiver readback is a separate choice. `--teleport` produces a local continuation whose later work does not appear in the original cloud session, so it is unsuitable as transparent continuation of that cloud executor. [Cloud controls](https://code.claude.com/docs/en/claude-code-on-the-web)

Do not label ordinary CLI, UI, or SDK prompt injection as native peer delivery without origin evidence. The SDK's `SDKUserMessage` is explicitly user-role input. Its origin union also contains peer and channel variants; the peer declaration describes host-declared mode and sender-asserted navigation/reply fields, while `verifiedPeerPid` identifies the connecting process, potentially a relay. Those declarations are useful evidence design inputs, not proof that an arbitrary external caller can mint trustworthy peer provenance. [Versioned SDK declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz)

### SDK browser and worker interfaces

The **source-examined browser export** is the strongest new remote-inspection lead in this pass. `SSEOptions` takes a session ID, stream URL, send URL, headers, and resume cursor. It declares `onDeliveryUpdate`, `getCcrEvent`, `getSseLastSequenceNum`, and dropped-frame counters. Delivery updates distinguish worker receipt, processing, and processed; updates themselves are not replayed on reconnect. Durable event envelopes have an event ID and sequence number, with source when supplied. Selected implementation passages confirm an SSE GET, POST of session events, delivery-update parsing, and envelope storage separate from the message payload. A transport or worker progress label still does not establish the requested work's semantic completion. [Versioned SDK distribution](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz)

This browser `query()` uses remote transports and streams input; it is distinct from spawning a new local SDK query. It is nevertheless an active client, with initialization/control machinery, not a proven passive observer. The source does not establish this account's accepted credentials, required client headers, supported third-party caller status, exact Desktop-to-remote identity mapping, or concurrent-client effects. Assess those before any live proposal. Legacy WebSocket remains listed alongside preferred SSE; its declaration lacks the SSE envelope/cursor helpers.

The **source-examined bridge export** serves the worker side. `createCodeSession` creates a remote session using caller-supplied OAuth credentials. `fetchRemoteCredentials` registers the worker and advances its epoch; `attachBridgeSession` uses worker credentials and can register when no epoch is supplied. The API is alpha with independent stability expectations. This is **partial for a deliberately owned worker lifecycle and unsuitable as a passive existing-Desktop attachment**. An epoch-changing call risks affecting the current worker; any such proposal requires explicit ownership and interruption scope. No bridge credential request was made. [Versioned bridge declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz)

The main SDK remains **partial for controller-owned execution**. `query()`, streamed input, result messages, resume by ID, and fork support that population; a fork creates a new identity, and history does not preserve filesystem state. Session readers inspect stored transcripts. None of those facts establishes attachment to Desktop's already-held query. The former TypeScript V2 session API was removed at 0.3.142, so it is an **unsuitable current API candidate**. [SDK session contract](https://code.claude.com/docs/en/agent-sdk/sessions)

`resolveSettings` in 0.3.296 describes what a prospective query would see from the settings cascade. Its own declaration excludes the policy-helper execution and distinguishes the raw cascade from trust decisions. It cannot replace a sample of the selected task's complete effective permissions. Initialization getters and current query-control getters also have different freshness and effect boundaries. The retained Desktop source conclusions must be reassessed field by field, not dismissed because a newer SDK export exists. [Versioned SDK declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz)
