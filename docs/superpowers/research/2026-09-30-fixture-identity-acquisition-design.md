# Acquire a disposable fixture identity after persistence

## Recommendation

Adopt a disabled-by-default acquisition mode that starts with the candidate launch, observes one normal new-local-task creation and its qualifying metadata write, and emits an immutable writer-witness receipt. That receipt remains provisional. Acquisition becomes accepted only when the same process validates the selected metadata and final observer configuration, synchronously closes the selection guard, and publishes a distinct terminal admission record.

This removes the circular requirement to know the task and Code session IDs before candidate launch while preserving two full launch cycles: one candidate launch and one restored-original launch. It does not claim that this duration or the proposed admission-decision deadline has been measured.

This is source design for [Design the fixture-identity acquisition receipt](https://github.com/nisavid/provingkit/issues/352). Adoption remains with [Decide whether to incorporate the fixture-identity receipt](https://github.com/nisavid/provingkit/issues/353). Implementation and review belong to [Prepare and review the disposable observer probe](https://github.com/nisavid/provingkit/issues/278); live authority remains with [Authorize the disposable Desktop observer probe](https://github.com/nisavid/provingkit/issues/279) and execution with [Run the disposable observer probe and restore Desktop](https://github.com/nisavid/provingkit/issues/280).

## Claim and boundary

A valid terminal admission establishes only that:

- one candidate process used one reviewed acquisition configuration;
- one bound manager instance registered one eligible new local record during the open selection interval;
- the record satisfied the observed manager-entry discriminator, including `initiator: "user"`;
- the record, manager, registration generation, profile, account, organization, project, effective user-data root, and account-transition epoch remained bound through the qualifying writer operation;
- the actual writer helper fulfilled for a serialized projection containing the selected task ID, Code session ID, and project path;
- the same acquisition sidecar later acquired the one derived metadata file through the bounded exact-file contract, retained only the approved projection, and matched it with the selected record;
- the sidecar validated the immutable final observer configuration, closed the selection guard, and published terminal admission before continuing into the observer.

`initiator: "user"` proves only that the observed manager-entry discriminator matched. The inspected source does not establish that every caller was exhaustively excluded or that this value authenticates a click or human intent. Live evidence must separately show creation through the normal new-local-task UI.

The writer-witness receipt proves historic writer fulfillment, not accepted acquisition and not the continued contents of the metadata file. Receipt-only consumers must not construct authority from it or treat it as an accepted fixture. Only a valid admission record with state `accepted` can support post-acquisition publication and observer continuation.

The design does not establish current account use by a query, current model or permission state, runtime cwd, native-address binding, creation of a fresh query, prompt delivery or completion, acknowledgment, universal write atomicity, historical metadata bytes, or crash durability. It does not defend against a compromised Desktop, renderer, or hostile process running as the selected UID.

Identity discovery performs no task, session, transcript, settings, metadata-directory, or project-directory scan. This does not prohibit the approved nonrecursive emptiness check of the dedicated project, the exact selected metadata reads, or bounded enumeration of task-owned output directories.

## Profile and project binding

`profileBinding` has exactly `kind`, `name`, `configDirectory`, and `expectedUserDataRoot`. Each directory object has exactly `path`, `device`, `inode`, `uid`, `gid`, and `mode`. The populated values remain private and do not appear in this artifact.

At readiness, registration, every writer boundary, receipt validation, metadata acquisition, and final admission, the sidecar must:

- open the configured profile and expected user-data directories without following the final component;
- require same-UID directories that are not group- or world-writable;
- compare path, device, inode, UID, GID, and mode;
- require the path still names the opened identity;
- require the manager’s effective `userDataPath`, after exact realpath resolution, to equal `expectedUserDataRoot.path` and its opened identity;
- require the configured project realpath and opened path, device, inode, UID, GID, and mode to remain equal, require ownership by the selected UID, and reject group- or world-writable mode.

The initial project binding before candidate launch applies the same selected-UID ownership and nonwritability requirements. Every later project boundary listed above rechecks both those permissions and the bound identity.

The selected UID is the trust boundary. Profile names, launcher paths, and configuration-directory names are not substitutes for the opened user-data identity. `CLAUDE_USER_DATA_DIR` presence and unresolved third-party relocation remain stops.

## Acquisition lifecycle and selection

The candidate launch receives only `PROVINGKIT_ACQUISITION_CONFIG`. The evolved loader validates that path and configuration, inserts the manager into its one-shot guard once, installs the hooks, arms one manager instance, and publishes readiness. It neither reads nor attempts the final observer configuration before a writer witness exists.

The state machine is:

`initializing → ready → registered → writer-witnessed → validating → guard-closed → admitted`

Any state before `guard-closed` may instead enter `rejected`. `admitted` and `rejected` are terminal. A publication failure may leave no terminal record. There is no retry, second manager, second fixture, second receipt, or second observer start.

The acquisition coordinator owns the writer and account-transition hooks from installation until an explicit successful transfer to the observer adapter. Rejection, readiness or receipt failure, accepted-admission publication failure, post-acquisition publication failure, and any preliminary continuation failure before transfer require the coordinator to remove all acquisition hooks exactly once. Ownership transfer and disposal are serialized so no terminal path can leave the hooks ownerless or dispose them twice.

At `startSession(e,r)` entry, a correlation token is created only when:

1. `r.initiator === "user"`;
2. `r.prewarmHidden`, `r.remoteControl`, `r.dispatchParentId`, `r.origin`, and `r.sideSessionAuthorized` are absent;
3. `e.scheduledTaskId`, `e.sshConfig`, `e.wslConfig`, and the entire `e.spawnedFrom` field are absent;
4. `e.cwd` matches the bound project identity;
5. the manager is the armed manager.

These predicates establish only the observed manager-entry discriminator. They do not prove that `LocalSessions.start` was the exclusive caller. Normal new-local-task UI origin remains a separate required live-provenance observation.

A supplied new `e.sessionId` is allowed. The manager’s existing collision and parked-ID checks still apply.

Backend selection occurs later. At the call to `createOrResumeSession`, the token qualifies only if the exact same `e` object arrived, the selected backend is local, the existing and held-first-start branches were not selected, and the new branch registers the exact record object. Resumed, reused, parked, forked, scheduled, SSH, WSL, remote-control, prewarm, dispatched, and auto-continuation routes are rejected. Unknown optional fields are not interpreted as safe discriminators.

Registration assigns a monotonically increasing `registrationGeneration` for the armed manager. The first eligible registration after readiness becomes provisional, binds the exact task ID, and records `codeSessionId` as pending. The first qualifying serialized projection containing a valid `cliSessionId` may bind that Code session ID exactly once to the exact selected record object and registration generation. A second eligible registration before guard closure synchronously changes the state to `rejected` with reason `ambiguous-registration`.

An `accountTransitionEpoch` starts at zero. Hooks on both `onAccountOrgChanged` and `onAccountResolved` increment it synchronously before either path changes account or organization state or begins an await. This detects a change away and back. The epoch, current account ID, and current organization ID must match their registered values at every later boundary. Complete coverage of both hooks and their exceptional exits is an implementation gate.

All registration, writer, transition, configuration, metadata-read completion, timeout, and handoff events enter one coordinator. Before and after every acquisition-side await, the coordinator compares:

- exact manager object and manager nonce;
- exact record object;
- registration generation;
- task ID and the phase-appropriate pending or bound Code session identity;
- derived metadata path;
- effective user-data root and profile identity;
- project identity;
- account and organization IDs;
- account-transition epoch;
- current acquisition state.

Before binding, comparisons require `codeSessionId` to remain pending and do not demand a Code session field from a record, projection, configuration, or signal that cannot contain it in that phase. After binding, absence, clearing, replacement, or change of the Code session ID at every writer, metadata, configuration, and admission boundary rejects the run. Any other mismatch also rejects the run. Relevant writer operations in progress are counted; admission cannot close the guard while one is in flight.

At final admission, the coordinator handles the completed final metadata read in one synchronous turn. It revalidates every predicate, including the exact manager and record references, registration generation, account-transition epoch, and bound identity, and requires no relevant operation in flight. The timeout event and this admission-authorization event contend exactly once in the serialized coordinator state machine. If timeout wins, the coordinator enters `rejected`; no accepted admission may be published and no observer continuation may begin. If authorization wins, its monotonic timestamp must be at least `readyAtMonotonicMs` and strictly less than `readyAtMonotonicMs + admissionDecisionDeadlineMs`; the coordinator changes `validating` to `guard-closed`, freezes the immutable accepted-admission decision and its `admissionAuthorizedAtMonotonicMs`, and rejects further selection-changing events. At that same synchronous authorization point, the coordinator requires the acquired record to expose one live query object, one live input stream, and a safe-integer observer generation. It freezes those exact references and generation with the exact manager and record handoff. Their contents and the prompt text are not copied or retained. Absence or replacement stops authorization; the coordinator does not submit another prompt or create or install a replacement query. This synchronous authorization and guard closure is the acquisition-acceptance linearization point.

An authorization win permits publication of that frozen decision to complete later. Publication may take additional time; no total wall-clock bound or cancellation guarantee is claimed. Only successful accepted-admission publication makes the authorized decision consumable. A registration, transition, or write observed after `guard-closed` is a late event. It cannot retroactively retract an already consumable admission record and is outside the admitted selection interval. The claim therefore concerns the interval from readiness through guard closure, not indefinite uniqueness. No zero-time agreement is claimed between filesystem visibility, an asynchronous read, and subsequent Desktop activity.

Guard closure stops admission mutation but does not stop identity bookkeeping. Both account-transition hooks remain installed and continue incrementing the live epoch synchronously until their owner disposes them; the acquired record reference, manager reference, registration generation, bound IDs, frozen query reference, frozen input-stream reference, and frozen observer generation remain available to the private continuation validator. A late mismatch terminates continuation or a later selection without rewriting, retracting, or replacing the historical admission and without starting or waiting for another timeout.

## Persistence witness and metadata validation

The candidate writer hook captures the exact manager and record references, registration generation, task ID, current Code-session binding state, project, account, organization, epoch, profile, effective user-data root, and derived metadata path before directory preparation. It repeats the complete phase-aware comparison:

- after `ensureStorageDir`;
- immediately after serialization;
- before invoking the helper;
- after helper fulfillment;
- immediately before submitting the writer event.

Immediately after serialization it projects only `sessionId`, `cliSessionId`, and `cwd`. A projection qualifies for binding only when `sessionId` equals the selected task ID, `cwd` matches the bound project identity, and `cliSessionId` is valid. The first such projection binds its `cliSessionId` exactly once to the exact selected record object and registration generation. A pre-binding save or projection without a valid `cliSessionId` cannot witness persistence. The writer invocation that produces the first qualifying projection is the sole binding attempt; failure of that qualifying write rejects the run. Only its actual helper fulfillment through one of the approved helper classifications permits submission of the writer event and publication of the provisional writer-witness receipt. The raw object and bytes are then discarded. No snapshot digest is exported because it would suggest authority over historical bytes that the later read cannot confirm.

`resolved-path-helper-fulfilled` includes fulfillment through that helper’s internal direct-write fallback. `caller-direct-helper-fulfilled` applies only when the writer catch invokes the separate direct helper and it fulfills. A debounced or public save promise, cancellation, hidden/prewarm resolution, swallowed error, or unfulfilled helper is not a witness.

The resulting immutable receipt means only: the selected writer invocation fulfilled for the stated record and serialized projection at the recorded time. Later legitimate saves do not invalidate this historic statement.

The acquisition sidecar is the sole owner of selected-metadata acquisition. This is additional private scope proposed for a later grant; current authorization does not permit it. The external coordinator performs no metadata read.

After the writer receipt, the sidecar performs two bounded acquisitions of the one derived file: an initial validation and a final reread immediately before guard closure. Both reuse the existing exact component, no-follow, stable-descriptor, 65,536-byte, strict UTF-8, and projection contract. They project only `sessionId`, `cliSessionId`, `cwd`, `originCwd`, `worktreePath`, `spawnedFrom`, `dispatchParentId`, `dispatchParentOrigin`, `forkedFromSessionId`, and `lineageDetached`; retain no raw bytes or unprojected fields; and require matching file identity and projection. Required IDs and project identity must match. Optional path and lineage semantics remain unchanged. The approved projection is placed in the private admission record so later procedure construction does not require a competing external read owner.

Valid output prefixes are: the pre-acquisition record alone; that record plus configuration; those files plus readiness; those files plus an optional provisional receipt; and a readiness-bearing prefix plus exactly one terminal admission record whose receipt variant matches the files actually established. An accepted admission is valid only after a provisional receipt and may additionally be followed by exactly one accepted post-acquisition record. A rejected admission may validly follow readiness without a provisional receipt. A missing or invalid post-acquisition record does not retract a published accepted admission, but it prohibits observer continuation and later arm creation. Any absent or invalid prerequisite, rejected state, ambiguous state, publication uncertainty, timeout, or digest mismatch means no observer continuation.

## Final configuration and observer continuation

After validating the provisional receipt, the external coordinator constructs and exclusively creates the existing immutable `observer-config.json`. It uses the receipted IDs and the same `candidateSha256` and `sidecarSha256`. It does not read selected metadata.

The sidecar polls only that exact configured path within the remaining admission-decision deadline. It validates the final configuration through the existing bounded exact-file contract, including canonical bytes, target IDs, archive digest, shared sidecar digest, and separation from the observer run directory. It then performs the final selected-metadata reread and closes the guard as described above. Accepted admission certifies that both internal selected-metadata acquisitions completed and matched; no additional signal channel reports initial-validation completion.

After it publishes accepted admission, the sidecar publishes the accepted post-acquisition record from the frozen decision and already validated file identities. The coordinator retains hook ownership through that publication and through all preliminary continuation checks. The adapter then invokes `runDesktopObserver` exactly once with the validated `configPath`, `modulePath`, and `copiedAsarPath` plus a private immutable `continuationBinding`. External validation does not gate that app invocation; it gates later arm creation. The adapter does not mutate the environment, rewrite either configuration, call `bootDesktopObserver`, submit another prompt, create or install a query, or add the manager to another guard. Post-record publication or continuation failure is terminal and does not retract accepted admission.

`continuationBinding` has exactly the acquired manager object reference, record object reference, manager-instance nonce, registration generation, account ID, organization ID, live account-transition epoch value, task ID, Code session ID, frozen query object reference, frozen input-stream reference, and frozen observer generation. It is an internal closure-owned object and never appears in the public observer configuration, bootstrap, arm, or sample schemas. `runDesktopObserver` passes it privately to the evolved `createDesktopAdapter`.

Before adapter construction, on every `selectReceiver` call, on every access through a returned receiver view, and immediately before and after each observation boundary that relies on that view, the private validator requires the same manager object, the same acquired record object, the same acquisition registration generation, the same account and organization, the same current epoch, the same task and Code IDs, and the exact frozen query object, input stream, and observer generation. `manager.sessions.get(targetTaskId)` is used only to require object identity with the acquired record; an ID match cannot establish preservation. The continuation selector validates outside the adapter's existing null-return catch path. During setup, a selector validation failure propagates from `captureCandidate` and terminates continuation. During observation, `checkBound` catches a selector failure and converts it to a false identity check; the existing terminal sample or failure path must then report `identity_changed` and prevent further observation. No replacement prompt, replacement query, or new timeout is permitted.

Hook ownership transfers only after preliminary checks succeed and `createDesktopAdapter` accepts the continuation binding. Before that point, any failure leaves disposal with the acquisition coordinator. After that point, the observer adapter owns the hooks and live epoch ledger through its `finally` disposal, including setup or observation failure. The current owner removes them exactly once. Events after guard closure may therefore stop continuation while leaving the immutable admission historically valid.

The observer preserves its current schemas. Its independently generated `appStartNonce` remains distinct from `acquisitionNonce`. Admission’s `acceptedFinalConfigSha256` must equal bootstrap `configSha256`. Validation also compares run ID, PID, process start ticks, UID, clock ID, Linux boot ID, candidate digest, shared sidecar digest, task ID, and Code session ID across the fields where those values already exist. The bootstrap need not gain acquisition fields.

## Complete two-launch procedure

The proposed order is:

1. Complete the existing package, profile, launch-route, project, private-directory, and restoration preflight. Create and nonrecursively verify the empty dedicated non-Git project. Do not create a task.
2. Create and validate the empty acquisition and observer run directories. Construct and exclusively create `acquisition-prelaunch.json`, then construct and exclusively create `acquisition-config.json` bound to that exact pre-acquisition path, digest, and identity. Complete all stable-descriptor, parent-identity, source, package, protected-asset, launch-route, project, and recovery checks before staging.
3. Stop Desktop, stage the reviewed candidate, and perform the one candidate launch with only `PROVINGKIT_ACQUISITION_CONFIG`.
4. Attest the candidate process and validate `acquisition-ready.json`. The proposed 15-minute monotonic admission-decision deadline starts at readiness publication.
5. Through the normal new-local-task UI, create exactly one top-level disposable task in the bound project.
6. After candidate readiness, submit the sole fixed setup prompt exactly once:

   > This is a disposable observer fixture. Reply exactly `PROBE_READY`. Do not use tools, inspect files, change settings, or begin other work.

   This proposed operating sequence uses that submission to start the candidate process query and establish the Code ID. It retains no private message content and makes no delivery, completion, or current-settings qualification claim.
7. Wait for the qualifying registration, CLI identity, persistence witness, and provisional receipt, then validate only that provisional receipt. There is no separate external wait for the sidecar’s initial selected-metadata validation. A missing or rejected result stops the candidate phase.
8. Construct and validate the immutable final observer configuration outside the observer run directory.
9. The sidecar validates that configuration, performs the final metadata reread, and synchronously authorizes admission while closing the guard. At authorization it also freezes the exact existing query object, input stream, and observer generation with the exact record handoff. The timeout and authorization contend once in the serialized state machine. The proposed 15-minute deadline ends at authorization, not publication. An authorization win freezes `admissionAuthorizedAtMonotonicMs` and permits accepted-admission publication to complete later; a timeout win permits no accepted publication or observer continuation. Publication may take additional time, with no total wall-clock bound or cancellation guarantee. This bound is proposed, not accepted or measured. After accepted-admission publication, publish `acquisition-post.json` from the exact pre-record, witness, admission, final-configuration, process, and complete-identity bindings; do not create or accept it before admission.
10. After accepted post-record publication, the adapter automatically enters `runDesktopObserver` with the private immutable continuation handoff. The preliminary configuration, archive, module, process, run-directory, and continuation-binding checks have no new aggregate deadline or continuation gate. The existing setup deadline begins only inside `waitForCandidate`, not at readiness, admission authorization, either publication, or continuation entry. `waitForCandidate` may select only the same live query object, input stream, and observer generation frozen at guard closure. If that pair is absent or replaced, continuation stops without another prompt or query creation. Live viability of the pair remains unverified and is a later gate. No claim is made that a timer or operator stop cancels outstanding operations; actual Desktop stop followed by established quiescence controls exit.
11. After the external coordinator validates accepted admission and its exact accepted post-acquisition binding, validate bootstrap, create the arm, collect the bounded samples, and stop collection. Bootstrap publication starts the existing separate 60-second arm clock. External validation authorizes arm creation, not the adapter’s app-side observer invocation.
12. Establish quiescence, restore the pristine archive, perform the one restored-original launch, verify restoration, perform authorized package cleanup, and construct the cleanup manifest.
13. Every partial or failed stage proceeds only to the already authorized stop, quiescence, restoration, and reporting path. It authorizes no replacement task, receipt, prompt, query, candidate launch, observer start, arm, or restart cycle.
