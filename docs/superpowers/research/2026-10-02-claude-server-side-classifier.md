# Claude Code's server-side classifier review: what it reads and when it runs

Claude Code documents in detail when auto mode asks the server to review actions, and documents almost nothing about what that review reads. Every published statement of the classifier's inputs is limited to the classifier requests Claude Code sends itself. The server-side review runs inside the session's own model request, which carries much more than those client-side requests do. The measurements behind the Claude Code consent floor, taken in sessions that the docs then placed on client-side review, therefore cannot be carried over to a server-reviewed session on documentation alone.

## Summary

**When it runs.** In auto mode, Claude Code can ask the server to check the actions it would otherwise send to its own classifier. The check happens "as part of the session's own model requests" (`auto-mode-classifier-billing.md:9`; `permission-modes.md:329`). On a direct connection to the Anthropic API, interactive terminal sessions ask from 2.1.271 on Pro, Max, and Team, and from 2.1.278 on Enterprise and Claude API accounts. `-p`, Agent SDK, VS Code, and desktop app sessions ask from 2.1.281. Every one of these asks only as Anthropic rolls it out, whatever the plan (`permission-modes.md:331`). From 2.1.282, a session that does not fetch feature flags, for example with telemetry off, asks by default. Cloud providers and gateways ask by default from 2.1.278 (`:332`), and Claude apps gateway sessions from 2.1.280 (`:333`). `CLAUDE_CODE_AUTO_MODE_SERVER=0` turns it off and `=1` turns it on where it is not on yet (`:340`). No settings key of its own controls it, but the variable can be set in the shell or in the settings `env` key (`auto-mode-classifier-billing.md:32`). The only documented way to see whether a session uses it is the `/status` "Auto mode server" row (`auto-mode-classifier-billing.md:49`).

**What it reads.** No page says. The docs state the classifier's inputs only for the classifier requests Claude Code sends itself: user messages, tool calls other than read-only lookups, and `CLAUDE.md` content, with tool results stripped (`permission-modes.md:521`; `auto-mode-config.md:92`). Those requests also skip Claude Code's system prompt (`llm-gateway-protocol.md:199`). Statements that name no path, such as that the classifier reads `CLAUDE.md` and the `autoMode` rules (`auto-mode-config.md:62,64-70`), neither include nor exclude server review. The server-side review instead rides on the main model request, which carries the system prompt, the `CLAUDE.md` or `AGENTS.md` content, skill text, assistant text, and tool results, plus a `safeguards` request field (`llm-gateway-protocol.md:258`). Which of these the review reads, how it frames them, which rules it applies, and which model runs it are all undocumented. It also reviews read-only and sandboxed shell commands, which the client-side path auto-approves (`permission-modes.md:499`; `CHANGELOG.md:767`).

**Whether the client-side findings transfer (one line).** They do not transfer on documentation alone: the merge-closeout figures (declarations mentioning merge allowed 2 of 26, the control with no declaration 0 of 6, operator words 5 of 5) were measured in headless 2.1.283 sessions that the 2026-09-27 docs placed on Claude Code's own classifier requests, no trial record shows which path judged them, and nothing published says server-side review reads the same inputs or applies the same rules, so a server-reviewed session would need its own measurement.

- **Switches.** `CLAUDE_CODE_AUTO_MODE_SERVER=0` makes every check a client-side classifier request; on a direct connection the variable needs 2.1.281 (`permission-modes.md:340`; `env-vars.md:216`; `CHANGELOG.md:768`). `=1` turns server review on in a session that does not have it yet, unless `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` is also set. That variable with `CLAUDE_CODE_AUTO_MODE_SERVER` unset also stops the server asks (`permission-modes.md:340`). The variable can be set in the shell or in the settings `env` key, and it is documented as temporary (`auto-mode-classifier-billing.md:32-40`). The settings reference and the published settings schema have no key for it: the schema's `autoMode` object holds only `allow`, `soft_deny`, `environment`, `hard_deny`, and `classifyAllShell`.
- **Fallback.** When the server does not review the session, for example because a gateway drops the request field or the platform does not have the checks yet, Claude Code falls back to its own classifier requests (`permission-modes.md:337`). Pro, Max, and Team plans never show the fallback notice (`auto-mode-classifier-billing.md:44`). In `-p` the notice goes to stderr, and in `stream-json` it is a `system` warning, but only on accounts where the notice appears at all (`:26`). So a headless run on a Pro, Max, or Team plan has no documented marker of which path judged it. This note does not establish which plan Ivan's account is on (see [This host](#this-host)).
- **No verdict.** When the server returns no verdict for an action, Claude Code denies it rather than run it unreviewed. After ten responses in a row without a verdict it stops the turn (`permission-modes.md:338,470`; `errors.md:627-656`). These denial messages name the server-side classifier, so their presence shows that server review was asked for. Their absence shows nothing.
- **Observation.** `/status` has had an "Auto mode server" row since 2.1.278 (`CHANGELOG.md:931`). It reads `Enabled` while the server's checks decide the session's actions and `Disabled` once the session has fallen back (`auto-mode-classifier-billing.md:49`). None of the pages read here documents an equivalent for `-p`, `stream-json`, or the Agent SDK.
- **Not the prompt-injection probe.** A separate server-side probe scans incoming tool results before Claude reads them (`permission-modes.md:525`). It predates server-side classifier review, and the engineering post describes it as the input layer, distinct from the action classifier.

**The docs moved after the classifier study.** On 2026-09-27 the page said direct-connection server review applied in interactive terminal sessions, and that `-p` and Agent SDK sessions needed `=1` (`classifier/docs/permission-modes.md:321,330`). The 2026-10-02 page extends the default, during rollout, to `-p`, Agent SDK, VS Code, and desktop app sessions on 2.1.281 or later (`permission-modes.md:331`). No changelog entry between 2.1.281 and 2.1.287 records that change, so it reads as a server-side rollout rather than a client release. By the 2026-09-27 page, the study's headless trials on 2.1.283 ran on client-side review, but no trial record shows which path judged them. The denial messages, for example in the control trial `classifier/trials/t001/`, say only "denied by the Claude Code auto mode classifier", which names no path. The study's one server-side attempt (trial record `classifier/trials/t500/`, run with `CLAUDE_CODE_AUTO_MODE_SERVER=1`) marked the PR ready and stopped without attempting a merge. It is the only trial with a `debug.log`, which shows the feature-flag fetch and first-party API dispatch but no line that says which path judged `gh pr ready 101`.

**Correction to the ticket.** The ticket says the changelog places server review at 2.1.271 for Pro, Max, and Team. The changelog has no server-side entry under 2.1.271 (`CHANGELOG.md:1307-1405`). The 2.1.271, 2.1.278, and 2.1.281 version requirements come from the permission-modes page. The changelog's own entries are 2.1.273 (cloud providers kept on the local classifier, with `=1` opting in), 2.1.278 (Claude API and Enterprise accounts, cloud providers, and gateways default to server review, and the `/status` row is added), 2.1.281 (the variable applies on a direct connection, and read-only and sandboxed commands wait for review), and 2.1.282 (telemetry-off default).

## What server-side review reads

| Input | Client-side classifier requests (documented) | Present in the request the server reviews | Read by server-side review |
| --- | --- | --- | --- |
| Operator turns | read (`permission-modes.md:521`) | yes | not documented |
| Tool calls (the action and earlier calls) | non-read-only calls read (`:521`) | yes | not documented |
| Tool results | stripped (`:521`; `auto-mode-config.md:92`) | yes | not documented |
| Assistant text | stripped (engineering post, "Why we strip assistant text and tool results") | yes | not documented |
| `CLAUDE.md` | read, framed as the user's configuration (`permission-modes.md:521`; `auto-mode-config.md:62`) | yes, in Claude's context | not documented |
| `AGENTS.md` | read in `CLAUDE.md`'s place when no `CLAUDE.md` exists (inferred at medium confidence in the [earlier merge-closeout authority note](https://github.com/nisavid/provingkit/blob/4e654eeb13e198f0eb5257df7e6aa9095b630eec/docs/superpowers/research/2026-09-27-merge-closeout-authority.md), not documented) | yes, when it loads (`memory.md:349-360`) | not documented |
| Claude Code system prompt | skipped (`llm-gateway-protocol.md:199`) | yes | not documented |
| Skill text | not named | yes: the listing always, the body once invoked (`skills.md:555`) | not documented |
| `autoMode` rules (`environment`, `allow`, `soft_deny`, `hard_deny`) | read from user, managed, and `--settings` scopes (`auto-mode-config.md:64-70`) | not in the conversation; whether the `safeguards` field carries them is not documented | not documented |
| `PostToolUse` `classifierContext` | read as application context (`permission-modes.md:523`) | not documented | not documented |

- **The request field.** Server review adds an `anthropic-beta` value and a `safeguards` request field (`llm-gateway-protocol.md:258`), and results come back in a `safeguard_results` response field (`auto-mode-classifier-billing.md:30`). I found no public API reference for either field: the Claude Platform docs index has no match for "safeguard", and a ctx7 query of the Claude API docs returned nothing about them. What Claude Code puts in `safeguards` is in the binary, which this ticket did not read.
- **Rules and model.** The rule set the server applies is not documented. `claude auto-mode defaults` prints the rules the client ships, and no page says the server uses the same text. The docs give Sonnet 5 only as the classifier's default, and the statement names neither path. A classifier model Anthropic configures server-side takes precedence, and Sonnet 4.6 sessions, an `availableModels` list that excludes Sonnet 5, and Fable sessions change it (`permission-modes.md:537`). No page names the model behind server-side review.
- **Scope of actions.** Server review also checks read-only and sandboxed shell commands, and blocks them if it flags them (`permission-modes.md:499`; `CHANGELOG.md:767`). The client-side path auto-approves those. A server-reviewed merge closeout therefore has more checked actions. Commands such as `gh pr view` and `gh pr checks` would be among them if Claude Code counts them as read-only, but no page says it does.
- **What is unchanged by documentation.** The statements that the classifier reads `CLAUDE.md` (`auto-mode-config.md:62`) and the `autoMode` rules from the user, managed, and `--settings` scopes (`auto-mode-config.md:64-70`), the precedence tiers (hard deny, soft deny, allow exceptions, then explicit user intent; `auto-mode-config.md:221-226`) and the rules on approvals stated in conversation (`permission-modes.md:455-461`) are written for "the classifier" without naming either path. Nothing says they hold for server review, and nothing says they do not.

**Shipped rule text since the study.** These are client-side default rules; whether server review uses them is the open question above. The 2.1.284 defaults are byte-identical to the 2.1.283 snapshot. In 2.1.287 the "Merge Without Review" rule is unchanged, but five `soft_deny` rules changed, two were added (70 entries became 72), and the repository-visibility `environment` entry changed. None of these changes appears in the 2.1.285 to 2.1.287 changelog entries. Three of them touch merge-closeout steps other than the merge:
- "External System Writes" now names resolving a review thread as a write that PR work does not cover.
- "Git Destructive" now presumes other people's work on shared and default branches, blocks elsewhere only when the destroyed work is clearly someone else's, and requires the user's words to name the remote scope before deleting a remote branch beyond the agent's own session branches.
- The new "Unrequested Commit in a Connected App" rule applies where the user asked only to read, review, draft, or prepare, or said they will take a step themselves. There it covers marking a PR ready and merging it unless the user's own message asked for that exact step or, for `gh pr merge --auto` on that PR, "Merge Without Review" says the user's instruction authorizes it.

## Open questions

- **What server-side review reads and applies.** Inputs, framing of `CLAUDE.md` and `AGENTS.md`, treatment of tool results and assistant text, rule set, and model are all undocumented. Only a measurement under server review, or a first-party statement, can answer them. Reading how the 2.1.287 binary builds the `safeguards` field would show what Claude Code sends, but not what the server does with it. It was outside this ticket's scope, and the earlier study's attempt to read classifier prompt text from the binary was denied as `[Auto-Mode Bypass]`.
- **Desktop sessions.** Claude Desktop sessions are named with the 2.1.281 requirement, but which Claude Code version a Desktop session runs, and whether its `/status` shows the row, was not checked.
- **The launcher profile.** Does the `typesafe` `secret-exec` profile that launches `claude` set a gateway or proxy? A gateway that strips the `safeguards` field forces fallback (`auto-mode-classifier-billing.md:46`). This session's `ANTHROPIC_BASE_URL` names the official endpoint.
- **Headless observability.** Is there any per-run signal of the review path for `-p` sessions on subscription plans, such as an `init` field or a debug-log line? None is documented. The debug log of the study's one server-side attempt has none.
- **Rule-text changes.** Were the 2.1.287 `soft_deny` changes made in 2.1.285, 2.1.286, or 2.1.287? Those two binaries are not on this host, and the changelog does not mention the changes.
