# Native and T3 route reuse for the required Codex–Claude link

T3 Code has shipped its inter-harness orchestration overhaul. Its supported coordination surface is a useful candidate for T3-owned threads and for outside agents addressing those threads. The examined sources do not establish access to two independently existing native Codex/ChatGPT GUI and Claude Desktop Code sessions. This refresh therefore supports retaining T3 as a partial or complementary candidate; it does not yet justify selecting a private IPC fallback.

## Scope and evidence

This is an ordinary public-source compatibility investigation using research, wayfinder, and codebase-design. It evaluates capability and maintenance facts, not security enforcement, operating authority, installation, or live qualification. No researched code, provider session, message, build, or test was executed. Existing public issue bodies supplied requirements and discovery pointers, not fresh provider proof.

The current requirement is direct requests, receiver acknowledgment, and replies between actual current native counterparts, including automatic idle wake, busy-work preservation, and recovery without duplicate handling. Controller-created CLI/SDK workers and T3-owned tasks remain distinct populations. See [Choose existing routes and durable recovery for the first Dispatch cutover](https://github.com/nisavid/provingkit/issues/710).

The investigation used three discovery queries and 32 primary-source retrieval attempts. Large results were bounded; two adapter files and the ancestry comparison were read only through their first 128 KiB. Some combined terminal output was truncated, including historical issue bodies and long release changelogs. The initial v0.1.0 REST release response exceeded the read bound and was not used as complete evidence; the subsequent GraphQL release result exposed its introductory capability notes, with the long changelog output truncated. These limits preclude exhaustive absence claims. No local files were written.

## What the overhaul changes

The overhaul supplies a concrete reusable controller rather than merely a shared transcript. Its stable MCP implementation has scoped request identity, stable operation message identity, run linkage, waits, and explicit delegated-result delivery state. Its current architecture documents an event store, transactional command receipts and outbox effects, followed by provider work. It expressly distinguishes intent acknowledgment from effect completion. These are useful mechanisms for correlated submission and recovery; a peer's semantic ACK still needs an actual correlated receiver response. [Stable MCP implementation](https://github.com/pingdotgg/t3code/blob/2359643cffa6ba9ee84d6f2694b935de54a8013e/apps/server/src/mcp/OrchestratorMcpService.ts), [current architecture](https://github.com/pingdotgg/t3code/blob/cefb544af3c98224874419198c0359b652ca3c94/docs/internals/overview.md).

The first stable release documents server queues surviving restart but waiting for operator resume. Later stable release notes include fixes for held agent/scheduled queues and restart continuations. Therefore neither the original release promise nor a generic “durable queue” label establishes unattended receiver restart recovery for this requirement. Current main also contains later fixes, including busy-parent question delivery on November 3, after the examined nightly's target. Keep release identity attached to every claim. [v0.1.0 notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0), [v0.1.6 notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.6), [busy-parent fix](https://github.com/pingdotgg/t3code/commit/e2bb9e63e129001aa37fa1f9f51cb334d1a3db42).

The release also warns that provider switching transfers a budgeted selection of messages while omitting prior reasoning, tool calls/results, and attachments. A provider handoff within one T3 thread is thus another distinct operation, not delivery to a second independently existing peer. [v0.1.0 notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0).

## Reuse and ordinary maintenance costs

Retain T3's native MCP surface for outside-agent access to T3 threads and its cross-provider delegation for controller-created work. These can complement a native GUI adapter where some consumers actually live in T3. Moving the required consumers into T3 would change the accepted task population; it is an architectural choice, not an adapter implementation detail.

Prefer the native T3 MCP surface over reconstructing its WebSocket protocol when its population fits. Ordinary costs include a running environment, provider installations and authenticated accounts, compatible clients/server versions, provider-version floors, MCP connectivity, and version-specific recovery behavior. The current guide distinguishes local and hosted callers: a hosted ChatGPT caller needs an internet-reachable environment. These are compatibility requirements; this report does not accept the access model or authorize setup. [README](https://github.com/pingdotgg/t3code/blob/cefb544af3c98224874419198c0359b652ca3c94/README.md), [outside-agent guide](https://github.com/pingdotgg/t3code/blob/cefb544af3c98224874419198c0359b652ca3c94/docs/user/outside-agents.md), [v0.1.0 compatibility notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0).

The actual GUI-owner gap is specific: the examined T3 surface addresses a T3 environment/thread and its managed provider execution; it has not been shown to discover, subscribe to, start a turn in, or steer the already active session owned by either separate native desktop application. Importing/resuming native history or reusing an account does not establish that control path. This is an unresolved capability, not an exhaustive finding that supported controls cannot exist.

A version-bound private IPC adapter remains a candidate only after that supported-owner check. Its ordinary maintenance cost would include build-specific discovery, framing, method schemas, lifecycle distinctions, subscription/readback, and upgrade revalidation. The existing public [Codex desktop Steer route ticket](https://github.com/nisavid/provingkit/issues/644) already identifies a timeout-versus-delivery ambiguity and the duplicate-send risk of treating timeout as rejection. That is a historical defect pointer, not current private-protocol proof.

## A real seam grounded in two adapters

The stable Codex and Claude adapters demonstrate actual variation: Codex uses native app-server thread references; Claude runs an SDK query with a queued prompt stream and owned child process. Both translate a controller's app identity into provider identity and normalize provider output. That supports a small coordination module whose interface carries target identity/owner, correlation, submission disposition, and observed progress/result. Provider-specific attachment, busy behavior, and completion rules belong behind that seam.

It does not support promising one universal “send and await ACK” method with identical semantics. T3's own command receipt, delivery result, provider result, and delegated completion acknowledgment occupy different stages. Preserve those stages and unknown outcomes rather than flattening them into delivery. This conclusion rests on the two concrete stable adapters and MCP service above; it does not require adopting T3's whole architecture.

## Smallest remaining observation

Before choosing a fallback, finish one focused public-source check of current supported native owner controls: can an external caller address the actual existing Codex GUI session and the actual existing Claude Desktop Code session without creating or taking over a new CLI/SDK task? Record target identity, owner, busy/idle operation, event/readback mechanism, and restart/rebinding semantics for each direction. Use current Context7 documentation for relevant CLI/SDK facts; that refresh was not completed here.

If that check exposes a supported route, prepare one minimal thin adapter observation against the existing-session population. If it exposes a specific missing owner operation, define only that operation for a version-bound fallback. A later authorized live case should retain a correlation through submission, receiver receipt, semantic ACK, reply, controller completion, and the original foreground read completion; a timeout or pending tool operation stays unknown until reconciled. No such live case was performed in this investigation.

The release-inclusion question is resolved. Final supported-native availability, actual GUI-owner access, busy/idle behavior on the required consumers, receiver restart recovery, and the architectural choice remain open.
