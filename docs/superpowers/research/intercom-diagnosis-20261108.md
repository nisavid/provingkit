# Codex Desktop missing-active-turn-ID diagnosis

The upstream reports identify two separable defects. Overlapping starts can leave a Desktop renderer with an unfinished provisional turn whose ID will never arrive. A later send can then wait on that entry and fail before dispatch. The proposed patches address different parts of this chain. The initiating transition in Provingkit’s Lead and Concierge incidents remains unknown. Both upstream issues are open, and their comments and timelines contained no accepted Desktop fix. [Overlapping-start report](https://github.com/openai/codex/issues/45194) · [Timeout report](https://github.com/openai/codex/issues/56503) · [Provingkit receiver evidence](https://github.com/nisavid/provingkit/issues/847)

## Causal account

1. **An overlapping start can produce the orphan.** Desktop creates separate optimistic records for submissions A and B. If B reaches `turn/start` while A is active, the server can admit B’s input to A and return A’s ID. The inspected renderer lookup prefers an existing record with the returned server ID before looking for the provisional record with B’s `clientUserMessageId`. Completion settles A, leaving B `inProgress` with `turnId: null`. The original reporter reproduced this with extracted `b$t`, `Xg`, and `L$t`. A later reporter reproduced the same lookup order and blocked queue admission in `Zfn`, `qfn`, `nT`/`K6t`, `ppn`, and `Smn.canSend`. The pinned server code confirms the existing-ID response is a valid result of start-or-steer. Successful start responses and one persisted turn are consistent with this mechanism. They leave the historical renderer state unresolved. [Original report](https://github.com/openai/codex/issues/45194) · [Later extracted replay](https://github.com/openai/codex/issues/45194#issuecomment-6450936479) · [0.153.4 response handling](https://github.com/openai/codex/blob/3d2ee51ca2d5db578f328aa75e20aa22c0197c9a/codex-rs/app-server/src/request_processors/turn_processor.rs#L626-L686) · [0.154.0-alpha.6.2 core admission](https://github.com/openai/codex/blob/b5bffd3ec4db487e7e3dec59663875b0ef7b72ca/codex-rs/core/src/session/turn_input.rs#L237-L308)
2. **A later send can fail while consuming that state.** In `26.1016.61520`, `Tfn` waits through `kfn` before `Ofn` can dispatch. `kfn` reads and subscribes to local `ex(conversation)` state. A concrete ID resolves the wait, and a transition out of `inProgress` produces the typed inactive error. A persistent null ID produces the plain missing-ID error, which bypasses the `_fn`/`Npn` inactive fallback. In `26.1007.30912`, the analogous path is `Goa` → `Pln` → `sendPreparedMessage` → `ifn` → `Qun`/`ndn`. `yz` can select a newer null-ID placeholder even when an older turn has an ID. The reporter’s 30-second virtual-time fixture recorded zero transport calls on this branch. That establishes where this fixture’s *new* request stopped. The disposition of any earlier uncertain submission requires separate evidence. [Timeout symbols and extracted fragments](https://github.com/openai/codex/issues/56503) · [Native routing and mocked transport](https://github.com/openai/codex/issues/45194#issuecomment-6182774641)
3. **The incident reports support a shared symptom with different observed states.** The original macOS report and the later `26.1021.31345` replay describe two starts converging on one server turn. The Windows `26.1021.22027` report records two successful starts and one persisted turn, with no renderer capture. The macOS native-send report saw an active native turn with a concrete ID, while the later build-20398 report saw idle/completed after the failure. The September Windows report observed two approximately 30-second native failures. One send succeeded after a combined restart and update, while the inspected timeout and fallback logic remained present. Those observations leave the relative effects of restart, update, timing, and renderer state open. [Windows September report](https://github.com/openai/codex/issues/45194#issuecomment-5695567373) · [macOS native report](https://github.com/openai/codex/issues/45194#issuecomment-6182774641) · [Build-20398 follow-up](https://github.com/openai/codex/issues/45194#issuecomment-6199892578) · [Windows October report](https://github.com/openai/codex/issues/45194#issuecomment-6384396313)

## Verification and the next discriminator

- **Reproduced here:** The #56503 candidate and test fences matched their published SHA-256 values, `3f3f10ccce6fcdff9afc2a1c66c3ebbe9eba6cc865e28e36a103dffdca83d21d` and `20e63557effdd5d58d5132cb08f5de7b74b4571d94cd479ffd3db28c67c19ad2`. All 16 checks passed under Node `v26.11.1` with an in-memory loader substituting the published JSON fragments for the fixture file read. This includes the actual posted `kfn`/`gfn`/`_fn` snippets and the mocked reference algorithm. A separate implementation of #45194’s lookup pseudocode left B null/in-progress with a shared response ID and settled both records with distinct IDs. That second check uses a constructed event sequence and the published lookup order. [Timeout attachment](https://github.com/openai/codex/issues/56503) · [Lookup pseudocode](https://github.com/openai/codex/issues/45194#issuecomment-6450936479)
- **Reported in Provingkit:** The Lead’s native send failed after completion. One same-ID archive/unarchive restored a separately verified native acknowledgment. Concierge had a separate GUI failure after successful work and a native completed/idle read. Its same-ID recovery preserved the checked history, workspace, pin, checkpoint, and result, and recovered both native and GUI entry for the checks. #847 also records the completed inert four-case routing replay and one later successful idle-return profile on ChatGPT `26.1103.32239`. The failing renderer’s exact loaded bytes, initiating event, and recovery durability remain unresolved. [Lead failure and recovery](https://github.com/nisavid/provingkit/issues/847#issuecomment-6672866452) · [Concierge case](https://github.com/nisavid/provingkit/blob/85f22c6d7fc93e52189219144f8245b70fe97750/docs/coordination/batches/2026-11-06-concierge-checkpoint-continuation.md#L24-L38) · [Routing replay and idle-return profile](https://github.com/nisavid/provingkit/issues/847)
- **Smallest discriminating prototype:** Start from a consistent fixture and use the actual optimistic insertion, response merge, and completion reducers from one pinned renderer source set. Feed A and B with distinct client identities, return A’s server ID for both, and complete A. Compare distinct IDs and B starting after A completes. Inspect the exact provisional records before exercising the already-verified timeout path. If evaluating the native `toolOutput` branch, run the same shared-ID sequence through its actual start callback and check that it neither leaves a new orphan nor dispatches when an earlier submission is unresolved. Keep clocks and transport inert. A match would establish the mechanism for that source. Attribution to the historical Provingkit incident still needs the original correlated request/response IDs and notification order, tied to the renderer bytes that processed them. [Existing replay boundary](https://github.com/nisavid/provingkit/issues/847) · [Reporter’s response-correlation evidence limits](https://github.com/openai/codex/issues/45194#issuecomment-6450936479)

A product repair still needs an accepting maintainer, a supported source-to-signed-build mapping, and owner/follower integration evidence. Withhold a candidate if it loses correlation, dispatches against UNKNOWN, creates a new orphan, or changes explicit idle behavior. Preserve the existing Intercom refusal and each original attempt through any evaluation or rollback. Same-ID recovery remains an assisted profile with separate acceptance. This diagnosis supplies a prototype-selection input while Intercom qualification continues on its own evidence.
