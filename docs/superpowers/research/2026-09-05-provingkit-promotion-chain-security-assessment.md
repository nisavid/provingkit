# Provingkit promotion and release-chain security assessment

The frozen public source is a coherent seven-member source-stage Kit, but it has no current path to one immutable Provingkit release. Current public routes and entrypoints reject Task Witness runtime and final validation, Mergecraft required review, generic production validation, and Phase 7 production integration. Other required layers—including the committed eval-receipt check, authoritative receipt production and issuance, an accepted product-route matrix, production producers and issuers, native qualification, and final composition—are absent. An absent control is not fail-closed; only the implemented rejecting boundaries below carry that description. The closed chain is not evidence of an exploitable bypass, and this research makes no member, route, or artifact release-eligible.

The desired evidence shape is an acyclic set of independently authoritative branches: one reconciled seven-member candidate and final identity; an accepted final-candidate eval-receipt set distinct from receipts used to admit intermediate pull-request heads; every accepted product host-route cell and an accepted aggregate matrix; two Task Witness native-host receipts; authenticated Rolecasting execution followed by independent Tricritical terminal review; a public-release control and composition contract selected by [Define the Provingkit release contract][i-3]; identity-preserving integration; and separately authorized signing, publication, hosted readback, and final acceptance under [Integrate release-ops and publish the first signed Provingkit release][i-36]. No report, schema, fixture, same-job output, hash, source merge, or manifest composition can mint any missing authority.

## Counterexample checks

1. **An intermediate PR receipt is carried into a later release candidate.** The receipt names the PR head and its content-lock, eval, fixture, runner, grader, policy, waiver, issuer, and evidence inputs. A later candidate, receipt commit, merge result, or promotion successor changes at least the candidate binding unless the future release contract proves otherwise. The final-candidate receipt branch is therefore missing, not inherited. Because the source checker is absent, no current control catches this; the evidence model blocks release on the unresolved proof gap instead of inventing a rebinding policy.

2. **One unchanged cell is used to preserve a matrix after the supported route set changes.** The exact cell may remain potentially reusable only if every cell input survives. It cannot prove that the new route set is complete. Adding, removing, or reclassifying a route invalidates aggregate matrix acceptance and every dependent manifest, final validation, and receipt. This conclusion requires no choice about whether the cell will eventually be reused.

3. **A provider change is treated as one-cell work.** Provider identity, installation source, runtime, account boundary, trust root, or issuer may be shared by several host-route cells. The affected closure is every consuming cell. All of those cells and the aggregate matrix become stale before downstream composition. The report does not assume the closure’s future size; the accepted matrix and dependency bindings determine it.

4. **Retained generic controls are treated as current public-release acceptance.** The generic and Phase 7 production entrypoints reject before argument parsing, the Task Witness child rejects final-release mode, and current `production_eligible=false` excludes Task Witness from generic production validation. The retained generic evidence tuple becomes mandatory only after promotion, while Phase 7 cannot forward its five operands; tests prove that conditional seam only with a patched roster and substituted downstream results.
