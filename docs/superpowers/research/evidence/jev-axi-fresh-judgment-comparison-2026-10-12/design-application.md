# Applying the Jev design procedure

This comparison tests a wording correction for one supplied statement and its source evidence. It applies `adopting-jev` to a diagnostic question, before selecting an integration or assigning work to Jev. Freeze the resolved skill's `SKILL.md` and its `question-design.md`, `fit-and-limits.md`, `validating.md`, and `integration.md` references with the execution bindings and review inputs.

The output is one of four evidence relations. The complete source packet provides the context for that judgment; local code establishes source identity, availability, and packet construction first. The model produces no rationale, rewrite, or action. TypeSafe's [citation-checking example](https://docs.typesafe.ai/cookbooks/citation_check.md) also uses one relation Choice after deterministic source checking. Its examples, meanings, reported results, and confidence threshold are not this comparison's labels or acceptance evidence.

The current and revised questions preserve one categorical output and the same four meanings. The revised wording expresses an ordered distinction among ambiguity, contrary evidence, adequate support, and unsupported extension. This is not a test of decomposition into several narrow questions with a code-based combination rule. Decomposition remains a plausible successor, including if this wording fails; a failure cannot rule out that design or Jev's suitability in general. A pass likewise does not establish that this is the best Jev design.

The procedure recommends batching independent questions about one state. Here, each formulation is a separate experimental treatment: each request contains only that treatment, consistently across Jev, Decisions, and Responses. Separate requests isolate formulation and preserve per-treatment request accounting; their duplicated state and round trips are research costs. This deliberate diagnostic choice does not qualify an efficient deployed check. A later design containing multiple judgments over one state should evaluate batching rather than copy this treatment schedule into production.

The fresh cases are synthetic and independently labeled. They test known failure distinctions without reusing the earlier statements, but they have explicit cues and related source bundles. They do not satisfy the procedure's representative holdout, repeated measurement, shadow-workflow, calibration, or rollout requirements. No confidence band or action authority is selected. Ordinary-model controls answer the identical question; ordinary authoring and omission remain workflow alternatives whose value this isolated test does not measure. Local preparation already handles exact facts; no semantic rule comparator has been shown adequate for this input boundary, and none is claimed.

The retained public documentation includes the TypeSafe index, API, primitives, design guidance, models, jaggedness, citation example, Python SDK, and SDK changelog. The runner reuses the existing direct HTTP transport and introduces no SDK migration. The explicit no-retry research protocol takes precedence over general service-retry guidance. Preserve failures, raw answers, and complete costs as the contract specifies. Changes to these procedures or material public API facts require assessing affected review before execution.
