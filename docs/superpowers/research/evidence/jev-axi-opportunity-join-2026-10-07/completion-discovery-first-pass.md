# Compare access to completion evidence before adding a completion judgment

I recommend developing a comparison of **claim-specific evidence access for Ivan at completion**. The candidate is a short completion report whose verification claim opens directly to the relevant retained result, candidate identity, and stated limits. Ordinary reporting with equally good links is its strongest rival. A Jev assessment should not be included initially.

This is my research recommendation, not a selected experiment or behavior assignment. The predicted benefit is less effort deciding whether a particular completion claim needs further inspection. No supplied observation measures that benefit.

## What changes from the earlier portfolio

The earlier completion proposals began with current requirements, amendments, final claims, candidate identities, and an agent-produced claim/evidence pairing. That is appropriate for judging whether the entire task is complete, but expensive preparation for a narrower question: **“What supports this reported verification result, and does it cover the delivered revision?”**

I would compare that narrower consumer decision first. It needs the selected claim and its supporting result; it does not initially need a complete interpretation of every task requirement. If Ivan instead asks whether all current requirements are satisfied, the broader context becomes necessary and the narrower aid must say so. This restriction reduces the proposed producer’s responsibilities without weakening the meaning of “complete.”

The delivery point also changes. Evidence originates when ordinary verification occurs and becomes accessible from the completion report. It is not reconstructed by another process searching a large conversation after a Stop event. Nor does the proposal require a new requirements ledger, classifier, or mandatory completion interruption. The earlier portfolio explicitly permits separating purpose, delivery point, implementation, and authority. ## Strongest candidate: evidence available from the verification claim

**Consumer and decision.** Ivan reads an ordinary completion report and decides whether a reported check is sufficiently supported, whether to inspect its source, or whether a specific recheck is needed. This does not delegate whole-task acceptance to the aid.

**Ordinary workflow.** The agent reads applicable instructions, performs the work and required verification, resolves required reviews, and reports the result. Ivan may inspect linked records, search earlier output, or ask for clarification. Those are possible ordinary actions; their occurrence and effort remain unmeasured here.

**Proposed assistance.** Keep the ordinary report concise. Its verification sentence links to the result that produced it. Opening that reference exposes:

- The actual check or review and its retained outcome.
- The candidate identity or explicitly bounded artifact coverage already established for that result.
- The relevant output or review passage.
- Any limitation that changes the claim’s meaning.

Use existing links and native result references where they suffice. A separate compact view earns a place only if it makes the same evidence materially easier to inspect. Deterministic reference, identity, and availability checks can assist navigation; they cannot certify semantic support or test adequacy.

**Producer and inputs.** The ordinary executing agent already receives the verification result and writes the completion sentence. It selects the supporting reference while those facts are available. Existing tool records or retained artifacts supply the bytes. A deterministic renderer could expose supplied fields without generating a new verdict.

Two prerequisites remain specific and feasible: an accessible result reference that survives until consumption, and an observed association between that result and its claimed candidate coverage. If the ordinary route lacks either, the coordinator must price the smallest retention change. Hashing today’s file cannot retroactively establish which bytes an earlier check used.

**Expected benefit.** Ivan should need fewer searches or clarification exchanges to answer the selected verification question. That is a hypothesis about effort, not error prevention. A successful task is a legitimate case.

**Why no Jev initially.** The proposed work is primarily preservation, navigation, and identity comparison. The agent still authors the claim, and Ivan still interprets the evidence. Adding a support score would introduce another judgment without removing those activities. A later semantic comparison becomes plausible only if supplied claim/evidence pairs leave a consequential, recurring interpretation problem after good access is available. The pairing producer and fallback would then belong in Jev’s costs. ### Illustrative decision

This is an authored example, not an observed task.

The report says: “The source validator and unit tests passed for the delivered change.” Ivan wants to know whether those results preceded the final edit.

With ordinary reporting, he follows the supplied links or reconstructs the sequence. With the candidate, the claim opens to the result and its recorded coverage. If the result covers the delivered bytes, Ivan can inspect that support directly. If a subsequent edit changed a covered file, the view exposes the mismatch; it does not convert the earlier success into a current pass.

If the report already contains a direct, understandable reference and Ivan resolves the question immediately, the additional view has no demonstrated job. If the result only supports source validation, the presentation must not imply native qualification.

## The comparison that could defeat it

Compare three presentations of equivalent permitted evidence:

1. The ordinary report, including whatever useful links ordinary work would supply.
2. The same report with direct references to the relevant result and coverage, but no new summary view.
3. The candidate’s compact evidence view, produced and maintained at its actual cost.

Omission means omitting the new assistance, not degrading ordinary reporting or withholding required evidence. The second arm matters: improved linking may capture the entire benefit.

The minimum informative comparison needs an actual checking decision: accept the narrow claim, inspect a specified gap, or require a recheck. Retain Ivan’s searches, opened sources, clarification requests, active checking effort, and resulting decision; independently assess whether the decision is justified. Do not ask Ivan to inspect evidence he would otherwise have no reason to inspect merely to manufacture savings. Repeated exposure to the same answer would contaminate an effort comparison, so later design must address learning.

Include an already-clear ordinary report, current support, a changed candidate, an unavailable reference, a source-only result, and a legitimate partial checkpoint. Missing context must remain visible. Required checks and reviews remain required.

The candidate loses if ordinary links achieve the same justified decision with equal or less effort, if maintaining the view consumes the proposed saving, or if the presentation encourages an unsupported acceptance or unnecessary recheck. A small successful comparison could justify further qualification; it would establish neither population reliability nor a general completion gate. These distinctions follow the accepted operator-benefit scope and the maintained comparison contract. ## Serious alternative purpose: retrieve verification guidance when the task identifies its member

Discovery should remain a separate outcome. Its strongest concrete alternative is **task-time retrieval of the owning plugin’s verification guidance**, rather than recurring general command/status injection.

The consumer is the implementing agent choosing which documented verification route to investigate and run. The producer can use the task-owned paths and repository instructions to locate the relevant member README, then retrieve its validation section and referenced requirements. This supplies authoritative guidance; it does not establish installed readiness or decide that every listed command is sufficient for the particular change.

There is concrete source material. Rolecasting’s README names its validator and multiple test entrypoints. Versionkeeping distinguishes package validation, repository validation, and repository-only evaluation evidence. These are materially different routes; a generic “run tests” hint would discard useful distinctions. [Rolecasting README](https://github.com/nisavid/provingkit/blob/ca2c510c304cb7fd3216a1f2b0ac02645dceea12/plugins/rolecasting/README.md), [Versionkeeping README](https://github.com/nisavid/provingkit/blob/ca2c510c304cb7fd3216a1f2b0ac02645dceea12/plugins/versionkeeping/README.md)

Compare ordinary instruction/README reading against a deterministic link or section lookup when the affected member becomes known. Include already-known guidance, multiple affected members, documentation-only work, stale pointers, and an explicit command request. Count lookup maintenance and the agent’s applicability reasoning.

This rival wins priority if there is naturally upcoming unfamiliar-member work but no actual operator checking decision available. It loses if ordinary repository reading already reaches the correct section cheaply. Jev has no justified role in mapping an explicit member path to its authoritative README; semantic routing would need a different unresolved choice.

## Costs and the next scope decision

For completion, the executing agent owns reference selection and any coverage reconciliation; the harness or artifact mechanism owns retention and retrieval; the consumer owns inspection; maintainers own link/view upkeep. Record refresh after changes, unavailable records, failed retrieval, questions, rechecks, context consumption, all model attempts, latency, and money. Their totals are unknown.

For discovery, charge locating and maintaining the source pointer, retrieval, applicability reasoning, and downstream correction. If that discovery already produces evidence later used at completion, count the shared work once and retain both standalone and marginal costs. Better integration supplies no evidence of Jev’s incremental value. [Shared preparation](https://github.com/nisavid/provingkit/blob/ca2c510c304cb7fd3216a1f2b0ac02645dceea12/docs/superpowers/research/evidence/jev-axi-consumer-opportunities-2026-10-04/shared-preparation.md)

The coordinator should bring three concrete questions to scope selection:

- **Can an ordinary verification result already be opened with trustworthy candidate coverage?** If yes, develop the presentation comparison. If no, identify and cost the precise missing retention/association step before selecting that implementation.
- **Is Ivan making a real evidence-checking decision in the proposed work?** If yes, operator benefit is testable. If no, do not substitute an invented inspection exercise; consider the discovery rival or defer this purpose.
- **Does an ordinary direct link already resolve the question?** If yes, prefer that smaller intervention or ordinary reporting. If a further semantic uncertainty remains, name it before considering any Jev arm.
