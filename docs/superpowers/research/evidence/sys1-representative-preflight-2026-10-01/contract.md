# Qualify supervision inputs during representative work

This proposed preflight tests which task instructions and tool outcomes are available at actual Claude Code and Codex supervision-hook boundaries. It can supply additional native input evidence for [Freeze the first jev-axi catalog comparison contract](https://github.com/nisavid/provingkit/issues/336). It does not choose an assignment for Jev or establish a benefit from supervision.

The operator accepted a broader workload after the small tasks often finished before cadence ten. This preparation combines one representative development task with qualification of the corrected Codex receipt identity and owned shell temporary directory. It adds no separate native smoke. The earlier four attempts, including the censored attempt and their costs, remain evidence; this batch does not replace them.

## Two serialized episodes

| Order | Harness | Ordinary task | Messages | Episode deadline |
| --- | --- | --- | --- | --- |
| 1 | Claude Code | Extend a working report command, then add JSON and sorting | 3 | 480 seconds |
| 2 | Codex CLI/app-server | The same seed and ordered requests | 3 | 480 seconds |

The working Python seed spans parsing, aggregation, rendering, CLI orchestration, public command tests, and a README. The first request adds multiple inputs, grouping, and filtering; the second adds JSON and obsolete-report cleanup; the third adds numeric sorting while retaining the prior JSON request. The three prompts are ordinary developer instructions. Both sessions receive the same bytes from `representative-workload/`; external artifact checkers stay outside evaluated projects. The seed's three CLI tests pass. Fourteen local runner/checker tests pass; these checks launch no native harness.

Each episode starts a fresh native session in a separate standalone fixture repository. Follow-ups are delivered in that session only after the preceding turn completes. There is no compulsory assistant proposal, active-turn message injection, forced wrong action, minimum tool count, or extra work to reach cadence ten. Successful work with no failure or assessment opportunity remains valid evidence. This workload has no deliberately broken seed or prescribed failed command.

At each completed turn, the coordinator captures the known report bytes and source-data hashes before delivering the next amendment. Offline literal checks expect tools=27, books=10, art=10: first CSV in appearance order, then JSON in that order, then JSON ordered art, books, tools. They also check obsolete known report removal and unchanged source data. Missing, invalid, oversized, or unreadable artifacts are retained as explicit outcomes, with bounded raw bytes for invalid content. They do not stop subsequent amendments when native/context receipts remain usable. Failure to write the coordinator record still stops the episode. These are artifact checks only. CLI behavior, changed tests/documentation, and preservation of unrelated files require separate inspection; no quality claim follows merely from the native client's success response.

The later comparison still needs both paired contrasts: loops versus legitimate repetition, and obsolete-requirement drift versus authorized change. This passive task does not replace those trials. If it still supplies no native cadence or failure opportunity, report that limit and stop or narrow the affected comparison. Do not automatically enlarge the workload, lower cadence, force an error, or run again.

Stop assessment is also omitted for this passive qualification; this is not the formal comparison's common Stop treatment.

The observer retains the native hook envelope, tool response or error when present, and the first bounded transcript read at hook receipt. It does not register PostToolUseFailure or reinterpret failed commands as successful ones. The native stream and later hook snapshots may reveal failed executions that did not trigger PostToolUse. Missing, malformed, truncated, inaccessible, or unbound context produces an unavailable record and stops that episode. Capture records are published atomically. A capture failure returns a nonzero hook exit and attempts to publish a failure marker; the controller also rejects native hook errors, unfinished receipts, malformed records, and native completion/capture count mismatches before continuing to the next turn. Native run IDs and observer UUIDs remain separate: the reconciliation establishes aggregate agreement by event within a session, not an individual identity join. The Claude receipt parser follows the public SDK lifecycle definitions and the Codex parser follows the installed CLI schema. Earlier attempts supply partial compatibility observations; the corrected controller still needs native qualification. Later evidence must not be represented as available to an earlier hook.

Prepared manifests bind the source and compiled-file hashes, installed production dependency files and resolution paths, settings, project seed, hook configuration, prompts, native versions, model selections, and episode bounds. Source drift, an existing reservation, or initialization/permission mismatches stop execution; there is no automatic retry. Local synthetic checks exercise cadence/bookkeeping and record preservation, without claiming native coverage.

The intended cohort is Claude Code 2.1.284 with `claude-opus-5-5` at medium, and Codex CLI 0.159.0 with `gpt-6.1-sol` at medium. ## Observations and admission requirements

Launch each episode with an existing, absolute coordinator receipt directory supplied through `--receipt-dir`. The launcher reserves a unique receipt before manifest validation, lock acquisition, or attempt reservation. Each receipt retains the invocation command, expected manifest digest, start/end timestamps, launcher exit, error, and launcher stdout/stderr. Existing episode reservations and outcomes remain untouched on rejection. `rejected-before-controller` and `native-episode-failed` are distinct receipt statuses; controller entry alone does not establish a native session or provider request. An interrupted launcher may leave an in-progress receipt, which requires reconciliation. A missing or unusable receipt directory refuses launch before episode work; the coordinator must retain that invocation error separately. Receipt output describes the launcher; child-process output remains in the transport records. Preserve every attempted episode, controller delivery, native acknowledgment, ordered turn, tool call/result identity, hook invocation, snapshot, bookkeeping count/baseline, native terminal result, raw stream boundary, error, and final artifact. Record the source revisions and configuration that produced each record. User amendments come from actually delivered messages, not from grader labels or a later reconstructed approval summary.

Admission for each harness requires:

1. A fresh session and supported initialized tool/model/profile inventory, with the selected project hook configuration.
2. Bound message receipts and ordered same-session report continuation. At a later PostToolUse boundary, identify whether the intermediate JSON amendment is present in the real transcript and whether the integration's first/latest projection omits it. Existing files may supply the format independently; prompt omission alone is not proof of inadequate total context.
3. Actual edit and command-result shapes, plus whatever success/failure and exit/output information is available before hook execution. An episode without a failed execution leaves new failure coverage unqualified; reuse applicable earlier native observations with their versions and limits.
4. Native PostToolUse and Stop coverage, preserved session counts and baseline, and explicit eligibility/skip information. No native cadence-ten opportunity means native cadence coverage remains unqualified even though the local synthetic check passes.
5. Complete attempt records through terminal outcome or an explicit failure reason, with the quantity and scope of native usage reports retained.

These are per-harness, per-property admissions. A missing opportunity cannot become a pass or silently invalidate unrelated source facts. The coordinator will report unsupported properties and the smallest needed next step before admitting affected judgment trials.

For a possible deterministic comparison, inspect three distinct completed executions with the same command, working directory, known nonzero exit code, and exact captured native output text. This predicate cannot claim complete stdout/stderr equality: Codex exposes combined output, and Claude's required fields still need observation. Missing, declined, ambiguous, or known-truncated outcomes cannot satisfy it. Its proposed notice reports repeated captured failures, not unchanged inputs, unauthorized repetition, or a loop. Its usefulness remains a later native comparison question.
