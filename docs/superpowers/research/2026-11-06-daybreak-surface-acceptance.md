## Corrections required when consuming the matrix

1. **Add the research worker to observed execution.** The note's prior-evidence summary was limited to the UI observation and two sentinels. The now-completed worker adds a substantive native legacy-selector research/tool-use observation. It does not add explicit-program evidence, independent provider attestation, general tool qualification, or cross-account proof. Preserve both the artifact and this addendum rather than silently rewriting its frozen history.

2. **Do not generalize the status helper's unavailable probe.** Its `harmless-probe` really returns `DA031` before launch; its status operation really checks Blue catalog exposure. But that helper's closed-world tool-denial limitation does not establish that every account-home or CLI route is unavailable. #469 expressly requires deriving restrictions from the actual operation and distinguishing no-task-data from universally tool-free. The matrix's broad unavailable-route wording and its proposal to require a tool-denying actuator need that scope correction. Preserve any tool restriction that actually governs the selected consumer and the existing harmless-probe requirement where applicable.

3. **Scope native-child inheritance to the inspected implementation.** The public release's spawn handler passes the parent's `turn.cyber_access_program` into `SpawnAgentOptions`. That is strong source evidence, not a verified binding to every hosted native controller or a runtime child observation. An explicit spawn field is not inherently mandatory if a source-supported inherited binding can meet the consumer's actual requirements. Conversely, an ordinary parent has no observed explicit-program child route through this schema.

4. **Keep proposed assurance and publication gates conditional.** A preserved request, correlated native terminal, and local persisted context support the local claim they actually report; they are not provider attestation. Require stronger evidence only where a consumer's accepted minimum calls for it. #551's product identity is settled as `chatgpt-codex`, while its publication/installation remains separate; the ticket explicitly creates no blanket prerequisite for independent source preparation.

5. **Narrow absence claims.** The worker identified no concrete SDK or Responses API consumer in its targeted inspection, which is sufficient to omit those rows here. It did not prove that every possible API use is absent. No protected account catalog was inspected, so individual account routes remain unassessed, not denied.

6. **A Daybreak toggle is not an exact Blue selector.** The TUI and default CLI resolver call `ModelAccessPrograms.daybreak()`, which prefers Blue but selects Red when only Red is advertised; missing/empty metadata preserves automatic treatment. The note's opening claim about explicit Blue on CLI/TUI is too broad. For a Blue-specific consumer, use the explicit CLI Blue flag or establish the exact resolved request and applicable Blue catalog support; do not treat `/daybreak` alone as sufficient. Sources: [TUI resolver](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/tui/src/daybreak.rs), [catalog selection helper](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/protocol/src/openai_models/access_programs.rs), and [CLI resolver](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/exec/src/daybreak.rs).
