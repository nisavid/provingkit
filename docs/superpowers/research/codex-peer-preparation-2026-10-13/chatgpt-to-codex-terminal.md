# Terminal peer notification: initial source design

This packet designs a notification route from ChatGPT in Codex mode to one independently opened Codex terminal peer. Queue is the candidate for deferred user input; direct App Server controls offer immediate start or steering with different busy-task semantics. Neither route is qualified here. The missing caller-to-owner association and receiver event production remain explicit prerequisites.

## Separate receiver profiles

| Profile | Source-supported seam | Required association and limit |
| --- | --- | --- |
| Interactive TUI with embedded App Server | TUI `start_app_server` returns an in-process client; launch selection can choose embedded ownership (TUI:561–619,1028–1056). | Bind the exact independently opened TUI to that embedded server and its store. This packet does not establish an externally reachable control endpoint for it. Starting another server is not attachment. |
| Interactive TUI using a local daemon | Launch selection can choose a default Unix socket; connection failure can fall back to embedded ownership (TUI:523–557,580–603,1047–1053). | Record actual successful owner selection, not merely the configured socket. Prove that the addressed manager owns the terminal's native ID and that caller/store permissions match. |
| Interactive TUI using explicit remote App Server | `connect_remote_app_server` constructs a remote client with experimental API enabled (TUI:506–520); SELECT:265–269 uses remote parameter mode. | Bind endpoint, authenticated connection where applicable, remote owner/store, and exact terminal ID. A local home or displayed remote session is insufficient. |
| Independently opened headless terminal worker | The dated comparison treats `exec` and `exec resume` as a distinct controlled-job/stored-continuation fabric (comparison:18,79). | Its actual owner, Queue extension, reader, and ingress are unknown. The supplied `cli_lib.rs` does not trace the exec runtime. Do not import TUI/App Server delivery claims. |
| Other App Server-owned terminal client | Thread/turn and queue request processors provide server-side seams (QP:77–94; TURN:525–539,1044–1063). | Identify the actual client, manager, lifecycle registration, event subscription, and owner. An SDK-created worker or cold resume is a separate population. |

A stored native ID can exist without being loaded in the addressed manager: QP `require_thread` checks the manager, then stored metadata (253–292). TP `thread_loaded_list_response_inner` lists that manager's IDs (2885–2929). These observations can support a later association record; they do not identify a process from source alone.

Cold resume cannot be treated as existing-peer attachment. `live-writer.rs` `resume_thread` first requires recorder absence and acquires a writer lock (40–46); `writer_lock.rs` returns “already has an active writer” on lock contention (65–71). Neither the lock nor a stored ID exposes the actual owner's address.

## State and correlation design

Proposed input is a frozen association record plus an operation record. The association carries caller surface/version/control interface; terminal profile and independent origin; exact native thread ID; actual owner/client association; endpoint/transport/schema capability; home/store identity or remote equivalent; evidence source/time; and allowed inspection/send scope. All live values are currently unknown. The operation carries operation ID, attempt ID, client user-message ID, exact inert payload/correlation, strategy, expected turn if steering, prior grant references, bounded wait/reconciliation rules, and required receipt/optional ACK.

Proposed output appends evidence without rewriting earlier stages: preflight, possible submission, queue admission, turn submission, correlated receiver receipt, optional ACK, and inspection completeness. Every observation names target, correlation, source, time, and limits. This implements the accepted distinctions in [confirmed operation decision](https://github.com/nisavid/provingkit/issues/538#issuecomment-6112579765); it is an interface proposal, not an implemented observer.

- Loaded idle: QS `enqueue` stores input, emits a change, and calls `wake_if_loaded` (265–279). Wake asks a loaded, non-interrupted thread to emit its idle lifecycle (472–481). Dispatch calls `start_turn_if_idle` and deletes after a Started result (405–448). Report admission, start, and receipt separately.
- Loaded busy: Queue can retain input until an eligible idle lifecycle; its watcher avoids dispatch for Running/Interrupted/Shutdown/NotFound (QS:215–225), and normal idle handling excludes Interrupted (549–564). Explicit `turn/steer` is a different strategy with a current-turn precondition. Do not silently switch strategies.
- Unloaded: QP can admit eligible stored input (253–292); QS dispatch requires its manager to return the thread (405–411). The watcher considers loaded manager IDs (149–178). Stored admission does not establish wake or receipt.
- Held/refused/stale: preserve intentionally held input and non-dispatch states. Explicit Queue start requires loaded state and rejects active/pending turns or draining (QP:186–227). Queue checks ephemeral status in the loaded branch and archived records in the stored-thread fallback (253–287), and direct-input restrictions include multi-agent V2 spawned children and unloaded spawned children (296–311; `thread_input.rs:12–20`). Expected-turn mismatch is stale precondition evidence, not permission to retarget.
- Unknown: timeout, connection loss, or lost response after possible send retains possible submission. Inspect Queue and receiver history by both client ID and payload correlation before any resend. Queue disappearance alone is not receipt: dispatch also deletes invalid/non-user records (QS:425–435). Source does not establish end-to-end idempotency or safe replay; a newly generated CLI client ID is not reconciliation. Follow [confirmed operation decision](https://github.com/nisavid/provingkit/issues/538#issuecomment-6112579765).

The basic portfolio positive is correlated receiver-side receipt. ACK remains separately qualified ([confirmed operation decision](https://github.com/nisavid/provingkit/issues/538#issuecomment-6112579765)). The stronger Desktop reverse route still requires both and its additional evidence; no terminal result weakens that separate contract ([stronger Desktop contract in the comparison](https://github.com/nisavid/provingkit/blob/61b99e73ebedf8afb33b28a531daea8089504394/docs/superpowers/research/2026-10-11-peer-portfolio-comparison.md#L199)).

## Meaningful later synthetic boundary

Agree these public adapter boundaries before adding code or tests:

1. **Association admission and strategy selection:** invented exact-ID/owner/store/schema records must produce an allowed Queue/steer/idle-only plan or an explicit blocked/held/refused result. Counterexamples include same ID with wrong owner, daemon fallback, ambiguous labels, unloaded target, and absent caller control. Assert observable plan/disposition and preservation of grants; do not mirror helper calls.
2. **Request encoding against frozen wire shapes:** fake transport captures exact native ID, client correlation, disclosed user input, and expected turn. Assert no creation/resume, no unsolicited configuration override, and no strategy change on failure. These tests establish encoding, not real schema support or authentication.
3. **Evidence reduction:** invented responses, queue pages, user-item events/history, receiver ACK, and incomplete/gapped streams produce monotonically retained stages. Admission/start/queue deletion/wrong-target item/wrong-client ID must never qualify receipt. Correlated receiver user item may qualify receipt only under the agreed owner and producer provenance contract; ACK requires its own matching receiver reply.
4. **Unknown-send reconciliation:** a fake transport accepts then loses the response; later reader finds queued input, correlated receipt, or inconclusive history. Assert no resend for unresolved, held, or refused states. A proven pre-submission transient failure can retry only within the declared bounds and grant.

The smallest useful prototype is an in-memory state demonstrator using those invented records, with visible association, strategy, stages, correlation, and uncertainty after each action. No real listener, SQLite/home access, subprocess, provider, persistence, or installed harness is needed. TDD follows boundary agreement. Synthetic tests would establish constructed handling only; later separately granted exact-target idle/busy receipt evidence remains necessary ([confirmed operation decision](https://github.com/nisavid/provingkit/issues/538#issuecomment-6112579765); [terminal preparation brief](https://github.com/nisavid/provingkit/issues/562)).
