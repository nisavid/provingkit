## Consequential claims checked

### Native messages and Desktop tab messages have different timing

The owning references confirm both Claude rows. Native SendMessage reaches an active receiver between tool calls and starts a turn when idle, subject to accept/hold/refuse admission. Desktop tab messages wait until current work finishes. Desktop's surface addresses eligible app-run local, SSH, and WSL sessions; it excludes cloud, terminal, and VS Code sessions. A native idle notice describes state and does not acknowledge the requested content. These are separate notification/continuation candidates for eligible existing or controller-created tasks. The OpenAI report's sidebar follow-up and native-child distinction likewise gives no reason to merge these Claude routes. [Native messaging](https://code.claude.com/docs/en/cross-session-messaging), [Desktop tab contract](https://code.claude.com/docs/en/desktop#work-across-sessions).

The current MCP documentation still describes a stdio tool server but does not enumerate a current ListAgents/SendMessage schema. Keep the observed 2.1.280/2.1.283 peer-tool exposure historical; neither that history nor the 2.1.296 release identity establishes present exposure, sender access, receiver admission, or a return inbox. The raw socket remains a partial protocol lead. [MCP server contract](https://code.claude.com/docs/en/mcp#use-claude-code-as-an-mcp-server), [historical sender evidence](https://github.com/nisavid/provingkit/blob/ee76e2a85c6cff97bd2111eefdc41fa6dfd433be/docs/superpowers/research/2026-09-26-claude-inbox-feasibility.md).

### Browser transport is an active client; bridge registration owns worker state

In SDK 0.3.296, browser query constructs a Query whose constructor immediately begins initialization; initialization sends a control request. An empty prompt iterable therefore does not establish passive attachment. SSE delivery updates identify worker receipt, turn start, and turn end. They are not replayed after reconnect, while durable event envelopes carry IDs and sequence numbers. The public cursor covers yielded messages; truncated catch-up requires separate gap recovery. A processed update is not the requested work's semantic result. Legacy WebSocket remains a separate transport without the SSE-specific helpers. [Versioned SDK distribution: browser-sdk.d.ts and browser-sdk.js](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz).

**Correction:** replace the FIRST report's broad missing-header claim with a narrower gap. SSEOptions explicitly names Authorization and anthropic-client-platform. Supported external credential scope, accepted client-platform value, endpoint access, initialization effects, concurrent-client behavior, and the selected Desktop-to-remote binding remain unestablished. Declared header names do not resolve those questions.

The same distribution's bridge.d.ts confirms that fetchRemoteCredentials registers a worker and advances worker_epoch. attachBridgeSession registers when the epoch is omitted; providing an already obtained epoch avoids that redundant registration. Its handle writes worker state, events, delivery status, and control responses. This supports an explicitly owned worker lifecycle. It cannot serve as a passive observation substitution for an existing Desktop/cloud worker. A malformed successful credential response can already have advanced the epoch, so an uninformed retry is consequential. [Versioned bridge declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.296.tgz).

### Cloud acceptance and correlated work remain separate

The current cloud reference confirms that the exact-ID CLI follow-up queues one message and exits without waiting for a reply. Its success object establishes submission, with no receiver result or peer-origin proof. Teleport gives the terminal a local continuation whose new work does not appear in the cloud conversation. Both findings preserve the FIRST report's limited existing-cloud-task mapping. [Cloud follow-up and teleport](https://code.claude.com/docs/en/claude-code-on-the-web#send-follow-ups-from-the-cli).

The OpenAI report's queue distinction survives independent source checking: at Codex release commit `092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`, queue start uses start_turn_if_idle and wake_if_loaded requires a loaded, non-interrupted thread. Claude cloud submission and Codex queue admission therefore need separately correlated receiver/result acquisition. Neither transport receipt supplies the other harness's reverse route. [Codex queue service](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/ext/queue/src/service.rs#L367).
