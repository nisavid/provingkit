# Shared protocols and cross-harness fabrics

This inventory identifies complementary ways to create controlled workers, address opted-in existing tasks, and expose host-managed sessions across the portfolio. None is qualified by this research. The strongest distinction is the population a route can address: an ACP session, a T3 thread, an OpenClaw session, and a native conversation are different identities until a specific adapter binds them.

## Scope and evidence

This is the independent first report for [Research shared protocols and cross-harness fabrics](https://github.com/nisavid/provingkit/issues/536), under [the coordination portfolio](https://github.com/nisavid/provingkit/issues/533). The source baseline is [Provingkit 34ab07d](https://github.com/nisavid/provingkit/tree/34ab07d80ace058d9c009c79bd810f75d36bc0ac). Research was performed on 10 October 2026 in America/New_York; public observations extend into 11 October UTC. GitHub source timestamps below are UTC.

The six operations are notification, work request, task creation, status/result inspection, reply, and continuation. Independently opened user-owned tasks and controller-created tasks remain separate profiles. A controller-created task can still be user-owned. No row establishes all six operations across all portfolio directions.

Evidence labels have these meanings:

- **Documented:** an owning specification or project describes the behavior.
- **Source-examined:** relevant implementation declarations or paths were read at the cited revision; this is not a complete implementation audit.
- **Project-reported:** an upstream README asserts a successful test or stronger property that I did not reproduce.
- **Historical:** the supplied dated research describes an earlier observation.
- **Unobserved:** a behavior or binding was not established here.

No installed harness help/schema, private account or task state, synthetic test, or live channel was exercised. Public source schemas are source evidence, not a live tools/list response. No downloaded implementation was executed. No installation, activation, send, task creation, or project mutation was performed. The supplied request, common input, atlas, and retained report matched their provided SHA-256 digests. No findings were exchanged with the other research lanes before this report.

The dated atlas supplied discovery leads. I refreshed public release/source identities and relevant contracts. Firecrawl had no callable tool in this session; public GitHub APIs, raw source, static archives read in memory, and web search supplied the fallback. Context7 resolved ACP and returned current documentation; proposed RFDs returned by that search were checked against versioned source rather than treated as stable requirements. The unauthenticated GitHub API eventually returned a rate-limit error; the affected identity gap is retained below.

## Complementary combinations

These combinations are hypotheses for comparison, not a selected winner.

1. **Native receiver actuator plus a small CLI or MCP wrapper.** Suits an exact existing peer when a first-party route exists. Add a common result envelope for submitted, accepted, queued, refused, delivered, replied and completed states. It minimizes new host state but retains per-receiver compatibility work.
2. **ACPX plus a pinned ACP adapter.** Suits controlled workers and supported stored sessions. It offers a common queue/watch interface while leaving native-ID and restart behavior adapter-specific. Compare the queue owner and record costs with a direct App Server/SDK client.
3. **T3 orchestration plus its provider adapters.** Suits a common host containing the three distinct Wave 2 endpoints. First-party main MCP and third-party connectors offer different caller access and release dependencies. Host creation does not replace an existing-native-task profile.
4. **OpenClaw or Hermes native session APIs plus a narrow external caller.** Can expose useful later-wave receivers earlier in research. Keep channel, host session, native backend and caller identities explicit. OpenClaw supervision's local branch and node continuation require different claims.
5. **Explicit binding or registered broker plus a return route.** Agent Bridge, Intercom, Relay and cross-agent_mcp cover different opted-in populations. Compare setup, resident processes, restart reconciliation, active-owner conflicts, and message-origin semantics before adopting one.
6. **A2A service wrappers plus MCP caller tools.** Makes remote created-worker request/result flows portable. It adds service/task IDs and deployment state; native session continuity and asynchronous reply still need evidence.
7. **Observer plus actuator.** A bounded transcript or event observer can strengthen a positive correlation result. It cannot turn absence of evidence into refusal or nondelivery, and a receipt label cannot establish completed work.

## Proposed basic checks and costs

The portfolio grants a 30-active-minute exploration budget per fabric/operation once that probe's scope is authorized. Setup and debugging count; human approval and quota waits pause that clock. Reassessment at the limit preserves the obstacle and result and completes cleanup; it does not qualify an unfinished route.

No runtime duration, token bill, resident memory, or success rate was measured here. Expected cost components are installation/setup time, idle server/daemon processes, storage/journal growth, endpoint exposure and maintenance, caller tool/context volume, and provider usage for every actual turn. Project test and benchmark claims are not measurements from this research.

A smallest useful check should name:

- One directed sender/receiver pair and one operation; exact existing-task reference or explicit creation contract; ownership and permitted data.
- Exact fabric, adapter, provider/runtime versions and a native-ID map. Keep wrapper job, host thread, native thread, turn/run and message correlation IDs separate.
- One unique inert correlation token and the required result. Sender return proves only what its returned fields actually state; an assistant reply must identify the intended request.
- Idle/busy behavior, including truthful queue/hold/refusal. A queued acceptance can qualify queue admission, but cannot be counted as receiver consumption.
- A bounded status/result acquisition route, ambiguous-send reconciliation, and cleanup. Restart continuity is a separate check.
- The configured model/account/permission/workspace observations required by that profile. Stronger preservation and attestation remain separate from the basic operation result.

Before live work, synthetic checks can exercise wrong IDs, expired bindings, ambiguous responses, queue cancellation, reply correlation and false success labels. None was run in this first report.

## Capture and unresolved facts

I used research and capturing-agent-procedures. The reusable candidate procedure is: freeze the public inventory; join independent reports; select a concrete operation/population; bind its versions and identities; define a scoped probe and cleanup; distinguish admission, receiver evidence and domain result; retain unsupported profiles; and refresh only materially affected evidence after changes.

This procedure remains a proposal for [the agent-panel workflow owner](https://github.com/nisavid/provingkit/issues/306). The downstream consumer should load the reviewed published inventory before selecting a prototype and record the source revision it used. Maintained procedure placement, invocation pointers, independent review, publication and any installation belong to the coordinator's subsequent work. This report supplies neither portable model/authority attestation nor a completed procedure-installation claim.

Open facts that can change the next increment:

- Which existing native tasks are actually loadable or addressable by each adapter without creating a different execution owner.
- Which Wave 1 cloud callers can reach and authenticate to the candidate MCP/API surfaces.
- The chosen T3 release/deployment and its actual outside-caller tools; the examined current-main contract cannot be assigned to v0.0.45.

- End-to-end message origin, admission, receiver consumption, reply correlation and domain result for every direction.

- Actual setup effort, provider charges, resident footprint and maintenance burden.
