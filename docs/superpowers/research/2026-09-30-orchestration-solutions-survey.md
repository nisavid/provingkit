# Orchestration mechanisms and methods for Praxis

The surveyed sources offer useful mechanisms for source-correlated handoffs, selective observation, recovery, and economical evaluation. They support comparing small adaptations through the existing owners. They do not establish a preferred framework, continuation architecture, cadence, or economic ranking for Provingkit.

This catalog supplies [Survey existing workflow and multi-agent orchestration solutions](https://github.com/nisavid/provingkit/issues/346). The sibling [continuation synthesis](2026-09-30-continuation-synthesis.md) compares these findings with conceptual, native-capability, and historical evidence. The [whole-Kit method handoff](2026-09-30-whole-kit-method-handoff.md) carries broader engineering questions to the separately scoped follow-up.

## Evidence and fixed contracts

**Project claim** denotes a project's documentation or design assertion. **Inspected source** denotes implementation shape or an authored test assertion retained in the research packet. The source reads were selective; a test discussed here was not executed in this survey. **Published evaluation** denotes the specified authors' reported study, without local reproduction. **Retained observation** denotes dated native or historical evidence from the other lanes. **Inference** and **proposal** describe comparisons and possible owner work. Integrity checking establishes artifact identity, not semantic coverage or runtime correctness.

The [accepted domain](https://github.com/nisavid/provingkit/issues/96#issuecomment-5721914053), [cohort](https://github.com/nisavid/provingkit/issues/144#issuecomment-5745003755), and [kernel](https://github.com/nisavid/provingkit/issues/157#issuecomment-5745374858) remain inputs. Praxis reconciles effort obligations through a workflow-independent kernel, focused procedures, and optional adapters. The immutable, versioned Effort Envelope keeps grants, claims, ownership, source evidence, and lifecycle distinct; its validation, reconciliation, and assessment primitives do not actuate external operations. Rolecasting retains topology, model selection, and dispatch; Versionkeeping retains Git and worktrees; Mergecraft retains PR operations; Tricritical retains general review; Artifact Customs retains component lifecycle; Proseweaving retains generic prose. A completed worker increment is not accepted whole-effort completion.

Aeon Bell retains its [registered external-condition scope](https://github.com/nisavid/provingkit/blob/ce12d1c1211e7641936dec176fae0a06b0a29024/plugins/praxis/skills/aeon-bell/references/native-monitor.md). Owners register, remove, or rearm episodes; the monitor does not discover arbitrary unfinished efforts. Its [engine contract](https://github.com/nisavid/provingkit/blob/ce12d1c1211e7641936dec176fae0a06b0a29024/plugins/praxis/skills/aeon-bell/references/engine-cli.md) separates persisted registration, runnable scheduled coverage, accepted send, and receipt/action. Human waits, explicit pauses, and standby remain controlling. No surveyed timeout auto-resolves a human question or enlarges monitoring scope.

## Deep comparisons and adverse corrections

### File handoffs and monitor causes

Dispatch v3.0.0 is an instruction skill hosted by a live Claude conversation. Claude workers use the host Agent tool; other CLIs run as background commands. Numbered question, answer, and `001.done` files distinguish stages; global `ipc/.done` marks completion. Temporary-file rename publishes answers. Saved plan/context/answer material can seed a replacement worker, but cannot restore in-flight execution or establish external-effect outcomes. [Skill][dispatch] and [actual referenced IPC contract][dispatch-ipc] support these source distinctions.

Both supplied monitor examples check global completion first, then unanswered question, then timeout. Completion and question exit zero; timeout exits one. The subsequent handler describes every notification from the monitor ID as a worker question with a live worker. It supplies no cause branch. Reading current files can establish a present condition, while a delayed notification can concern an older condition. Startup reconciliation selects questions with absent answers; neither selected instruction path supplies a rule for an existing answer without worker acknowledgment. Publication-before-ack, ack-before-observation, stale notices, timeout races, and answer-after-worker-exit remain useful adverse cases.

The worker's approximately three-minute human-answer exit policy is foreign behavior, not a proposed local wait policy. README claims about effective context and no loss lack a captured controlled evaluation. Dispatcher/worker lifetimes, file inspection, repeated context loading, and polling all cost resources; their amount is unmeasured. R2 strengthens the distinction between monitor exit cause and request receipt without qualifying a runtime.

### Change detection and delivery routes

Agent Deck's OS daemon calls `heartbeat-tick`, sends with `--no-wait`, and commits suppression after send-command success. Its [tick builder][deck-tick] fingerprints sorted waiting/error session views, inbox count and exact-byte digest, and a rules stamp. No actionable state clears the fingerprint; read errors bypass ordinary equality suppression. The rules stamp is size/mtime, not content identity. Persistence uses temporary-file rename without fsync shown in that function.

The CLI's commit path compares the rendered message after rereading state. Changed inbox bytes can leave that message unchanged. This is an inferred dependency-correspondence gap, not an observed dropped wake. Authored tests assert unchanged suppression, recurrence, same-count inbox change, and failed-send retry with fixtures/fake commands; none was run here.

The [Python bridge][deck-bridge] has another heartbeat with in-memory suppression. Its send helper can return an accepted-turn receipt on completion timeout; the sampled heartbeat discards that receipt, leaves suppression uncommitted when `ok=false`, and continues. Other bridge handlers have late-reply facilities. Separately, [send transport][deck-send] distinguishes a queued write, an observed but uncorrelated response, and unknown busy outcome. [Queue restart tests][deck-queue] assert no retyping while an orphan child runs, newly landed transcript correlation, and unknown settlement when child/result vanish. The inspected evidence does not show that the OS heartbeat takes that queue route. Journal events follow the send verdict.

R2 therefore corrects any product-wide “no receipts” reading. Accepted send, reply completion, durable receipt, useful receiver work, and effort satisfaction remain distinct. Persisted tick suppression, in-memory bridge suppression, and queue recovery cannot be pooled into one restart guarantee. A narrow observation/wake adapter would need exact CLI versions/parsers, notifier lifetime, route identity, human-answer behavior, and receiver-origin evidence. No real receiver or restart experiment occurred.

### Lost execution, retained evidence, and bounded finalization

Overstory's [local turn lock](https://github.com/jayminwest/overstory/blob/ff38f3f76f084abcc34f519bcaa69580f6e53cf1/src/agents/turn-lock.ts) combines an in-process chain with a SQLite claim under `BEGIN IMMEDIATE` and stale-PID handling. This serializes occupancy for a local agent key. Its mutable JSON checkpoint does not establish an atomic crash-durable transaction with mail/Git state. The archived README points to Warren and describes cost/error/debugging/merge-conflict concerns as project commentary, without measured adverse rates.

Warren's [restart scenario][warren-restart] asserts a failed local run with `sandbox_run_lost` and retained pre-restart events. The in-process LocalRunStore is lost. It does not assert a resumed local worker. Its separate [finalization source][warren-finalize] targets a still-running Kubernetes pod with missing finalize intent after a grace period. Row/run/provider checks and in-process guards limit that operation. Classification prefers a hint, then event evidence, then defaults to success; that fallback is authored behavior, not a verified effort result. Its tests use an in-memory DB, fake provider/reap, and injected clock.

R2 corrects R1's compressed restart description: event preservation, live execution, and missing finalization are three subjects. Kubernetes finalization tests cannot substantiate local process recovery. Harvesting these adverse distinctions avoids adopting the success fallback or Warren's broad deployment/Git/delivery control plane.
