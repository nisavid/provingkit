# Jev experiment configuration routes

Codex CLI can select a dedicated Jev experiment profile while ordinary sessions keep their existing settings. Claude Code offers launch-specific settings controls, with different inheritance rules. The Codex profile route has also been exercised through native per-hook trust review; model behavior is a separate qualification.

The initial research used installed CLI help and public primary documentation. The subsequent Codex trust check below opened the native TUI without submitting a model prompt.

## Codex CLI

Installed `codex-cli 0.158.0` supports `--profile jev`, which loads `$CODEX_HOME/jev.config.toml` above the base user config; `-c key=value` supplies a higher-priority, single-run TOML override. Current Codex documentation specifies the same profile-file form and says the old `[profiles.jev]` form is no longer selected by `--profile` as of 0.134.0. [CLI configuration](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles), [configuration precedence](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence).

A named profile is the smallest candidate if the existing normal hook entries stay disabled. Put only the reviewed Jev hook definition in `jev.config.toml`, then start the experiment with `codex --profile jev -C <experiment-directory>` (or `codex exec --profile jev -C <experiment-directory> ...`). Ordinary invocations do not select the profile. The event, matcher, handler path, and trust action must be chosen from the reviewed hook contract; this research does not supply them. Codex supports inline TOML hook entries in config files and requires review/trust of non-managed hook definitions before they run. [Inline hook form](https://learn.chatgpt.com/docs/config-file/config-advanced#hooks), [hook trust](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks).

A profile is an overlay, not a clean hook namespace. Codex loads matching hooks from every active source; a higher-priority profile does not remove lower-priority user, project, or plugin hooks. Setting `features.hooks=false` would turn off the experiment hook too. `-c` can add or change a config value for one run, but cannot make accumulated hook sources exclusive. [Hook sources and accumulation](https://learn.chatgpt.com/docs/hooks#where-codex-looks-for-hooks), [hook feature](https://learn.chatgpt.com/docs/hooks#turn-hooks-off), [one-off overrides](https://learn.chatgpt.com/docs/config-file/config-advanced#one-off-overrides-from-the-cli).

For a separate Codex settings and state root, create a dedicated directory before launch and use `CODEX_HOME=<dedicated-directory> codex --profile jev -C <experiment-directory>`. This relocates config, auth, logs, sessions, skills, and package state. It therefore needs a separate login or another authorized credential route; do not copy a live auth file merely to make the experiment start. Project, system, managed, and enabled plugin sources still need inspection for the actual launch. `codex exec --ignore-user-config` is not a shortcut for combining a clean base with a named profile: the current upstream loader applies that flag to both base and profile user layers; this specific loader behavior was not exercised on the installed 0.158.0 binary. [CODEX_HOME](https://learn.chatgpt.com/docs/config-file/environment-variables#core-locations), [credential storage](https://learn.chatgpt.com/docs/auth#credential-storage), [upstream loader](https://github.com/openai/codex/blob/main/codex-rs/config/src/loader/mod.rs).

## Claude Code CLI

Installed Claude Code is 2.1.284. `--settings <file-or-json>` adds session settings above user/project/local files, but hook entries merge across settings sources; a high-priority JSON file alone will not remove normal Stop, PostToolUse, or SessionStart hooks. `--setting-sources` selects which of `user`, `project`, and `local` sources load. The installed CLI also accepts `--plugin-dir` for one-session plugin discovery. [CLI flags](https://code.claude.com/docs/en/cli-reference), [settings precedence](https://code.claude.com/docs/en/settings#settings-precedence), [hook merging](https://code.claude.com/docs/en/hooks#hook-locations).

For a Claude CLI exploration that retains the repository's project skill, the small candidate is a launcher with a separate `CLAUDE_CONFIG_DIR`, `--setting-sources project`, and `--settings <dedicated-jev-settings.json>`. The Sys1 Provingkit candidate contains `.claude/skills/handling-sys1-incidents/` and no `.claude/settings.json` or `.claude/settings.local.json`; that candidate inventory is only a snapshot. The dedicated directory keeps user settings, locally installed plugins, and sessions apart from normal Claude Code, while `project` should keep project skill discovery available. Whether that skill actually appears under this flag combination is untested. Plugins synced from the signed-in claude.ai account can still load in terminal sessions, so the active plugin hook inventory needs inspection; project settings or plugins added later would also need a fresh source check. A launcher candidate, after a reviewed JSON hook file and separate login exist, is:

```sh
CLAUDE_CONFIG_DIR="$HOME/.claude-jev" \
  claude --setting-sources project \
  --settings "$HOME/.claude-jev/jev-settings.json" "$@"
```

A plugin package can instead be supplied explicitly with `--plugin-dir <reviewed-plugin-root>`; a skill directory alone is not a plugin root. [Setting sources and settings file](https://code.claude.com/docs/en/cli-reference), [CLAUDE_CONFIG_DIR](https://code.claude.com/docs/en/env-vars#environment-variables), [session plugin flag](https://code.claude.com/docs/en/cli-reference), [hook locations](https://code.claude.com/docs/en/hooks#hook-locations), [account-synced plugins](https://code.claude.com/docs/en/desktop#extend-claude-code).

`CLAUDE_CONFIG_DIR` also separates claude.ai login state for ordinary accounts, so a first launch may require login; Claude Console sign-ins without an API key have a documented exception and may be shared outside that directory. This is an operational settings split, not adversarial containment. `--restricted` would suppress user/project/local settings and permit `--settings`, but it also changes built-in tool availability and previously suppressed project discovery in this task. `--bare` and `--safe-mode` skip hooks, so neither is a Jev hook experiment route. [Authentication](https://code.claude.com/docs/en/authentication#log-in-to-claude-code), [restricted and bare modes](https://code.claude.com/docs/en/cli-reference).

Claude Desktop Code sessions share CLI configuration files, and the documented flag-equivalence table gives no per-session equivalent for these settings-source controls. The shell launcher should be treated as CLI-only, not as a Desktop Code profile. The Linux desktop app is now available in beta; Desktop and terminal sessions signed in to the same account can also load account-synced skills and plugins. [Desktop shared configuration and CLI comparison](https://code.claude.com/docs/en/desktop#shared-configuration), [Desktop plugin sources](https://code.claude.com/docs/en/desktop#extend-claude-code).

## Native Codex profile review

Codex CLI 0.158.0 rejected `app-server --profile` before initialization: the flag is supported for runtime commands and `codex mcp`, but not the standalone app-server command. That failed metadata probe is not a hook or model result.

The profile-aware TUI provided the supported route. Its `/hooks` browser displayed the synthetic PreToolUse, PostToolUse, and Stop handlers alongside ordinary hooks. Each candidate was inspected and trusted individually. Codex wrote the three hash-bound trust records into the selected profile's config file; the normal user config remained byte-for-byte unchanged. The ordinary Jev entries remained disabled. No model prompt was submitted during this review. Other enabled SessionStart hooks may execute when the TUI opens, so this is not a hook-free session. [Profile selection](https://github.com/openai/codex/blob/rust-v0.158.0/codex-rs/tui/src/startup_orchestration.rs#L90-L95), [native hook review](https://github.com/openai/codex/blob/rust-v0.158.0/codex-rs/tui/src/hooks_rpc.rs#L21-L92), [selected config writes](https://github.com/openai/codex/blob/rust-v0.158.0/codex-rs/app-server/src/config_manager_service.rs#L203-L216).

This observation qualifies profile selection and individual trust persistence for the inspected configuration. It does not establish model behavior, hook delivery during a tool call, process containment, or default Jev installer coverage. The synthetic Codex adapter matches `apply_patch`, which the default Jev installer does not cover. The [built correction report](2026-09-28-sys1-built-correction.md) keeps the native behavior evidence separate.

Before using a different profile or handler, inspect its actual sources and commands again. Claude's dedicated-directory candidate remains untested; inspect `/status` and `/hooks` in an authorized test session before claiming its effective inventory. The inspected normal Codex Jev entries were disabled. The inspected Claude settings had no Jev PreToolUse entry; Jev Stop, PostToolUse, and SessionStart entries remained. This investigation does not re-enable normal-session Jev.
