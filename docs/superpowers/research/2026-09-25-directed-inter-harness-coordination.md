# Directed inter-harness coordination: routes and proof

A small operation contract with pair-specific native adapters is the best next hypothesis. Start with notification to an existing peer, the need demonstrated by the retained incident. Use ACPX for newly controlled ACP sessions, and expose a qualified adapter through MCP only when that improves how a harness calls it. No inspected protocol alone discovers arbitrary existing peers, preserves their authority, delivers a message, and proves the requested work finished.

## Scope and evidence

This report resolves [Research directed inter-harness communication and recovery](https://github.com/nisavid/provingkit/issues/191) within [Plan lean inter-harness peer coordination](https://github.com/nisavid/provingkit/issues/190). It compares public primary sources and read-only local surfaces as of 2026-09-25 at Provingkit baseline [7ce7f56](https://github.com/nisavid/provingkit/tree/7ce7f568fc38e710076c1ffce6ad07c0009986ed). No live harness message, task, session, permission, installed skill, or framework was changed for this research; the Wayfinder issues above are the authorized tracker changes. [The classifier map](https://github.com/nisavid/provingkit/issues/165) retains its own work; [the model-policy map](https://github.com/nisavid/provingkit/issues/174) is complete.

Evidence labels here are narrow. **Specification/source** establishes a named version's contract or implementation. **Documented** means the provider describes the operation. **Local surface probe** means help or tool schema exposed it, without a send. **Historical observation** means one retained sender/receiver outcome. **Inference/proposal** needs qualification. None of the first three labels proves live interoperability on this host.

The private incident packet retains a credential-free plan and frame, receiver-origin record, and explicit acknowledgment. On 2026-09-25 a Codex coordinator notified an existing Claude Code 2.1.280 task hosted by Claude Desktop through that receiver's authenticated local peer inbox. The receiver recorded peer origin, verified the handoff digest, and acknowledged it. The ambient terminal CLI was 2.1.282, a different executor. The send did not create, fork, resume, or restart the receiver or change its account, model, permissions, or worktree. This is **historical observation** for one Codex-app-to-Claude-Desktop direction, not a public API claim; private session details are omitted. The [public handoff context](https://github.com/nisavid/provingkit/issues/178#issuecomment-5834632798) identifies the related work, not independent inbox proof. The earlier receiver was not revalidated as a current live target in this increment.

## Separate the operations

| Operation | Required result | Relevant interfaces |
| --- | --- | --- |
| Notify existing peer | Intended existing receiver accepts one informational message; no new work contract. | Codex send/queue within Codex, Claude SendMessage within Claude, historical Codex-to-Claude inbox. |
| Request work | Receiver accepts a bounded contract and returns a correlated result or rejection. | Native task/child/team/turn routes; Cloud Agent run; or a correlation-capable adapter. Raw notification is insufficient. |
| Create task/session | New identity with workspace, account, model, tools, ownership, and creation authority. | Codex create/spawn/thread start, Claude agent/team creation, Cursor Cloud Agent creation, ACP session/new. |
| Inspect status/results | Caller distinguishes queued, running, terminal, unavailable, and unknown and retrieves results. | Codex wait/read/events, Claude views, Cursor run status/stream, ACPX status/watch; assurance varies. |
| Reply | Original requester matches receiver response to request. | Native same-harness return address or cross-harness correlation and routing. Synchronous tool output is not a later peer reply. |
| Continue existing work | New turn reaches the same eligible task under its current account, workspace, model, and permission binding. | Codex follow-up/queue/turn, Claude messaging or session continuation, Cursor resume/later run, ACP prompt. Stored ID alone is insufficient. |

A complete adapter path discovers the candidate; binds surface, version, executor, session/worktree and account route; checks operation authority and receiver policy; submits one correlation ID; observes acceptance and receiver delivery; then awaits the required acknowledgment or completed result. Busy recipients may queue or defer; idle ones may wake if the native contract supports it. Restart can invalidate process, socket, account route, or session mapping. Stale IDs, unavailable recipients, refusal, and ambiguous post-send outcomes require distinct results. This path is a **proposed adapter obligation**, not a current jointly enforced guarantee.

Report **submitted** (sender returned), **accepted** (target admitted), **delivered** (receiver record names the ID), **acknowledged** (receiver explicitly confirms), and **completed** (requested work plus verification) separately. The incident reached acknowledgment, not completion of a new assignment. A socket write or peer message never supplies operator approval.

Two designs remain hypotheses. Pair-specific native commands use the fewest moving parts for one direction, but each can define acceptance and reply differently. A small shared operation/result contract would make those distinctions visible to callers, at the cost of an extra adapter interface. Compare both on the first two directed paths before standardizing more than the vocabulary.

A full broker helps if repeated cross-product requests need registered presence, asynchronous replies, and restart recovery across several active pairs. Agent Intercom rejects an unregistered target rather than reaching an arbitrary offline peer; its [Claude worker](https://github.com/dataforxyz/agent-intercom-claude/blob/7de76e5d4f6461b007b19dfc5dbcf11928868adc/claude/worker-daemon.ts#L246-L297) and [Codex sidecar](https://github.com/dataforxyz/agent-intercom-codex/blob/ff1f0e2258ded8c81ae6fcf33048c78a7f8580fe/codex/bridge-daemon.ts#L474-L550) can wake their own configured sessions. One incident does not establish that infrastructure demand. ACPX is a sound candidate when creation of a leader-owned external session is authorized, not when an existing operator-owned peer must be notified. MCP and AXI can present the same backend. MCP specifies its client-server [transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), but neither layer selects the backend route to a peer or establishes its delivery semantics.

## Measuring fluent and lean

Measure by operation, direction, and pinned version, retaining denominators rather than a single success flag.

| Dimension | Proposed measure |
| --- | --- |
| Outcome/recovery | Recipient resolution, acceptance, delivery, acknowledgment, verified completion, unknown and duplicate outcomes after timeout/restart/retry. |
| Effort | Recipient facts the agent/operator needs, setup steps, approvals, tool calls, visible tokens, follow-up calls, interventions. |
| Time/cost | Discovery-to-submit, submit-to-accept, accept-to-ack, request-to-completion; actual provider tokens/prices at probe time and idle process cost. |
| Maintenance | Dependencies, config surfaces, source and instruction size, version drift, number of pair qualifications. |
| Observability/preservation | Correlation ID end to end; session, account route, model, permissions, worktree before and after. Requested controls remain separate from enforced controls. |
| Authority | Peer-origin text remains distinct from Ivan's approval; user-owned task creation/steering is separate from leader-owned child work. |

Keep three evidence layers separate. **Instruction evals** test whether the agent chooses the operation and stops on missing authority or ambiguous delivery. **Adapter contract tests** use disposable fake backends for discovery, stale IDs, partial writes, errors, and duplicate handling. **Harness qualification** requires real disposable sender/receiver sessions at pinned builds, receiver-side evidence, preservation checks, and failure probes. Green source tests are not runtime qualification. Change to the adapter, receiver, settings, or evidence dependencies makes its pass stale.

| Small probe | Required observation | Additional authority |
| --- | --- | --- |
| Codex app to disposable Claude Desktop, idle and busy | Fresh exact receiver discovery; one correlated notification; target acceptance, receiver-origin delivery, explicit ack; unchanged settings. | Create disposable receiver and send actual messages. The historical task is not a fixture. |
| Disposable Claude to Codex, request/reply | Bind Codex thread/account; accept bounded request; correlate and verify reply. | Create/send through a separate disposable Codex task. |
| ACPX to compatible backend | Create leader-owned session, prompt, watch terminal result, continue. Confirm new-session semantics. | Invoke/install ACPX and create disposable backend session. |
| Stale/unavailable/refusing recipient | Wrong ID, restarted process, changed account/worktree, offline or refusal yields distinct result. | Synthetic adapter tests first; real restarts only in isolated sessions. |
| Ambiguous send/retry | Lose sender response after submission; reconcile receiver correlation before retry; no unsupported exactly-once claim. | Fault injection only in disposable fixtures. |
| Authority boundary | Peer text asks for publication or receiver denies admission; preserve denial, no permission change or approval promotion. | Synthetic eval first; live classifier probe needs separate scope. |

A successful command exit without substantive result proves only caller return. A synchronous tool result may itself carry acceptance or completed work evidence; classify what its returned fields actually establish. Delivery needs receiver evidence tied to the ID; acknowledgment needs receiver action; completion needs the requested result and its verification. Report any level the product cannot expose as **unobserved**.

## Recommendation and decision

1. **Standardize the words, not a wire protocol.** Define notify, request, create, inspect, reply, and continue, with target binding, authority, correlation ID, and separate outcome states. This is a proposed minimal operational contract, not an issuer or a general orchestration platform. Leave session IDs, admission, busy handling, and restart behavior adapter-specific.
2. **Qualify one directed pair at a time.** First test Codex app to an existing disposable Claude Desktop Code receiver, because it directly addresses the observed gap. Prefer a documented native SendMessage actuator if a sender-callable path exists; otherwise assess a version-pinned adapter to the receiver's ordinary inbox under its current policy. Reverse Claude-to-Codex and Codex app-to-CLI identity binding are separate follow-ups. Preserve receiver account, model, permissions, worktree, and ongoing work.
3. **Keep presentation small.** A narrow CLI using AXI's ergonomics is a sensible first caller surface for shell-capable harnesses. Add MCP only when a target needs tool discovery or measured calls/context improve. Evaluate ACPX for newly owned ACP-compatible sessions separately. Avoid broker infrastructure until multiple pair qualifications justify it.
4. **Capture the procedure at its owner after qualification.** [Rolecasting topology](https://github.com/nisavid/provingkit/blob/7ce7f568fc38e710076c1ffce6ad07c0009986ed/plugins/rolecasting/topology.json) owns route topology, task ownership, authority, and assurance; choosing-agent-models owns model selection for actual new or continued work. An informational notification should preserve the existing peer's observed model rather than silently choose another. Future Praxis work may consume status for work stewardship but does not own transport. Task Witness is optional future equipment, not a current issuer. This method remains a proposal until the route, maintained source, invocation pointer, final revision, and live evidence are settled.

The smallest next increment is **disposable qualification of Codex app to Claude Desktop notification**, limited to notification and acknowledgment. Acceptance requires fresh target/version/executor binding; one accepted message at the intended task; receiver-origin delivery and explicit ack with the same ID; preserved account/model/permission/worktree; truthful busy/idle, stale, and ambiguous outcomes; and clean instruction, adapter-contract, and live passes on the same final candidate. That qualifies only this direction, operation, build range, and settings. Stop expanding when the route is usable; add directions on measured need.

[Choose the first inter-harness route and qualification contract](https://github.com/nisavid/provingkit/issues/192) holds the next operator decision: accept this first path and disposable probe authority, or select a documented-only route even if it cannot notify the existing Desktop peer directly. Current evidence does not establish a stable public cross-product peer API, a Codex app/CLI shared identity here, Cursor local-peer injection, or a reason to adopt a broker.
