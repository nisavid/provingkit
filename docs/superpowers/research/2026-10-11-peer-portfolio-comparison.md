# Wave 1 coordination fabrics and caller reachability

This report gives a source-bound comparison of the five Wave 1 endpoints, their 20 directed pairs, and the smallest useful probes to consider next. It is an exploration checkpoint: the three independently frozen first inventories were cross-examined, corrected in separate addenda, reviewed, and published. No candidate was installed, called against a private task, or live-qualified by this packet. No pair has demonstrated receiver delivery and a correlated result. The accepted [first ChatGPT in Codex mode → Claude Desktop-hosted Code notification](https://github.com/nisavid/provingkit/issues/212) retains its separate, stronger qualification contract.

Their [OpenAI first inventory](https://github.com/nisavid/provingkit/blob/48150f1af4e71a8cf9b7d4a9ac42240832bdd4e0/docs/superpowers/research/2026-10-10-peer-portfolio-openai.md), [Claude first inventory](https://github.com/nisavid/provingkit/blob/fc990e98646e66001a790b02896734ae30722cc0/docs/superpowers/research/2026-10-10-peer-portfolio-claude.md), and [shared first inventory](https://github.com/nisavid/provingkit/blob/e73bce3517e77f46d0dab2b693fafcf3b2760c2f/docs/superpowers/research/2026-10-10-peer-portfolio-shared.md) preserve discovery. ## Operation and task-population evidence

The vectors below describe source-declared calls or partial mechanisms, not satisfaction of the operation contracts still to be chosen and not live passes. Positions are **notification / work request / creation / inspection-status-result / reply / continuation**. `S` means the source declares an operation-shaped call for that route and its own eligible population; `P` means a necessary component or a narrower result only; `?` means not established by this packet; `U` means unsuitable for the claimed task population. In the independently opened profile, `–` marks creation as inapplicable to the task being addressed; the created profile separately assesses creation. A source-supported call still requires real caller access, consent, a bound target, receiver observation and correlation. An independently opened task may belong to a native harness, T3, OpenClaw, Hermes, or another host. Host ownership does not establish that our controller created it. Every row names its eligible population; native Wave 1 tasks opened outside a host cannot borrow that host’s capabilities. Grouped entries use `?` where their distinct routes cannot honestly share a vector; the subprofile table below preserves their differences. “Reply” means a return from the receiver through the claimed route; an invoking process receiving a completion stream is narrower than an independently initiated later reply.

## Cross-examination retained for the decision

1. **Identity and ownership:** a stored Codex/Claude ID can be valid while its active writer/query belongs to another process. Codex rejoin needs the addressed App Server's manager; a cold stored resume can acquire a writer or fail, and an eligible idle cache entry may restart under overrides while a loaded observable one keeps its current behavior. Claude SDK and ACP resumes may create another query. No source names the actual installed GUI owner. [Codex owner path](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/thread-store/src/local/live_writer.rs#L40), [Claude ACP reuse](https://github.com/agentclientprotocol/claude-agent-acp/blob/4e1fc1e8df2b9af3b1b2d6880ba90c5862283ba8/src/acp-agent.ts#L9329).
2. **Queue, steer, and result:** Codex queue can store unloaded input; an operating shared-store watcher may later wake an eligible loaded idle owner. Direct start requires loaded idle state. `turn/steer` requires the active turn ID. Claude cloud CLI queues and exits; native Claude busy delivery is between tool calls, while Desktop tab messages wait for current work. ACPX no-wait, Intercom broker delivered, Agent Bridge delivered, SDK worker processed, and a started turn have different boundaries. None is semantic work or an independent reply. [Codex queue service](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/ext/queue/src/service.rs#L405), [Claude cloud](https://code.claude.com/docs/en/claude-code-on-the-web#send-follow-ups-from-the-cli).
3. **Creation versus continuation:** Codex fork, Claude fork, transfer/import, OpenClaw Continue as branch, and Hermes unknown-ID ACP resume can produce new identities. ACPX ordinary reconnect may replace a failed session; imported sessions require provider load. Intercom Codex catches resume failure and starts a new thread. Hermes history replay can return partially. Strict continuation must record requested and resolved native IDs plus a context marker, and reject or separately classify replacement; wrapper-level success or equal outer ID is insufficient. [Hermes manager](https://github.com/NousResearch/hermes-agent/blob/v0.21.6/acp_adapter/session.py#L176), [Intercom fallback](https://github.com/dataforxyz/agent-intercom-codex/blob/ff1f0e2258ded8c81ae6fcf33048c78a7f8580fe/codex/bridge-daemon.ts#L473).
4. **Plugin and wrapper selection:** OpenAI's Claude plugin resume is associated-job selection, including unsuccessful terminal jobs and fallback search, not an arbitrary supplied ID. AI Functions has an explicit stored Codex ID but a separate SDK owner; active notification is user-input steer, idle notification is only buffered. mcp-agents creates one-shot workers with declared model fallback/retry, not preserved Desktop execution. No model substitution or configuration override is silently accepted as preservation. [AI Functions connection](https://github.com/strands-labs/ai-functions/blob/145efc8398dc1a0d91fface870a240e6d813a0b2/src/ai_functions/codex/codex.py#L673).
5. **Cloud and bridge identity:** Codex current Cloud, legacy Cloud, CLI backend and ChatGPT Work histories are distinct until a real reference mapping is shown. Claude browser query is an active client and declares header names; accepted external credential scope, initialization effects, concurrency and Desktop-to-remote mapping remain unknown. Worker bridge registration advances an epoch and is not a passive observer. T3 outside OAuth cannot borrow in-thread delegation; main source is not v0.0.45 behavior. OpenClaw local branch and paired-node continuation are separate profiles.
6. **Ownership depends on the actual runtime and namespace:** AI Functions' docstring asserts cross-process single-writer refusal; OpenClaw v2026.10.1 documents no exclusive cross-process runner/approval-owner lease. The OpenAI addendum inspected a concrete Codex 0.162.1 writer lock in the same Codex-home namespace. That primary source narrows the conflict: a data-store writer lock and an application’s runner/approval-owner lease are different protections. AI Functions’ broad dependency range and OpenClaw’s chosen runtime are not bound to the inspected Codex implementation. A later scoped coexistence check must identify actual builds, homes, stores, and active owners; this packet establishes no runtime safety or cross-home exclusion. [Wrapper assertion](https://github.com/strands-labs/ai-functions/blob/145efc8398dc1a0d91fface870a240e6d813a0b2/src/ai_functions/codex/codex.py#L61), [OpenClaw limit](https://github.com/openclaw/openclaw/blob/v2026.10.1/docs/plugins/codex-harness-runtime/threads.md#L61).
7. **The first Desktop route has a stronger obligation:** the [reviewed qualification continuation](https://github.com/nisavid/provingkit/blob/34ab07d80ace058d9c009c79bd810f75d36bc0ac/docs/superpowers/research/2026-10-10-qualification-continuation.md) still requires fresh exact-peer consent, receiver-origin delivery and explicit correlated ACK, before/after applied model, effective query account/org/auth route, complete applicable Code/Desktop permissions and pending changes, worktree, raw selected-main cwd, bounded acquisition and unknown-outcome reconciliation. Live idle and busy delivery remain qualification obligations. Busy-task resumption and predeclared context canaries are diagnostic evidence; they do not add a pass/fail context-retention threshold. Model/worktree source coverage is conditional; account, complete permissions, and cwd remain qualification gaps. Main-turn context lifetime remains a diagnostic uncertainty. SDK `resolveSettings`, near-simultaneous getters, hooks or transcript readers do not close those applied-state gaps. Basic portfolio operation proof is a separate, weaker profile, not a replacement.

## Decisions and procedure proposal

The [portfolio map](https://github.com/nisavid/provingkit/issues/533) has already set six operations, two task populations, exact references or explicit creation contracts for initial probes, receiver/result evidence, idle/busy distinction, separate restart and stronger preservation profiles, and the 30-active-minute reassessment rule. These are discoverable settled requirements, not choices to reopen. The next targeted research is actual installed build/deployment and tool schema, caller auth/egress, task-owner/store identity, receiver result reader and missing Desktop applied-state producers; no operator preference can substitute for those facts.

The immediate choice in [Choose Wave 1 operation and evidence contracts](https://github.com/nisavid/provingkit/issues/538) is what each operation promises beyond the settled basic bar: what positive outcome completes notify, work request, creation, inspection, reply, and continuation; how partial, held, refused, stale, and unknown outcomes are exposed; who validates work results; whether a response stream counts only as synchronous return or supplies a later-addressable reply; what exact input and assurance each profile accepts; and which deterministic, behavioral, and live checks support those claims. These decisions need Ivan’s words. The registry’s source-declared vectors do not answer them.

After that contract, [Choose the maintained capability catalog and visual update procedure](https://github.com/nisavid/provingkit/issues/539) chooses the maintained source owner, schema, evidence/update/review procedure, and initial views. In parallel, [Choose the first basic capability prototype cohort](https://github.com/nisavid/provingkit/issues/540) chooses the first directed pair, operation, actual candidate version, and task population, then maps the specific source/synthetic and live-proposal work. The exact task or creation contract, text/data, read/write/provider/setup/interruption, and cleanup grant follows a concrete reviewed live proposal. Later choices can expand a useful result to reverse reply, discovery ergonomics, restart, or stronger preservation without treating those as already qualified. The full Desktop route remains separately governed by its accepted contract and the [next qualification-action decision](https://github.com/nisavid/provingkit/issues/529).

I propose, without installing equipment, that [reusable agent-panel workflow work](https://github.com/nisavid/provingkit/issues/306) capture a procedure with this trigger: before selecting or running a cross-harness probe, load the reviewed first inventory plus governing addendum and this join at recorded revisions; bind caller, exact receiver, owner, task relationship, wrapper/host/native/turn/message IDs and versions; define operation-specific receiver/result evidence, busy/restart scope, cost meter and stop/cleanup; reject replacement-as-resume and receipt-as-result; carry unresolved claims forward. A downstream probe would name that reviewed procedure revision and verify its output against those criteria. Placement, review, publication, targeted installation and invocation pointers remain later authorized work, not an outcome of this report.
