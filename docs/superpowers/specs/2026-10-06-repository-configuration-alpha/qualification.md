# Repository-configuration alpha qualification contract

This contract defines the evidence required for a useful Mergecraft repository-configuration alpha: five complete GitHub workflows, adaptable judgment, live personal/public and organization/private use, and fresh discovery and useful invocation in Codex, Claude Code, and Cursor. It is a proposal for [Define the alpha's behavioral qualification contract](https://github.com/nisavid/provingkit/issues/376). The operator authorized the two hosted fixtures, their create/test/retain scope, free standard GitHub Actions on the public fixture, and native Buildkite on the private fixture within verified existing allowance. No additional CI charges are authorized.

## Claims and phases

The alpha supports creating a repository, assessing existing configuration, adopting recommended defaults, making a focused change, and adding project-specific CI hardening, including authorized application through existing tools. Qualification establishes the selected representative cases and recorded limits. It does not establish an exhaustive settings catalog, every GitHub plan or owner arrangement, every client mode, or every workflow on every client.

| Phase | Completion evidence | Consumer |
| --- | --- | --- |
| Source and pre-deployment behavior | Canonical Skill/resources and truthful Mergecraft contracts; required validators and meaningful tests; independent review of current instructions and real agent traces; all selected behavior and hosted cases complete on the final candidate | Publish and install the qualified alpha |
| Publication and installation | Verified immutable published member artifacts, exact receipt bytes and modes, retained recovery inputs, actual installed correspondence and conflict disposition in each selected client | Verify the alpha through fresh client invocations |
| Fresh installed invocation | Ordinary-language discovery, useful task execution, and nearby non-invocation in fresh Codex, Claude Code, and Cursor sessions, each using the installed reviewed candidate | Delivery map destination |

The implementation phase does not depend on the installation it must first unblock. Source behavior may use an explicitly supplied real candidate in isolated workers or a supported temporary client package; these runs do not count as final installed discovery. Each evidence record names the claim and phase it supports.

Prompts supplied to the execution agent contain the user task, relevant policy, and ordinary project inputs; they do not reveal the expected branch or rubric. Independent evaluators inspect the actual tool trace, resulting state/source, and final answer. Structural plugin-eval analysis is additional evidence, never a substitute for execution.

Hold out at least two combinations joining these mechanisms and changing superficial details. Include matched no-skill runs where isolation makes the comparison meaningful; relative improvement alone cannot satisfy a required outcome.

## Discovery and client evidence

Use separate positive and negative discovery tasks. Positive ordinary-language requests cover each of the five intents across the corpus without naming the Skill or directing the client to its body. Nearby negatives include an ordinary code edit, a unit-test fix, a PR review, and an already-qualified merge. Those tasks may invoke their appropriate existing owner but must not acquire whole-repository configuration work or control changes.

For each of Codex, Claude Code, and Cursor, require fresh native client sessions over the installed candidate. Retain loaded member/Skill identity, actual body or native Skill delivery evidence, effective tool inventory, and the observed result. Two useful cases per client establish a bounded initial claim: an already authorized focused setting change with readback, and assessment/CI reasoning over contrasting content. Include ordinary-language positive discovery and at least two nearby negative cases per client. A no-op is positive application, not negative discovery.

Codex uses a fresh native CLI session for this client claim; current-app native workers can supply pre-deployment behavior evidence. Claude uses a fresh native CLI session with real Skill delivery and the necessary behavior tools. Cursor uses a fresh native Agent CLI session with actual deployed projection discovery/body reads and necessary tools. This contract does not add desktop/TUI/IDE qualification beyond those selected surfaces; broader claims require their own evidence. Launcher presence, a sentinel body, a project shim advertising an explicit path, or another client's result is insufficient.

Before each run, establish actual executable/version and supported flags, fresh session identity, authentication through its existing owner without retaining secrets, intended configuration inheritance, effective provider/Skill/tool inventory, and candidate resources. HOME isolation must not silently break the secret-exec launcher. Test real supported provider shadowing or otherwise demonstrate which candidate bytes were selected. Requested model flags and cooperative read-only instructions do not prove the effective model or product-enforced isolation.

## Live hosted cases and authority

The authorized fixtures are `nisavid/provingkit-repo-config-public-qualification` (personal/public, generated Python and content-contract project) and `nisavid-io/provingkit-repo-config-private-qualification` (organization/private, generated TypeScript project). They have not yet been created. Recheck names, actor permissions, owner/plan, effective inherited controls, and other writers immediately before dependent effects. A private 404 does not prove a name is free.

The operator authorized creation, generated source publication, repository-only settings/protections, fixture PRs and merges, bounded workflows, and positive/negative enforcement attempts. This scope excludes production repositories, organization-wide policy changes, entitlement purchase/activation, deployment credentials, and deletion. Use non-sensitive content because organization members may access the private fixture. Retain private control evidence privately and publish a value-free summary.

Live personal/public and organization/private cases must each include actual assessment/application and useful context-specific CI behavior. The public fixture establishes a useful CodeQL run matched to its supported language and a separate content validator through standard GitHub Actions. The private fixture establishes useful ordinary TypeScript CI through native Buildkite and a required external-result gate in GitHub. This combination qualifies two real CI producers; it does not claim observed private GitHub Actions event, permission, or orchestration behavior. Private CodeQL is not a selected entitlement claim; record any entitlement limit. Adding private Code Security later needs its own authority and evidence; organization/private qualification cannot be replaced by replay.

For hosted merge enforcement, isolate the claimed cause. Record the required result's producer/App identity, PR revision, event/path, current protection/ruleset, actor, bypass, and neighboring blockers. First demonstrate a valid control satisfying neighboring gates. Then vary only the claimed check failure or missing result, observe rejection attributable to it, and restore a passing result to observe acceptance. A failing build, draft state, absent approval, denied actor, or unknown inherited control cannot stand in for the selected cause. Skipped and missing results are separate states; do not assume that a skipped required check blocks merging.

Independent-review approval, CODEOWNERS eligibility, last-push approval, and Copilot approval enforcement are outside the live claim unless eligible actors are separately established. Their contextual handling can still be exercised in supplied fixtures. Harm cases use synthetic/replay conditions, without exposing real credentials.

For the private fixture, the operator authorized one retained Buildkite pipeline, `provingkit-repo-config-private-qualification`, in the existing `nisavid` Buildkite organization, with access only to the authorized private GitHub fixture. Use an eligible existing Linux hosted queue, preferably the two-vCPU Small shape; do not add users, create shared queues, alter existing pipelines, start a subscription/trial, or change organization-wide policy. The dotfiles native pipeline and versioned provider-settings record supply a method to adapt, not a pipeline to reuse or a proof of fixture access. Observe the actual source/result identity and ensure that a blocked build cannot satisfy the required gate before tests run.

Create and connect the pipeline with automatic triggering and dispatch disabled. Before admitting runs, establish the actual plan, queue shape, sufficient included Linux vCPU allowance, relevant storage/other allowances, and a reliable basis for avoiding additional charges. Use the smallest useful causal run matrix, explicit maximum trigger/job counts, no recurring schedule, minimal cache/artifact retention, and retained usage observations. The task ceiling is 400 Linux vCPU minutes, equivalent to at most 200 aggregate job minutes on a two-vCPU shape. It is not a platform-enforced cap or a reserved allowance. Before each job group, account for upload and execution jobs, retries, timeout/cancellation behavior, and other account activity; retain stopping margin within both the task ceiling and observed allowance. Do not admit unbounded subsequent uploads or automatic retriggers. Job timeouts and spend alerts alone do not establish a hard cap. Missing cost evidence holds affected execution. A paid alternative requires a concrete new decision; the earlier $10 Actions proposal grants no spending authority. Public larger runners and paid feature activation are not inferred.

Depot remains a prospective provider alternative; this qualification does not initiate or settle the broader Buildkite-versus-Depot adoption comparison.

After qualification, disable fixture workflows and automatic Buildkite triggering, and retain the repositories and fixture pipeline with their evidence and purpose documented, as authorized. Changes by another actor stop affected cleanup rather than being overwritten. Exact deletion would need its own authorization.
