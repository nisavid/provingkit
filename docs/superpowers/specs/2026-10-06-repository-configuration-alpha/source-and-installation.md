# Repository-configuration source and installation contract

This contract binds one repository-configuration Skill in Mergecraft to maintained source, an immutable member-alpha candidate, and a verified installation in Codex, Claude Code, and Cursor. It is a proposal for [Bind the alpha to maintained source and an installation contract](https://github.com/nisavid/provingkit/issues/375). Open deployment choices below must be resolved before this ticket is closed.

## Maintained interface

The canonical public Skill is `plugins/mergecraft/skills/configuring-repositories/SKILL.md`. Its interface accepts the requested repository outcome, supplied project context and policy, observed repository state, and the work already authorized. It covers creating a GitHub repository, assessing existing settings, adopting recommended defaults, making a focused configuration change, and adding project-specific CI hardening, including authorized application.

The Skill owns configuration judgment and its application through available native tools. Concise source-linked guides explain recurring settings relationships and verification hazards. Helpers are added only where repeated mechanical risk and behavior evaluation justify them. Uncataloged settings remain usable through current research and native tools; catalog membership is not an authority or support gate.

Its canonical manifest, generated Claude adapter, human entrypoints, public roster, interface metadata, development operation declarations, changelog, validator inventory, and ordinary content lock must agree with that responsibility and the added Skill. Existing public paths remain stable. Runtime instructions must work from the projected artifact, without development-only files excluded by the projection policy.

The source branch used for implementation starts from the freshly verified public default-branch commit. The accepted design remains linked to its published research revision. Neither a current-main source check nor a historical design review establishes behavior of the new Skill.

## Composition and correction ownership

Versionkeeping continues to own Git checkpoint and publication mechanics. Mergecraft's PR publisher continues to own PR publication when a PR is needed. General review and appropriate security scrutiny retain their established owners. A setting change does not acquire a Git or PR workflow unless its actual outcome needs one.

Configuration changes can invalidate observations consumed by existing workflows, including cached closure-policy observations in Issue–PR relation handling and required-check observations in readiness and merge work. The new procedure must disclose material changes and compose with the existing invalidation contracts. Qualification covers these affected consumers and direct discovery of the new interface; unrelated historical behavior is rerun only when its dependencies change.

Future corrections are maintained in the canonical Mergecraft source, reviewed and qualified against their affected behavior, published through the same member route, and delivered through its installation owner. Consumer tasks identify the producer revision they actually loaded and return useful corrections to that source owner. Immutable installed caches are never the correction source.

Installation is coordinated with the existing local-marketplace owner. The proposed route updates Mergecraft in Codex, Claude Code, and Cursor while preserving unrelated members' effective installed bytes, enabled states, and recovery inputs. Do not infer this route from supported artifact formats or the existing six-member alpha.4 rollout. The existing same-name Codex marketplace rebind requires removing and reinstalling every affected registration. The operator selected planning this broader native transition while preserving the other five payloads, versions, enabled states, and recovery inputs. This route selection does not authorize an installation window or establish host readiness. A dedicated member-only transition is not a prerequisite for this increment. No new registration alias is selected by this proposal.

Before installation, retain the prior member artifacts and their verified identities, target registration/source/scope state, relevant cache and provider-selection observations, and the supported restoration steps. Record owned and shared paths and other writers. An unexpected or unknown effect requires observation and reconciliation; do not blindly replay a mutation or restore a snapshot over another writer's changes.

The installation owner obtains the separately required shared-host write-window approval in its acting chat, applies the settled route, and verifies the resulting identity and conflict disposition. Any control needed to enable the selected CLI route remains an operational prerequisite even when observing or changing it requires another surface.
