# Choose security and quality controls from the evidence needed

Use this guide when selecting or assessing repository security, dependency, secret, vulnerability, and quality controls, or when configuring or assessing security reporting and support commitments. Start with the behavior and evidence the project needs; the controls below are conditional starting choices, not a universal profile.

GitHub product facts cited here were checked against the supplied primary documentation on 2026-11-15. Recheck the current documentation and target repository before relying on them: documented availability does not establish the target's plan, permission, configuration, coverage, or effective enforcement.

## Start with promises and proof

Name the desired behavior, threat, affected content, actor, and acceptance evidence before choosing a feature. Keep setup, coverage, and enforcement separate: enabling a service establishes setup; observed inventory or analysis of the relevant sources and events establishes coverage; an effective rule plus causal rejection establishes enforcement. A successful run or settings readback proves only its own layer.

Inspect owner, visibility, plan, permissions, inherited policy, bypass actors, current settings, actual producers, allowance, and maintained writers. Prefer the smallest existing qualified method. Honor informed alternatives and settled authority; do not replace a working project choice with a preferred profile, activate a paid feature, or broaden policy merely because a stronger control exists.

Keep ordinary support and sensitive security reporting distinct. Provide a monitored reporting route and state supported versions, response expectations, disclosure handling, backports, and service levels only when maintainers have accepted those commitments. A policy file or private-reporting setting is not useful coverage when nobody owns the inbox or remediation path; verify current private-reporting eligibility and permissions before recommending it.

## Separate dependency inventory, alerts, and maintenance

A dependency graph shown as enabled proves service state, not complete inventory. Use the [current ecosystem table](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems) to identify supported manifests, lockfiles, graph jobs, and submission methods, then observe the expected direct and transitive dependencies in the target. After changing manifests, generators, or submission routes, confirm that intended direct and transitive coverage remains present. Platform support or alert reporting does not prove that an upstream package is maintained, that the project supports its current version, or that anyone has committed to respond; establish those facts from the applicable maintainers and project policy.

GitHub currently recognizes workflows under `.github/workflows/` as dependency manifests and parses referenced actions and reusable workflows. Its [ecosystem table](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems) lists no static-transitive, Dependabot-graph-job, or automatic-submission route for Actions and says Dependabot vulnerability alerts for Actions apply to semantic-version references, not SHA references. When immutable Action references fit the project's trust policy, preserve verified pins to full commit SHAs and a reviewed, supported update route as described in [CI hardening](ci-hardening.md); listing a pin in the graph or enabling alerts neither gives it vulnerability-alert coverage nor updates it.

Treat security remediation and routine version freshness as separate policies. For each ecosystem, decide who owns security updates and version updates, which branches and manifests they cover, how often they run, and which changes may be grouped. Group changes only when their compatibility, urgency, evidence, and review route align; do not make an urgent remediation wait for an unrelated routine group. Choose cadence from exposure, release practice, CI capacity, and maintainer capacity rather than copying a fixed schedule.

Treat a malware finding as a possible compromise and containment problem, not an ordinary upgrade to group or dismiss. Dismissing development-scope alerts can reduce noise, but a development dependency may execute in builds or CI, reach credentials, or affect shipped artifacts. Use such dismissal only after mapping execution, reachability, privilege, and artifact influence, and preserve a route for exceptional impact.

## Select code scanning and gates for the intended claim

Follow [CI hardening](ci-hardening.md) for the conditional choice between CodeQL default and advanced setup and for verification of analysis coverage. Keep setup, coverage, and enforcement separate when using that guidance, and renew the conclusion when its material source, language, build, query, event, or setup inputs change.

The [GitHub Code Quality product](https://docs.github.com/en/code-security/responsible-use/security-and-quality-ai-features) is separate from the CodeQL `security-and-quality` query suite. It combines CodeQL quality queries with LLM analysis and fix suggestions, reports through pull-request bot comments and default-branch AI findings, and can generate coverage workflows; the suite is only an advanced-setup query selection. Treat product discovery, enablement, billing, and coverage as separate questions: confirm target access and the current billing model, make any enablement choice on that evidence, and verify the selected workflows, events, analyzed sources, and findings. The supplied source establishes neither target access nor current Code Quality pricing; the Security and quality page title and a suite selection establish neither product enablement nor coverage.

Choose a [native code-scanning merge-protection rule](https://docs.github.com/en/code-security/concepts/code-scanning/merge-protection) or a required status check according to the evidence each consumes. The native rule is separate from status checks and does not enable scanning; verify its current alert-threshold semantics and applicability before selecting a threshold. Preserve existing required checks when they establish producer completeness, tests, or behavior the native rule does not cover. The current native rule does not apply to merge queue groups or Dependabot pull requests analyzed by default setup, and an alert qualifies only when all identified lines exist in the pull-request diff. Verify ruleset eligibility, target matching, bypass, and these exclusions rather than treating the rule as universal enforcement.

Code scanning complements rather than replaces project tests, dependency evidence, content validation, and owning source validators. Validate workflow, manifest, generated projection, and instruction content through their maintained validators; generic syntax success is not semantic coverage.

## Protect secrets and distinguish remediation

Secret scanning and push protection address different points in the exposure path. Use detection for the repositories, history, patterns, and actors it actually covers; consider push protection when interrupting supported secrets before acceptance fits the workflow and has an authorized bypass and incident route. Verify current eligibility, pattern support, event coverage, bypass behavior, and reporting semantics before claiming either result.

The [generic unstructured-secret detector](https://docs.github.com/en/code-security/responsible-use/security-and-quality-ai-features) uses AI, and GitHub's current supported-pattern documentation says generic patterns have no validity checks; an optional AI regex generator is distinct from a maintained custom regex. [Custom patterns](https://docs.github.com/en/code-security/concepts/secret-security/custom-patterns) can be scoped at enterprise, organization, or repository level and can participate in push protection only where eligible. Confirm the exact feature, target access, scope, pattern and event coverage, AI use, and expected noise rather than treating these controls as one toggle. Common custom regexes can produce noisy matches and disrupt pushes, so a prudent validation proposal is a dry run with representative non-secret positive and negative samples before enforcement; never use real credentials or private alert contents as test data.

Before enabling [validity checks](https://docs.github.com/en/code-security/concepts/secret-security/validity-checks), disclose that GitHub periodically sends a detected credential to its issuer and tests it against the issuer's API; some secret types also require contextual data such as a host or URL. GitHub says it typically makes GET requests, chooses the least intrusive endpoints, and selects endpoints that do not return personal information. That response-data limit does not change the outbound disclosure: the credential and, for some secret types, host or URL context still leave GitHub for the issuer. The target's governance still controls that transmission. Treat `active`, `inactive`, and `unknown` as prioritization evidence, not proof that exposure is remediated.

If a maintained configuration exposes `suggestionAutofix`, establish its current semantics from the owning API documentation; its name alone does not prove autonomous repair, enforcement, or billing behavior. The supplied [Advanced Security billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-advanced-security) distinguishes classic Copilot Autofix, which it says does not consume AI credits, from AI Scan and agentic autofix, which consume Code Security AI credits even in public repositories. Push protection for AI-detected secrets consumes Secret Protection AI credits based on content scanned, including pushes where no secret is found or blocked. Verify the exact feature, eligibility, SKU, included allowance, and hard budget before enablement.

## Respect eligibility, spending, and ownership

The supplied billing documentation says public repositories on GitHub.com have free access to code scanning, secret scanning, and dependency review, while Advanced Security use in private GitHub.com repositories and repositories on GitHub Enterprise Server or a data-residency site requires licensing. Actual feature access can still depend on owner type, plan, permissions, policy, and rollout. Do not infer paid activation authority or remaining allowance from documentation, a visible toggle, or the ability to start a run.

Where SKU-level Advanced Security hard budgets are available, the current documentation says their limit prevents new enablement but does not disable already enabled repositories or stop billing for their active committers; new active committers and an enablement larger than the remaining budget can still exceed the budget. AI-credit features have separate usage and budget behavior. Inspect the billed account, current consumption, included credits or licenses, budget scope, stop behavior, and reporting delay before a chargeable activation or qualification run. Keep Actions run and storage spending within the separate boundary in [CI hardening](ci-hardening.md).

Change settings through the existing Terraform, App, security configuration, or other maintained writer. Do not add a competing direct write.

Before changing a centrally maintained source, inspect its complete attachment set and the writer's target-specific override and precedence semantics. Authority for one repository does not authorize effects on other attached repositories. When any attachment is outside the authorized outcome, use an existing maintained target-scoped route only after its inheritance and preservation behavior is established; if none exists, return the broader effect or missing route to the source owner instead of editing the shared source. Preserve unrelated attached repositories and fields. Introducing a new Action, App, scanner, updater, or other third-party component is a component-adoption decision: return the needed capability, constraints, and evidence to the caller for its existing adoption owner rather than silently adopting it here.

## Reconcile the result and qualify every claim

Follow [application and verification](apply-and-verify.md) for no-op classification, ambiguous responses after possible writes, preservation of confirmed partial results, and outcome reporting. Use the evidence distinctions below to qualify the security-and-quality claim.

Complete only the claim demonstrated on the final relevant source and target state. Separate owning source-validator success, settings readback, inventory or analysis coverage, alert delivery, update production, and causal merge enforcement. Source preparation alone establishes none of installed discovery, hosted behavior, live enforcement, spending safety, or cryptographic identity.
