# Capability Probes And Fallbacks

## Prove An Exact Pair

1. Identify the exact target family, surface, version, executor, and transport
   from the frozen invocation plan; an explicitly witnessed consumer also binds
   the authenticated invocation topology receipt.
2. Require a currently fresh catalog observation. For Daybreak, including continuations, reuse an unchanged observation inside its declared freshness window; refresh only when missing, stale, or invalidated. Use `codex debug models` for a needed Codex refresh or the target harness's live model catalog for another target.
3. Inspect the target executor tool or schema for accepted model slugs and reasoning efforts.
4. Resolve the newest proven same-name GPT or Claude version below, then apply [effort eligibility](effort-policy.md), including fixed and default efforts.
5. Map display labels such as Terra Light/Low to the exact executor's supported native model and effort labels using current target evidence. A release announcement or comparison is not execution support; never invent a Terra slug or a native `light` alias.
6. Record the exact live-catalog and target-executor-schema intersection, and pass only a pair present in both.

Anthropic lists `claude-haiku-5-5` for the Claude API and advertises
`xhigh` and `max` for it there. Verify the selected Haiku pair on the exact
Claude executor. Rolecasting excludes Haiku `max` under [effort eligibility](effort-policy.md).
[Haiku 5.5 model ID](https://platform.claude.com/docs/en/models/haiku-5-5/overview) · [Claude effort support](https://platform.claude.com/docs/en/build-with-claude/effort)

For an explicitly selected versioned ordinary current-tree Cloud profile,
product build may be recorded as unavailable when the consumer does not need
it and the exact surface/controller capability binding is frozen. Bind the
profile revision and actual observations; an environment publication version
is not a product version. Desktop/CLI and witnessed requirements are unchanged.

Catalog presence never proves that a native subagent, task, CLI, app-server,
remote API, or peer accepts the pair. Proof for one product surface does not
prove its paired surface. Model support also does not prove relationship,
ownership, transport, or assurance. When the target exposes no selection
fields, apply the fixed-binding branch below; otherwise pass every supported
selection field.

## Pass Every Supported Selection Field

Choose deliberately under the existing selection order before creating any
agent thread, task, session, or subagent. Inspect each field independently:

| Target controls | Creation request and selection record |
| --- | --- |
| Model and effort | Pass the selected model and effort explicitly, even when they equal the global, desktop, or parent defaults. |
| Model only | Pass the selected model. Record that the surface exposes no effort control and the observed fixed effort or its absence. |
| Effort only | Pass the selected effort. Record the inherited model binding and the absence of a model control. |
| Neither | Record the inherited model and effort binding and why neither can be set. |

Omit only a field the exact surface does not expose. Model inheritance is
permitted only without a model field, with its binding and reason recorded.
For every unavailable control, establish the fixed binding sufficiently to
pass suitability, effort eligibility, and consumer requirements before sending
task data. A missing effort control does not waive a named-family effort floor;
an unknown or ineligible binding returns `NEEDS_CONTEXT` or `BLOCKED` through
the existing route gates. Never invent an unsupported field or value.

Claude Code's Agent tool and native Codex subagent or task creation follow the
same rule. Set Claude Code Agent `model` and `effort` when supported; this is
the instruction to expose its effort control. If the actual tool schema still
lacks effort, set model and record that limitation. For CLI and app-server
creation, bind the outgoing creation fields and any separate turn-level effort
control before the first worker inference. A selected pair written only in a
plan or worker prompt does not apply an exposed request field.

Retain the actual outgoing selection fields with the selection record, including
omission reasons and proven fixed bindings. This establishes requested
configuration, not actual model execution or product-enforced authority.

## Resolve Named Successors

The written GPT and Claude versions are baselines for their named roles. Always select a newer available version of the same named model instead of any lower version, even when the written policy has not caught up. GPT-6.1 Sol supersedes every earlier Sol. Preserve the named model's role, provider preference, effort policy, authority, and all capability or proof gates; an Astra successor stays Astra, and a Sol successor stays Sol.

Use current provider or target-catalog evidence that establishes the exact advertised slug, same named lineage, and version ordering. A similar slug, guessed version arithmetic, or another named family is not successor proof. Record that evidence and the chosen pair's catalog/schema intersection. Fable successors also need their own current successful target proof; an older version's proof does not transfer.

When a proven newer version is advertised but its required pair is unsupported on the frozen executor, report that route unavailable rather than downgrade to an older version. When an alleged successor's identity or ordering is unproven, report the missing evidence and do not guess or silently select a lower version. A contract-preserving fallback to another eligible named family still follows the owning workflow's target and authority rules. An operator-fixed older model or immutable environment binding that conflicts with this policy requires `NEEDS_CONTEXT` or `BLOCKED`; do not silently alter it or treat it as a version exception.

## Return The Selection Record

For ordinary same-leader work, return `adapter:model-selection-record` bound to
the dispatch identity, execution role, exact target, selected
model and effort or inherited fixed-model binding, current catalog and executor
schema observations, and existing selection authority. Record the source and
freshness of those observations, successor lineage/version evidence, and
effort eligibility, including the task-fit or role-default branch, its judgment evidence, native label mapping, and every `max` gate when requested. This record establishes the selected request
and available capability; it does not attest the model that actually executed.
The completed plan binds this record's identity before dispatch. Do not describe opaque provider rerouting as an observed execution fact.

An explicitly witnessed consumer additionally requires its authenticated
`adapter:model-selection-receipt`. An ordinary record cannot substitute for
that receipt, create issuer authority, or increase any assurance dimension.
Stronger model or effective-authority minima still block an insufficient route.

Model selection does not grant authority to invoke a model, peer, CLI, API, or external harness. Capability inspection and any proof invocation must remain within the authority already granted by the operator and worker contract.

During an already authorized no-task-data refresh, you may inspect route metadata exposed for unrelated tasks, including advertised model availability; this does not authorize reading task data. An existing task is eligible only when delegation created it for the current source task and bounded purpose, or the operator identified it as a same-purpose companion. Do not use an unrelated task as an execution or authorization route for current-task work, including to execute with its model or under its account, entitlement, permissions, or context.

## Re-prove Continuation Capability

### Ordinary current-tree Cloud

For the explicitly selected versioned native-tree profile, establish that the
current controller still owns the exact observed target and binding generation
for the authorized bounded purpose. Retain the original requested selection,
its source, current capability observations, authority, and consumer minima.
Reclassify the continuation's work and confirm that this retained selection
remains suitable. Reuse unchanged observations within their valid binding and
freshness window; refresh when stale, absent, or invalidated by a relevant
change. Initial selection alone does not establish continued suitability.

Pass every selection field the continuation actually supports. If it exposes
none, retain the established requested binding and record that no field can
change it; do not invent a separate account or served-model readback. This
establishes requested configuration and current native capability, not actual
model execution. Missing required binding or capability blocks the operation.
A replacement child must meet creation requirements. A new root or lost
controller continuity requires verified new bindings or explicit handoff, not
restoration from an old target string.

This branch applies only to ordinary current-tree Cloud operations. It does
not relax Desktop/CLI, foreign/account-routed, or witnessed requirements, and
cannot satisfy a consumer requiring stronger model or account evidence.

### Other continuation routes

Initial capability proof does not prove continuation capability. Before sending continuation task data, require a currently fresh observation of the same private account binding and the exact selected model on the continuation surface. Reuse an unchanged observation inside its declared freshness window; run a new no-task-data refresh only when the observation is missing, stale, or invalidated by a tuple change. A task or session ID and its stored provider or model are useful identity facts, but a shared session database is not account-affinity evidence.

Require the continuation actuator to select and observe the same private account binding used for the successful initial dispatch. If it cannot, treat capability as unproven and fail closed without sending the continuation payload. A newly created dedicated task or session still requires the owning workflow's creation authority and a fresh capability proof; it does not make an unrelated task eligible.

Pass the deliberately resolved model and effort in every supported continuation
field. When a continuation has no selection control, verify and record its
retained binding; a stored model alone cannot establish current account affinity
or effort. Apply the field-specific rules above without silently inheriting a
global, desktop, or parent default. A continuation that creates a replacement
thread, task, session, or subagent must also satisfy the creation requirement.

## Handle Probe Failure

Treat capability as unproven when the executable is absent, a probe exits nonzero, output is malformed or unparseable, or the surface cannot isolate the requested scope and authority. Record the attempted surface, probe, and result. Never invent a slug, selection field, or dispatch.

When a task that must be isolated cannot be created or verified, do not dispatch: return `NEEDS_CONTEXT` or `BLOCKED` so the owning workflow can select its no-runnable-route disposition. Unrelated-task reuse is never a fallback.

Use a sufficient native route only when it preserves the original task contract.
Pass every supported selection field and apply the fixed-binding rules only to
controls the surface lacks. Unknown defaults cannot establish a required
suitability or policy gate; fixed low defaults are ineligible for Astra/Fable
and Sol/Opus, while other models follow their own effort rules. If no eligible
binding can be established, do not dispatch: return `NEEDS_CONTEXT` with the
missing fact or `BLOCKED` with the failed-probe evidence.

## Apply Fallbacks

For roles without a fixed effort, choose the lowest accepted effort that preserves the task's judgment margin and passes [effort eligibility](effort-policy.md). Raise effort before widening scope or changing models when reasoning can resolve the uncertainty.

Prove every replacement model-effort pair independently in both the current catalog and executor schema, including a lower effort on the same model. Consider eligible Terra alongside Sol or Opus when the task fits its economical frontier and existing target/authority boundaries. Rejecting the requested pair establishes no capability for an alternative. Evidence for GPT does not prove an Opus pair, and schema support alone does not prove catalog availability. Leave any unproven replacement unselected. If no proven authorized alternative preserves the task contract, return `NEEDS_CONTEXT` or `BLOCKED` with the missing evidence.

When an eligible GPT-6 Luna pair fits but the target executor schema lacks it, apply the same fallback gates. Where fallback is authorized, consider suitable Terra, Haiku, Sol, or Opus pairs proven on the settled executor. Pass every supported model and effort field; use a proven eligible fixed binding only for an absent control. Never invent a slug or effort, and report a fallback that materially changes confidence, cost, or speed.

For another harness, inspect its local capability surface and use only its exact supported values. Report an unavailable user-requested model rather than silently substituting.

## Prove Fable

Anthropic lists `claude-fable-5-2` for the Claude API. Verify the executor's own model and effort labels. [Claude Fable 5.2 model overview](https://platform.claude.com/docs/en/models/fable-5-2/overview)

Every Fable version requires current successful proof for the exact model-effort pair and target. The proof record must contain:

- harness and version;
- exact slug and requested effort;
- invocation result; and
- an observable successful response.

Help or catalog advertisement is insufficient. If no current successful proof exists, do not invoke Fable merely to establish one. Only the operator's explicit authorization for the exact proof invocation permits the attempt; that authorization does not itself prove availability. Until all fields are recorded after an authorized successful invocation, treat the requested Fable pair as unavailable. A fallback consent decision authorizes only its stated scope; it is not proof that Fable ran or authority to make a proof-only invocation.
