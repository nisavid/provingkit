# Daybreak Routing Capability Reference

This reference selects a model-routing disposition for actual cybersecurity work, obviously cybersecurity-related work with another primary domain, and cybersecurity-adjacent work. It does not decide whether to delegate, create tasks, mutate trackers, or perform actions. The owning delegating workflow retains action authority and topology.

Apply [effort eligibility](effort-policy.md) to the selected pair and every fallback, including inherited or default effort. An incapable effort route does not waive consent, refusal, authority, or target gates.

First apply [scope classification and block diagnosis](classifying-security-work.md) to the complete bounded operation. A suitable, available, and authorized Jev route for that entire narrow System One judgment is first. Otherwise prefer a genuinely runnable Daybreak Blue route for all three security classes. This reference overrides the general model matrix for those classes. A safety refusal is not a capability failure that authorizes fallback.

Route the bounded security operation to Daybreak Blue whenever a permitted route is genuinely runnable. Resolve its exact live model slug through the target capability gates; the name alone is not a selector proof. Daybreak executes the work, rather than merely selecting another worker. These rules do not govern unrelated work.

Classify the complete current bounded scope immediately before every concrete delegation, including initial creation, reuse, resume, follow-up with the same agent, and each review cycle. Prior Daybreak assignment, agent identity, or continuation does not carry classification forward. Use the general tiers when a new bounded scope is unrelated, even inside an existing Daybreak task. Keep a resumed operation in any of the three security classes on this route unless complete-operation Jev suitability and runnability apply. Never relabel or narrow scope to avoid these guardrails.

When a security-relevant dependency or other evidence dependency changes enough to invalidate an earlier review, review the whole changed security-relevant scope supported by that invalidated evidence. A review of only the dependency delta does not preserve the earlier pass.

Inventory these routes independently before selection:

1. A Daybreak model in the native subagent selector.
2. A Daybreak model in the peer or sibling task selector.
3. Every Codex session-launch surface available to the harness, expanded across every authenticated account home allowed by the operator's permitted private account-binding catalog (`~/.agents/daybreak-account-bindings.md` for Codex account-home routes), including cross-harness Codex invocation.

A route is one invocation surface plus the account home, authenticated identity, model, and capability state required by that surface. Catalog entries are inputs, not routes. Inventory cross-harness Codex invocation before declaring Daybreak unavailable. Read the permitted private catalog before using an account-home route. If it is absent, unreadable, or does not match the authenticated identity, treat that route as unavailable. Never disclose its entries or infer a binding from a directory name.

### Maintained account-home procedure

Resolve the installed `choosing-agent-models` skill root, then use its `scripts/` resources. The catalog program recognizes headings and prose around list-item bindings. Each binding has a nonempty private binding label and exactly these nonempty scalar fields: `codex_home`, `authenticated_account_id`, `account_classification`, `authentication_observation`, `configuration_topology`, `database_topology`, `usage_capacity`, `daybreak_selector`, `harmless_probe`, and `task_data_authority`. Any missing, duplicate, or unknown binding field invalidates the complete catalog. A `codex_home` is either an absolute path or safe `~/PATH` syntax; other relative paths, home-relative parent segments, and NUL-bearing paths are invalid.

Run `daybreak_catalog.py inspect --catalog CATALOG` to emit only the schema, binding count, and one-based positions. Run `daybreak_catalog.py select --catalog CATALOG --position N` only with an explicit position. Selection emits one strict `rolecasting-daybreak-account-selection-v1` object containing the private account home and expected authenticated account identifier. It preserves the catalog's absolute or `~/PATH` home syntax without expanding it. Pass the selection directly on standard input; do not publish or persist it in public evidence. The catalog program reads only `CATALOG`. It does not consult the process home or an ambient catalog, read account state, launch a process, or write a result file.

Run `daybreak_account.py status-refresh --selection-stdin --codex ABSOLUTE_CODEX --model MODEL/EFFORT --freshness-seconds SECONDS` with exactly one selection object on standard input. The account program rejects missing, multiple, duplicate-key, trailing, unknown-field, or NUL-bearing account-home input. Before accessing authentication, it rejects a nonpositive freshness interval, malformed exact selector, or nonabsolute executable path. For a selected `~/PATH`, it expands that exact suffix against the process home; it never searches that home for another account. It opens only the resulting selected `auth.json` with a nonblocking file descriptor, accepts the opened descriptor only when it is a regular file, and reads at most 1,048,577 bytes to enforce a 1,048,576-byte authentication ceiling. A symlink is supported when its opened target is a regular file. Nonregular authentication is unavailable; content above the ceiling is malformed. The descriptor check follows the open, so a path replacement cannot switch the checked object before the bounded read. The helper then checks the expected identity and launches the explicitly supplied trusted Codex executable as `app-server --stdio` with `CODEX_HOME` set to that selected home. The executable inherits the caller's environment, may read and write local state under its configured home, and may contact its provider.

Status refresh uses a separate provider-identity admission phase. After `initialize`, it asks `account/read` without token refresh and validates the authenticated ChatGPT shape. It then asks `account/rateLimits/read`, the required identity-bearing bootstrap query, and compares its string `accountId` with the selected expected identity. The helper does not know provider identity before making that query. A missing or mismatched identity stops the operation without `model/list`, status output, or any later discovery request. Only an admitted identity may enter bounded complete `model/list` discovery and allowlisted usage/capacity projection. Status refresh creates no task thread, sends no task prompt, and exposes no task tools. Its standard output contains only protocol-type-validated allowlisted fields and is not authenticated native evidence.

The line-delimited RPC transport accepts frames of at most 1,048,576 bytes, holds at most 1,048,577 incoming bytes, reads at most 65,536 bytes at a time, processes at most 128 messages for one request, and allows at most 100 model pages. Outgoing pipe writes use nonblocking operations and wait at most 10 seconds for writable progress; each response has its own 10-second deadline. Authentication and RPC JSON reject duplicate keys and non-finite constants. Notifications have no status consumer and are discarded as they are processed; they are never retained in a notification collection. A closed pipe, selector, write, or read failure, oversized newline-terminated or newline-free frame, message flood, malformed message, timeout, or teardown failure stops the operation without status output. The helper attempts process cleanup on every post-launch path. The nonblocking authentication open prevents named-pipe producer waits, but no actuator imposes a universal filesystem or storage-response deadline. These application limits do not provide operating-system containment.

Both programs publish only this fixed diagnostic vocabulary. They never append parser input, catalog or selection fields, provider payloads or error bodies, exception text, or machine-local paths:

This status-only helper surface provides no probe actuator. `daybreak_account.py harmless-probe --selection-stdin --codex ABSOLUTE_CODEX --model MODEL/EFFORT --workspace WORKSPACE` is an explicit unavailable operation: it validates the strict selection and supplied path shapes, then fails before authentication access or process launch. Current Codex controls do not provide a closed-world task-tool deny across built-ins and selected-home configuration. Observing and rejecting a tool event afterward would not satisfy the no-task-tool boundary.

An explicit workspace path is only an input. The account program does not infer authority or disposability from the workspace path; the owning workflow must establish both before any probe actuator runs. Likewise, an absolute executable path identifies what to launch but does not establish that the executable is trusted. These helpers separate application effects; they do not provide operating-system containment.

A no-task-data local status refresh may refresh only authentication, selector exposure, entitlement, capacity, and the exact exposed model. It has the selected-home and provider effects described above, but must not create a task session, transfer task data, use task workspace or task tools, delegate, or execute task work. Run this refresh automatically whenever a permitted account route needs a missing or stale observation. It requires no operator prompt because it sends no task data and performs no task work. Selector exposure is not model runnability, and this status-only helper cannot supply probe evidence.

The status refresh is distinct from the separate harmless runnability probe. The harmless probe contains no task data and may run only when existing task or workflow authority covers its route, account, workspace, tools, and applicable actions. A status refresh never satisfies or consumes that probe.

During an authorized status refresh, route metadata exposed for unrelated tasks may be observed without reading their task data. An existing task is eligible for execution only when delegation created it for the current source task and bounded purpose or the operator identified it as a same-purpose companion. Never reuse an unrelated task as an execution or authorization route, including its model, account, entitlement, permissions, or context.

A route is genuinely runnable for delegated or executed task work only when existing task or workflow authority covers the account, data boundary, workspace, tools, harmless probe, and applicable external actions; the current status confirms the exact Daybreak selector, matching authenticated account, and remaining capacity; and the harmless no-task-data probe succeeds.

Existing task or workflow authorization covers ordinary route setup, the harmless probe, and handoff of data that is not sensitive, secret, or uniquely proprietary when each stays within the authorized account, data, workspace, tool, and action scope. Do not request separate Daybreak-specific permission for that ordinary work. This does not expand scope, authorize consequential actions, or override explicit prohibitions. The owning workflow remains responsible for any separate consequential-action permission.

Before any actual sensitive, secret, or uniquely proprietary item is exposed to Daybreak through a prompt, attachment, retained context, workspace read, or tool result, obtain explicit approval to transfer that item to the selected Daybreak route. Apply this gate at the point of exposure, including later tool use and continuations; mere access to an item that will not be exposed does not require approval. Identify every such item by safe description and location, never by exposing contents or secret values in the request. Reuse an existing approval without another prompt only while it remains valid for the exact items, selected route and account, data boundary, workspace, tools, action scope, and bounded purpose. Reuse never waives classification before the next delegation event.

Picker visibility, selectability, authentication, capacity, session start, and successful execution are separate facts. Status and incidental route metadata establish facts but create no task-data, workspace, tool, action, delegation, or execution authority. Neither status nor the harmless probe implies protected-data transfer approval. Resolve the exact model currently exposed; never invent a slug or reuse a stale one.

If authority for the account, workspace, tools, probe, or applicable actions is absent, classify the route as unavailable without running the harmless probe; the automatic no-task-data refresh remains permitted. Pending itemized approval blocks only the unapproved protected item or tool result from reaching Daybreak. Ordinary nonprotected handoffs and an otherwise authorized harmless probe may proceed within existing authority; a later protected exposure awaiting approval does not make the route unavailable for that ordinary work.

Record a timestamped, redacted status and a declared freshness window for each exact invocation-surface, account-binding, authenticated-identity, model, and capability-state tuple. Reuse it only inside that window while the full tuple is unchanged. A dated catalog observation is historical, not current by default.

Invalidate the observation when the tuple, selector, entitlement, capacity, authentication, route or probe authority, data boundary, workspace, tool scope, external-action scope, or freshness window changes. The changed tuple receives one new no-task-data refresh and, separately, one harmless probe when route and probe authority covers it. Permit only one of each operation per exact tuple per freshness window. Neither creates task-work authority or protected-data transfer approval.

Local/private operational state may use account IDs, account-home identifiers, or safe stable local labels to distinguish permitted accounts. Scrub account IDs, account-home identifiers, stable labels, and derived home or path names before any nonlocal or public persistence or transmission. Use only a generic non-stable marker or redacted status there. Never expose credentials, tokens, decrypted secrets, catalog entries, or unrelated task data outside the narrow local operation that requires them.

## Unavailable Daybreak Blue

When no permitted Daybreak Blue route is genuinely runnable, record each route's reason and tell the operator in redacted terms that Daybreak is unavailable and why before asking for fallback. Do not expose account bindings or identifiers. Then apply the following decision. Capability failure is distinct from a safety refusal; [diagnose a refusal](classifying-security-work.md#diagnose-a-block-or-refusal) before any fallback.

- For **actual cybersecurity work**, ask once per thread whether the operator authorizes non-Daybreak fallback: proven Claude Fable 5.1 when the operation needs deep cognition, or proven Claude Opus 5.5 otherwise. Without that authorization, wait for Daybreak Blue.
- For **obviously cybersecurity-related work with another primary domain**, automatically use that same proven fallback only when **security and other concerns are largely known, uncomplicated, and architecturally clear**. If any predicate fails, use the once-per-thread consent route and wait without authorization.
- For **cybersecurity-adjacent work**, automatically use that same proven fallback only when **the security implications are readily recognizable and easily fixable**. If either predicate fails, use the once-per-thread consent route and wait without authorization.

A Fable 5.1 selection for deep cognition still requires its current successful [target proof](capability-probes-and-fallbacks.md#prove-fable); neither fallback may run without the exact catalog/schema intersection, existing invocation authority, and the original data and workspace permissions. If the prescribed pair is unavailable or cannot preserve required judgment, wait for Daybreak Blue or obtain a new operator decision. Automatic fallback is permission only for the stated class and all its predicates; it does not grant missing target, account, data, workspace, tool, or action authority. For a non-Daybreak destination, the owning workflow must verify its existing data-transfer and action permissions before sending task data; Daybreak-specific item approval above does not replace those rules. Deadline, sunk cost, and convenience do not grant fallback.

Track the fallback decision in the current thread. Ask at most once per thread unless the operator requests another question or revises the decision. The act of asking leaves consent pending; a missing answer is not approval. Preserve an explicit denial and wait. Apply an explicit approval only to the scope it covers, then select Fable for deep cognition or Opus otherwise with current proof. A later user revision supersedes an earlier approval or denial. An explicit operator restriction on fallback takes precedence over an automatic branch. Reclassify each new bounded operation and recheck capability and authority even when consent remains valid.

When a required question is pending, continue independent authorized work without sending the security operation to a fallback. If Daybreak Blue becomes runnable, use it under the ordinary route gates. Do not infer that an alternate harness, account, task, or selected model is an execution or authorization route. The owning delegation workflow retains topology and external-action authority.

For root-only work, when the native route cannot run Daybreak but a permitted peer, sibling, or cross-harness Daybreak route is genuinely runnable, return that route and the bounded Daybreak scope to the owning workflow. The workflow must create the dedicated peer or sibling task before execution; a direct cross-harness session does not bypass that boundary. Keep integration and non-security coordination in the original task.
